# Assignment: Build, docs and misc round 1 (audit, then drafts for the draftable tickets)

Claim first: add `claims/build-docs-misc-round-1.md`, then work. Report: `reports/build-docs-misc-round-1.md`. Drafts, for the tickets the audit finds draftable, go in `pr-drafts/build-docs/` following `pr-formula.md`.

Staffing: run this round with 6 subagents in parallel, split by ticket cluster, with the lead writing the roll-up report. Hard cap from Nick (2026-10-09): never more than 6 to 7 subagents running at once across ALL assignments combined, on either side; subagents slow each other down past that. Run rounds one after another, not together.

Convergence (standing rule): start from the receipts in `receipts/`. A branch already gated at its exact live tip, or already decided on the main side's record, is NOT re-audited; the audit verifies the recorded state against the branch and judges PR readiness. The round is one audit pass; the main side then does one answers pass; then drafts; then an openings slate goes to Nick. Do not open a second audit loop on settled branches.

The review side does not run gates or builds (Windows builds are revoked). Gate evidence comes from the main side's receipts; where a receipt says NO GATE or gated at an older head, say what is owed instead of substituting a local run. This round is the catch-all area, and its evidence shapes vary more than any earlier round: two branches are verified by a documentation build or a light gate rather than a test gate, one by a purpose-built harness for a release script, and one ticket's only run anywhere is a single focused test run on GitHub, which the receipt does NOT count as a gate. State each branch's evidence as it is; do not dress a light verification up as a test gate, and do not treat the absence of a test gate on a docs-only branch as a defect by itself.

## The audit

Per ticket: read the Jira ticket, the branch diff against its base, and the receipt. Verify the recorded state against the branch (a moved tip or a diff that differs from the record gets flagged, not silently adopted). For the verified tickets, judge PR readiness: premise, scope, changelog entry, and what the description must state or avoid claiming. For the audit-only tickets, the audit's job is the premise read against current main and a precise statement of what a verification would need; do not present them as draftable. For the retire candidates, confirm the factual basis of the retirement against current main (a class or dependency that has since returned would reopen the question) and carry the owner items forward. For the two live PRs, run only the consistency check described above. Follow the standing rules: no new Jira ticket unless someone asks for one; a scope question goes in a draft's Limits or A Choice; a needed follow-up fix is named in Limits or a Choice with a stated plan to submit it; public PR text carries no internal process vocabulary (no gate, receipt, ledger, rc=0, "fresh JUnit XML", or "pre-fix proof" as a label); Proof sections state plainly what ran, at which head, and what passed (where a receipt records a documentation build, a light verification, or a harness run, the Proof says that and names what it was checked against; where a receipt records a proof as inconclusive by construction, the draft says why instead). Titles must be accurate. Where a draft must name a Lucene version, name every version that applies: main and branch_10x pin Lucene 10.4.0, branch_9x pins Lucene 9.12.3; if one version is mentioned, the others that apply are mentioned too.
