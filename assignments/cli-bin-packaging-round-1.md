## The audit

Per ticket: read the Jira ticket, the branch diff against its base, and the receipt. Verify the recorded state against the branch (a moved tip or a diff that differs from the record gets flagged, not silently adopted). For the verified tickets, judge PR readiness: premise, scope, changelog entry, and what the description must state or avoid claiming. For the four audit-only tickets, the audit's job is the premise read against current main and a precise statement of what a verification would need; do not present them as draftable. Follow the standing rules: no new Jira ticket unless someone asks for one; a scope question goes in a draft's Limits or A Choice; a needed follow-up fix is named in Limits or a Choice with a stated plan to submit it; public PR text carries no internal process vocabulary (no gate, receipt, ledger, rc=0, "fresh JUnit XML", or "pre-fix proof" as a label); Proof sections state plainly what ran, at which head, and what passed (where a receipt records BATS evidence, the Proof says a BATS suite ran; where it records a construction proof, the Proof says the change is verified by construction and names the run still owed; where a receipt records a proof as partial, the draft says that instead). Titles must be accurate. Where a draft must name a Lucene version, name every version that applies: main and branch_10x pin Lucene 10.4.0, branch_9x pins Lucene 9.12.3; if one version is mentioned, the others that apply are mentioned too.
