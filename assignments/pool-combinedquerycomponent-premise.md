## The recorded reading (verify or refute)

Component: `solr/core/src/java/org/apache/solr/handler/component/CombinedQueryComponent.java`, method `mergeIds`. Line numbers are from main `d76fc14b9857e77b830d7a82514b28c523a239c2`; re-locate every line by content on the main tip you actually read and cite that SHA in the report. The loop structure differs from `QueryComponent.mergeIds`: an outer loop over the combined queries (`queriesToCombineKeys`), an inner loop over the shard responses for that query, per-query totals (`queryNumFound`, `queryApproximateTotalHits`), and a per-query sort values subsection named `sort_values_<queryIndex>`.

1. **Totals accumulate before the partial skip.** When a shard's per-query document list is read, `queryNumFound += docs.getNumFound()` (around line 342) and the `hitCountIsExact` fold (around line 343) run immediately. `queryApproximateTotalHits` is accumulated further down (around lines 384 to 386, both the header branch and the fallback branch). The partial skip, `if (thisResponseIsPartial && sortFieldValues.size() == 0 && needsUnmarshalling) continue;`, sits after all of it (around line 399). So a shard whose documents the skip drops still contributes its numFound, its exactness fold, and its approximate count to the per-query totals, the same defect the mergeIds ticket reports for `QueryComponent`. One difference to state precisely: in this component the accumulation at lines 342 to 343 also runs before the exception check (`srsp.getException() != null` continues the loop a few lines later); say whether a response carrying an exception can carry a per-query document list at all, and if it cannot, say so as a checked path rather than an assumption.
2. **The approximateTotalHits fallback adds the running total, in the other direction.** When a shard response has no approximateTotalHits header, the fallback (around line 384) adds `queryNumFound`. At that point `queryNumFound` already includes the current shard (it was folded in at line 342), so the fallback double-counts the current shard and every earlier shard again. Worked example from the review: two shards with numFound 2 and 3 and no headers on either. The first fallback adds 2 (running total 2); the second adds the running 5, giving `queryApproximateTotalHits` 7 where 5 is correct. Compare `QueryComponent` before its fix, where the fallback added the running total before the current shard was folded in (giving 2 where 5 was correct): same line shape, opposite error direction. State the general rule for n shards with mixed headers: which shards' counts enter the total, how many times each.
3. **A pointed question on the exactness fold.** As written, line 343 reads `hitCountIsExact = hitCountIsExact && Boolean.FALSE.equals(docs.getNumFoundExact());`. On its face that keeps the merged flag true only while shards report their count as NOT exact, and turns it false as soon as a shard reports an exact count, which is the inverse of the `QueryComponent` fold (`if (hitCountIsExact && Boolean.FALSE.equals(docs.getNumFoundExact())) hitCountIsExact = false;`). Verify or refute that this is inverted, taking into account: `hitCountIsExact` is declared once, outside the per-query loop, so it is shared across all combined queries; it is written to the combined response once, after the loops (`responseDocs.setNumFoundExact(...)`); and what `SolrDocumentList.getNumFoundExact()` returns when a shard list carries no flag. If the fold is sound under some reading, give that reading exactly. If it is inverted, it is a third defect in the same lines and the report says so plainly.
