## 2. What the change does

**[verified: diff]** **[verified: code]**

- **The fix is an ordering change in `SpellCheckCollator.java`.** At the tip, the removal of `tie`, `pf`, `pf2`, `pf3`, `bq`, and `bf` runs at lines 110-117, before the `spellcheck.collateParam.*` override loop (lines 118-131). Before the change, the removal ran after that loop, so any override for those six parameters was erased before the collation check ran. Now an override can set them.
- **Inherited parameters are still stripped.** The parameters are copied from the request first (line 109). Scoring parameters the user sets without the `collateParam` prefix are therefore still removed for the collation check. This matches the code comment at lines 110-111.
- **Test.** `SpellCheckCollatorTest.java:279-333`, `testCollateParamOverrideOfScoringParams`, has two `assertQ` checks on edismax with `qf=teststop`:
  - (a) `spellcheck.collateParam.bq=teststop:political`, a valid boost query. It expects the collation `parisian political machine`. It passes with or without the fix, so it is a non-regression check.
  - (b) `spellcheck.collateParam.bq=teststop:(`, an unparseable boost query. It expects zero collations. **[hypothesis]** Before the fix the boost query is stripped, so a collation would be found and check (b) would fail. This was read from the code, not run.
- **Unparseable overrides fail silently to the client.** The collation re-query is wrapped in `catch (Exception e)` (`SpellCheckCollator.java:174-177`), which logs a WARN and continues. So a bad override produces no collation and no error in the response. The test codifies this.
- **Changelog** (`type: fixed`, author Nick Shanin with the `nick` key used on upstream main): says the collateParam overrides can now set those six parameters for the collation check.
