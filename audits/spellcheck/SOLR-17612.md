## 2. What the change does

**[verified: diff]** **[verified: code]**

With a fractional `spellcheck.maxResultsForSuggest` (a share of the matching documents), the threshold used to be computed from the coordinator core's own searcher. The branch moves the computation to the coordinator and uses counts from all shards.

- **Shard side.** On a shard request with a fractional value, the shard does not apply the fraction (`SpellCheckComponent.java:174-175` sets `deferToCoordinator`, and the shard passes `null` as the threshold). The shard reports its filtered document count under `maxResultsByFilters` in its spellcheck response (lines 234-239).
- **How a shard computes its count.** `maxResultsByFilters(rb)` (lines 304-336) takes the explicit `spellcheck.maxResultsForSuggest.fq` if given. Otherwise it takes the minimum, over all `fq` filters, of that shard's document count (line 326). It returns null when there are no filters.
- **Coordinator.** `finishStage` (lines 465-470) calls `maxResultsForSuggest(rb, sum)` with `sum` from `sumMaxResultsByFiltersFromShards` (lines 341-354). That method adds each shard's reported value. The fraction is applied to that sum (lines 285-292). If no shard reports the key, the sum is null and the coordinator falls back to its own local evaluation (lines 286-288).
- **Refactor.** `maxResultsForSuggest` is split into three helpers (`isFractionalMaxResultsForSuggest` at line 258, `maxResultsByFilters` at 304, and the override-taking form at 272). The refactor is the tidy part. The behavior change is the coordinator threshold.
- **Test.** `DistributedSpellCheckComponentTest.java:161-177` adds one distributed comparison: `q=*:*`, `spellcheck.q=quoet`, `fq=lowerfilt:quote`, fraction 1.5. The comment says the filter matches 12 documents, so the threshold is round(12 × 1.5) = 18 and suggestions must still appear. The test uses one `fq` only.
- **Changelog** (`type: fixed`, author Nick Shanin): says a fractional value is applied to the filtered count summed across all shards.

**DRIFT flag (VM2 sweep, "tidy-only").** The flag does not hold at the live tip. The diff changes behavior on the distributed path: the shard threshold deferral (`SpellCheckComponent.java:174-175`), the shard response key (lines 234-239), and the coordinator threshold (lines 465-470). Only the helper split is tidy. The VM2 sweep record is not visible in this workspace, so what it compared is unknown. Whatever it compared, the flag is superseded for this tip.

## 5. Blockers at the live tip

1. **High, code defect (confirmed by reading): the multi-filter threshold is wrong.** Each shard reduces its filters to one number: the minimum over filters of that shard's count (`SpellCheckComponent.java:304-336`, minimum at line 326). The coordinator then sums those per-shard minima (lines 341-354). The correct value is the minimum over filters of the cross-shard sums. Example: two `fq` clauses whose per-shard counts are [100, 10] on one shard and [10, 100] on another. The branch computes 10 + 10 = 20. The correct value is min(100 + 10, 10 + 100) = 110. With fraction 0.5 the branch uses 10 where the correct threshold is 55, so suggestions can be suppressed for a query that is under the correct threshold. The single-`fq` test (lines 161-177) cannot show this. The round-28 review states the same finding.
2. **Formatting, confirmed.** The blank line between `sumMaxResultsByFiltersFromShards` (ends at line 354) and `addCollationsToResponse` (line 355) is missing in the tip. The committed tree would not pass a Spotless check as it stands. The queue's `spotlessApply` step would add the line, but the commit itself is not clean. **[hypothesis]** Spotless was not run.
3. **Outbound file, confirmed.** `SOLR-17612-TESTING.md` (31 lines, repository root) is added by the branch. The workspace review step in `AGENTS.md` asks for ticket-scoped files only, with no stray files. The doc must not go outbound in a PR.
4. **Fail-before not established.** The test suppresses suggestions only under the buggy code, and only when the coordinator's local share `s` of the 12 matching documents gives `Math.round(1.5 × s) < 12`, which is `s ≤ 7`. At `s = 8` the threshold is 12 and the test passes without the fix. Random routing decides `s`. The branch's own doc says this (guess 1). Not run.

## 8. Owner decisions

Keep that silent fallback, which covers mixed-version clusters and shard responses without the key, or fail or log in that case? Facts: the fallback path; a rolling upgrade would produce shards without the key.

Facts: the threshold condition `s ≤ 7` (blocker 4); the single-`fq` test (lines 161-177); the multi-filter defect (blocker 1).
