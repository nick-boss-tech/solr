## 1. What the change does

Makes a suggester's configured `allTermsRequired` apply to context-filtered requests (`suggest.cfq`). Before, `SuggestComponent` defaulted `suggest.allTermsRequired` to `true` and always passed it on, so a configured `allTermsRequired=false` was ignored on the context path.

- `SuggestComponent.process` reads the request value without a default, so an omitted parameter is `null` (`SuggestComponent.java:270`). `SuggesterOptions` takes a nullable `Boolean` (`SuggesterOptions.java:37, 46`).
- `SolrSuggester` reads the suggester's own `allTermsRequired` in init with `Boolean.parseBoolean` (lines 108-110). The field defaults to `true` (line 93).
- On the context path only, the request value wins if present; otherwise the configured value is used (lines 244-247). The non-context path (lines 240-241) is unchanged and still uses the lookup's own configured value.
- Effect: a suggester configured with `allTermsRequired=false` now returns partial matches for context-filtered requests that do not pass `suggest.allTermsRequired`. Suggesters without the setting keep the old default of `true`. **[verified: code]**
- Test: `testContextFilterHonorsConfiguredAllTermsRequired` (test lines 381-411), using the new suggester `suggest_blended_infix_suggester_any_term` (XML lines 49-62, with `allTermsRequired=false` at line 62). It checks a partial match with no override, and that an explicit `suggest.allTermsRequired=true` returns none. **[verified: diff]**

The branch's handoff doc (`SOLR-14171-TESTING.md`) says the fix and test were written without being compiled or run, and lists four guesses to verify first, including the response-entry naming and OR semantics for the nonmatching term.

## 4. Blockers

The code change is narrow. These items shape the draft:

1. **Limit: configured `true` gives different answers on the two paths.** For a suggester configured with `allTermsRequired=true`, the context path now reads it with `Boolean.parseBoolean` (true), while the non-context path reads the factory's `Boolean.getBoolean("true")`, which is false (`AnalyzingInfixLookupFactory.java:101-102`; `BlendedInfixLookupFactory.java:92-93`). That split existed before this branch (the context path was always `true`, the non-context path was false), so the branch does not create it. It does not fix it either, and the test covers only `false`. The handoff calls the factory parsing a "Related finding, NOT fixed here" and says "Worth its own ticket." The owner decides whether to fix it here or separately. Name it in the draft either way.
2. **Choice: fallback source and the public constant.** The fallback is a literal `true` in `SolrSuggester` (line 93), not Lucene's constant. Decide whether to keep the literal or to read the lookup's default. The new public constant `ALL_TERMS_REQUIRED` (line 78) is part of the same choice.
3. **Choice: the default for an unconfigured suggester.** The review asks the owner to confirm that keeping the newer default (`true`) is intended. On this branch an unconfigured suggester keeps `true`, so no existing request changes. Only configured-false suggesters with a context filter change. Owner confirms.
4. **Record: handoff doc in tree.** `SOLR-14171-TESTING.md` must not ship. Its guess list (response entry naming, OR semantics for the nonmatching term) is still unverified.
