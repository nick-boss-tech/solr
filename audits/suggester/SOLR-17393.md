## 1. What the change does

Changes how the coordinator merges shard results for distributed suggest. It does not change the shard-side lookup.

- The base code merged each token's shard results through a bounded `Lookup.LookupPriorityQueue` of size `count`, which orders by weight only. Equal-weight candidates came out in an order that depended on shard response order. That is the handoff's mechanism, not verified by a run. **[hypothesis]**
- The tip collects all shard candidates for each suggester and token into one list, sorts them with `MERGE_ORDER` (highest weight first, then suggestion text; `SuggestComponent.java` lines 78-82), and keeps the first `count` (lines 368-378). The sort is at line 375; the truncation at lines 376-378.
- `merge` changes from private to package-private `static` (line 352) so the unit test can call it.
- The shard side is unchanged. `count` still reaches each shard's local lookup (`SuggestComponent.java` lines 273 and 285-286), and the default is 1 (line 273).
- Changelog, type `fixed`: equal-weight suggestions come back in a stable order by text, not an order that depends on which shard answered first.
- Test: `SuggestComponentMergeTest` (new, a unit test of `merge`, not a distributed test). `testHigherWeightComesFirst` (line 55) checks that weight still dominates. `testEqualWeightsDoNotDependOnShardResponseOrder` (line 62) checks three shard orders. No distributed test is changed. **[verified: diff]**

The reporter's query (`suggest.q=TEST`, with no `suggest.count`) runs with `count` = 1 (line 273). That matters for finding 1 below.

## 4. Blockers

1. **HIGH finding open (the main blocker).** For the reporter's case (`count` = 1, equal weights, one shard holding several candidates), the fix does not establish that `TEST` wins. Each shard returns its own top candidate by Lucene's tie order before the merge sees anything. Needed: a regression on the per-shard path, or a shard-side tie rule, or a documented scope that says the merge only orders what shards return.
2. **Owner decision: tie policy.** Equal-weight ties by text is a choice. The JIRA (`research/jira-context/SOLR-17393.json`) does not define "closest", does not mention weights, and has no comments. The handoff's premise that the reporter had equal weights is unproven. **[hypothesis]**.
3. **Choice: payload.** Decide whether duplicate text with different payloads is in scope. If not, document that the stable order applies to distinct suggestion text.
4. **Choice: memory bound.** Decide whether the all-candidates sort is acceptable for large `suggest.count` and many shards, or whether a bounded top-N keeps the new order.
