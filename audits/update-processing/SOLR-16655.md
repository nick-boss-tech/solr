## Wider-descent probe (2026-10-09, main side, by run)

The final-round report asked whether the walk into child documents
changes any outcome when the parent field is not selected
(`FieldMutatingUpdateProcessor.java` lines 128-141 at head
`aa7898d972a7`). Settled by run with a throwaway test
(`Probe16655WiderDescentTest`, scratch worktrees only, never
committed to the submit branch).

with an explicit fieldName selector of exactly {name, foo_t}). The
root document carries name=" root " as a root-level control and a
labelled child document as the value of field "child_doc", which is
not in the selector. The child carries name=" child " and
foo_t=" childfoo " (names the selector does select) plus
other_s=" untouched " as an in-child control. Same test, same seed
(16655C0FFEE16655), run at the branch head and at base

run.

  root.name=[root], child.name=[child], child.foo_t=[childfoo],
  child.other_s=[ untouched ].
- Base: 1 test, 1 failure (the probe's head-expectation assertion,
  expected:<[child]> but was:<[ child ]>). Values after processing:
  root.name=[root], child.name=[ child ], child.foo_t=[ childfoo ],
  child.other_s=[ untouched ].

Verdict: the wider descent does change an outcome. The root control
and the in-child unselected control are identical on both trees; the
only differences are the child's two selected fields, which the head
mutates by descending through the unselected parent field and the
base leaves exactly as submitted. No error difference: the add
succeeds on both trees. Selection inside the child stays per field
name (other_s is untouched at head). Two bounds on the finding: the
branch's own labelled-child parse-date test does not isolate this
case, because the ParseDate default selector selects any field
absent from the schema, so "child_doc" counts as selected there; and
the anonymous-children descent (lines 144-149) has no parent field
and is not part of this finding.

only when `selector.shouldMutate(fname)` is true for that field.
