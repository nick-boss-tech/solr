## Premise

`StreamingSolrClients.getErrors()` returns the live synchronized list. `SolrCmdDistributor.doRetriesIfNeeded` copies it (`errors.addAll(clients.getErrors())`, base line 107), resubmits, and later calls `clients.clearErrors()` (base line 167). An error reported between the copy and the clear would be cleared unseen. [verified: code, `cabedd1d968`]

Reachability, by reading: `blockAndDoRetries()` calls `clients.blockUntilFinished()` (`SolrCmdDistributor.java:279-280`) before `doRetriesIfNeeded()` (`:294`). The base `blockUntilFinished()` waits for the queue to empty and for the runners to finish (`ConcurrentUpdateBaseSolrClient.java:515-522`). The runner removes itself from `runners` in its `finally` (`ConcurrentUpdateBaseSolrClient.java:259-280`), after its error handling (`handleError` at lines 272 and 337-348). The error is recorded by `StreamingSolrClients.handleError` (base lines 138-146). So on the normal path every error is recorded before the copy. [verified: code] One exit from the wait loop does not wait for the runners: `if (ExecutorUtil.isShutdown(scheduler)) break;` (`ConcurrentUpdateBaseSolrClient.java:530`). A barrier on a client whose scheduler is shut down can return while runners are still active, and a runner could then record an error after the copy. Whether a distributor reaches `doRetriesIfNeeded` on such a client is not checked here. [verified: code for the exit; hypothesis for the reachability]

Conclusion: the change is hardening, not a fix for a reproduced bug. That matches the Oct 8 TESTING decision (ADOPTED, "SOLR-5754, hardening framing"). The draft says so ("hardening, not a fix for a reproduced bug"). [verified: draft text]
