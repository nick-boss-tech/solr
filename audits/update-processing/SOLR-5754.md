## Premise

**Verified part.** On `upstream/main`, `StreamingSolrClients.getErrors()` returns the live synchronized list (`StreamingSolrClients.java:60-62`). The JIRA asks for a copy. The branch changes that.

**Part that does not hold.** The skip-list audit (`research/pipeline/queue.json`, SOLR-5754, verdict `confirmed-skip`, 2026-10-06) says "synchronizedList gone". That is wrong on main:
- `StreamingSolrClients.java:51` still wraps `errors` in `Collections.synchronizedList`.

- Only the public `SolrCmdDistributor.getErrors()` is plain. It returns `allErrors` (`SolrCmdDistributor.java:727-728`).

So the skip verdict's evidence is right for one getter and wrong for the list. The record needs correcting before this branch is judged against it.

**Race the TESTING note describes.** The note says an error reported between the copy at `SolrCmdDistributor.java:107` and the `clearErrors()` call that the branch removes can be lost without a retry. Whether that window can open is the real premise question. Findings below.

## The branch's own diff (verified by reading)

- `StreamingSolrClients`: the `errors` field becomes `final` and package-private. `getErrors()` returns a copy taken under the list's lock. New `drainErrors()` copies and clears under the same lock.
- `SolrCmdDistributor.doRetriesIfNeeded` takes `clients.drainErrors()` at line 107. The later `clients.clearErrors()` call is removed (main line 167).
- `clearErrors()` stays public and has no caller left in main code.
- Public behavior change: `getErrors()` now returns a snapshot, not the live list. The only main caller (line 107) moves to `drainErrors()`, so nothing in main depends on the live view.

## Reachability of the race (verified by reading, not run)

- `SolrCmdDistributor.blockAndDoRetries()` (main, lines 278-293) calls `clients.blockUntilFinished()` first, then drains pending async commit futures, then calls `doRetriesIfNeeded()`.
- `StreamingSolrClients.blockUntilFinished()` calls each client's `blockUntilFinished()`. That method waits until the runner set is empty (`ConcurrentUpdateBaseSolrClient.java`, around lines 515-540 on main). After it returns, no runner thread is active, so none can add to the list.
- The pending futures (`SolrCmdDistributor.java:346-355` on main) call `clients.getSolrClient(req).request(...)`. For a commit with no documents, `ConcurrentUpdateBaseSolrClient.request` calls `blockUntilFinished()` and then sends synchronously. Its errors come back as exceptions to `doRequest`, which adds them to the distributor's own list, not to `StreamingSolrClients.errors`.
- On the paths read, no runner thread adds to `StreamingSolrClients.errors` during the window. The race the note describes appears unreachable.
- This is a reading, not a run. The TESTING note asks the same question ("can errors really arrive during the backoff sleep") and this pass answers it for these paths only.

## Test oracle (verified by reading, not run)

- `StreamingSolrClientsTest` writes `clients.errors` directly and calls `drainErrors()`.
- On the base code, `errors` is private and `drainErrors()` does not exist. The test does not compile on base.
- So the fail-before run is **inconclusive by construction** (did not compile on old code). The TESTING note's claim that "the first test fails (`snapshot.size()` becomes 2)" would hold only if `errors` were accessible on base, which it is not.
- The tests are single-threaded. They check the API semantics: snapshot isolation, drain order, and an error that arrives after a drain is kept. They do not exercise the concurrent case the change is meant for.
