## Findings

1. **A registry keeps successful requests alive (new; blocking). Open.**
   - `StreamingSolrClients.reqByUpdateRequest` gets an entry in `getSolrClient()` (line 78 on the branch).
   - An entry leaves only when its stream fails (line 165). Successful requests are never removed.
   - `StreamingSolrClients` is created per `SolrCmdDistributor` (constructor, line 72). Each `DistributedZkUpdateProcessor` creates one per update request (line 118).
   - So each successful `UpdateRequest`, and the documents it carries, stays reachable until the update request ends.
   - The code comment says entries live for "a single distribution round". The code does not do that.
   - **[verified: code]**. The memory cost on large batches is a **[hypothesis]**. It needs a heap test.

2. **Tolerant error counts can double (new; blocking). Addressed at `f8d4bdbea518`; the reading below is of `8f7a36fa6dd`.**
   - At `8f7a36fa6dd`, `TolerantUpdateProcessor.finish()` looped over every `SolrError` in `DistributedUpdatesAsyncException.errors`. For each one it added the remote tolerated-error entries to `knownErrors` (`TolerantUpdateProcessor.java:90`, an `ArrayList`, so duplicates were kept).
   - The branch records one `SolrError` per request in a failed stream, and all of them share one exception object. At `8f7a36fa6dd` each copy carried the same remote metadata and was aggregated again, so the count was once per request.
   - **[verified: code]**. At `8f7a36fa6dd` the effect on `maxErrors` and on the reported count is a **[hypothesis]**.
   - The gate did not run `TestTolerantUpdateProcessorCloud` or `TestTolerantUpdateProcessorRandomCloud`. Both exist on main.
   - Correction, 2026-10-09 (checked at `f8d4bdbea518`): the loop now keeps an identity set of the exceptions it has aggregated and skips a repeat (`TolerantUpdateProcessor.java` lines 242-246). So each distinct remote exception is counted once, even when several errors share it, which is what the 5939 draft says. The shared exception is one object per failed stream (`StreamingSolrClients.java` lines 165-168 pass the same `ex` to `recordError`, which sets `error.e`). This line supersedes the first half of Readiness blocking item 2, which was written against `8f7a36fa6dd`. The request to run the tolerant tests still stands: the 5939 receipt for `f8d4bdbea518` does not name them. The dedupe is verified by reading only.

3. **Client-visible error text changes (new). Open.**
   - Errors from failed forwards and from leader-side failures are thrown as `DistributedUpdatesAsyncException`.
   - With more than one error, its message becomes "N Async exceptions during distributed update:" followed by each message (`DistributedUpdateProcessor.java:1221` and `buildMsg` below it).
   - Before this branch, one failed stream gave one error. The draft's Limits do not mention the change. **[verified: code]**

4. **Every request in a non-retriable failed stream is marked failed (new; not in the draft). Open.**
   - When a stream fails and `shouldRetry` says no (for example, a 400 for one bad document), `recordError` calls `trackRequestResult(null, null, false)` for each request in the stream.
   - Before this branch, only the first request got that call.
   - So requests that were fine can be counted as failed, and the client's error list can include them. The effect on replication-factor counts is a **[hypothesis]**. **[verified: code]**

5. **Every request in a failed stream is retried on its own budget (by design; stated in the draft's Limits).** A request that would have succeeded can be resent. **[verified: code]**

6. **The ticket's premise.** Correct on main. `ErrorReportingConcurrentUpdateSolrClient` captures the first request for the node and stamps every stream error with it. The branch passes the stream's own requests to a new callback. The Jetty and JDK clients record each update they write. **[verified: code and diff]**
   - Test 1 (`testMergedStreamErrorIsAttributedToEveryRequestInTheStream`) expects the error doc ids `[1, 2]`. On base the expected result is `[1]`.
   - Test 2 (`testDeleteByQueryRetryRuleIsJudgedOnItsOwnRequest`) expects two errors. On base the expected result is one.
   - Both tests discriminate by reading. The base run is a **[record]**. **[verified: test]**

7. **The first update in a merged stream is recorded.** The Jetty loop starts with `upd = update` and records each update before writing it. So the request that opened the stream is always in the failed list. **[verified: code]**

8. **Per-request attribution is a design choice.** The branch chose per-request errors. The report lists two other routes: per-document callbacks and fail-the-batch. The assessment asked for maintainer agreement before a PR. **[record]**

The draft says no existing signature changes. That is true, but the additions should be named. **[verified: diff]**

10. **Test hygiene (open).** `StreamingSolrClientsErrorAttributionTest.beforeClass()` sets `solr.cloud.client.pollQueueTime` to 500 and never clears it. Other test classes in the same JVM would inherit it. **[verified: code]**

11. **Overlap with SOLR-5754 (Group B).** Both branches change `StreamingSolrClients.java` and `SolrCmdDistributor.java`.
    - A three-way merge is clean in both orders (`git merge-tree` exits 0 both ways). Neither merge has a textual conflict.
    - Semantically, 5754 replaces the `getErrors()` and `clearErrors()` pair in `doRetriesIfNeeded` with an atomic `drainErrors()`. Without that, an error added between the read and the clear is lost.
    - 5939 adds one error per request in a failed stream, so it adds more errors per failure. The 5754 fix closes a window that 5939 makes wider.
    - Can they proceed independently? At the code level, yes. The merge is clean in either order, and the Group B audit of 5754 (`audits/update-processing/SOLR-5754.md` on this branch) reaches the same reading. My caution is about gating, not merging: 5939 widens the window that 5754 closes, so the combined tree should be gated before either is called final. The smaller change, 5754, should go first.
