## Findings

1. **Distributed commits fail (new; blocking). Open.**
   - The new guard at the top of `DistributedZkUpdateProcessor.processCommit` (branch lines 158-163) calls `req.getParams().getBool(COMMIT_END_POINT, false)`.
   - Forwarded commits carry string values in that parameter: `"leaders"` (set at `DistributedZkUpdateProcessor.java:218` on main) and `"replicas"` (line 235).
   - `SolrParams.getBool` calls `StrUtils.parseBool`. That method throws `BAD_REQUEST "invalid boolean value"` for any value that is not a true/false word (`solr/solrj/.../StrUtils.java:267-277`).
   - So a forwarded commit throws before the cluster logic runs. A commit sent to a non-leader fails at the leader. A commit forwarded to replicas fails on each replica, and the leader ignores those errors (`doDistribFinish` skips errors when `commit_end_point` is set).
   - **[verified: code]**. The gate did not run any SolrCloud test, so this was not caught.

2. **A claim in the report is wrong (refuted).** The report says "`StrUtils.parseBool` returns false for 'leaders' and 'replicas'". It does not. It throws. See item 1. **[verified: code]**

3. **The same problem in `RoutedAliasUpdateProcessor.wrap()` (new).** The new guard calls `getBool` on every request that reaches `wrap()` on a routed-alias core. A forwarded commit with a string value throws there as well. **[verified: code]**

4. **Version clock and update lock taken on every autocommit in SolrCloud (new; not named in the draft).**
   - On main, `CommitTracker` stamps a version only for a cloud leader's hard commit (main line 271).
   - On this branch, the autocommit reaches `DistributedUpdateProcessor.doLocalCommit`. That method calls `vinfo.getNewClock()`, sets the version on the command, and takes the update lock (`DistributedUpdateProcessor.java:1166-1192`).
   - This runs on replicas too. On a leader, the version set by `CommitTracker` is overwritten.
   - The report says clock stamping is "unchanged". That is not true. **[verified: code]**

5. **Autocommits can be dropped on a replica that is not ACTIVE (new; not stated in the draft's main text).**
   - `doLocalCommit` commits only when the update log is ACTIVE or the commit is a replay (`DistributedUpdateProcessor.java:1174-1185`). Otherwise it logs "Ignoring commit" and returns.
   - Before this branch, an autocommit always committed. Now it can be dropped while a replica buffers or replays.
   - The draft's Limits mention this. The draft's "What this change does" says the behavior is "exactly as it does today". Those two statements contradict each other.
   - The draft says the normal recovery commit covers the replica. I did not verify that. `RecoveryStrategy.java` has commit calls at lines 247-249, 321 and 737 on main. I did not trace them. **[verified: code; claim not verified]**

6. **The ticket's premise (autocommit skips the chain).** Correct. On main, `CommitTracker.run()` calls `core.getUpdateHandler().commit(command)` directly. **[verified: code]**
   - `AutoCommitUpdateChainTest` checks that a recording processor sees one autocommit, marked as an autocommit and as an end point, and that the document becomes searchable.
   - The test is standalone. It does not cover SolrCloud or forwarded commits.
   - The base-code failure (`expected:<1> but was:<0>`) is a record from the report. **[verified: test; record for base run]**

7. **Ignore-commit processor.** `IgnoreCommitOptimizeUpdateProcessorFactory.java:125` (main) reads the same parameter with `getBool`. The branch makes autocommits reach that check. Their flag now means "do not ignore", which matches the report. The same `getBool` already throws on `"leaders"` and `"replicas"` on main, so the parameter was never boolean. **[verified: code]**
