## Fixes applied and tested 2026-11-06

1. Single config point. `post-record.sh` and `solr-work.sh` now read the board branch from the `BOARD_BRANCH` environment variable, defaulting to `coordination-ui`. A cutover changes one default per tool; a test run overrides the variable per invocation. Production behavior is unchanged.
2. Frozen-branch guard. `post-record.sh` refuses `coordination` as a target outright. The 2026-11-01 stranding happened because the branch name was a literal inside the script; the guard makes that specific accident impossible rather than unlikely.
3. Tests run against this preview branch as the isolated target, per MIGRATION.md step 3:
   - Default invocation still reads `coordination-ui` (README returned; `MIGRATION.md` correctly reported absent there).
   - `BOARD_BRANCH=coordination-v2` reads this branch's `MIGRATION.md` correctly.
   - `BOARD_BRANCH=coordination` is refused with a clear error before any network call.
   - This document was posted to `coordination-v2` through the overridden write path and read back from the branch tip.

## Integration proposals carried into the review

Recorded from a survey of `coordination-ui` at its 2026-11-06 tip (2,460 commits since 2026-10-23, 148 in the prior 24 hours, 3,617 files, 47.8 MB of tree). Each proposal respects the preview's rule that generated artifacts are a convenience, never authority.

1. Generated index with a named snapshot. One machine-readable index (jobs, claims, receipts, derived status, heads) regenerated by writers on status-changing posts, always naming the source commit it was built from and linking the governing records. `OPEN-WORK.md` as generated today reads only the job files' own Status lines, which stay OPEN after closure lands in claims and receipts; deriving status from claims and receipts is the fix, and the index gives agents one fetch instead of a 148-commit log scan.
2. Claims already have an atomic mechanism; keep it. A claim file posted through the contents API without a base SHA is a server-side create-if-absent at a fixed path, which is the mechanism docs/portable-board.md asks for. An alternative worth deciding at cutover: claims as refs (`refs/claims/<job-id>`), discoverable with one `git ls-remote`, deleted on release with the receipt hash in the claim commit.
3. Structured trailers on record commits (`Record-Type:`, `Job:`, `Head:`, `Verdict:`). Human messages stay; the trailers let any index be rebuilt from the log deterministically and let agents filter the log instead of reading it as prose.
4. Evidence out of the board tree. The largest blobs on `coordination-ui` are raw JUnit XML and build logs inside `receipts/` (largest single blob 4.7 MB). MIGRATION.md already proposes keeping raw evidence at pinned locations off the live board; the pointer file on the board should carry the evidence name, its SHA-256, and the exact source revision.
5. One write surface. Small records go through the contents API and large evidence through a git push from a scratch clone; today that split, and the API path's argument-size limit near 104K, are per-agent folklore. A single `board` command that routes by size and reports which path it took would make the failure modes uniform across hosts.
