# PR review draft: apache/solr #4181

Status: PROPOSED. Nothing is posted. Reviewer host: vm4. Head branch `copilot/migrate-realtimegetapi-to-jax-rs` (epugh/solr), PR base `ae262ba33e`. Outcome: NEEDS-CHANGES.

## Summary of the change

Moves the real-time get v2 API (`RealTimeGetAPI`) from `@EndPoint`/`AnnotatedApi` to JAX-RS, with a new endpoint interface `RealTimeGetApi` and response model `GetDocumentsResponse`. The RTG logic stays in `RealTimeGetHandler`. The change also edits the shared Jersey JSON layer (`SolrJacksonMapper`, +48 lines; `MessageBodyWriters`, +3/-1) to serialize `SolrDocument` and `SolrDocumentList`, and adds a test (`RealTimeGetAPITest`, +95).

## Proposed comments

1. Shared JSON layer needs tests. `SolrJacksonMapper.java` is the mapper for every Jersey JSON response, and this PR adds serializers for `SolrDocument` and `SolrDocumentList` there. `MessageBodyWriters.java` also changes. Neither `SolrJacksonMapperTest` nor any writer test is in the PR. A test should cover a document with multi-valued and nested fields, and a document list with `numFound`, so that other APIs that return these types are not changed by accident.
2. `V2ApiIntegrationTest.java` loses 16 lines. Could the PR body say why, and show that the removed case is still covered by `RealTimeGetAPITest` or another test?
3. Parity with v1. The PR says the response path had a gap that it fixes. A before and after comparison of `/get` (v1 and v2) for the same `id` and `ids` values, including a missing id, would show that the JSON output matches. Could that be added as a test, or described as a manual check?
4. Rebase. The PR base is `ae262ba33e`, older than current main. The new files (`RealTimeGetApi`, `GetDocumentsResponse`) do not exist at apache/main `c8ab71430f`, so they do not collide. `RealTimeGetAPI`, `SolrJacksonMapper`, `MessageBodyWriters` and `JerseyResource` do exist there, so a rebase may touch the shared files.
5. Generated client. The PR body says the generated SolrJ client now exposes `id` and `ids`. A reviewer should check the generated output against the endpoint interface, since that output is not in review in the text above.
