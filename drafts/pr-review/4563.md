# PR review draft: apache/solr #4563 (SOLR-18295)

Status: PROPOSED. Nothing is posted. Reviewer host: vm4. Head branch `SOLR-18295-replicationfactortest-flaky` (janhoy/solr), PR base `c851aae5c8`. Outcome: NEEDS-CHANGES (evidence for the flake fix).

## Summary of the change

Removes `@AwaitsFix` from `ReplicationFactorTest` and wraps the single-document send in `runAndGetAchievedRf` with a retry loop (up to 5 retries) on `SolrServerException` and `IOException`. The test comment says the failure comes from http proxy port manipulation in the test.

## Proposed comments

1. Root cause and evidence. The fix is a retry in test code, and the comment says the test "may fail due to http proxy port manipulation". Could the PR show the failing run that matches this cause (the stack trace or log line for SOLR-18295), and say why the proxy is the source rather than a Solr bug that the retry hides?
2. Repeat runs. The test was re-enabled, so it needs evidence it now passes reliably. A number of repeated runs with different seeds on the rebased branch (for example 20), before and after the change, would show the flake rate. None is in the PR.
3. Idempotency of the retry. The loop re-sends the same update after a failure. The send is keyed by `docId`, so a retry should be an upsert, but the PR should say so, since a retry after a partial success could otherwise double-count the achieved replication factor.
4. Retry bound and exception type. Five retries with no backoff is a narrow window if the proxy port change takes longer. Could the PR say why five is enough, and whether `throws Exception` on `runAndGetAchievedRf` is needed?
5. Base. The base `c8ab71430f` still has the `@AwaitsFix` annotation and the same method, so the change applies there. The PR base `c851aae5c8` is older; a rebase is still needed before merge.
