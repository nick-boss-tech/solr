# PR review draft: apache/solr #4626 (SOLR-17433)

Status: PROPOSED. Nothing is posted. Reviewer host: vm4. Head branch `SOLR-1743-changed-default-request-timeout` (VishnuPriyaChandraSekar/solr), PR base as in the snapshot. Outcome: NEEDS-OWNER (the default request timeout).

## Summary of the change

Makes the default HTTP request timeout infinite in the SolrJ clients. `HttpSolrClient.getRequestTimeoutMillis()` now returns 0 (no timeout) when none is configured, where it used to fall back to the idle timeout. `HttpJettySolrClient` keeps a global idle timeout only as the read default, and `HttpJdkSolrClient` skips the JDK request timeout when the value is non-positive. `SolrHttpConstants` gets a `DEFAULT_IDLE_TIMEOUT`. The test fixture `ServletFixtures.SlowStreamServlet` takes a `packetMs` parameter, and `LB2SolrClientTest` (+93/-13) and `HttpJettySolrClientTest` are updated.

## Proposed comments

1. Default behavior. Requests that never get a response now wait forever by default. That fixes the 60-second cut-off in SOLR-17433, but a dead or hung node can now hang a client thread with no time bound. This is a default change for every SolrJ user, so it is an owner decision: infinite by default, or a large finite default (for example the existing socket timeout) that a user can raise. The PR body should state the choice and the trade-off either way.
2. Changelog. The entry needs a type that matches the change. A default change is `changed`, and the entry should say how to restore the old bounded behavior (`withRequestTimeout`).
3. Tests. The fix needs tests on both sides: a default request on a slow servlet completes after more than 60 seconds, and an explicit request timeout still fires. `LB2SolrClientTest` and `HttpJettySolrClientTest` change, but the PR does not say which of these two cases each test pins.
4. Comment text in `HttpJettySolrClient`. The new comment reads "timeout.The read timeout" with a missing space, and the note about the builder idle timeout is cut off in the patch. Please tidy before merge.
5. The `DEFAULT_IDLE_TIMEOUT = 60000` constant is added to a public interface. If it is only used internally, consider keeping it out of the interface.
6. The JDK client change (skip the timeout when non-positive) is a small, reasonable guard. No comment.
