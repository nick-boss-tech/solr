# PR review draft: apache/solr #4921 (SOLR-18466)

Status: PROPOSED. Nothing is posted. Reviewer host: vm4. Head branch `streaming-search-route/SOLR-18466` (tsornin14/solr), PR base as in the snapshot. Outcome: READY-WITH-NOTES (documentation and two small code checks).

## Summary of the change

Adds `_route_` support to the streaming expression `search` function, so the shards queried are pruned to those that hold the routed keys. `CloudSolrStream` gets a new overload `getSlices(collection, client, checkAlias, SolrParams)` that reads `ShardParams._ROUTE_`, and the old two-argument method delegates to it with empty params. `TupleStream.getReplicas` now calls the new overload after the request params are built. Adds a changelog entry (`type: added`) and a 223-line test `testCloudSolrStreamWithRouteParam` in `StreamExpressionTest` using an implicit-router collection.

## Proposed comments

1. Documentation. This is a user-facing feature (a new `_route_` behavior for the `search` stream source), but the diff has no reference-guide change. The stream source reference page is the place where `search` parameters are listed. Could a short entry be added there, with one example?
2. Multiple route keys. `routeKeys` is read as a single string. The PR should say what a comma-separated list of keys means (any key, or all keys), and add a test for two keys, since the existing test uses one route at a time.
3. Composite router. The new test uses an implicit router (`createCollectionWithImplicitRouter`). A route key on a `compositeId` collection maps to a hash, not a shard name. A test for that router would show the pruning is correct there too.
4. Unused import. `CloudSolrStream.java` adds `org.apache.solr.common.cloud.DocCollection`. Please check whether it is used; if not, remove it so the compile does not warn.
5. Public overload. `CloudSolrStream.getSlices` gains a public overload in `solrj-streaming`. It is a new public signature, so the PR body should say it is intended for external callers, or the method could stay package-private.
6. Ordering in `TupleStream`. The `getSlices` call moved after the request params are assembled. The PR should say why the order changed (so the route key is available), so a later refactor does not move it back.
