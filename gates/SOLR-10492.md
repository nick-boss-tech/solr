## What happens today

**With group.facet=true, distributed facet.field results can show document counts where group counts belong.**

The reporter used facet.limit=50 on a SolrCloud collection. The facet.query count was a grouped count of 8, but the facet results showed 233 for the same field, and those were document counts ([JIRA](https://issues.apache.org/jira/browse/SOLR-10492)). When a small facet.limit makes the coordinator refine terms, the listed-term refinement counts each term with `numDocs`, which counts documents, not groups ([SimpleFacets.java, base](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/request/SimpleFacets.java#L979)). Those document counts replace the correct grouped counts.

## What this change does

**Refinement counts are grouped counts when group.facet=true.**

- Listed-term refinement uses the grouped counter for a field with group.facet=true ([SimpleFacets.java L1002-L1019](https://github.com/nick-boss-tech/solr/blob/f9707a5691f1ef4136ae36698ff6a400b8960539/solr/core/src/java/org/apache/solr/request/SimpleFacets.java#L1002-L1019)). The shared grouped counter is at [L807-L825](https://github.com/nick-boss-tech/solr/blob/f9707a5691f1ef4136ae36698ff6a400b8960539/solr/core/src/java/org/apache/solr/request/SimpleFacets.java#L807-L825).
- A refinement request can arrive with group.field but no grouping specification. The stored-fields shard request removes the group parameter, as it does at the base commit ([StoredFieldsShardRequestFactory.java L66](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/search/grouping/distributed/requestfactory/StoredFieldsShardRequestFactory.java#L66)); this change does not touch that file. For that refinement request only, the field is read from the request parameters ([L1059-L1065](https://github.com/nick-boss-tech/solr/blob/f9707a5691f1ef4136ae36698ff6a400b8960539/solr/core/src/java/org/apache/solr/request/SimpleFacets.java#L1059-L1065)).
- Other requests keep their behavior. A facet.field request with group.facet=true and group.field, but without group=true, still returns BAD_REQUEST, as it does at base. [TestGroupingSearch](https://github.com/nick-boss-tech/solr/blob/f9707a5691f1ef4136ae36698ff6a400b8960539/solr/core/src/test/org/apache/solr/TestGroupingSearch.java#L533-L549) pins that response.

## Proof

- TestDistributedGrouping 2 of 2 pass. The new case, with facet.limit 1 and 2 and overrequest off, fails on base e2cdb2d7e8ae: the refined term carries a document count where the grouped count is 5.
- TestGroupingSearch 18 of 18 pass, including the new 400 test, which also passes on base.
- DistributedFacetPivotSmallTest 1 of 1 passes.
- Verified at f9707a5691f on DATE, from the focused JUnit results.

## Limits

**Grouped counts are tested on distributed refinement only.**

- A group.field given only as a local parameter, with group.facet=true and without group=true, is not covered by a test in this change. It still returns BAD_REQUEST for facet.field and facet.query.
- The cost of grouped refinement counts on large fields is not measured.
