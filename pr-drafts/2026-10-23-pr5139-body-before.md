## What happens today

**A replica whose core will not load can block leader election.**

The ticket describes four nodes. A schema change, made while one node was down, left two nodes with cores that would not load. The two remaining nodes could not finish a leader election, because their versions requests to the broken cores got HTTP 500 ([ticket](https://issues.apache.org/jira/browse/SOLR-7550)). The remaining nodes ended in `recovery_failed`, and the cluster went offline.

A core that fails to initialize is reported through [`SolrCoreInitializationException`, thrown by `CoreContainer`](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/core/CoreContainer.java#L2222). On the merge base, PeerSync treats that 500 as a failure ([PeerSync.java L428-L431](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/update/PeerSync.java#L428-L431)).

## What this change does

**PeerSync counts a versions request that fails with a core initialization failure as success, when `cantReachIsSuccess` is set. Every other 500 still fails.**

PeerSync checks the exception class that Solr writes into the error metadata ([PeerSync.java L424-L435](https://github.com/nick-boss-tech/solr/blob/5f4570b20ad4d830a4affdfd2e45527753093729/solr/core/src/java/org/apache/solr/update/PeerSync.java#L424-L435); [ResponseUtils.java L77](https://github.com/nick-boss-tech/solr/blob/5f4570b20ad4d830a4affdfd2e45527753093729/solr/core/src/java/org/apache/solr/servlet/ResponseUtils.java#L77)). The 503 and 404 rules are unchanged ([L400-L422](https://github.com/nick-boss-tech/solr/blob/5f4570b20ad4d830a4affdfd2e45527753093729/solr/core/src/java/org/apache/solr/update/PeerSync.java#L400-L422)).

Leader election passes the flag as true ([SyncStrategy.java L225-L232](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/cloud/SyncStrategy.java#L225-L232)). The `/get` sync request reads the flag from the caller too ([RealTimeGetComponent.java L1293-L1295](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/component/RealTimeGetComponent.java#L1293-L1295)), so the rule applies there. A caller who can set the flag already gets success for a refused connection ([PeerSync.java L381-L398](https://github.com/nick-boss-tech/solr/blob/5f4570b20ad4d830a4affdfd2e45527753093729/solr/core/src/java/org/apache/solr/update/PeerSync.java#L381-L398)), so this adds no new outcome.

Two `ShardResponse` setters are now public ([L81](https://github.com/nick-boss-tech/solr/blob/5f4570b20ad4d830a4affdfd2e45527753093729/solr/core/src/java/org/apache/solr/handler/component/ShardResponse.java#L81), [L100](https://github.com/nick-boss-tech/solr/blob/5f4570b20ad4d830a4affdfd2e45527753093729/solr/core/src/java/org/apache/solr/handler/component/ShardResponse.java#L100)), and `handleResponse` is package-visible ([L368-L369](https://github.com/nick-boss-tech/solr/blob/5f4570b20ad4d830a4affdfd2e45527753093729/solr/core/src/java/org/apache/solr/update/PeerSync.java#L368-L369)), for the test.

## A choice to check

**Three ways to stop a broken core from blocking the election. This PR implements the first.**

1. **Count a 500 only when it names the initialization failure class (this PR).** The status code does not change. Cost: a node that does not send the class name still blocks the election.
2. **Count every 500 for a versions request.** This was the first version of this PR. Cost: a replica that returns 500 for a runtime fault, while holding newer updates, is also skipped, so the leader can miss updates only that replica holds.
3. **Return 503 for the initialization failure.** The existing 503 rule then applies. Cost: a client sees 503 instead of 500 for this error. The 500 is set on purpose and pinned by tests, and 503 suggests a retry for a failure that does not clear on its own.

Was option 1 the right call, or should the status change in option 3 be made instead?

## Limits

- The tests call `handleResponse` directly. The path from a real broken core to this rule is not tested end to end.
- Older Solr versions may not send the class name. Those nodes keep today's failure. That is not checked here.
- The `/get` sync path is not tested.
- The two `ShardResponse` setters are wider than the fix needs. They exist for the test.
