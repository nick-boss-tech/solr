The recursion described in this ticket is still in the code on main. In a test with forced failures, the loop repeated 31 times and the stack grew by 6 frames each time. The stack did not overflow in that run.

- On [commit b73f03976f](https://github.com/apache/solr/commit/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb), `ShardLeaderElectionContext.rejoinLeaderElection` calls `LeaderElector.joinElection`, which calls `checkIfIamLeader` and then `runLeaderProcess`. That can call `rejoinLeaderElection` again. The call is at [line 494](https://github.com/apache/solr/blob/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb/solr/core/src/java/org/apache/solr/cloud/ShardLeaderElectionContext.java#L494). Nothing in the path limits how many times it repeats.
- Rejoining happens when a sync fails ([line 245](https://github.com/apache/solr/blob/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb/solr/core/src/java/org/apache/solr/cloud/ShardLeaderElectionContext.java#L245)), when the leader publish fails ([line 318](https://github.com/apache/solr/blob/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb/solr/core/src/java/org/apache/solr/cloud/ShardLeaderElectionContext.java#L318)), or when the replica is not allowed to lead in time ([line 188](https://github.com/apache/solr/blob/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb/solr/core/src/java/org/apache/solr/cloud/ShardLeaderElectionContext.java#L188)).
- Each attempt waits at a leader throttle of 5 seconds, set at [line 130](https://github.com/apache/solr/blob/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb/solr/core/src/java/org/apache/solr/cloud/ShardLeaderElectionContext.java#L130). The throttle came in [f2bf0e2235](https://github.com/apache/solr/commit/f2bf0e2235b4b5e0b18dc8755716fad10df78ac2) (SOLR-7033 and SOLR-5961), after this ticket was filed. The 5-second pause limits how fast the stack grows, but it does not stop the growth.
- Two duplicates are resolved, SOLR-5692 and SOLR-6285. I found no commit on main that fixes this path.
- The test forced 30 failed syncs. Each attempt came 5 seconds after the last. A stack overflow would need a long run of failed syncs, and the number needed depends on the stack size of the thread. I did not measure that limit.

**Recommendation:** Keep open. A limit on the rejoin loop changes leader election, so it needs its own change and a test that forces repeated failures over a long run.
