## What happens today

**The Word Delimiter Graph examples show catenated tokens at positions that do not match the filter.**

The page lists the output for `hot-spot 100+42 XL40` as `hot` at position 1, `spot` at 2, `hotspot` at 2, and `10042` at 4 ([filters.adoc L3840, base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solr-ref-guide/modules/indexing-guide/pages/filters.adoc#L3840)). For `XL-4000/ES` it lists `XL4000ES` at position 3 ([L3859, base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solr-ref-guide/modules/indexing-guide/pages/filters.adoc#L3859)). The filter starts a catenated token at the position of its first part, so those positions are wrong.

## What this change does

**The examples now show each catenated token at the position of its first part, listed before the parts.**

The output for `hot-spot 100+42 XL40` now shows `hotspot` at position 1 and `10042` at position 3 ([L3840, head](https://github.com/nick-boss-tech/solr/blob/8a945757e6687253f61f7dc1e46130fa722c3f14/solr/solr-ref-guide/modules/indexing-guide/pages/filters.adoc#L3840)). The output for `XL-4000/ES` now shows `XL4000ES` at position 1 ([L3859, head](https://github.com/nick-boss-tech/solr/blob/8a945757e6687253f61f7dc1e46130fa722c3f14/solr/solr-ref-guide/modules/indexing-guide/pages/filters.adoc#L3859)). A new note says the filter produces a token graph, and that a catenated token spans the parts it joins ([L3861, head](https://github.com/nick-boss-tech/solr/blob/8a945757e6687253f61f7dc1e46130fa722c3f14/solr/solr-ref-guide/modules/indexing-guide/pages/filters.adoc#L3861)).

The change edits the reference guide and adds a changelog fragment. It does not change any code.

## Proof

**No test ran, because this change is documentation only. The evidence is a documentation build and a check of the filter's behavior.**

- The local reference-guide build (`:solr:solr-ref-guide:buildLocalSite`) passed at head 8a945757e66, verified 2026-10-11: 69 tasks, 65 executed and 4 up-to-date. The rendered filters page shows `hotspot` at position 1, `10042` at position 3, and `XL4000ES` at position 1, with the token graph note. The build compiles Java code as a prerequisite, but no Java test task ran.
- The changelog check (`logchangeLint`) passed at the same head.
- The positions come from Lucene's `WordDelimiterGraphFilter`. In Lucene 10.4.0 (Solr main and `branch_10x`) and in Lucene 9.12.3 (`branch_9x`), the filter starts a catenated token at the first subword and spans its parts. At one start offset it sorts longer arcs first. The implementation is the same in both versions, and existing Lucene tests assert output at the same position.

This is light evidence by design. A documentation change has no test that could fail before it.

## Limits

**The Lucene Javadoc for the filter still says a catenated token sits at the last subword.**

That text conflicts with the implementation and the Lucene tests. This change does not edit Lucene's Javadoc, so the Solr page and the Lucene API text will disagree until that text is fixed. A follow-up for the Lucene text can be opened on request.

The check covers Lucene 10.4.0 and 9.12.3. Other Lucene versions were not checked.
