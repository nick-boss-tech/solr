Title: Log the node and response key names, not the shard request, in the corrupted response warning

https://issues.apache.org/jira/browse/SOLR-17752

## What happens today

**A corrupted shard response is logged with the whole shard request and the whole response, and the query text can appear in both.**

When a shard response lacks the expected section and does not set partial results, the warning logs the shard request and the full response at WARN ([SolrResponseUtil.java#L55](https://github.com/apache/solr/blob/e5c0a64f993c7ce5e9a594f5a6eb0679925e9de9/solr/core/src/java/org/apache/solr/util/SolrResponseUtil.java#L55)). The response header can echo the request params. SolrCore adds them when echoParams is explicit or all ([SolrCore.java#L3004](https://github.com/apache/solr/blob/e5c0a64f993c7ce5e9a594f5a6eb0679925e9de9/solr/core/src/java/org/apache/solr/core/SolrCore.java#L3004)), and the default configset sets explicit on `/select` and `/query` ([solrconfig.xml#L597](https://github.com/apache/solr/blob/e5c0a64f993c7ce5e9a594f5a6eb0679925e9de9/solr/server/solr/configsets/_default/conf/solrconfig.xml#L597)). The ticket notes that a query can carry customer data.

## What this change does

**The warning now names the responding node and lists the response's top-level key names. It no longer prints the shard request or the response.**

The new line reads `corrupted response on <node> : response contains keys [<top-level key names>]`. The node is the responding node name, or the shard address when the node name is null ([SolrResponseUtil.java#L58-L61](https://github.com/nick-boss-tech/solr/blob/e5c0a64f993c7ce5e9a594f5a6eb0679925e9de9/solr/core/src/java/org/apache/solr/util/SolrResponseUtil.java#L58-L61)). The key-name helper, with a comment on why values are left out, is at [lines 84-94](https://github.com/nick-boss-tech/solr/blob/e5c0a64f993c7ce5e9a594f5a6eb0679925e9de9/solr/core/src/java/org/apache/solr/util/SolrResponseUtil.java#L84-L94).

The warning no longer shows the request's params, its purpose or its response count, or any response values. The exception thrown after the warning is unchanged.

## Proof

**TestShardResponseLogging passed 1 of 1 at head e5c0a64f993c7ce5e9a594f5a6eb0679925e9de9.**

The test builds a shard response whose request and response header both carry a query term. It checks that the warning names the node and does not contain the term ([TestShardResponseLogging.java#L34-L70](https://github.com/nick-boss-tech/solr/blob/e5c0a64f993c7ce5e9a594f5a6eb0679925e9de9/solr/core/src/test/org/apache/solr/handler/component/TestShardResponseLogging.java#L34-L70)). On the unpatched code the test fails at the node-name assertion, and the warning it captures holds the query text in both the request and the response header. The formatting check, the Error Prone compile, and the core module check with tests excluded also passed at this head.

## Limits

- The test builds the shard response by hand. It does not run a cluster with echoParams set.
- Other log lines print request params at INFO or DEBUG, for example [SuggestComponent.java#L181](https://github.com/apache/solr/blob/e5c0a64f993c7ce5e9a594f5a6eb0679925e9de9/solr/core/src/java/org/apache/solr/handler/component/SuggestComponent.java#L181). They are not changed here. I can open that follow-up on request.
