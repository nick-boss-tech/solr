Title: SOLR-17752: Don't log the shard request or response in corrupted-response warnings

https://issues.apache.org/jira/browse/SOLR-17752

## What happens today

**A corrupted shard response is logged with the whole shard request and the whole response, and the query text can appear in both.**

When a shard response lacks the expected section and does not set partial results, the warning logs the shard request and the full response at WARN ([SolrResponseUtil.java#L55](https://github.com/nick-boss-tech/solr/blob/56ec140e3636d5f4150fa87fbf7103529536ac99/solr/core/src/java/org/apache/solr/util/SolrResponseUtil.java#L55)). These links point to the merge-base commit, `56ec140e3636`, which is the code before this change. The response header can echo the request params. SolrCore adds them when echoParams is explicit or all ([SolrCore.java#L3004-L3007](https://github.com/nick-boss-tech/solr/blob/56ec140e3636d5f4150fa87fbf7103529536ac99/solr/core/src/java/org/apache/solr/core/SolrCore.java#L3004-L3007)), and the default configset sets explicit on `/select` ([solrconfig.xml#L597](https://github.com/nick-boss-tech/solr/blob/56ec140e3636d5f4150fa87fbf7103529536ac99/solr/server/solr/configsets/_default/conf/solrconfig.xml#L597)) and on `/query` ([solrconfig.xml#L605](https://github.com/nick-boss-tech/solr/blob/56ec140e3636d5f4150fa87fbf7103529536ac99/solr/server/solr/configsets/_default/conf/solrconfig.xml#L605)). The ticket notes that a query can carry customer data.

## What this change does

**The warning now names the responding node, the shard request purpose, and the response's top-level key names. It no longer prints the shard request or the response.**

The new line reads `corrupted response on <node> : response contains keys [<top-level key names>], shard request purpose <int>`. The node is the responding node name, or the shard address when the node name is null, and the exception thrown after the warning uses that same name ([SolrResponseUtil.java#L58-L64](https://github.com/nick-boss-tech/solr/blob/041c5b0b2e44e903e7010a40530de3a24ea9bb06/solr/core/src/java/org/apache/solr/util/SolrResponseUtil.java#L58-L64)). The key-name helper, with a comment on why values are left out, is at [lines 87-99](https://github.com/nick-boss-tech/solr/blob/041c5b0b2e44e903e7010a40530de3a24ea9bb06/solr/core/src/java/org/apache/solr/util/SolrResponseUtil.java#L87-L99).

The warning no longer shows the request's params or its response count, or any response values. If the response carries an error section, the warning names that key but not the error's message, because an error message can echo the query, as a parse error does.

## Proof

**TestShardResponseLogging passed 2 of 2 at head 041c5b0b2e, verified 2026-10-16, and the distributed tests of the components that read shard responses this way also passed.**

The test builds a shard response whose request and response header both carry a query term. It checks that the warning names the node and does not contain the term ([TestShardResponseLogging.java#L34-L74](https://github.com/nick-boss-tech/solr/blob/041c5b0b2e44e903e7010a40530de3a24ea9bb06/solr/core/src/test/org/apache/solr/handler/component/TestShardResponseLogging.java#L34-L74)). On the unpatched code the test fails at the node-name assertion, and the warning it captures holds the query text in both the request and the response header. A second test ([lines 75-117](https://github.com/nick-boss-tech/solr/blob/041c5b0b2e44e903e7010a40530de3a24ea9bb06/solr/core/src/test/org/apache/solr/handler/component/TestShardResponseLogging.java#L75-L117)) covers a null node name: the exception names the shard address. On the head before this change that test fails, because the exception reads "is absent in response from null". DistributedTermsComponentTest, DistributedExpandComponentTest and DistributedSpellCheckComponentTest passed 1 of 1 each at this head, and TestDistributedGrouping passed 2 of 2. The formatting check, the Error Prone compile, and the core module check with tests excluded also passed at this head.

## Limits

**The test builds its response by hand, and other log lines still print request params.**

- The test builds the shard response by hand. It does not run a cluster with echoParams set.
- Other log lines print request params at INFO or DEBUG, for example [SuggestComponent.java#L181](https://github.com/nick-boss-tech/solr/blob/56ec140e3636d5f4150fa87fbf7103529536ac99/solr/core/src/java/org/apache/solr/handler/component/SuggestComponent.java#L181), at the merge-base commit. They are not changed here. I can open that follow-up on request.
