Title: Add JettyConfig.withMaxThreads for the test framework's embedded Jetty pool

https://issues.apache.org/jira/browse/SOLR-3684

## What happens today

**The test framework's embedded Jetty always gets a 10000-thread pool, and a test cannot change it.**

JettySolrRunner always uses the fixed constant `THREAD_POOL_MAX_THREADS = 10000` ([JettySolrRunner.java#L207](https://github.com/nick-boss-tech/solr/blob/663b8ce754b69fd81dcd1b5c1abe7e94ca8e6faa/solr/test-framework/src/java/org/apache/solr/embedded/JettySolrRunner.java#L207)), and JettyConfig has no setting for it. Production has its own setting, `solr.jetty.threads.max`, default 10000 ([jetty.xml#L34](https://github.com/nick-boss-tech/solr/blob/663b8ce754b69fd81dcd1b5c1abe7e94ca8e6faa/solr/server/etc/jetty.xml#L34)). The ticket reports full GC under about 1000 indexing threads.

## What this change does

**It adds an optional thread pool size to the test framework's JettyConfig. No default changes.**

`JettyConfig.Builder.withMaxThreads(int)` sets the size for one embedded runner ([JettyConfig.java#L110-L113](https://github.com/nick-boss-tech/solr/blob/663b8ce754b69fd81dcd1b5c1abe7e94ca8e6faa/solr/test-framework/src/java/org/apache/solr/embedded/JettyConfig.java#L110-L113)). JettySolrRunner uses that value when it is set and keeps 10000 when it is not ([JettySolrRunner.java#L207](https://github.com/nick-boss-tech/solr/blob/663b8ce754b69fd81dcd1b5c1abe7e94ca8e6faa/solr/test-framework/src/java/org/apache/solr/embedded/JettySolrRunner.java#L207)). The production `jetty.xml` file is not touched.

## Proof

**TestJettySolrRunner passed 4 of 4 at head 663b8ce754b69fd81dcd1b5c1abe7e94ca8e6faa, checked 2026-10-03.**

The two new tests are `testJettyThreadPoolDefaultIsUnchanged`, which pins the default at 10000, and `testJettyThreadPoolCanBeConfigured`, which sets 123 and reads it back ([TestJettySolrRunner.java#L34-L63](https://github.com/nick-boss-tech/solr/blob/663b8ce754b69fd81dcd1b5c1abe7e94ca8e6faa/solr/test-framework/src/test/org/apache/solr/embedded/TestJettySolrRunner.java#L34-L63)). The formatting check, the Error Prone compile, and the module check also passed at this head.

This proof is inconclusive by construction. Both new tests call `getConfiguredMaxThreads`, and the configured test also calls `withMaxThreads`. Neither exists on the base commit, so the tests cannot be run there to show a failure. The default test checks a value the base already has.

## A choice to check

**The ticket's remedy is a lower Jetty default. This change keeps the default.**

The option considered was to set the default to 254 in `jetty.xml` and in JettySolrRunner, which is Jetty's own default. A comment on the ticket (Robert Muir, 2012-08-07) says 10000 was probably set to prevent a deadlock (SOLR-683), and asks whether a better fix exists now. A lower default changes every deployment and every test cluster. This branch has no stress test or other evidence that 254 is safe.

Was keeping the default at 10000 and adding only the option the right call?

## Limits

- The memory problem in the ticket is not addressed, including the per-field analyzer reuse the reporter proposes.
- No production behavior changes, and no test here uses a smaller pool to reproduce the ticket's load.
- `getConfiguredMaxThreads()` is a package-private test accessor on JettySolrRunner.
- A lower production default needs its own change and deadlock check. I can open that follow-up on request.
