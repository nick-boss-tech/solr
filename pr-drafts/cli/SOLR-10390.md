## What happens today

**Without a working `lsof`, `bin/solr start` cannot check the port. It prints a note and waits a fixed 10 seconds.**

The start wait checks the port with `lsof` ([solr/bin/solr, lines 1384-1385 at the merge base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/bin/solr#L1384-L1385)). When `lsof -v` does not print `revision`, the script prints "NOTE: Please install lsof as this script needs it to determine if Solr is listening on port", sleeps 10 seconds, and reports that Solr started ([lines 1410-1414](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/bin/solr#L1410-L1414)).

## What this change does

**The start wait uses `lsof` when it works, and a bash `/dev/tcp` connect when it does not.**

A new function, `port_is_listening`, runs the `lsof` check when `lsof -v` prints `revision`. Otherwise it opens a connection to `SOLR_HOST_BIND`, or to 127.0.0.1 when that is unset or a wildcard address ([solr/bin/solr, lines 469-481 at the head](https://github.com/nick-boss-tech/solr/blob/5a86f908052f031b6ce0f0004c0bdf3e825a12c5/solr/bin/solr#L469-L481)). The start wait calls it on each tick ([line 1404](https://github.com/nick-boss-tech/solr/blob/5a86f908052f031b6ce0f0004c0bdf3e825a12c5/solr/bin/solr#L1404)). When the check passes, the start reports success without the fixed 10-second wait. The change touches only the start wait.

## Proof

**The new BATS case fails on the old script and passes with this change.**

- Old script (merge base `cabedd1d968`), verified 2026-10-11: the case `SOLR-10390 start detects the listening port without a working lsof` fails at `refute_output --partial 'Please install lsof'` (test line 129), because the output contains the note.
- This head (`5a86f908052f`), verified 2026-10-11 at this head: the same case passes, 1 of 1.

The case puts a stand-in `lsof` that exits with an error first on the path. It then starts Solr and checks the started state ([test, lines 121-133](https://github.com/nick-boss-tech/solr/blob/5a86f908052f031b6ce0f0004c0bdf3e825a12c5/solr/packaging/test/test_start_solr.bats#L121-L133)).

## A choice to check

**The fallback uses a `/dev/tcp` connect when `lsof` is unusable. That adds a false failure when neither tool works.**

Option A, this change: use `lsof` when it works, and a bash `/dev/tcp` connect otherwise. This removes the fixed wait. Its cost: on a system where neither `lsof` nor bash `/dev/tcp` works, the start wait never sees the port. It then reports that Solr is not listening, where the current script reports success. Option B: keep the fixed wait for that case. Was option A the right call, or should the fixed wait stay as the fallback?

## Limits

**The test covers the fallback only. It does not cover a system with neither tool.**

- The stand-in `lsof` exits with an error. The case does not test a real `lsof` on any platform.
- The case with neither `lsof` nor `/dev/tcp` is not tested (see the choice above).
- The `lsof` check still runs first when `lsof` works.
- The stop and status paths are unchanged.
- If SOLR-18339 lands first, the start wait no longer calls this function ([SOLR-18339](https://issues.apache.org/jira/browse/SOLR-18339)). The test would then still pass without this change, so it becomes a regression check.
