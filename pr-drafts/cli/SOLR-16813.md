Title: Fetch a package version's manifest.json into the local file store when the version loads, best effort

https://issues.apache.org/jira/browse/SOLR-16813

## What happens today

**A node can load a package version without its manifest.json, and package commands on that node then fail.**

The loader validates a version's JAR files and fetches any that are missing from other nodes ([SolrPackageLoader.java, base, L264-L274](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/pkg/SolrPackageLoader.java#L264-L274)). The manifest is not in the version's file list, so nothing fetches it. Package commands read each installed version's manifest from the Solr node they contact ([PackageManager.java, base, L205-L210](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/packagemanager/PackageManager.java#L205-L210)), and a file that is missing on that node fails the read ([ClusterFileStore.java, base, L163-L167](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/filestore/ClusterFileStore.java#L163-L167)). Registration checks the JAR files but not the manifest ([PackageAPI.java, base, L276-L283](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/pkg/PackageAPI.java#L276-L283)), so a registered version can lack its manifest on some nodes. The ticket reports this on a node that joins the cluster ([SOLR-16813](https://issues.apache.org/jira/browse/SOLR-16813)).

## What this change does

**When a version loads, its manifest.json is fetched into the local file store, and a failed fetch only logs a warning.**

The fetch runs after the JAR files are validated ([SolrPackageLoader.java, L276](https://github.com/nick-boss-tech/solr/blob/1b288170e8aa9c3b1ea9bce418e26bd61f08498e/solr/core/src/java/org/apache/solr/pkg/SolrPackageLoader.java#L276)). It uses the same lazy fetch as the JAR files, `getType(path, true)`, which pulls a missing file from other nodes ([FileStoreUtils.java, base, L54](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/filestore/FileStoreUtils.java#L54)). If the manifest is still not a file afterward, or the fetch throws, a warning is logged and the version loads ([fetchManifest, L294-L315](https://github.com/nick-boss-tech/solr/blob/1b288170e8aa9c3b1ea9bce418e26bd61f08498e/solr/core/src/java/org/apache/solr/pkg/SolrPackageLoader.java#L294-L315)). A version without a manifest path skips the fetch.

The manifest is posted without a signature, as RepositoryManager posts it ([RepositoryManager.java, L192-L196](https://github.com/nick-boss-tech/solr/blob/1b288170e8aa9c3b1ea9bce418e26bd61f08498e/solr/core/src/java/org/apache/solr/packagemanager/RepositoryManager.java#L192-L196)). Package commands check its SHA-512 against the value registered with the version when they read it ([PackageUtils.java, L184-L199](https://github.com/nick-boss-tech/solr/blob/1b288170e8aa9c3b1ea9bce418e26bd61f08498e/solr/core/src/java/org/apache/solr/packagemanager/PackageUtils.java#L184-L199)).

Behavior change: a version load now makes one more file store lookup, and a fetch from another node can run during the load, as the JAR fetch already does.

## A choice to check

**The manifest is best effort: a version loads without it, with a warning.**

The ticket asks whether the manifest should be mandatory ([SOLR-16813](https://issues.apache.org/jira/browse/SOLR-16813)). The two options:

- Best effort, as implemented. The version loads with a warning. Package commands on a node that still lacks the manifest keep failing until the manifest arrives.
- Mandatory. The version fails to load when the manifest cannot be fetched. The cost: a node that cannot reach a peer holding the manifest cannot load a version whose JAR files it already has.

Was best effort the right call?

## Proof

**On the base code, the new manifest test fails. With this change, it passes.**

`TestPackages` 6 of 6 at head 1b288170e8aa9c3b1ea9bce418e26bd61f08498e, verified 2026-10-07. Against the base code, the class still runs six tests, and one fails: [`testManifestIsFetchedWhenVersionLoadsOnNodeMissingIt`](https://github.com/nick-boss-tech/solr/blob/1b288170e8aa9c3b1ea9bce418e26bd61f08498e/solr/core/src/test/org/apache/solr/pkg/TestPackages.java#L235-L302), with `expected FILE but was NOFILE` for the manifest on the restarted node.

That test posts the manifest without a signature, as RepositoryManager does. It stops one node, deletes that node's copy of the manifest, restarts the node, and loads the version. The manifest must be a file on that node afterward.

The second new test, [`testPackageLoadsWhenManifestIsNotInFileStore`](https://github.com/nick-boss-tech/solr/blob/1b288170e8aa9c3b1ea9bce418e26bd61f08498e/solr/core/src/test/org/apache/solr/pkg/TestPackages.java#L193-L232), covers the best effort path: a version with no manifest in the file store still loads. It passes on the base code and with this change.

## Limits

- The fetch runs only when a node loads the version. A node that never loads the version does not fetch its manifest.
- No test asserts the warning. The best effort test checks only that the version still loads.
