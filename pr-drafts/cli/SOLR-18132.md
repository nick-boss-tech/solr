## What happens today

**Tools that take a ZooKeeper connection pick the node URL scheme only from the urlScheme cluster property, so an SSL cluster gets http URLs unless that property is set.**

The ticket reports a 9.10.1 cluster with SSL enabled for Solr and a plaintext external ZooKeeper. Collection creation fails with an unhelpful "IOException", and turning SSL off avoids it. On the base code (main at the merge-base), the tool reads the urlScheme cluster property with an http default and builds node URLs from it ([CLIUtils.java lines 265-266, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/cli/CLIUtils.java#L265-L266)).

## What this change does

**Tools that take a ZooKeeper connection now use solr.ssl.enabled to choose the scheme, and the launcher passes that setting to the server and tool JVMs.**

- The tool gets the scheme from the cluster state provider's getUrlScheme() ([CLIUtils.java line 265](https://github.com/nick-boss-tech/solr/blob/54835cac6f8518d7110865d73ec8a37f18419f1d/solr/core/src/java/org/apache/solr/cli/CLIUtils.java#L265)). For a ZooKeeper connection, that method checks solr.ssl.enabled first, then the urlScheme cluster property, then falls back to http ([ZkClientClusterStateProvider.java lines 277-287](https://github.com/nick-boss-tech/solr/blob/54835cac6f8518d7110865d73ec8a37f18419f1d/solr/solrj-zookeeper/src/java/org/apache/solr/client/solrj/impl/ZkClientClusterStateProvider.java#L277-L287)).
- With solr.ssl.enabled=true and no urlScheme property, the tool builds https URLs.
- Behavior change: a tools host that sets solr.ssl.enabled=false explicitly now builds http URLs, even when the urlScheme cluster property is https. Before this change, the tool built https URLs in that case. This is the intended behavior.
- The launcher adds -Dsolr.ssl.enabled=true to the server options when SSL is on ([bin/solr lines 212-216](https://github.com/nick-boss-tech/solr/blob/54835cac6f8518d7110865d73ec8a37f18419f1d/solr/bin/solr#L212-L216)). It also turns SSL on when only SOLR_SSL_KEY_STORE is set, but it does that after the environment export loop ([lines 116-120](https://github.com/nick-boss-tech/solr/blob/54835cac6f8518d7110865d73ec8a37f18419f1d/solr/bin/solr#L116-L120) and [lines 205-209](https://github.com/nick-boss-tech/solr/blob/54835cac6f8518d7110865d73ec8a37f18419f1d/solr/bin/solr#L205-L209)). For that key-store-only case, the server JVM would not see the flag without this option. The same options reach tool JVMs through run_tool ([line 504](https://github.com/nick-boss-tech/solr/blob/54835cac6f8518d7110865d73ec8a37f18419f1d/solr/bin/solr#L504)).

## Limits

**This change does not add the early failure the ticket asks for, and it targets main only.**

- The ticket also asks for a clear, early failure when SSL is all-or-nothing. This change does not add one.
- The ticket was filed against 9.10.1. This change depends on the solr.ssl.enabled detection that [SOLR-18056](https://issues.apache.org/jira/browse/SOLR-18056) added to main, and SOLR-18056 is not in 9.10.1. So this branch targets main only. A 9.10.1 port would need its own change, and I can open a follow-up ticket and pull request for it on request.
