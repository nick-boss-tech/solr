## What happens today

**The start wait polls lsof for a listening port, and without lsof it reports a successful start without checking Solr.**

With lsof installed, bin/solr polls for a listening socket on the port ([lines 1381-1404, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/bin/solr#L1381-L1404)). A listening socket does not show that Solr answers requests. On timeout, the loop prints a message and exits its subshell without an error code ([lines 1394-1396, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/bin/solr#L1394-L1396)). Without lsof, the script prints a note, sleeps 10 seconds, and prints the started message ([lines 1406-1410, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/bin/solr#L1406-L1410)). The Unix installer also recommends installing lsof ([install_solr_service.sh line 199, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/bin/install_solr_service.sh#L199)).

## What this change does

**The start wait now calls StatusTool, and a start fails when Solr does not answer within SOLR_START_WAIT seconds.**

- The wait runs solr status with --max-wait-secs set to SOLR_START_WAIT, against the node's http or https URL on the bind host and the start port. It succeeds when Solr answers the system information request ([bin/solr lines 1391-1392](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/bin/solr#L1391-L1392); [StatusTool.java lines 267-292](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/core/src/java/org/apache/solr/cli/StatusTool.java#L267-L292)).
- The host is SOLR_HOST_BIND, defaulting to 127.0.0.1. A wildcard bind is probed on 127.0.0.1 for 0.0.0.0 and on [::1] for :: or [::]. Other IPv6 addresses are wrapped in brackets ([lines 1380-1389](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/bin/solr#L1380-L1389)).
- If Solr does not answer in time, the start prints a message, tails the last 30 lines of solr.log when that file exists, and exits 1 ([lines 1393-1397](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/bin/solr#L1393-L1397)).
- The start output now comes from StatusTool: "Waiting up to N seconds to see Solr running on port P", then "Started Solr server on port P. Happy searching!". The pid is no longer printed ([StatusTool.java lines 194-197](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/core/src/java/org/apache/solr/cli/StatusTool.java#L194-L197)).
- install_solr_service.sh no longer checks for lsof or prints the recommendation ([line 199, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/bin/install_solr_service.sh#L199)). The production guide drops its Red Hat lsof prerequisite ([line 75, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solr-ref-guide/modules/deployment-guide/pages/taking-solr-to-production.adoc#L75)). The sample output in that guide ([line 198](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/solr-ref-guide/modules/deployment-guide/pages/taking-solr-to-production.adoc#L198)) and in the tutorial ([lines 77 and 84](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/solr-ref-guide/modules/getting-started/pages/tutorial-techproducts.adoc#L77)) shows the new started line.
- solr.cmd already waits through StatusTool with --max-wait-secs and is not changed in this branch ([line 1181](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/bin/solr.cmd#L1181)).

## A choice to check

**The status wait sends no credentials, so a secured node that answers 401 is reported as a failed start. We left this as it is and flagged it for maintainers to confirm.**

- The wait does not pass --credentials ([bin/solr line 1392](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/bin/solr#L1392)). The tool JVM does get the script's authentication options ([run_tool, line 501](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/bin/solr#L501)), so a probe can authenticate when those options carry credentials. One example is SOLR_AUTH_TYPE=basic with solr.security.auth.basicauth.credentials set in SOLR_AUTHENTICATION_OPTS.
- StatusTool rethrows auth-related errors instead of retrying ([StatusTool.java lines 276-278](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/core/src/java/org/apache/solr/cli/StatusTool.java#L276-L278)). A 401 from the probe ends the wait at once, and the start fails ([bin/solr lines 1392-1397](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/bin/solr#L1392-L1397)).
- The other routes are passing credentials to the wait, or retrying on a 401. Passing credentials needs a new way to supply them, and the --credentials option puts the password on the command line. Retrying on a 401 would make a wrong password wait out the whole start timeout before the failure shows. Both routes change StatusTool or the start path, so neither is in this change. solr.cmd also makes its status call without credentials ([line 1181](https://github.com/nick-boss-tech/solr/blob/47e53884609c0c7f84e85069881f9d820342e70e/solr/bin/solr.cmd#L1181)).
- Was flagging this for a follow-up the right call, or should the wait handle a 401 before this change merges?

## Limits

**The HTTPS probe for wildcard binds is not tested, and the certificate-name question is still open.**

- The two new cases use HTTP only. For HTTPS with a wildcard bind, the probe uses the loopback address described above. Whether the certificate names match that address is not tested here, and the question is open.
