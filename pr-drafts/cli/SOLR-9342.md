Title: Solr GC logging not respecting user timezone

## What happens today

**The GC log can show a different time zone than the Solr log.**

The start script sets `-Duser.timezone` from `SOLR_TIMEZONE` for the Solr JVM ([base L1329](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/bin/solr#L1329)). It never sets the process `TZ`, so the JVM writes GC log timestamps in the host's zone. In a test run on a UTC host with `SOLR_TIMEZONE=Asia/Kolkata`, the GC log showed `+0000` while the Solr log showed Kolkata time. The ticket reports the same split with `-Duser.timezone=PST`.

## What this change does

**The server JVM's GC log now uses `SOLR_TIMEZONE`.**

The script sets `TZ` on the server JVM only, in the foreground `exec` ([L1352](https://github.com/nick-boss-tech/solr/blob/833e11192a7ff918f7e401bde920cf63c89df063/solr/bin/solr#L1352)) and the background `nohup` launch ([L1356](https://github.com/nick-boss-tech/solr/blob/833e11192a7ff918f7e401bde920cf63c89df063/solr/bin/solr#L1356)). An operator's own `TZ` wins, because the value is `${TZ:-$SOLR_TIMEZONE}`. The script does not export `TZ` for itself, so tool commands ([run_tool, L498](https://github.com/nick-boss-tech/solr/blob/833e11192a7ff918f7e401bde920cf63c89df063/solr/bin/solr#L498)) and other child processes see only the operator's `TZ`.

`SOLR_TIMEZONE` defaults to UTC ([L1196](https://github.com/nick-boss-tech/solr/blob/833e11192a7ff918f7e401bde920cf63c89df063/solr/bin/solr#L1196)). With no settings, the GC log now uses UTC on any host. Hosts that are not on UTC see different GC timestamps after this change.

## Proof

**The new BATS test fails on the base script and passes with this change.**

- `test_start_solr.bats`, test "SOLR-9342 GC log follows SOLR_TIMEZONE" ([L59-L66](https://github.com/nick-boss-tech/solr/blob/833e11192a7ff918f7e401bde920cf63c89df063/solr/packaging/test/test_start_solr.bats#L59-L66)). On the base script, it fails at the check for a `+0530` timestamp in `solr_gc.log`.
- At head `833e11192a7f` (verified 2026-10-07), the full file ran 10 tests: 9 passed, 1 skipped. The skip is the timeout-utility check, the same skip the file had before this change.
- Evidence shape: a BATS suite, run by hand against the distribution built from this head, as a non-root user. The start script refuses to start Solr as root ([L1001](https://github.com/nick-boss-tech/solr/blob/833e11192a7ff918f7e401bde920cf63c89df063/solr/bin/solr#L1001)). This is a BATS run, not a Gradle test run.

## A choice to check

**The GC log follows `SOLR_TIMEZONE`, which defaults to UTC. The other route keeps each host on its own zone until a zone is set.**

- Implemented: UTC by default, so the Solr log and GC log agree on every host that sets nothing.
- Other route: set `TZ` only when an operator sets `SOLR_TIMEZONE` or `TZ`. Hosts that set neither keep their current GC log zone. The cost is that the two logs still differ on those hosts, which is the split the ticket reports.

Was changing the default GC log zone to UTC the right call?

## Limits

**Two settings can still split the logs, and the new test covers only one case.**

- An operator `TZ` that differs from `SOLR_TIMEZONE` makes the GC log follow `TZ`, while the Solr log follows `SOLR_TIMEZONE`.
- A `-Duser.timezone` in `SOLR_OPTS`, as in the ticket's example, changes the Solr log only ([L1334](https://github.com/nick-boss-tech/solr/blob/833e11192a7ff918f7e401bde920cf63c89df063/solr/bin/solr#L1334)). The GC log follows `TZ`, so set `SOLR_TIMEZONE` instead. Making one value drive both logs is not part of this change. A follow-up can cover it on request.
- The new test covers only `SOLR_TIMEZONE` with `TZ` unset. The `TZ` precedence and the child-process behavior are read from the code, not tested.
- Only the unified-logging GC log was checked. The OpenJ9 path writes its GC log with `-Xverbosegclog` ([L1088](https://github.com/nick-boss-tech/solr/blob/833e11192a7ff918f7e401bde920cf63c89df063/solr/bin/solr#L1088)), and its timestamps were not checked.
- `solr.cmd` is not changed. The Windows JVM does not read `TZ` for GC log timestamps, so this change adds no line there.
- In one earlier combined run of the file, an existing test about deprecated system properties failed. The cause appears to be a race in when the log is flushed, not this change. The counts above come from a run without that failure.
