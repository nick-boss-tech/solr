## What happens today

**A schema cached for a configset can still be used after the configset is deleted and uploaded again.**

With schema sharing on (`shareSchema` set to `true` in solr.xml, which is off by default), a core looks up its schema in a cache. The cache key includes a modification version for the schema file. In SolrCloud, that version is the ZooKeeper data version of the schema znode. A new znode starts that version over at 0. So a configset that is deleted and uploaded again can match an old cache entry, for example after a backup restore that reuses the configset name. The old schema stays in use. Fields added in the restored configset are missing from the schema API until the server restarts. SOLR-15478 reports this.

The cache key is built in [ConfigSetService.java](https://github.com/nick-boss-tech/solr/blob/0478bdf0ac5cd100d5020451a6732ca5cbaa1a52/solr/core/src/java/org/apache/solr/core/ConfigSetService.java#L304-L318). The base code returned the data version in [ZkConfigSetService.java](https://github.com/apache/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/cloud/ZkConfigSetService.java#L117).

## What this change does

**The schema cache key now uses the ZooKeeper modification ID (mzxid) of the schema znode, not its data version.**

[ZkConfigSetService.java](https://github.com/nick-boss-tech/solr/blob/0478bdf0ac5cd100d5020451a6732ca5cbaa1a52/solr/core/src/java/org/apache/solr/cloud/ZkConfigSetService.java#L101-L118) returns `stat.getMzxid()`. ZooKeeper does not reuse this ID, so a recreated configset gets a new cache key. Two effects to know:

- Uploading the same content again after a delete now loads the schema once more, because the key changed.
- The standalone configset service (`FileSystemConfigSetService`) is not changed. It still uses the file's last-modified time.

## Proof

**The new test fails on the base code and passes with this change.**

`ZkConfigSetServiceModificationVersionTest`: 1 of 1 passes at head `0478bdf0ac5`, verified 2026-10-03. The test uploads a configset, deletes it, uploads it again, and checks that the schema's version changes. It also checks that an unchanged file keeps its version and that a changed file gets a new one. On the base code (fork point `b5c71bc5573`), the new test fails. With this change, it passes.

## Limits

**Covered: SolrCloud configsets with schema sharing on.**

- The test checks the version value that the cache key uses. It does not load a schema through the cache and does not run a backup restore.
- The backup and restore steps from the ticket are not part of the test.
- The standalone configset service is not changed.
