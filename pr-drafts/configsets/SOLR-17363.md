## What happens today

**A config API update can fail when a replica is deleted while the request waits for all replicas.**

A `/config` update such as `set-user-property` waits up to 30 seconds for each active replica to report the new overlay version. The replicas to wait for are chosen when the request starts ([SolrConfigHandler.java](https://github.com/nick-boss-tech/solr/blob/b8e8e1c48461be964ac0ef9a0cc570c277e7420d/solr/core/src/java/org/apache/solr/handler/SolrConfigHandler.java#L865-L867)). If one of them is deleted during the wait, it can never report the version. The request still fails with HTTP 500 and this message: "N out of M the property overlay to be of version V within 30 seconds! Failed cores: [...]". SOLR-17363 shows this error from a cluster running 9.4.

The base code fails the request for any core that did not report the version ([SolrConfigHandler.java, base commit](https://github.com/apache/solr/blob/56ec140e3636d5f4150fa87fbf7103529536ac99/solr/core/src/java/org/apache/solr/handler/SolrConfigHandler.java#L912-L922)).

## What this change does

**A replica that misses the version check no longer fails the request if it is not an active replica when the wait ends.**

After the wait, the handler reads the cluster state again ([SolrConfigHandler.java](https://github.com/nick-boss-tech/solr/blob/b8e8e1c48461be964ac0ef9a0cc570c277e7420d/solr/core/src/java/org/apache/solr/handler/SolrConfigHandler.java#L909-L937)). A failed core still fails the request only if its replica is an active replica on a live node ([helper](https://github.com/nick-boss-tech/solr/blob/b8e8e1c48461be964ac0ef9a0cc570c277e7420d/solr/core/src/java/org/apache/solr/handler/SolrConfigHandler.java#L964-L977)). So these cases no longer fail the request:

- a replica removed from the collection during the wait;
- a replica that goes down or starts recovering during the wait;
- a replica whose node is no longer live.

A replica that is already down when the request starts is not waited for, as before.

Behavior change: a replica that goes down or starts recovering during the wait no longer fails the request. Its version is not checked.

## Proof

**Two new tests fail on the base code and pass with this change. Two guard tests pass on both.**

[TestConfigWaitForReplicas](https://github.com/nick-boss-tech/solr/blob/b8e8e1c48461be964ac0ef9a0cc570c277e7420d/solr/core/src/test/org/apache/solr/handler/TestConfigWaitForReplicas.java): 4 of 4 pass at head `b8e8e1c4846`, verified 2026-10-05.

- New: `testReplicaRemovedDuringWaitDoesNotFailRequest` and `testReplicaDownDuringWaitDoesNotFailRequest`. On the base code (fork point `56ec140e363`), both fail with the overlay version error.
- Guards: `testActiveReplicaThatNeverReportsStillFails` and `testConfigUpdateSucceedsWhenAllReplicasReport`. They pass on the base code and with this change.

Existing config API tests at the same head: TestSolrConfigHandler 8 of 8, TestReqParamsAPI 1 of 1, TestSetPropertyConfigApis 4 of 4.

## A choice to check

**The request also succeeds when a replica goes down or starts recovering during the wait.**

Options:

- Implemented: any replica that leaves the active set during the wait is excused. That covers removed replicas, replicas that go down or recover, and replicas on a node that is no longer live.
- Narrower: excuse only a replica removed from the collection. A replica that goes down or recovers during the wait would still fail the request.

Cost of the implemented route: the request can return success while that replica has not reported the new version. Was it right to excuse a replica that goes down or recovers during the wait, not only one that was removed?

## Limits

**Not covered: an active replica that does not report the new version in time still fails the request.**

This is the second cause in the ticket. The ticket says a node reloads only one replica at a time, so the wait can run out while every replica is still active. [testActiveReplicaThatNeverReportsStillFails](https://github.com/nick-boss-tech/solr/blob/b8e8e1c48461be964ac0ef9a0cc570c277e7420d/solr/core/src/test/org/apache/solr/handler/TestConfigWaitForReplicas.java#L99-L124) pins that this still fails. If maintainers want it covered, I can open a follow-up ticket and PR on request.

- The two new tests set the replica state in ZooKeeper directly. The collections API unloads the core too early for the test to observe the wait.
- Only the test classes named in Proof were run.
