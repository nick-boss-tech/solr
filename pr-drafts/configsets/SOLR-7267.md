## What happens today

**The _default configset names Czech only with "cz", which is a country code. The ISO language code is "cs".**

The _default configset has a Czech field type, `text_cz`, a dynamic field `*_txt_cz`, and the stopword file `lang/stopwords_cz.txt` ([managed-schema.xml L620-L628](https://github.com/nick-boss-tech/solr/blob/59f34a339b0d3cc227c79e56bc2e59814fed2daf/solr/server/solr/configsets/_default/conf/managed-schema.xml#L620-L628)). A schema author who looks for Czech by its language code finds no `text_cs`, no `*_txt_cs`, and no `stopwords_cs.txt`.

## What this change does

**The _default configset adds the "cs" names next to the "cz" names. The "cz" names stay.**

The change adds a `*_txt_cs` dynamic field, a `text_cs` field type, and `lang/stopwords_cs.txt` ([managed-schema.xml L630-L639](https://github.com/nick-boss-tech/solr/blob/59f34a339b0d3cc227c79e56bc2e59814fed2daf/solr/server/solr/configsets/_default/conf/managed-schema.xml#L630-L639)). The `text_cs` analyzer matches `text_cz`. The stopword file is an exact copy of the cz list.

Behavior change: a new collection built from _default now treats a field whose name ends in `_txt_cs` as Czech text. In that configset the name had no rule before. Existing collections keep their own schema.

## Proof

**The new test fails without the change and passes with it.**

`DefaultConfigSetCzechTest.testCzechLanguageCodeAlias` ([DefaultConfigSetCzechTest.java L33-L57](https://github.com/nick-boss-tech/solr/blob/59f34a339b0d3cc227c79e56bc2e59814fed2daf/solr/core/src/test/org/apache/solr/schema/DefaultConfigSetCzechTest.java#L33-L57)) reads the _default schema and the two stopword files. On the base configset it fails with "expected text_cs but was empty". With the change, DefaultConfigSetCzechTest passes 1 of 1. Recorded 2026-10-07 at c3d8cb47d27.

## A choice to check

**The change adds the cs names next to the cz names. The alternative renames cz to cs.**

Renaming would give the default configset one name for Czech, and that name would match the ISO code. The cost: new collections built from the default would lose the cz names. Code that indexes into `*_txt_cz` fields would stop getting a Czech analyzer. The additive route costs a second field type and a second copy of the stopword list, 172 lines. Was adding the cs names next to cz the right call, or should the cz names be renamed?

## Limits

**The Czech stopword list is a copy of the cz list. This change does not review its content.**

The test checks that the two files match. It does not check the list against another Czech source. The ticket's one comment asks that the naming question be settled with [LUCENE-6366](https://issues.apache.org/jira/browse/LUCENE-6366) before the sample configs change. This change does not settle LUCENE-6366. Existing configsets do not change.
