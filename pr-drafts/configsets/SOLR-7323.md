## What happens today

**An unknown configSet error gives one path and does not explain it.**

When a core names a configset that is not in the configset base directory, the file-system configset service throws "Could not load configuration from directory" followed by the full path ([FileSystemConfigSetService.java L340-L343, base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/core/FileSystemConfigSetService.java#L340-L343)). It does not say that a configset was requested, what the base directory is, or which setting controls it.

## What this change does

**The message now names the configset, the base directory, and the setting that controls the base directory.**

The new text keeps the old sentence. It adds the configset name, the base directory, and a note that the default is `SOLR_HOME/configsets`, which `configSetBaseDir` in `solr.xml` can change ([FileSystemConfigSetService.java L340-L349, head](https://github.com/nick-boss-tech/solr/blob/b832dc0048c02294dcaae3bf0ca59c250cb2d17e/solr/core/src/java/org/apache/solr/core/FileSystemConfigSetService.java#L340-L349)). The setting name is the one the node configuration reads ([SolrXmlConfig.java L361, base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/core/SolrXmlConfig.java#L361)). The default is set in [NodeConfig.java L662, base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/core/NodeConfig.java#L662).

Behavior change: only the text of this one error changes. The status code and the lookup stay the same. The change touches only the file-system configset service, so other configset services keep their wording.

## A choice to check

**The message repeats the server path. The alternative names only the setting.**

The old text already printed the full configset path, and that path includes the base directory. The new text prints the base directory again, so one error shows the same path twice. The other route leaves the path out and names the configset and `configSetBaseDir`. Its cost is that an operator has to look up where the base directory is. Was repeating the path the right call, or should the message leave it out?

## Limits

**Only the message changes. Other configset services and the status code are unchanged.**

The change does not add a new setting, a new lookup, or a new status code. The test covers the message for one missing configset name.
