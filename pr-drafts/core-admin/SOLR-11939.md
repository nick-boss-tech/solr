## What happens today

**On CREATE, `property.name` is accepted, but it does not set the core names, and the guide does not say so.**

The ticket passes `property.name=carmen_test` to CREATE with four shards. The cores do not take that name. With the current code each core name has the form `<collection>_<shard>_replica_<type><number>`, for example `carmen-test_shard1_replica_n1`. Solr builds the names from the collection, shard and replica. The [reference guide entry for `property._name_=_value_`](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solr-ref-guide/modules/deployment-guide/pages/collection-management.adoc#L246-L262) describes core properties in general terms and does not mention this.

## What this change does

**The CREATE section gets a note that core names are generated, and that `property.name` does not rename the cores of a new collection.**

The note sits under the `property._name_=_value_` entry, after its warning block, in [collection-management.adoc](https://github.com/nick-boss-tech/solr/blob/cdb9903506e9c20c32aa4ec2be77f500235399ba/solr/solr-ref-guide/modules/deployment-guide/pages/collection-management.adoc#L264-L265). It gives an example generated name and says that one name cannot be valid for every shard and replica. This is a documentation change only.

## Limits

**The note covers CREATE only. ADDREPLICA reads `property.name` as the new core name, and this change does not document that.**

ADDREPLICA copies `property.*` parameters into its message ([CreateReplica.java](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/admin/api/CreateReplica.java#L128) and [L157-L158](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/admin/api/CreateReplica.java#L157-L158)).
