## What happens today

**On CREATE, `property.name` is accepted, but it does not set the core names, and the guide does not say so.**

The ticket passes `property.name=carmen_test` to CREATE with four shards. The cores do not take that name. With the current code each core name has the form `<collection>_<shard>_replica_<type><number>`, for example `carmen-test_shard1_replica_n1`. One name cannot fit all four shards, so Solr builds the names from the collection, shard and replica. The reference guide entry for `property._name_=_value_` describes core properties in general terms and does not mention this.

## What this change does

**The CREATE section gets a note that core names are generated, and that `property.name` does not change them.**

The note sits under the `property._name_=_value_` entry, after its warning block, in [collection-management.adoc](https://github.com/nick-boss-tech/solr/blob/d4cff5e76430e6deb88115d6675db537b630948e/solr/solr-ref-guide/modules/deployment-guide/pages/collection-management.adoc#L264-L265). It gives the generated name format and says that one name cannot be valid for every shard and replica. This is a documentation change only.

## Limits

**The note covers CREATE only. ADDREPLICA reads `property.name` as the new core name, and this change does not document that.**

ADDREPLICA copies `property.*` parameters into its message ([CreateReplica.java](https://github.com/nick-boss-tech/solr/blob/d4cff5e76430e6deb88115d6675db537b630948e/solr/core/src/java/org/apache/solr/handler/admin/api/CreateReplica.java#L128) and [L157-L158](https://github.com/nick-boss-tech/solr/blob/d4cff5e76430e6deb88115d6675db537b630948e/solr/core/src/java/org/apache/solr/handler/admin/api/CreateReplica.java#L157-L158)). It uses `property.name` as the core name when `name` is blank ([AddReplicaCmd.java](https://github.com/nick-boss-tech/solr/blob/d4cff5e76430e6deb88115d6675db537b630948e/solr/core/src/java/org/apache/solr/cloud/api/collections/AddReplicaCmd.java#L355-L357)).
