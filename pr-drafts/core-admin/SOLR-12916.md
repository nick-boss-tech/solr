## What happens today

**A warming query written as a flat list of names and values is logged and skipped.**

The Config API accepts `"queries": [ ["q", "*:*", "rows", 1] ]` and deserializes it as lists of lists. The listener reads warming queries only as `NamedList` entries. On the base commit (`cabedd1d9680`), each value in such a list is logged as an unsupported warming config and skipped ([lines 107 to 121](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/core/QuerySenderListener.java#L107-L121)). No warming query runs.

## What this change does

**A list of alternating names and plain values now becomes one warming query.**

The check runs on a flat list directly under `queries` ([lines 108 to 110](https://github.com/nick-boss-tech/solr/blob/50b1f4bcab039f8d25a729a8d02a1e8a16defd3e/solr/core/src/java/org/apache/solr/core/QuerySenderListener.java#L107-L126)), and on a flat list one level down (lines 118 and 119). The helpers are at [lines 141 to 158](https://github.com/nick-boss-tech/solr/blob/50b1f4bcab039f8d25a729a8d02a1e8a16defd3e/solr/core/src/java/org/apache/solr/core/QuerySenderListener.java#L141-L158).

The same rule applies to XML. An XML `<arr name="queries">` of plain `<str>` values with an even count now becomes one warming query. Before, each value was skipped. An odd count is still skipped. This reaches past the ticket, which covers the Config API only.

## Proof

**One new test fails on the base code and passes with this change.**

[`QuerySenderListenerTest.testFlatNameValueQueryFromConfigApi`](https://github.com/nick-boss-tech/solr/blob/50b1f4bcab039f8d25a729a8d02a1e8a16defd3e/solr/core/src/test/org/apache/solr/core/QuerySenderListenerTest.java#L50-L67) fails on the base code with `expected:<2> but was:<0>`. On the base code the class shows 1 failure in 2 tests. With this change it passes 2 of 2, with 0 failures and 0 errors. Verified 2026-10-10 at head `50b1f4bcab03`.

## A choice to check

**The change also accepts flat lists from XML. The narrower route stops at the Config API.**

Option 1, as implemented: accept flat lists from both the Config API and XML. Option 2: accept them from the Config API only. Option 1 changes behavior for an XML config with an even run of plain strings in `queries`. Those now run a query, where they were skipped. Was it right to accept XML lists too, or should the change stop at the Config API?

## Limits

**Only the conversion method is tested. No Config API round trip was run.**

- The test calls the static `convertQueriesToList` method. A Config API request that adds a listener and then checks its warming queries is not exercised.
- No test uses an XML-shaped list by name. The XML form goes through the same branch as the Config API case.
