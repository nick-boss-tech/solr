## What happens today

**Luke keys each char filter by its class name, so two char filters of the same class in one analyzer share a key.**

In [`getAnalyzerInfo` on main](https://github.com/apache/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/handler/admin/LukeRequestHandler.java#L1008-L1017), the char filters go into a map keyed by simple class name. When the response is read as JSON, two values under one key cannot both survive, so a repeated char filter class cannot be shown in full.

[OWED BEFORE POSTING: check that the Jira ticket describes duplicate char filter keys in the Luke output. The ticket text is not on hand, so this section rests on the code. If the ticket describes only the Admin UI symptom, the summary line changes.]

## What this change does

**Luke now returns `charFilters` as an ordered list. Each entry has `className` and `args`.**

The list keeps every char filter in analyzer order ([lines 1008-1019](https://github.com/nick-boss-tech/solr/blob/f95b5010b3fe61078e8730986e1e4b309ead4bbc/solr/core/src/java/org/apache/solr/handler/admin/LukeRequestHandler.java#L1008-L1019)). Token filters keep their current shape; see Limits. The new test uses a field type with two `PatternReplaceCharFilterFactory` char filters ([fixture](https://github.com/nick-boss-tech/solr/blob/f95b5010b3fe61078e8730986e1e4b309ead4bbc/solr/core/src/test-files/solr/collection1/conf/schema-dup-charfilters-analyzer.xml)).

Clients that read `charFilters` by name get an array instead of an object. That is a response change.

## Proof

**`LukeRequestHandlerTest` passes 9 of 9 at head `f95b5010b3fe`. On the base code the suite fails, because `charFilters` comes back as an object, not the array the new test expects.**

`LukeRequestHandlerTest`: 9 of 9 at `f95b5010b3fe`, recorded 2026-10-03. The new `testDuplicateCharFilters` ([lines 256-284](https://github.com/nick-boss-tech/solr/blob/f95b5010b3fe61078e8730986e1e4b309ead4bbc/solr/core/src/test/org/apache/solr/handler/admin/LukeRequestHandlerTest.java#L256-L284)) checks for an array of two entries with the expected class names and patterns, and checks their order in the JSON output.

## A choice to check

**The two options are unique object keys or an ordered list, and this change uses the list.**

Options considered: keep the object and make each key unique, for example by adding an index to a repeated class name; or return an ordered list, which this change does. The list keeps every entry and its order, and no key has to be invented. Its cost is a shape change for any client that reads `charFilters` by name. The SolrJ Luke response class does not read `charFilters`, and the Admin UI reads the entries with a `for...in` loop that also works on arrays. Was the list the right call, or should the object keep its keys?

## Limits

**Token filters keep the class name as their key, and the Admin UI was read but not run.**

- Token filters (`filters`) still use the class name as the key ([lines 1030-1038](https://github.com/nick-boss-tech/solr/blob/f95b5010b3fe61078e8730986e1e4b309ead4bbc/solr/core/src/java/org/apache/solr/handler/admin/LukeRequestHandler.java#L1030-L1038)), so two token filters of one class still share a key. Should token filters get the same list shape? That is a second response change, so it is left out of this PR. A follow-up ticket and PR can follow if maintainers want it.
- The Admin UI was not run in a browser. The check was a read of its loop in [`schema.js`](https://github.com/nick-boss-tech/solr/blob/f95b5010b3fe61078e8730986e1e4b309ead4bbc/solr/webapp/web/js/angular/controllers/schema.js#L648-L670).
- The schema API output is unchanged.
