## What happens today

**When startup throws an exception that is not an `Error`, the servlet context still starts, and the node keeps running with no CoreContainer.**

[`CoreContainerProvider`](https://github.com/apache/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/servlet/CoreContainerProvider.java#L186-L193) catches every `Throwable` during startup and logs "Could not start Solr". It rethrows only an `Error`, so any other exception is swallowed. The container stays null. Every later request fails in [`checkReady`](https://github.com/apache/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/servlet/CoreContainerProvider.java#L100-L110) with `UnavailableException`, and the process keeps running until something stops it. The ticket names `SolrDispatchFilter.init()`. That class is no longer in main, and the startup code is in `CoreContainerProvider`.

## What this change does

**Startup failures that are not `Error`s now fail the servlet context.**

[`init`](https://github.com/nick-boss-tech/solr/blob/3432f950f0aed8e2b461e9d7255d590ed7df9b20/solr/core/src/java/org/apache/solr/servlet/CoreContainerProvider.java#L186-L194) rethrows a `RuntimeException` as it is. It wraps any other `Throwable` in a `SolrException` with `SERVER_ERROR`. Because `init` throws, `contextInitialized` does not set the provider attribute, and `getCoreContainer` keeps reporting that the container is unavailable.

## Proof

**The new test passes with this change. By code reading, it fails on the base code.**

[`CoreContainerProviderTest`](https://github.com/nick-boss-tech/solr/blob/3432f950f0aed8e2b461e9d7255d590ed7df9b20/solr/core/src/test/org/apache/solr/servlet/CoreContainerProviderTest.java#L44-L62) 1 of 1 passes at head `3432f950f0ae`, recorded 2026-10-03. The test writes a malformed `solr.xml`, expects context initialization to throw, checks that the provider attribute is never set, and checks that `getCoreContainer` reports unavailable. The base failure is read from the code, so its failure text is not quoted here. On the base code the startup exception is logged and not rethrown, so the expected exception never appears and the first assertion fails.

## A choice to check

**Option one fails the servlet context at startup, as this change does. Option two keeps the context up and answers every request with a 503 that names the startup failure.**

Option one makes the failure visible at startup. Option two keeps the current shape and makes the failure explicit in every response. Was failing the context the right call?

## Limits

**The test uses a mocked servlet context, so it does not show what the server does after the context fails.**

- The test does not start a server.
- The test accepts any `RuntimeException`, so it does not check the cause of the failure.
- No other startup path is changed.
