## What happens today

**REPLACENODE documents `parallel` and `timeout`, but the request never passes them on.**

The [reference guide](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/solr-ref-guide/modules/deployment-guide/pages/cluster-node-management.adoc#L838-L874) lists both parameters. The operation reads both, with defaults of `false` and 600 seconds ([lines 55 to 56](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/core/src/java/org/apache/solr/cloud/api/collections/ReplaceNodeCmd.java#L55-L56)). But on the base commit (`e2cdb2d7e8`), the request builder copies only the target node and `waitForFinalState` ([lines 72 to 75](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/handler/admin/api/ReplaceNode.java#L72-L75)). The v1 handler builds its request the same way ([lines 992 to 996](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/handler/admin/CollectionsHandler.java#L992-L996)). So a caller's values are dropped, and the defaults always apply.

## What this change does

**`parallel` and `timeout` now reach the operation in both the v1 and v2 APIs.**

The v2 request model gains the two fields ([lines 57 to 68](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/api/src/java/org/apache/solr/client/api/model/ReplaceNodeRequestBody.java#L57-L68)). `ReplaceNode` copies them into the operation message ([lines 79 to 80](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/core/src/java/org/apache/solr/handler/admin/api/ReplaceNode.java#L79-L80)). The v1 handler reads them from the request parameters and passes them the same way ([lines 997 to 998](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/core/src/java/org/apache/solr/handler/admin/CollectionsHandler.java#L997-L998)).

Two behavior changes follow. With `parallel=true`, each replica add runs in the background unless `waitForFinalState` is set ([lines 193 to 220](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/core/src/java/org/apache/solr/cloud/api/collections/AddReplicaCmd.java#L193-L220)). With `timeout`, the batch waits use the value. The batch allows up to `timeout` seconds for all new replicas to be added ([line 182](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/core/src/java/org/apache/solr/cloud/api/collections/ReplicaMigrationUtils.java#L182-L182)), then up to `timeout` seconds for leader replicas to recover ([line 191](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/core/src/java/org/apache/solr/cloud/api/collections/ReplicaMigrationUtils.java#L191-L191)).

[`ReplaceNodeAPITest.testParallelAndTimeoutAreForwardedToTheOverseerMessage`](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/core/src/test/org/apache/solr/handler/admin/api/ReplaceNodeAPITest.java#L57-L75) fails on the base code. The core module check also passed.

## A choice to check

**Both parameters now pass through. The other route removes them from the guide and the operation.**

Option 1, as implemented: pass both through. Option 2: remove both from the guide, and stop reading them in `ReplaceNodeCmd`. Option 1 changes results for any caller who already sends these parameters and gets the defaults. A timeout set low can now expire where the default would not. A 2022 comment on the ticket calls the omission a mistake and proposes passing both to the Overseer. Was passing them through the right call?

## Limits

**The timeout does not reach the add step. The guide and the v2 description still carry errors.**

- With `waitForFinalState=true`, each replica add still waits up to 600 seconds. The add step does not receive `timeout` ([line 129](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/core/src/java/org/apache/solr/cloud/api/collections/AddReplicaCmd.java#L129-L129), [line 208](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/core/src/java/org/apache/solr/cloud/api/collections/AddReplicaCmd.java#L208-L208)).
- The branch test calls the v2 class. The v1 change in `CollectionsHandler` has no test.
- The [reference guide](https://github.com/nick-boss-tech/solr/blob/51b7addddd45dfbb8e18e4f80982a3793206bdcd/solr/solr-ref-guide/modules/deployment-guide/pages/cluster-node-management.adoc#L867-L874) still gives 300 seconds as the default timeout. The code default is 600 seconds. This branch does not change the guide.
- The v2 description of `timeout` says "per replica move." The batch wait covers all replicas together. This branch does not correct the description.
- The generated OpenAPI and SolrJ output for the request model was not checked.
