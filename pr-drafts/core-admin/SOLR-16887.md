## What this change does

**Solr exits on an OutOfMemoryError instead of crashing the JVM, and the start scripts keep writing JVM crash files to the logs directory.**

- `bin/solr` and `bin/solr.cmd` replace `-XX:+CrashOnOutOfMemoryError` with `-XX:+ExitOnOutOfMemoryError`, as the ticket asks.
- The start scripts also keep `-XX:ErrorFile` pointing at the logs directory, so JVM crash files for other fatal errors stay where they are today. See the choice below.
- The BATS test that checks the flag is renamed from "solr exits on OutOfMemoryError instead of crashing" to "solr starts with ExitOnOutOfMemoryError". The test starts Solr and checks the system info. It does not run out of memory.
- The reference guide example is updated to match.

## Proof

**The head passes the BATS test, and the base fails it on the flag assertion.**

- Head: the test passes with `-XX:+ExitOnOutOfMemoryError` and `-XX:ErrorFile` in the system info.
- Base (merge base 9b3a84b1c460, with the head's test file): the test fails at the flag assertion, because the base system info has `-XX:+CrashOnOutOfMemoryError`.
- The changelog, tidy, Error Prone compile and module check pass at the head.

## Choice for maintainers

**Should the start scripts keep writing JVM crash files to the logs directory?**

- This PR: yes. The start scripts keep `-XX:ErrorFile` pointing at the logs directory, so crash files for other fatal errors stay where they are now.
- Alternative: no. The ticket patch removes only the crash flag. Crash files then go to the JVM's default location, which is not mentioned in the changelog or the reference guide.

**Our recommendation:** keep the ErrorFile flag. The change is one line in each script, and it avoids a silent move of crash files for users who collect them.

## Limits

**Auto-restart in Docker, the symptom in the ticket, has not been tested.**

- The ticket reports that the crash behavior breaks auto-restart in a Docker container. Nobody in the ticket has confirmed the restart behavior with the flag change. The proof above checks the flag and the system info only.
- The test host has no container runtime, and no rights to install one, so no container restart was run.
- A restart loop was run on the JVM alone with a small out-of-memory program. `ExitOnOutOfMemoryError` exits with status 3 and `CrashOnOutOfMemoryError` aborts with status 134. A restart policy that restarts on any non-zero exit restarts both. The exit codes alone therefore do not explain the reported restart failure, and its cause is still open.
- Heap dumps are unchanged. `SOLR_HEAP_DUMP=true` still adds the heap dump option in `bin/solr`, and the ticket discussion reports a heap dump with the patched build.
