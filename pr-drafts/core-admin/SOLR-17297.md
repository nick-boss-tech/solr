## What happens today

**A Lucene SPI in the shared lib directory can fail with ClassNotFoundException when modules are enabled.**

Before this change, `NodeConfig` loaded the shared lib directory first and the modules second. Adding the module jars replaces the class loader and closes the old one ([replace and close](https://github.com/nick-boss-tech/solr/blob/c0ab38fc0a8b57953f8b8df03f54085fb37e138d/solr/core/src/java/org/apache/solr/core/SolrResourceLoader.java#L263-L281)). A PostingsFormat from a shared lib jar was registered through the old loader, so its later class lookups fail once a core uses it. The Jira ticket reproduces this with a module enabled in solr.xml.

## What this change does

**`NodeConfig` adds the modules before the shared lib, so a shared lib SPI is registered with the loader that stays open.**

- The constructor calls `initModules()` before `setupSharedLib()` ([NodeConfig](https://github.com/nick-boss-tech/solr/blob/c0ab38fc0a8b57953f8b8df03f54085fb37e138d/solr/core/src/java/org/apache/solr/core/NodeConfig.java#L228-L229)).
- New URLs are appended after the old ones when the loader is replaced ([URL order](https://github.com/nick-boss-tech/solr/blob/c0ab38fc0a8b57953f8b8df03f54085fb37e138d/solr/core/src/java/org/apache/solr/core/SolrResourceLoader.java#L270-L271)). So when a module and a shared lib jar both provide a class with the same name, the module copy now wins. Before this change the shared lib copy won.

## Proof

**One new test fails on the base code and passes with this change.**

- `TestCoreContainer` passes at head `c0ab38fc0a8b`, with 26 tests, 3 skipped, 0 failures. Verified 2026-10-04. The new test is `testSharedLibSpiCanStillLoadItsClassesWhenModulesAreEnabled` ([test](https://github.com/nick-boss-tech/solr/blob/c0ab38fc0a8b57953f8b8df03f54085fb37e138d/solr/core/src/test/org/apache/solr/core/TestCoreContainer.java#L466-L506)).
- On the base code, that test fails. A run on the base code confirmed it.
- A test for the reverse order was run at this head, and it fails. It is not part of this change.

## A choice to check

**The reverse order is not covered. A module SPI can still lose its classes when a shared lib is also configured.**

Options considered:

- Ship the narrower change here, which fixes shared lib SPIs, and track the reverse order as a follow-up. This is the change in this PR.
- Widen this change so both directions work, for example by adding all the jars first and loading the Lucene SPIs once after both steps. This would need its own test and a new run.

The reverse order fails at this head, so it is not part of this change. Was the narrower fix the right call, or should this change also cover module SPIs when a shared lib is present?

## Limits

**Module SPIs are not fixed when a shared lib is present, and only shared lib SPIs are tested.**

- Module SPIs with a shared lib present are not fixed here (see the choice above).
- The new test covers a shared lib SPI only. Module precedence and same-name classes in both places are not tested.
