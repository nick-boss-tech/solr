## What happens today

**A clusterSingleton declared in solr.xml fails at startup when its class is in a module or in the shared lib.**

`SolrXmlConfig` checked each clusterSingleton class while it parsed solr.xml. At that point the class loader does not yet have the shared lib directories or the modules, so a class that lives there is reported as not found. The check was in the parser, before the constructor of `NodeConfig` adds those directories ([former check location](https://github.com/nick-boss-tech/solr/blob/22b5f209a11a593302b64b0e4e2c2632b540b3f7/solr/core/src/java/org/apache/solr/core/SolrXmlConfig.java#L682-L684)).

## What this change does

**The class check runs at the end of the `NodeConfig` constructor, after the shared lib and the modules are on the class loader.**

- `NodeConfig` calls `validateClusterSingletonClasses()` after `setupSharedLib()` and `initModules()` ([calls](https://github.com/nick-boss-tech/solr/blob/22b5f209a11a593302b64b0e4e2c2632b540b3f7/solr/core/src/java/org/apache/solr/core/NodeConfig.java#L229-L231)). The method is at [lines 240 to 256](https://github.com/nick-boss-tech/solr/blob/22b5f209a11a593302b64b0e4e2c2632b540b3f7/solr/core/src/java/org/apache/solr/core/NodeConfig.java#L240-L256).
- The check itself is unchanged. A missing class and a class of the wrong type fail with the same messages as before.
- `SolrXmlConfig` no longer checks the classes. `SolrXmlConfig.fromString` still raises the error in the same call.
- Changelog: [`changelog/unreleased/SOLR-17377.yml`](https://github.com/nick-boss-tech/solr/blob/22b5f209a11a593302b64b0e4e2c2632b540b3f7/changelog/unreleased/SOLR-17377.yml)

## Proof

**One new test fails on the base code and passes with this change.**

- `TestSolrXml` 35 tests, `NodeConfigClusterPluginsSourceTest` 3 tests, and `TestContainerPlugin` 3 tests pass at head `22b5f209a11a`, with 0 failures. That is 41 focused tests. Verified 2026-10-05.
- The new test is `testClusterSingletonClassFromSharedLib` ([test](https://github.com/nick-boss-tech/solr/blob/22b5f209a11a593302b64b0e4e2c2632b540b3f7/solr/core/src/test/org/apache/solr/core/TestSolrXml.java#L577-L615)). On the base code it fails at solr.xml parse time, with the same shape as the ticket: the class can be loaded only after the class loader is complete.
- On the base code, `TestSolrXml` runs 35 tests with exactly 1 failure, and that failure is the new test.
- The test compiles its class into `$SOLR_HOME/lib/classes`, so the class is visible only after the shared lib is added.

## Limits

**Only a shared lib class is tested, and the allowed classes do not change.**

- The new test covers a class from the shared lib directory. A class from a module follows the same path, but no test covers it.
- The change moves the check to a later point. It does not change which classes are allowed.
