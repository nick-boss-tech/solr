## What happens today

**POST `/collections/{coll}/snapshots/{name}` and GET `/aliases/{name}` return HTTP 405, although their handlers exist.**

Each path is also the path of a DELETE endpoint: [CollectionSnapshotApis.java L58](https://github.com/nick-boss-tech/solr/blob/f2b4ba164f565274286708d15989f1b1807b84c6/solr/api/src/java/org/apache/solr/client/api/endpoint/CollectionSnapshotApis.java#L58) for snapshots and [DeleteAliasApi.java L28](https://github.com/nick-boss-tech/solr/blob/f2b4ba164f565274286708d15989f1b1807b84c6/solr/api/src/java/org/apache/solr/client/api/endpoint/DeleteAliasApi.java#L28) for aliases. As the ticket describes, another resource answers with the 405, so the POST or GET handler never runs. The ticket shows both cases ([JIRA](https://issues.apache.org/jira/browse/SOLR-17731)).

## What this change does

**The POST and GET endpoints now declare the same class-level path as the DELETE endpoint beside them, and both requests reach their handlers.**

- Snapshots: the Create endpoint takes the full path at class level ([CollectionSnapshotApis.java L37-L40](https://github.com/nick-boss-tech/solr/blob/f2b4ba164f565274286708d15989f1b1807b84c6/solr/api/src/java/org/apache/solr/client/api/endpoint/CollectionSnapshotApis.java#L37-L40)).
- Aliases: the GET endpoint moves to its own interface with the same path as DELETE ([GetAliasByNameApi.java L33](https://github.com/nick-boss-tech/solr/blob/f2b4ba164f565274286708d15989f1b1807b84c6/solr/api/src/java/org/apache/solr/client/api/endpoint/GetAliasByNameApi.java#L33)). Its handler moves from `ListAliases` to a new `GetAliasByName` class, registered in [CollectionsHandler.java L1207](https://github.com/nick-boss-tech/solr/blob/f2b4ba164f565274286708d15989f1b1807b84c6/solr/core/src/java/org/apache/solr/handler/admin/CollectionsHandler.java#L1207). The lookup logic is the same as before.

## A choice to check

**The two endpoints share a class-level path. The other route is to change how the router picks between endpoints.**

- Implemented: give the POST and GET endpoints the same class-level path as the DELETE endpoint beside them. The change is local to two API declarations.
- Other route: change the router so it picks the endpoint that matches the HTTP method. This would also cover any other overlap of this kind, but it changes routing for every v2 API.

Was the local fix the right call, or should the router change?

## Limits

**Other overlapping v2 paths were not searched, and the alias response keeps its name field.**

- Other overlapping v2 paths were not searched for. A search is a possible follow-up, and a PR for it can be opened on request.
- The alias response still uses the existing wire key `name` for the alias field. This change does not touch it.
