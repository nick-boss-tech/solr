## What happens today

**Two edits to a standalone security.json that overlap in time can lose one change, and two overlapping writes can leave a file that is not valid JSON.**

The Admin UI sends one request per granted permission without waiting for each response ([security.js](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/webapp/web/js/angular/controllers/security.js#L1248-L1283)). Each edit reads security.json, applies its commands, and writes the whole file back ([SecurityConfHandler.java](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandler.java#L124), [line 151](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandler.java#L151)). If two edits start from the same content, the later write drops the other's change.

The write itself is not atomic. The file is opened for writing, which empties it, and the new content is written after that ([SecurityConfHandlerLocal.java](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandlerLocal.java#L86-L87)). Two overlapping writes can leave the start of one document followed by the tail of another. The corrupted file in the ticket also carries an empty-string key with `{"v":0}` in both sections. That is Solr's internal version marker, which standalone mode always writes as 0. The links in this section point to the merge-base commit 14c7aac0d151402b00259e2fb9bf5eed7049ec5d, which is the code before this change.

## What this change does

**Standalone edits now run one at a time on each node, and each write goes to a temporary file that then replaces security.json in one move.**

- Edits sent to a node's security handler run one at a time: an edit waits while another edit on the same node is running ([SecurityConfHandlerLocal.java](https://github.com/nick-boss-tech/solr/blob/2b5ad801c9e88807337f4f0a3fdd689126ad37d1/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandlerLocal.java#L44-L66)). Reads do not wait, and responses do not change.
- The new content is written to a temporary file in the same folder, and that file is then moved over security.json ([SecurityConfHandlerLocal.java](https://github.com/nick-boss-tech/solr/blob/2b5ad801c9e88807337f4f0a3fdd689126ad37d1/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandlerLocal.java#L103-L156)). On a file system with atomic moves, a reader sees the old file or the new one, never a partly written file. Where the file system does not support an atomic move, the code makes a plain move instead (see Limits). The existing permissions are copied to the new file before the move, so an edit keeps them; the copy is skipped or fails where POSIX permissions are not available.
- The internal version marker is removed before the file is written, so security.json and a later GET no longer show it after an edit. An existing file that still has the marker keeps it until the next edit.

## A choice to check

**The implemented route copies the existing permission bits onto the new file. The alternative leaves the new file with the default for a created file.**

Without the copy, the new file gets the default permissions for a created file, which can differ from the old file's and so change who can read security.json. The copy covers permission bits only, not the owner, ACLs or extended attributes. If the copy fails, the edit still goes through with the default, and the failure is logged at debug level. Should the edit keep the existing permission bits, and should a failed copy stop the edit instead?

## Limits

**Standalone mode only, and the lock covers one Solr process.**

- Cloud mode keeps security.json in ZooKeeper and uses SecurityConfHandlerZk ([CoreContainer.java](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/core/CoreContainer.java#L851), at the merge-base and unchanged by this PR). This change does not touch that path.
- Two Solr processes sharing one SOLR_HOME are not coordinated.
- Where the file system refuses an atomic move, the code makes a plain move. That move is not atomic, and a crash during it may leave no security.json.
- On Windows, the move over security.json can fail while another program holds the file open without allowing it to be deleted or renamed. Reads do not take the lock. No test covers this case.
- The file is not flushed to disk before it is replaced, so a power failure can still leave an empty or stale file. A process crash leaves the previous file in place.
- The move replaces security.json instead of writing into it. In a one-off test on Linux, an edit replaced a symbolic link at security.json with a regular file, and the file the link pointed to did not receive the edit. No committed test covers this. A single-file bind mount was not tested, and the move may fail there.
- The edit lock is held while the request body is read.
- The permission test runs only where POSIX permissions exist. On Windows it is skipped, so only a Linux run proves it.
- Cross-process coordination is not covered. A follow-up ticket and PR can be opened on request.
