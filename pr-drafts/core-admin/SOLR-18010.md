## What happens today

**Two edits to a standalone security.json that overlap in time can lose one change, and two overlapping writes can leave a file that is not valid JSON.**

The Admin UI sends one request per granted permission without waiting for each response ([security.js](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/webapp/web/js/angular/controllers/security.js#L1248-L1283)). Each edit reads security.json, applies its commands, and writes the whole file back ([SecurityConfHandler.java](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandler.java#L124), [line 151](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandler.java#L151)). If two edits start from the same content, the later write drops the other's change.

The write itself is not atomic. The file is opened for writing, which empties it, and the new content is written after that ([SecurityConfHandlerLocal.java](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandlerLocal.java#L86-L87)). Two overlapping writes can leave the start of one document followed by the tail of another. These links point to merge-base commit 14c7aac0d15.

## What this change does

**Standalone edits now run one at a time on each node, and each write goes to a temporary file that then replaces security.json in one move.**

- Edits sent to a node's security handler wait for earlier edits to finish ([SecurityConfHandlerLocal.java](https://github.com/nick-boss-tech/solr/blob/2b5ad801c9e88807337f4f0a3fdd689126ad37d1/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandlerLocal.java#L44-L66)). Reads do not wait, and responses do not change.
- The new content is written to a temporary file in the same folder, and that file is then moved over security.json ([SecurityConfHandlerLocal.java](https://github.com/nick-boss-tech/solr/blob/2b5ad801c9e88807337f4f0a3fdd689126ad37d1/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandlerLocal.java#L103-L156)). On a file system with atomic moves, a reader sees the old file or the new one, never a partly written file. Otherwise the code makes a plain move. The existing permissions are copied to the new file before the move, so an edit keeps them; the copy is skipped or fails where POSIX permissions are not available.
- The internal version marker is removed before the file is written, so security.json and a later GET no longer show it. Reading an existing file is unchanged.

## A choice to check

**The implemented route copies the existing permissions onto the new file. The alternative keeps the new file's default permissions.**

The new file is created owner-only on POSIX systems. Without the copy, an edit would change who can read security.json. The copy can fail, and then the edit still goes through with the default. Was copying the existing permissions the right call?

## Limits

**Standalone mode only, and the lock covers one Solr process.**

- Cloud mode keeps security.json in ZooKeeper and uses SecurityConfHandlerZk ([CoreContainer.java](https://github.com/nick-boss-tech/solr/blob/2b5ad801c9e88807337f4f0a3fdd689126ad37d1/solr/core/src/java/org/apache/solr/core/CoreContainer.java#L851)). This change does not touch that path.
- Two Solr processes sharing one SOLR_HOME are not coordinated.
- The plain-move fallback is not promised to be atomic.
- On Windows, the move over security.json can fail while another program has the file open. Reads do not take the lock; no test covers it.
- The permission test runs only where POSIX permissions exist. On Windows it is skipped, so only a Linux run proves it.
- Cross-process coordination is not covered. A follow-up ticket and PR can be opened on request.
