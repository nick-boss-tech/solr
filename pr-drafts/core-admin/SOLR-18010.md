## What happens today

**Two edits to a standalone security.json that overlap in time can lose one change, and two overlapping writes can leave a file that is not valid JSON.**

The Admin UI sends one request for each permission it grants, and it does not wait for one response before it sends the next ([security.js](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/webapp/web/js/angular/controllers/security.js#L1248-L1283)). Each edit reads security.json, applies its commands, and writes the whole file back ([SecurityConfHandler.java](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandler.java#L124), [line 151](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandler.java#L151)). If two edits start from the same content, the one that writes last drops the other's change.

The write itself is not atomic. The file is opened for writing, which empties it, and the new content is written after that ([SecurityConfHandlerLocal.java](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandlerLocal.java#L86-L87)). Two overlapping writes can leave the start of one document followed by the tail of another.

## What this change does

**Standalone edits now run one at a time on each node, and each write goes to a temporary file that then replaces security.json in one move.**

- Edits sent to a node's security handler wait for the edit before them to finish ([SecurityConfHandlerLocal.java](https://github.com/nick-boss-tech/solr/blob/c3685bb37d9d74e4ed538d6d1b65bb1b60970677/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandlerLocal.java#L44-L66)). Reads do not wait.
- The new content is written to a temporary file in the same folder, and that file is then moved over security.json ([SecurityConfHandlerLocal.java](https://github.com/nick-boss-tech/solr/blob/c3685bb37d9d74e4ed538d6d1b65bb1b60970677/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandlerLocal.java#L103-L147)). A reader sees the old file or the new one, never a partly written file. On a file system that does not allow an atomic move, the code makes a plain move instead.
- The internal version marker is removed from each plugin section before the file is written, so security.json no longer carries it. This change does not change how an existing file is read.
- An edit sent while another one is still running waits for it. The responses do not change.

On the base code, one edit's change is lost, and the other write leaves a file that does not parse as one JSON document. The existing testEdit passes on the base code too.

## Limits

**Standalone mode only, and the lock covers one Solr process.**

- Standalone mode only. Cloud mode keeps security.json in ZooKeeper and uses SecurityConfHandlerZk ([CoreContainer.java](https://github.com/nick-boss-tech/solr/blob/c3685bb37d9d74e4ed538d6d1b65bb1b60970677/solr/core/src/java/org/apache/solr/core/CoreContainer.java#L851)). This change does not touch that path.
- The lock covers one Solr process. Two Solr processes that share one SOLR_HOME are not coordinated.
- The fallback for file systems without atomic moves is a plain move, and the code does not promise that it is atomic.
- Cloud mode and coordination between processes are not covered here. A follow-up ticket and PR can be opened on request.
