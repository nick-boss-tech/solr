## What happens today

**Calling `create` before `load()` fails with a NullPointerException message, not a message about `load()`.**

The ticket reports a `NullPointerException` at search time, in `SearchHandler`, for cores created by hand on a container that was never loaded. On the base commit (`cabedd1d9680`), the config set service is created only in [`loadInternal()`](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/core/CoreContainer.java#L856-L856). A `create` call on an unloaded container reaches [`createFromDescriptor`](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/core/CoreContainer.java#L1674-L1674), which uses that null service. The error comes back as a `BAD_REQUEST` whose text includes `"this.coreConfigService" is null` ([catch block](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/core/CoreContainer.java#L1557-L1592)).

## What this change does

**`create` now checks that the container is loaded, and fails with a message that names `load()`.**

Both `create` overloads reach one method. It now checks the shard handler factory before it reserves the core name ([lines 1503 to 1507](https://github.com/nick-boss-tech/solr/blob/0ee4c644ee63c65cbda5752bb4e4e9fcdb70b4bf/solr/core/src/java/org/apache/solr/core/CoreContainer.java#L1503-L1507)). Only `load()` sets that factory. An unloaded container now gets a `SERVER_ERROR` that says to call `load()` first.

## Proof

**One new test fails on the base code and passes with this change.**

[`TestCoreContainer.testCreateBeforeLoadIsRejected`](https://github.com/nick-boss-tech/solr/blob/0ee4c644ee63c65cbda5752bb4e4e9fcdb70b4bf/solr/core/src/test/org/apache/solr/core/TestCoreContainer.java#L249-L261) fails on the base code. The error text is the NullPointerException message, so the assertion at line 257 fails. With this change, `TestCoreContainer` runs 26 tests, with 0 failures, 0 errors, and 3 skipped (Windows-only path assertions). Verified 2026-10-10 at head `0ee4c644ee63`. The core module check, without tests, also passed.

## A choice to check

**The guard sits in `create`. The ticket suggests a different place.**

Option 1, as implemented: the check runs in `create`, before any state changes. Option 2: call `load()` from the constructor. A 2014 comment on the ticket by Alan Woodward proposed this, with `load()` renamed to a private `init()`. Option 2 changes what every caller of the constructor gets, which is a wider change. Was the guard in `create` the right place?

## Limits

**Only `create` is checked. The search-time failure from the ticket is not tested.**

- Cores built without `create` are not checked. [`SyntheticSolrCore.createAndRegisterCore`](https://github.com/nick-boss-tech/solr/blob/0ee4c644ee63c65cbda5752bb4e4e9fcdb70b4bf/solr/core/src/java/org/apache/solr/core/SyntheticSolrCore.java#L53-L69) calls `registerCore` with no check.
- The new test stops at the error. It does not run a search.
- The error is `SERVER_ERROR`, which returns HTTP 500 for a call made too early. Whether another status fits better is not decided.
