## What happens today

**A core never closes its resource loader, so the loader's jars stay open.**

The ticket says `SolrCore` does not close its own `SolrResourceLoader`. That loader holds the class loader for the core's lib directories. Closing it releases those jars, and the ticket notes that open jars cannot be deleted on Windows. At the merge-base commit `cabedd1d968`, the close method ends without any such step ([SolrCore.java lines 1889-1893](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/core/SolrCore.java#L1889-L1893)).

## What this change does

**The core closes its resource loader when the core closes.**

`SolrCore.close()` closes the core's `SolrResourceLoader` after the close hooks run, unless the node caches schemas (`shareSchema` on). A failure is logged, and an `Error` is rethrown, the same way the other close steps handle failures ([SolrCore.java lines 1892-1906](https://github.com/nick-boss-tech/solr/blob/00060d2ed92bc6414fb420d7c52558c14c49f75a/solr/core/src/java/org/apache/solr/core/SolrCore.java#L1892-L1906)). The cache check is [ConfigSetService.java lines 272-275](https://github.com/nick-boss-tech/solr/blob/00060d2ed92bc6414fb420d7c52558c14c49f75a/solr/core/src/java/org/apache/solr/core/ConfigSetService.java#L272-L275).

`SolrResourceLoader.close()` now records that it ran. A package-private `isClosed()` returns that flag, and only the new test calls it ([line 141](https://github.com/nick-boss-tech/solr/blob/3fd85bedef646b5b73c26e26a86a6130b5fc209f/solr/core/src/java/org/apache/solr/core/SolrResourceLoader.java#L141), [lines 912-919](https://github.com/nick-boss-tech/solr/blob/3fd85bedef646b5b73c26e26a86a6130b5fc209f/solr/core/src/java/org/apache/solr/core/SolrResourceLoader.java#L912-L919)).

Once the core closes, its jars are released, and its class loader can no longer load lib classes it has not loaded yet. When the node caches schemas, a second core can still reach that loader through the cached schema, so the loader stays open in that case (see Limits).

## Limits

**Not every close path is tested, and with `shareSchema` on the loader stays open, so its jars are not released.**

- Shared schema: two cores built on one config set, with `shareSchema` on. The loader of the core that built the cached schema stays open after that core unloads or reloads, because the cached schema still uses it. Its jars are therefore not released while the node runs with `shareSchema` on. That is the behaviour before this change for that setting. With `shareSchema` off (the default), the loader closes as described above. A per-loader count in the config set service is the follow-up that would let the loader close safely with `shareSchema` on.
- The test checks the loader's closed flag. It does not check that the jar files are released.
- The shutdown path is not tested on its own. The tests drive an unload, a reload, and a direct close.
