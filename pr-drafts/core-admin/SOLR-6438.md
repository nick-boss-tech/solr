## What happens today

**A MERGEINDEXES request that gives both `indexDir` and `srcCore` silently drops the cores.**

The v2 handler reads the source cores only when no directories are given ([MergeIndexes.java L114-L116](https://github.com/nick-boss-tech/solr/blob/8c77988d59175e0a59a32ef00dabffd3ca9a76fa/solr/core/src/java/org/apache/solr/handler/admin/api/MergeIndexes.java#L114-L116)). When both are given, the directories are merged and the named cores are ignored. The request does not fail. The v1 `mergeindexes` action builds the same request body ([MergeIndexesOp.java L39-L44](https://github.com/nick-boss-tech/solr/blob/8c77988d59175e0a59a32ef00dabffd3ca9a76fa/solr/core/src/java/org/apache/solr/handler/admin/MergeIndexesOp.java#L39-L44)), so it has the same gap. The ticket asks for an error at the least.

## What this change does

**A request with both kinds of source now gets a 400 error, and no source is opened.**

The check runs before any source is opened ([MergeIndexes.java L107-L113](https://github.com/nick-boss-tech/solr/blob/8c77988d59175e0a59a32ef00dabffd3ca9a76fa/solr/core/src/java/org/apache/solr/handler/admin/api/MergeIndexes.java#L107-L113)). The message is "Only one of indexDir or srcCore can be specified, not both". A request with only one kind of source behaves as before.

## Proof

**One new test fails on the base code and passes with this change.**

- `MergeIndexesTest` 4 of 4 at head `8c77988d5917` (verified 2026-10-05). The new test, `testReportsErrorIfBothIndexDirAndSrcCoreAreGiven`, fails on the base code: it expected a 400 error and got a 500. The three existing tests pass on the base code too.
- Neighbor classes at the same head: `CoreMergeIndexesAdminHandlerTest` 1 of 1, and `CoreAdminOperationTest` 44 of 44.

## A choice to check

**The combined request is rejected. Merging from both sources is the other route.**

- Implemented: reject the combined request with a 400 error. This is the smallest change, and the ticket asks for at least an error.
- Other route: merge the directories and the cores together. This keeps such requests working, but it needs a rule for the case where one index appears in both lists.

Was rejecting the combined request the right call?

## Limits

- The new test covers the v2 class only. The v1 action reaches the same class through `MergeIndexesOp`, but no v1 test was added.
- Clients that sent both parameters now get a 400 error and must send one of them.
- The reference guide already presents the two sources as alternatives, so this change does not touch it.
