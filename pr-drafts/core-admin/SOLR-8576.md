## What happens today

**Creating a collection with a name that a collection or an alias already has is rejected, but no test covers that.**

The create path rejects a name taken by a collection with "collection already exists: <name>", and a name taken by an alias with "collection alias already exists: <name>" ([CreateCollectionCmd.java L127-L135](https://github.com/nick-boss-tech/solr/blob/4c46f95c7851f2adbf3377d746aadc9c2249cdb4/solr/core/src/java/org/apache/solr/cloud/api/collections/CreateCollectionCmd.java#L127-L135)). No test in `CollectionsAPISolrJTest` checks either message for a create. The ticket asks for tests of this path ([JIRA](https://issues.apache.org/jira/browse/SOLR-8576)).

## What this change does

**One new test covers both name collisions, and it checks that the rejected creates change nothing.**

This is a test-only change. The create path is not changed ([CollectionsAPISolrJTest.java L1157-L1189](https://github.com/nick-boss-tech/solr/blob/4c46f95c7851f2adbf3377d746aadc9c2249cdb4/solr/core/src/test/org/apache/solr/cloud/CollectionsAPISolrJTest.java#L1157-L1189)). The test creates a collection and an alias. It then tries to create a collection with each name. Both creates must fail with the existing message. After that, it checks that the original collection and the alias are unchanged.

## Proof

**The new test passes on the base code too. It adds coverage for behavior that already exists.**

- `CollectionsAPISolrJTest` 25 tests, 1 skipped, 0 failures at head `4c46f95c7851` (verified 2026-10-07).
- The new test, `testCreateCollectionNameAlreadyTaken`, passes on the base code. It pins error behavior that already exists, so it does not show a failure before the change. Its value is the coverage it adds.

## Limits

- Only creates with a name that is already taken are covered. Other create errors are not.
- The checks match the error text. A change to that text needs a matching test change.
