## What happens today

**With stopwords=false, edismax still removes words that a ManagedStopFilterFactory removes from the query.**

The `stopwords` parameter should turn off the stop filter in the query analyzer. The code only recognized `StopFilterFactory`. A `ManagedStopFilterFactory` in the query analyzer was never recognized, so its words were still removed. For example, a field whose query analyzer uses `ManagedStopFilterFactory managed="english"` still drops "the" from the query "the one" when `stopwords=false`. The query then matches on "one" alone, even with `mm=100%`.

## What this change does

**Both stop filter checks now accept `ManagedStopFilterFactory` as well as `StopFilterFactory`.**

When `stopwords=false`, the managed stop filter in the query analyzer is now removed, as a plain stop filter already was ([query-side check](https://github.com/nick-boss-tech/solr/blob/ca9573dabd385a38711bd60633973ae46b7a552e/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1521-L1524)). The index-side check now also counts a managed filter ([index-side check](https://github.com/nick-boss-tech/solr/blob/ca9573dabd385a38711bd60633973ae46b7a552e/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1510-L1513)). If the index analyzer has a stop filter of either kind, the query analyzer is left alone, as before.

That second part is wider than the ticket's narrow reading. A field whose index analyzer has a managed stop filter and whose query analyzer has a plain `StopFilterFactory` used to lose that query filter when `stopwords=false`. Now the query keeps it. The index never stores those words, so a required clause for them could match nothing. The reference guide and the changelog both state this.

## Proof

**Two of the three new tests fail on the base code. The third passes on both and pins the index-side rule.**

- `TestManagedStopFilterFactory`: 5 of 5 pass at `ca9573dabd3`, verified 2026-10-07.
- On the base code, exactly two of these five tests fail, both on a `stopwords=false` assertion: `testEdismaxStopwordsFalseKeepsManagedStopwords` and `testEdismaxStopwordsFalseWithManagedStopFilterInIndexAnalyzer`. The first finds a document where none is expected. The second finds no document where one is expected.
- `TestExtendedDismaxParser`: 39 of 39 pass. This change does not touch that class.
- The focused run covered 82 tests in nine classes. All pass at `ca9573dabd3`.

## A choice to check

**The index-side rule goes beyond the query-side fix. The narrower option leaves it out.**

The alternative checks managed filters only in the query analyzer. Then a field with a managed stop filter in the index analyzer and a plain stop filter in the query analyzer keeps the old behavior, where `stopwords=false` removes the query filter. Was it right to apply the index-side rule here?

## Limits

- Only `StopFilterFactory` and `ManagedStopFilterFactory` are recognized. Other filters that remove words are not covered.
- The change adds three field types to the shared test schema, [`schema-rest.xml`](https://github.com/nick-boss-tech/solr/blob/ca9573dabd385a38711bd60633973ae46b7a552e/solr/core/src/test-files/solr/collection1/conf/schema-rest.xml#L502-L540). The focused run covered nine test classes. A full run of every class that loads that schema is the remaining check.
