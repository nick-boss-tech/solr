## What happens today

**A multi-term edismax alias query can lose its second term when one alias target is not in the schema.**

With `f.myalias.qf=name nosuchfield`, the query `myalias:(Zapp Brannigan)` makes the parser throw on the missing target. The parser then retries the whole query with reserved characters escaped. After that retry, the second term no longer goes to the alias fields. The ticket reports that it goes to the `_text_` field. A single term such as `myalias:Zapp` gets the same retry and still matches.

## What this change does

**Alias targets missing from the schema are skipped on every alias path. An alias with no usable target matches nothing.**

A target that is not an alias, not a schema field, and not a magic field is skipped before the parser looks it up ([list path](https://github.com/nick-boss-tech/solr/blob/b80221f46d3ce5889c510b97a97d8748a2ea4c7c/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1411-L1413), [multi-term path](https://github.com/nick-boss-tech/solr/blob/b80221f46d3ce5889c510b97a97d8748a2ea4c7c/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1433-L1435), [helpers](https://github.com/nick-boss-tech/solr/blob/b80221f46d3ce5889c510b97a97d8748a2ea4c7c/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1449-L1474)). The multi-term query then keeps both terms on the alias fields, with no retry.

An alias with no usable target now returns a query that matches no documents ([single-term path](https://github.com/nick-boss-tech/solr/blob/b80221f46d3ce5889c510b97a97d8748a2ea4c7c/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1182-L1186), [multi-term path](https://github.com/nick-boss-tech/solr/blob/b80221f46d3ce5889c510b97a97d8748a2ea4c7c/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1230-L1234)). Before, its clause was silently dropped. This is wider than the ticket. In a compound query the result changes. For example, `myalias:Zapp AND name:Zapp` with no usable target returned the matches for `name:Zapp` before, and now returns none.

## A choice to check

**An alias with no usable target now matches nothing. Before, its clause was dropped.**

The other option keeps the silent drop. That keeps the old results for compound queries, where the other clauses decide the answer. The cost is that a misconfigured alias quietly widens the query. Was matching nothing the right call?

## Proof

**One new test, `testAliasingWithNonSchemaField`, fails on the base code and passes with this change.**

- On the base code, the multi-term assertion in that test fails. The parsed query does not contain both alias terms.
- `TestExtendedDismaxParser` passes 40 of 40 at `51fe1087fe9`, verified 2026-10-03. At the current head, `b80221f46d3`, the same class passes 40 of 40, verified 2026-10-07. The only commit after `51fe1087fe9` changes comments.
- The assertions for an alias with no usable target also return no documents on the base code. They guard the new result. They do not prove the compound-query change, which is stated above.

## Limits

- An alias that points at another alias whose targets are all missing is not tested. The outer alias keeps the inner one, and that branch matches nothing. A follow-up test for this shape can follow if maintainers want it.
- A missing target in an alias is now skipped without a message. A missing field in a plain `qf` still returns its error.
