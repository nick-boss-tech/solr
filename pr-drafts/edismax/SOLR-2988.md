## What happens today

**edismax drops a pf boost on a string field. dismax keeps it.**

The ticket's example uses `qf=name^5 features^3`, `pf=features^2 cat^4` and `q=hard drive`. dismax keeps `cat:hard drive^4.0` in its pf clause. edismax keeps only `features:"hard drive"^2.0`. The ticket is about non-tokenized fields such as `cat`.

## What this change does

**A pf clause on a string field is kept, so its boost applies. The pf phrase text also loses a trailing space.**

- A single term that contains whitespace is kept instead of dropped ([term check](https://github.com/nick-boss-tech/solr/blob/d2d144dfd9f4cd8208c856a7b955e6eb997da146/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1471-L1474), [helper](https://github.com/nick-boss-tech/solr/blob/d2d144dfd9f4cd8208c856a7b955e6eb997da146/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1498-L1500)).
- The pf, pf2 and pf3 phrase text puts one space between words. The old text put a space after the last word too, inside the quotes. A string field stores the value without that space, so the old text could not match it ([phrase text](https://github.com/nick-boss-tech/solr/blob/d2d144dfd9f4cd8208c856a7b955e6eb997da146/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L637-L647)).
- Behavior changes, stated openly. The phrase text changes for every pf, pf2 and pf3 field, not only string fields. For tokenized fields, the existing phrase tests in this class still pass at this head.
- A configuration that lists a string field in pf, pf2 or pf3 now gets that boost, so ranking can change for it. The changelog says so.

The tests fail without the fix.

## Limits

**The whitespace check is a heuristic.**

- It accepts any single term that contains whitespace. In practice that is a string field, or a text field that keeps the whole value as one token. The schema used by these tests has no text field with a keyword tokenizer, so that case is not tested.
- A stricter check on the field type would need more code. We did not add one. If a maintainer prefers that check, we will make it in this PR.
