## What happens today

**A parenthesized `*:*` is read as a wildcard term, not as match all. Signed and boosted forms fail the same way.**

The splitter escapes the colon in every clause except one that is exactly `*:*`. So `(*:*)` reaches the grammar as `(*\:*)`, which searches the query fields for the literal text. The report shows `(*:*)` parsing to `+DisjunctionMaxQuery((text:*\:*))`, while `( *:* )` with spaces parses as match all ([SOLR-3729](https://issues.apache.org/jira/browse/SOLR-3729)). The same escape hits `+*:*`, `-*:*`, and `*:*^2`. So `-*:*` does not exclude every document.

## What this change does

**A standalone `*:*` keeps its colon, with parentheses, a sign, or a plain-number boost around it. Other text on the same clause keeps the escape.**

Before it escapes a clause, the splitter asks `isStandaloneMatchAll` ([ExtendedDismaxQParser.java, L737-L798](https://github.com/nick-boss-tech/solr/blob/0fe7e503945c1a169f76a019392d68bdf4261eb7/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L737-L798); the call is at [L940-L943](https://github.com/nick-boss-tech/solr/blob/0fe7e503945c1a169f76a019392d68bdf4261eb7/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L940-L943)). The check accepts `*:*` with any leading `(`, `+`, or `-`, then optional `)` characters and an optional `^` boost. A boost is digits with at most one dot. Text glued to the clause, such as `foo(*:*)bar` or `(*:*)foo`, is not standalone, so its colon stays escaped. A `*:*` inside a larger group, such as `(foo *:*)`, is standalone, because the splitter breaks the query at whitespace.

Signed and boosted forms are match all too, so `-*:*` now excludes every document.

## Proof

**Two tests fail on the base code and pass with this change. A third new test passes on both.**

- `TestExtendedDismaxParser`: 41 of 41 pass at head `0fe7e503945c1a169f76a019392d68bdf4261eb7`, verified 2026-10-08.
- On the base code (`97d973814336`), exactly two fail: `testFocusQueryParser` (which gained the parenthesized match all assertions) and `testMatchAllColonEscaping`.
- `testMatchAllBoostGluedFieldClauseRespectsUserFields` passes on the base code too. It guards the new boost check, so that a field clause glued after `*:*^2` stays under `uf`. The base code already escapes that text, so this test locks in behavior rather than failing before the fix.

## A choice to check

**The change covers a broader set of spellings than the ticket names. Should it narrow to `(*:*)`?**

The ticket asks about `(*:*)`. This change also covers signed forms (`+*:*`, `-*:*`), boosted forms (`*:*^2`), a `*:*` inside a larger group, and combinations of these. The alternative is to narrow the check to `(*:*)` alone. That fixes the ticket's example and leaves the other spellings escaped as they are today. The broader set changes what `-*:*` and `*:*^2` return, and a maintainer could reject that change. Was the broader set the right call, or should this narrow to `(*:*)`?

## Limits

**Phrase fields still see the text of a match all clause. SOLR-3962 covers that in a separate change.**

- Phrase fields (`pf`, `pf2`, `pf3`) still analyze the text of a match all clause here. SOLR-3962 addresses that.
- Malformed forms take the old path. The check accepts some unbalanced forms, such as `(*:*`. The grammar then either parses the clause or rejects it, and a rejected query falls back to the escaped parse. The tests check that parsing does not throw for `*:*^abc` and `*:*)))`. They do not pin the parsed text for every malformed form.
