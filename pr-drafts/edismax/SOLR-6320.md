## What happens today

**With lowercaseOperators=true, a lowercase "and" or "or" next to an explicit operator makes the query fail to parse.**

`Zapp AND and Brannigan` is rebuilt as `Zapp AND AND Brannigan`, which is not valid. Edismax then uses the escaped form, which quotes the explicit AND and searches it as a term ([escaping](https://github.com/nick-boss-tech/solr/blob/cb710c963531c4f32166e6e0b28c45e54b164a3f/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L462-L495)). The ticket shows the same fallback on a long query with `AND and AND` in it, which then searches the default field.

## What this change does

**A lowercase "and" or "or" is read as a term when a neighbor is an uppercase AND, OR or NOT.**

One helper, [`isPromotedOperatorWord`](https://github.com/nick-boss-tech/solr/blob/cb710c963531c4f32166e6e0b28c45e54b164a3f/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L524-L529), decides promotion in [`rebuildUserQuery`](https://github.com/nick-boss-tech/solr/blob/cb710c963531c4f32166e6e0b28c45e54b164a3f/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L546) and the minimum-should-match check in [`foundOperators`](https://github.com/nick-boss-tech/solr/blob/cb710c963531c4f32166e6e0b28c45e54b164a3f/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L509-L511). A lowercase "or" that stays a term no longer switches off minimum-should-match.

Behavior changes, stated openly:

- With `lowercaseOperators=true`, a query that used to fall back to the escaped form now parses as a normal query. The default stays `false`, so default behavior does not change.
- A 2014 comment on the ticket expected `x AND and AND y` to fail under `lowercaseOperators=true`. This change makes that query parse for users who opt in.

`TestExtendedDismaxParser`: 44 of 44 pass at head `cb710c963531c4f32166e6e0b28c45e54b164a3f` (verified 2026-10-08).

On base `97d973814336101e12475558d7419321c743de79`, 3 of the 44 fail: `testLowercaseOperatorNextToExplicitOperator`, `testLowercaseOperatorNextToExplicitOperatorResults`, and `testLowercaseOperatorDemotedOrShapes`. The tests for shapes this change leaves alone pass on base too.

## A choice to check

**The neighbor test counts only uppercase AND, OR and NOT. A mixed-case word such as "And" does not count.**

The implemented rule uses exact uppercase words. So `Zapp And or Brannigan` still promotes both words and falls back. The alternative counts a mixed-case And, Or or NOT as an explicit neighbor, so the lowercase word stays a term. That costs a second rule for mixed-case words, which users would have to learn. Was counting only the uppercase words the right call?

## Limits

**Some cases are not covered, and one is not visible in the tests.**

- Two lowercase words in a row, such as `Zapp and and Brannigan`, have no uppercase neighbor. Both still promote, and the query still takes the escaped path. A follow-up PR can cover this on request.
- Mixed-case neighbors are not covered. See the choice above.
- The minimum-should-match change is not visible in the tests. Under `q.op=AND` every clause is required, and under `q.op=OR` the derived value is 0% either way.
