## What happens today

**An add made after the test cuts off one replica can fail, and the test stops there.**

`RecoveryAfterSoftCommitTest` closes one replica's socket proxy, then adds more documents through the normal cloud client. That client can send an add to the cut replica. The add fails with `SolrServerException: IOException occurred when talking to server at ...`, and its cause is a `ClosedChannelException`. The test fails before its recovery check.

## What this change does

**After the cut, this test sends its adds to the shard leaders first.**

The adds before the cut still use the normal client. The adds after it use a new client built to send updates to shard leaders first ([test](https://github.com/nick-boss-tech/solr/blob/14868bc7a7f5ec5c4fa1ade5f894cbda9533307d/solr/core/src/test/org/apache/solr/cloud/RecoveryAfterSoftCommitTest.java#L102-L117)). Whether the leader is the only endpoint is set by the test helper's randomized `directUpdatesToLeadersOnly` setting, so the cut replica can remain on the list as a failover target. The leader is not cut, so the adds reach it in either setting. The leader still sends each add on to the cut replica: a failed send to a replica of this shard is logged and does not fail the add ([DistributedZkUpdateProcessor](https://github.com/nick-boss-tech/solr/blob/14868bc7a7f5ec5c4fa1ade5f894cbda9533307d/solr/core/src/java/org/apache/solr/update/processor/DistributedZkUpdateProcessor.java#L1229-L1231)). The error is returned to the client instead in two cases: when the leader changed during the send (the `LeaderChanged` case) ([DistributedZkUpdateProcessor](https://github.com/nick-boss-tech/solr/blob/14868bc7a7f5ec5c4fa1ade5f894cbda9533307d/solr/core/src/java/org/apache/solr/update/processor/DistributedZkUpdateProcessor.java#L1254-L1262)), and when the replica is on another shard ([DistributedZkUpdateProcessor](https://github.com/nick-boss-tech/solr/blob/14868bc7a7f5ec5c4fa1ade5f894cbda9533307d/solr/core/src/java/org/apache/solr/update/processor/DistributedZkUpdateProcessor.java#L1345-L1348)). The document count is unchanged, so the replica still misses more updates than its update log keeps.

Our reading of the cause, which these runs do not prove: the cloud client still held a pooled connection to the cut replica's proxy. Endpoint failover in `LBSolrClient` moves an update to another endpoint only when it could not connect or the request was never sent ([LBSolrClient](https://github.com/nick-boss-tech/solr/blob/14868bc7a7f5ec5c4fa1ade5f894cbda9533307d/solr/solrj/src/java/org/apache/solr/client/solrj/impl/LBSolrClient.java#L675-L680)). Once the update has reached the server, a `ClosedChannelException` is not one of the causes that makes the cloud client resend an update ([CloudSolrClient](https://github.com/nick-boss-tech/solr/blob/14868bc7a7f5ec5c4fa1ade5f894cbda9533307d/solr/solrj/src/java/org/apache/solr/client/solrj/impl/CloudSolrClient.java#L213-L217)).

The change touches only this test. No product code changes.

## Proof

**This is a test-only change. The repeated runs pass, but they do not show that the change fixes the failure.**

- `RecoveryAfterSoftCommitTest` with this change: 6 of 6 runs passed. Checked 2026-10-10 at 14868bc7a7f5ec5c4fa1ade5f894cbda9533307d.
- The original test: 5 of 5 runs passed. It did not fail, so there is no before-and-after result.
- The failure is intermittent and did not appear in these runs. This change is not shown to fix it. The reasoning rests on the code path described above.

## A choice to check

**The adds after the cut use a leaders-first client, not a retry in the test.**

The other option was to keep the normal client and retry the same add when it fails with `ClosedChannelException`. That would keep any-replica writes during the partition in this test, which the leaders-first client removes. The existing test `CheckRetryUnrollTest` already asserts that `ClosedChannelException` is not retried ([test](https://github.com/nick-boss-tech/solr/blob/14868bc7a7f5ec5c4fa1ade5f894cbda9533307d/solr/core/src/test/org/apache/solr/update/CheckRetryUnrollTest.java#L97-L103)), and changing that rule would be a separate decision.

Was routing these adds through a leaders-first client the right call, or would you rather keep random routing and retry in the test?

## Limits

**The fix is not proven by these runs, and some neighboring cases are not covered.**

- The failure did not reproduce in the runs above, so the fix is not shown to remove it.
- Other tests that cut a replica's proxy and then write through the cloud client may have the same pattern. I have not checked them. A follow-up for those is available on request.
- Besides the adds and the soft commit succeeding, the test checks only that replicas become active. The wait after the cut allows 30 seconds. It does not check which recovery path ran. The document count is what rules out peer sync.
- The test helper randomizes `directUpdatesToLeadersOnly` for this client, so the cut replica can stay on the failover list; the leader is still tried first. Setting the flag explicitly would need a fresh set of runs, since the six passing runs used the randomized setting.
- SolrJ still does not retry a `ClosedChannelException` on an update once the update has reached the server. That is a separate product decision.
