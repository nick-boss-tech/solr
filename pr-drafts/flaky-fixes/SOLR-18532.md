## What happens today

**A failed restore or install can leave the core pointing at the wrong index directory.**

When a restore or install fails after the switch to the restored index, `RestoreCore` rolls back. The rollback deletes `index.properties`. That is correct only when the core used the default `index` directory before the restore; if it used another index directory, the delete drops the pointer to it, and the core then opens the default `index` directory instead.

## What this change does

**On rollback, the core's previous `index.properties` is written back.**

Before the switch, the change reads the file's bytes ([RestoreCore.java](https://github.com/nick-boss-tech/solr/blob/7dfd3d98d0a2f016c520139cbca96ea4a49f6689/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L213-L226)). If the switch fails, it writes those same bytes back. The file is deleted only when the core had no `index.properties` before the restore. The change is in [RestoreCore.java](https://github.com/nick-boss-tech/solr/blob/7dfd3d98d0a2f016c520139cbca96ea4a49f6689/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L213-L226), with a new test for the non-default case ([TestRestoreCore.java](https://github.com/nick-boss-tech/solr/blob/7dfd3d98d0a2f016c520139cbca96ea4a49f6689/solr/core/src/test/org/apache/solr/handler/TestRestoreCore.java#L242-L319)). No public method changes.

This is a product fix. The rollback path does not run in those tests, so this change does not address the teardown failure seen in the install tests.

Behavior change: a read error other than "file not found" now stops the restore before the switch. Before, that error was ignored.

## Proof

**The new test fails on the base code and passes with this change.**

`TestRestoreCore.testFailedRestoreKeepsNonDefaultIndexPointer` first runs a restore that succeeds, so the pointer names a restored directory. It then runs a restore that fails. With [RestoreCore.java](https://github.com/nick-boss-tech/solr/blob/7dfd3d98d0a2f016c520139cbca96ea4a49f6689/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L213-L226) reverted to the base commit and the test kept, the pointer check fails. The check expects the earlier restored directory, but the pointer is missing (null), because the old rollback deletes the file. With this change, the test passes.

- `TestRestoreCore`: 4 tests, 0 failures at `f1e5031fc3a9624b03daf353f26c977891d7d876`, verified 2026-10-10.
- `RestoreCoreOpTest`: 1 test, 0 failures at the same head, verified 2026-10-10.

## A choice to check

**The rollback writes back the saved file bytes, not only the directory name.**

The implemented route saves the file's exact bytes and writes them back. The other route saves only the previous directory name and sets it again through the existing modify path. Both routes fix the case the test covers. The exact-bytes route is the one implemented here. Was saving the exact bytes the right call, or should the rollback set only the previous directory name again?

## Limits

**The fix is proven on the in-memory test factory; a few rollback edges keep the old code's shape.**

- The proof runs on the in-memory test directory factory. The atomic file move used by the file-system factory is not run by these tests.
- If writing the saved bytes back fails, the error stops the rest of the rollback. The writer is not reopened and the restore directory is not removed. The base code has the same shape around its delete.
- If any step after the file is created fails, a temporary `index.properties.<number>` file can be left in the data directory. Nothing removes it. The existing code has the same pattern.
- On a factory that deletes and then renames, a failure between those two steps can leave no pointer. Only the in-memory factories use that fallback today; [StandardDirectoryFactory](https://github.com/nick-boss-tech/solr/blob/7dfd3d98d0a2f016c520139cbca96ea4a49f6689/solr/core/src/java/org/apache/solr/core/StandardDirectoryFactory.java#L130-L148) has a similar non-atomic move when an atomic move is not supported. This is not new.
- The test checks the pointer after the rollback. It does not check that the file is absent when the core had no earlier file.
- The SOLR-9865 change edits the same rollback lines and writes back only the previous directory name. Once this change lands, I will follow up on that branch by dropping its rollback edit, so the two do not conflict.
- The new test polls the restore status 10 times at 50 ms intervals while waiting for the failure, copied from the existing `testFailedRestore`. A slower failure would make the test fail rather than pass.
- The rollback path does not run in those tests, so this change does not address the teardown failure.
