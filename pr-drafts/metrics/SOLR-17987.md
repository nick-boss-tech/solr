## What happens today

**Metrics can be turned off for all registries at once, but not for a single registry.**

The `solr.xml` metrics flag is one boolean: either every registry collects, or none does. The only exception is the JVM registry, which has its own switch, `solr.metrics.jvm.enabled`.

## What this change does

**A new system property lists the registries to disable, and those registries get a no-op meter provider.**

The property is `solr.metrics.disabledRegistries`, a comma-separated list of registry names, with or without the `solr.` prefix. The node's metric manager reads it at startup ([SolrMetricManager.java](https://github.com/nick-boss-tech/solr/blob/38abf6423126112cf8a451f4d3fedea0920eae90/solr/core/src/java/org/apache/solr/metrics/SolrMetricManager.java#L178-L181)). A name on the list never gets a real provider or a Prometheus reader ([SolrMetricManager.java](https://github.com/nick-boss-tech/solr/blob/38abf6423126112cf8a451f4d3fedea0920eae90/solr/core/src/java/org/apache/solr/metrics/SolrMetricManager.java#L468-L472)), so the registry collects nothing and the metrics API does not expose it. The environment variable `SOLR_METRICS_DISABLEDREGISTRIES` sets the same property. The reference guide documents the setting.

Behavior change: if the JVM registry is on the list and a CPU circuit breaker is configured, core creation fails with "JVM metrics disabled", the same failure the existing JVM switch already causes in that setup.

## Proof

**The metric manager test class passes at this head, and the new test cannot run on the base code.**

- SolrMetricManagerTest: 18 tests, 0 failures at 38abf6423126, verified 2026-10-10, including the new [testDisabledRegistryUsesNoopProvider](https://github.com/nick-boss-tech/solr/blob/38abf6423126112cf8a451f4d3fedea0920eae90/solr/core/src/test/org/apache/solr/metrics/SolrMetricManagerTest.java#L77-L93), which checks that listed registries report no registry and no reader while an unlisted one does.

The proof is inconclusive by construction: the new test calls a constructor that this change adds, so it does not compile on the base code and cannot show the old behavior failing.

## A choice to check

**The list is a node-level system property, and the alternative is an element in `solr.xml`.**

Options considered: a system property (implemented), which matches the existing JVM switch and also works as an environment variable, or a new element in the `solr.xml` metrics section, next to the flag that turns all metrics on or off. The property keeps every metrics switch in one form. The element would put the on-off flag and the per-registry list in one file.

Was the system property the right place for this list, or should it sit in `solr.xml`?

## Limits

**Only exact registry names can be disabled, and only on the node's own metric manager.**

- Names match exactly after the `solr.` prefix, so a group such as all per-core registries cannot be disabled with one entry.
- Cross-data-center metrics reporting does not read this property.
- The value is a plain comma-separated list. A bracketed or JSON-style value is not supported.
- With metrics off, asking for a registry under a null name now throws a NullPointerException instead of returning the no-op provider.
