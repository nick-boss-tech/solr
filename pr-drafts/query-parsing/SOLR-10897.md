## What happens today

**A simple query on a point field returns no results, even when a document holds the value.**

With `defType=simple` and `qf=int_p`, where `int_p` is an `IntPointField`, the query `q=7` returns zero documents. A document with `int_p` set to 7 is in the index. Point fields index numeric point values, not analyzed terms, so a query built from analyzed terms cannot match them. The simple parser reports no error. It just finds nothing.

## What this change does

**For a point field, the simple parser now asks the field type to build the query.**

The default term path is overridden in [SimpleQParserPlugin.java](https://github.com/nick-boss-tech/solr/blob/d9240d0750faf55d21fb125668ea66db0142be79/solr/core/src/java/org/apache/solr/search/SimpleQParserPlugin.java#L184-L217). For each point field in `qf`, it calls that field type's own `getFieldQuery` with the text. Text fields keep the analyzed term query. Boosts apply the same way as before.

A value that is not a valid number for the point field is skipped for that field. It does not match, and the request does not fail. Other errors still fail the request.

Behavior change, stated openly: a non-number in `qf` on a point field produces no match and no error. In a mixed `qf` such as `text0 int_p`, the text field still matches as before.

The point field is set up in the [test schema](https://github.com/nick-boss-tech/solr/blob/d9240d0750faf55d21fb125668ea66db0142be79/solr/core/src/test-files/solr/collection1/conf/schema-simpleqpplugin.xml#L53-L56). With the new test file on the base source, the class runs 18 tests with one failure, `testPointFieldQuery`: `mismatch: '1'!='0' @ response/numFound` on the `qf=int_p` query for `7`. At head `d9240d0750f`, `TestSimpleQParserPlugin` passes 18 of 18. Verified 2026-10-05 at this head.

## A choice to check

**A non-number in a point field is skipped, not reported as an error.**

The other route is to return a 400 error when a value is not a valid number for a point field in `qf`. That is stricter, and a typo shows up at once. Its cost: a text word such as `pointdoc` would fail on the point field, so a mixed `qf` such as `text0 int_p` could never match on text alone. This branch skips the value, so the text field still matches. Was skipping the right call?

## Limits

**Prefix and fuzzy queries on point fields are not changed.**

- A prefix term on a point field, such as `7*`, still fails with a 400 error. The point field type rejects prefix queries ([PointField.java](https://github.com/apache/solr/blob/8e62c2686882aa704480ab13b6a60ee8f7b5c8af/solr/core/src/java/org/apache/solr/schema/PointField.java#L241-L247)). In a mixed `qf`, that error fails the whole request. Plan: a follow-up pull request after this one, for prefix terms on point fields.
- A fuzzy term on a point field, such as `7~1`, still matches nothing and reports no error. Plan: the same follow-up.
- Quoted phrases on point fields are not covered and not tested.
- Only `IntPointField` is tested. Other point types use the same code path, but they are not tested.
