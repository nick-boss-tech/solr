## What happens today

**Below luceneMatchVersion 10.2, a parenthesized pure-negative filter returns no document for `id:12` when `q.op=AND`.**

The ticket uses `fq=(NOT(eee_s:(Y)))` with `q=id:12`. With `q.op=OR`, the filter returns `id:12`. With `q.op=AND`, it does not. The ticket reports that the same negation without the outer parentheses returns `id:12` under both operators.

The parser's auto-fix repairs a pure negative clause. The auto-fix is on only from luceneMatchVersion 10.2 ([QParser.java lines 113 to 118](https://github.com/nick-boss-tech/solr/blob/876953fdc92714a1692615bb67685b22c3814483/solr/core/src/java/org/apache/solr/search/QParser.java#L113-L118)). Below 10.2 the nested negative is left as it is.

## What this change does

**With `q.op=AND`, a lone parenthesized pure negative leaves the parser unwrapped.**

In the `Query` production, a single required clause that is a pure negative is returned as it is ([QueryParser.jj lines 237 to 244](https://github.com/nick-boss-tech/solr/blob/876953fdc92714a1692615bb67685b22c3814483/solr/core/src/java/org/apache/solr/parser/QueryParser.jj#L237-L244)). All other queries keep the existing path. The generated [QueryParser.java](https://github.com/nick-boss-tech/solr/blob/876953fdc92714a1692615bb67685b22c3814483/solr/core/src/java/org/apache/solr/parser/QueryParser.java#L252-L259) has the same logic. The top-level `QueryUtils.makeQueryable` call then repairs the query.

Behavior change, stated openly: a caller that parses this shape and does not pass the result through `makeQueryable` now gets the raw pure negative back. At luceneMatchVersion 10.2 and later, the existing auto-fix repairs the query first, so this check does not change those results.

## Proof

**The second new test separates the base code from this change. The first one is a guard.**

- [testParenthesizedPureNegativeWithDefaultOpAnd](https://github.com/nick-boss-tech/solr/blob/876953fdc92714a1692615bb67685b22c3814483/solr/core/src/test/org/apache/solr/search/TestSolrQueryParser.java#L571-L584) passes on the base code too. At the default luceneMatchVersion the auto-fix already repairs the query, so this test guards that path. It does not show the fix.
- [testParenthesizedPureNegativeWithAutoFixDisabled](https://github.com/nick-boss-tech/solr/blob/876953fdc92714a1692615bb67685b22c3814483/solr/core/src/test/org/apache/solr/search/TestSolrQueryParser.java#L586-L616) turns the auto-fix off, as luceneMatchVersion before 10.2 does. With the auto-fix off, the base code fails the `q.op=AND` case, and this change passes it.

## A choice to check

**The fix sits at the top level, not inside the parser.**

Option 1, this branch: return the lone negative unwrapped, and let the top-level `makeQueryable` repair it. Its cost: a caller that skips `makeQueryable` gets a raw pure negative for this shape.

Option 2: apply `makeQueryable` inside the parser, as [SolrQueryParser.getBooleanQuery](https://github.com/nick-boss-tech/solr/blob/876953fdc92714a1692615bb67685b22c3814483/solr/core/src/java/org/apache/solr/search/SolrQueryParser.java#L32-L35) already does when the auto-fix is on. Its cost: the parser would repair this shape even when the auto-fix is off, so the flag would no longer decide it.

Was option 1 the right call?

## Limits

- Only the auto-fix-off path changes. At luceneMatchVersion 10.2 and later, the existing auto-fix already gives the right answer.
- Only a lone parenthesized pure negative is covered. A pure negative inside a larger query, such as `x:1 AND ((NOT y:1))`, is not changed and has no test. I can open a follow-up ticket and pull request for that case if maintainers want it.
- The ticket's own releases (6.6.2, 7.3, 8.0) were not run. The tests switch the auto-fix off instead.
- The boundary is the luceneMatchVersion check at 10.2. Values below it include all of 9.x, 10.0, and 10.1.
