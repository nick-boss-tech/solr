## What happens today

**An explicit slop in the query string is dropped when the analyzer turns the phrase into a token graph.**

With field `wdf_partspreserve`, which uses WordDelimiterGraphFilter with `preserveOriginal=1` and `generateWordParts=1`, the document "you just can't" is indexed. On the base code, the query `wdf_partspreserve:"you can't"~2` returns 0 hits. The word "just" sits between "you" and "can't", so slop 2 should match.

## What this change does

**The slop is applied to every phrase inside the query that a token graph produces, not only to a plain phrase.**

For a token graph, Lucene 9.12.3 and 10.4.0 both build a BooleanQuery of phrase queries (checked in both class files). The base code set slop only on a top-level PhraseQuery or MultiPhraseQuery. The change walks each BooleanQuery clause, applies the slop, and keeps each clause's occurrence and the minimum-should-match setting ([SolrQueryParserBase.java](https://github.com/nick-boss-tech/solr/blob/69c06da446797cec5c3c8dd885e19a28381789d3/solr/core/src/java/org/apache/solr/parser/SolrQueryParserBase.java#L563-L586)).

This is wider than the ticket. Any quoted phrase with an explicit slop whose analysis gives a BooleanQuery of phrases now uses that slop. Other token graphs, such as multi-word synonyms, may take this path too. That was not tested. Matching and ranking can change for those queries.

## Limits

**eDismax is not changed, and the new field sits in a shared test schema.**

- eDismax has its own slop path in [ExtendedDismaxQParser.java](https://github.com/nick-boss-tech/solr/blob/69c06da446797cec5c3c8dd885e19a28381789d3/solr/core/src/java/org/apache/solr/search/ExtendedDismaxQParser.java#L1067-L1074). The same graph phrase in eDismax is not changed or tested here. We can open a follow-up for it on request.
- The test adds a field type and a field to `schema12.xml`, which other test classes also load. Those classes were not run with this change.
