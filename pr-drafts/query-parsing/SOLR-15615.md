## What happens today

**An `{!mlt}` query fails with a 400 when the source document lives in another collection of the alias.**

On SolrCloud, `{!mlt qf=name mintf=2 mindf=3} <id>` against a time routed alias returns a 400 with "Error completing MLT request. Could not fetch document with id [<id>]" ([JIRA](https://issues.apache.org/jira/browse/SOLR-15615)). The same query works against one collection of the alias. The parser reads the source document only through the real-time get of its own core, so it cannot see the other collections.

## What this change does

**When the local lookup misses, the parser looks in the other collections of the request.**

- The request's `collection` parameter lists the alias-resolved collections. The parser asks each collection except its own, in list order, and uses the first document it finds ([lookup](https://github.com/nick-boss-tech/solr/blob/be77267bf5549ae6bdc91bc4122b5bf5256f41e1/solr/core/src/java/org/apache/solr/search/mlt/CloudMLTQParser.java#L118-L152)).
- A request that resolves to its own core's collection makes no extra lookups.
- A failed lookup in one collection is logged and skipped. If no collection has the document, the same 400 is returned as before.
- If the same id exists in several collections, the first one in list order wins.

## Proof

**One test class. The new test fails on the base code and passes with this change.**

- `CloudMLTQParserTest` 15/15 at `be77267bf55`, verified 2026-10-07. The new test `testMLTQParserOnAliasOverMultipleCollections` ([test](https://github.com/nick-boss-tech/solr/blob/be77267bf5549ae6bdc91bc4122b5bf5256f41e1/solr/core/src/test/org/apache/solr/search/mlt/CloudMLTQParserTest.java#L166-L211)) puts the source document in a second collection only. It sends the request to a core of the first collection, so the local lookup misses on every run.
- On the base code, the new test is the one failing test in the class.

## A choice to check

**The fallback asks the collections one at a time.** Finding a document costs one request per collection checked before it. A document that exists nowhere costs one request per other collection before the 400 comes back.

Options considered: walk the collections one at a time (implemented), run the lookups in parallel, or keep the lookup local and document that the source must sit in the handling collection. The walk keeps the request count low when the document is early in the list. Parallel lookups cut latency on long aliases but send more requests at once. A local lookup leaves the reported failure in place.

Was the one-at-a-time walk the right call for this fix?

## Limits

**Only the query parser changes. The cost is not measured on long aliases.**

- The MLT request handler and the non-parser MLT results described in the ticket are not changed. I can open a follow-up ticket and PR for that on request.
- The test covers two collections. The cost on aliases with many collections is not measured. I can measure it and add a bound on request.
