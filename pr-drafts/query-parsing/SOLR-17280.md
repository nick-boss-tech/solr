## What happens today

**A range query can fail with "IllegalStateException: Recursive update" during a facet query count.**

A `SolrRangeQuery` that matches more than 16 terms in a segment builds its DocSet itself. It then puts that DocSet into the filter cache. The ticket stack trace shows this put happening while the same cache is still computing the entry for an enclosing query. The facet query count (`facet.query`) is the enclosing computation. The cache rejects the nested update with `IllegalStateException: Recursive update`. See [SOLR-17280](https://issues.apache.org/jira/browse/SOLR-17280).

## What this change does

**The range query no longer puts its DocSet in the filter cache from inside its weight.**

The `put` is removed at [SolrRangeQuery.java L482-L489](https://github.com/nick-boss-tech/solr/blob/40817c5cb7ec96b6f4119a46bec3db8ae6a1f6de/solr/core/src/java/org/apache/solr/query/SolrRangeQuery.java#L482-L489). A range query used directly as a filter is still cached by the searcher, unless it has `cache=false`. A range query that is not a filter, such as a clause of `q` or of a larger query, no longer gets a cache entry of its own as a side effect. Each run of that query builds its DocSet again.

## A choice to check

**Remove the nested `put`, or let the cache handle recursive computation.**

Options considered:

1. Remove the `put` in `SolrRangeQuery`. This is the change here. A nested range query gets no cache entry of its own, so repeated runs rebuild its DocSet.
2. Keep the `put`. Detect a recursive call at runtime, and use a get then put only when that happens. This is the approach in [apache/solr PR 1481](https://github.com/apache/solr/pull/1481), which the ticket discussion favors. That PR was closed without merging. It keeps the cache entries, but it changes shared cache code.

Was removing the `put` the right call, or should the cache handle recursive computation?

## Proof

**A new test in `TestFiltering` checks that a nested range query is not put in the filter cache.**

- `TestFiltering` passes 5 of 5 in the focused run at head `40817c5cb7ec96b6f4119a46bec3db8ae6a1f6de`. The focused run covers the whole class.
- On the base code the same run has one failure, the new test `testNestedRangeQueryNotPutInFilterCache`. See [TestFiltering.java L109-L137](https://github.com/nick-boss-tech/solr/blob/40817c5cb7ec96b6f4119a46bec3db8ae6a1f6de/solr/core/src/test/org/apache/solr/search/TestFiltering.java#L109-L137).
- Verified 2026-10-07.

The test checks the cache entry. It does not reproduce the `Recursive update` exception, which needs a particular hash bin collision.

## Limits

**The cache itself is not changed, and the exception is not reproduced directly.**

A maintainer comment on this ticket says it is the same issue as [SOLR-16707](https://issues.apache.org/jira/browse/SOLR-16707). A cache level fix would cover both tickets. If the maintainers prefer that route, we can open a follow-up for it.
