## What happens today

**On a core below luceneMatchVersion 10.2.0, a pure negative traversalFilter stops the graph walk at the starting documents.**

The report uses `traversalFilter="-bogus_field_s:1"`. The walk returns only the start document, although the graph has edges from it. The same filter written as `traversalFilter="*:* -bogus_field_s:1"` walks the graph. The query parser repairs a pure negative query only when the core's luceneMatchVersion is 10.2.0 or later ([QParser.java](https://github.com/nick-boss-tech/solr/blob/395b24964fd05f2908c0340ef79c1ee4273775a8/solr/core/src/java/org/apache/solr/search/QParser.java#L114-L115)). The graph query adds the traversal filter as a MUST clause on each hop ([GraphQuery.java](https://github.com/nick-boss-tech/solr/blob/395b24964fd05f2908c0340ef79c1ee4273775a8/solr/core/src/java/org/apache/solr/search/join/GraphQuery.java#L227-L228)), so a filter that matches nothing ends the walk.

## What this change does

**The graph parser makes its traversal filter queryable itself.**

[GraphQueryParser.java](https://github.com/nick-boss-tech/solr/blob/395b24964fd05f2908c0340ef79c1ee4273775a8/solr/core/src/java/org/apache/solr/search/join/GraphQueryParser.java#L45-L48) calls `QueryUtils.makeQueryable` on the traversal filter. A pure negative filter gets a `*:*` clause. Filters that are not pure negative are not changed. On cores at 10.2.0 or later the query parser has already added that clause, so nothing changes there.

Behavior change, stated openly: on cores below 10.2.0, a pure negative traversal filter now walks the graph. Before, it stopped at the starting documents.

## Proof

**The new test fails on the base code and passes with this change.**

- `GraphQueryTest.testGraphNegativeTraversalFilterWithoutAutoFix` ([test](https://github.com/nick-boss-tech/solr/blob/395b24964fd05f2908c0340ef79c1ee4273775a8/solr/core/src/test/org/apache/solr/search/join/GraphQueryTest.java#L157-L188)) turns the query parser's auto-fix off for the sub-query. That stands in for a core below 10.2.0. On the base code it fails with `expected:<2> but was:<1>`. With this change it passes.
- The assertion added to `doGraph` runs with the auto-fix on, so it also passes on the base code. It guards the normal path. It does not prove the fix.
- Verified 2026-10-05 at head `395b24964fd`, one line per class: `GraphQueryTest` 3 of 3; `TestScoreJoinQPScore` 13 (one skipped); `TestScoreJoinQPNoScore` 4 of 4; `BJQParserTest` 18 of 18. Total 38.

## A choice to check

**Options: the graph parser repairs its traversal filter on every core (implemented), or it leaves the repair to the query parser and documents a `*:*` workaround for cores below 10.2.0.**

The implemented route changes results on older cores. A pure negative traversal filter that used to stop at the starting documents now walks the graph. A `*:*` workaround gives the same results as before. Was it right to change results on those cores, rather than document the workaround?

## Limits

**This targets main, and the root query has the same gap.**

- The 9.x line and the 10.0 line have no repair in the query parser for any luceneMatchVersion. A pure negative traversal filter is not fixed on those lines. This change does not backport it.
- A pure negative root query (the `v` parameter) has the same gap on cores below 10.2.0. The graph parser does not repair the root ([GraphQueryParser.java](https://github.com/nick-boss-tech/solr/blob/395b24964fd05f2908c0340ef79c1ee4273775a8/solr/core/src/java/org/apache/solr/search/join/GraphQueryParser.java#L41)). This change does not touch it. A follow-up PR can cover it if maintainers want it.
- The new test sets the auto-fix flag by hand. It does not load a real core with an older luceneMatchVersion.
