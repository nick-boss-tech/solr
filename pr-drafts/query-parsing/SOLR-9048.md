## What happens today

**A block join parser fails with a NullPointerException when its nested query has no terms after analysis.**

The report uses `{!child of=inStock:true}{!field f=title_en v='and'}`, where "and" is a stop word for that field. The nested field query produces no query. `FiltersQParser` passes that empty result into a `BooleanQuery` builder, and the builder rejects it. The request fails with a NullPointerException. The same failure happens with `{!parent which=inStock:true}{!field f=title_en v='and'}`. The ticket asks what the right result is.

## What this change does

**An empty nested query adds no clause, so the block join parsers apply no constraint.**

`FiltersQParser` skips a sub-query that produces no query ([FiltersQParser.java L62-L67](https://github.com/nick-boss-tech/solr/blob/b145018563cbc2ddd29e43a0fa8619545415b8c6/solr/core/src/java/org/apache/solr/search/join/FiltersQParser.java#L62-L67)). The block join parsers already read a query with no clauses as "no constraint" ([BlockJoinParentQParser.java L283-L284](https://github.com/nick-boss-tech/solr/blob/b145018563cbc2ddd29e43a0fa8619545415b8c6/solr/core/src/java/org/apache/solr/search/join/BlockJoinParentQParser.java#L283-L284)). `{!parent}` then returns all parents, and `{!child}` returns all children outside the parents. An empty `v` takes the same path today.

Behavior change, stated openly: the same skip applies to the `{!filters}` parser, which uses `FiltersQParser` directly. Before, an empty clause there hit the same NullPointerException. Now the clause is dropped.

## Proof

**A new test fails on the base code and passes with this change.**

- `BJQParserTest.testSubQueryWithoutAnyTermsAfterAnalysis` ([test](https://github.com/nick-boss-tech/solr/blob/b145018563cbc2ddd29e43a0fa8619545415b8c6/solr/core/src/test/org/apache/solr/search/join/BJQParserTest.java#L169-L185)) runs `{!parent}` and `{!child}` over a nested query that analysis empties. On the base code it fails with a NullPointerException ("Query must not be null"). With this change it passes.
- Verified 2026-10-05 at head `b145018563c`, one line per class: `BJQParserTest` 19 of 19; `BlockJoinNestedVectorsQParserTest` 17 of 17; `TestMmBoolQParserPlugin` 10 of 10; `TestFiltersQueryCaching` 2 of 2. Total 48 of 48.

## A choice to check

**Options: an all-stopword nested query matches everything, as an empty `v` does (implemented), or it matches nothing.**

Matching everything reuses the existing meaning of "no clauses". The cost is that `v=and` quietly matches every parent or every child. Matching nothing would be the stricter result, and a maintainer could reasonably want it. Was matching everything the right call?

## Limits

**The fix covers the `v` form. The `which` and `of` forms are not covered, and `{!filters}` has no test.**

- A stop-word-only `which` or `of` filter is not covered here and is not tested. Both pass their query straight to the parent filter ([BlockJoinParentQParser.java L293](https://github.com/nick-boss-tech/solr/blob/b145018563cbc2ddd29e43a0fa8619545415b8c6/solr/core/src/java/org/apache/solr/search/join/BlockJoinParentQParser.java#L293)). The plan is a separate follow-up PR for those two forms, submitted after this one is reviewed.
- The `{!filters}` parser now drops an empty clause too. No test in this change covers it.
