## What happens today

**A follower's leader URL can carry a password, and the follower's details response shows it in full.**

A follower can be configured with a `leaderUrl` that holds basic-auth credentials, such as `http://user:password@host:8983/solr/core`. The replication details response returns that value as configured ([ReplicationHandler.java](https://github.com/nick-boss-tech/solr/blob/e4f5e941cd8e88524196b03f2022261c2215c3ba/solr/core/src/java/org/apache/solr/handler/ReplicationHandler.java#L1041)). The ticket reports the password on the Replication tab of the admin UI. `IndexFetcher` also prints the same URL in an "Updated leaderUrl" log line and in the "Malformed 'leaderUrl'" and "is not allowed" errors ([IndexFetcher.java](https://github.com/nick-boss-tech/solr/blob/e4f5e941cd8e88524196b03f2022261c2215c3ba/solr/core/src/java/org/apache/solr/handler/IndexFetcher.java#L306-L336)).

## What this change does

**The details response and three messages show `********` in place of the password.**

A new helper, `URLUtil.redactUserInfo`, replaces the password ([URLUtil.java](https://github.com/nick-boss-tech/solr/blob/e4f5e941cd8e88524196b03f2022261c2215c3ba/solr/solrj/src/java/org/apache/solr/common/util/URLUtil.java#L121-L136)). It is applied to the details response, to the "Updated leaderUrl" line ([IndexFetcher.java](https://github.com/nick-boss-tech/solr/blob/e4f5e941cd8e88524196b03f2022261c2215c3ba/solr/core/src/java/org/apache/solr/handler/IndexFetcher.java#L486-L489)), and to the malformed and not-allowed errors. The follower still connects with the URL as configured.

Cross-area effect: the helper lives in the SolrJ module. It adds one public static method to `org.apache.solr.common.util.URLUtil`, and no existing method changes. No SolrJ class in this repository reads the follower `leaderUrl` from the details response, so SolrJ behavior does not change. A client that reads that field and reuses it to connect will get the masked value for a URL with credentials.

## Proof

**The redaction test fails on the base code and passes with this change.**

`IndexFetcherLeaderUrlRedactionTest` 2 of 2 at head `e4f5e941cd8`, verified 2026-10-07 ([test](https://github.com/nick-boss-tech/solr/blob/e4f5e941cd8e88524196b03f2022261c2215c3ba/solr/core/src/test/org/apache/solr/handler/IndexFetcherLeaderUrlRedactionTest.java#L60-L92)). Both tests fail on the base code, where the password is visible in both messages. Both pass with this change.

`URLUtilTest` 18 of 18 passes. Three of those tests call the new helper, so they do not apply to the base code. `TestUserManagedReplicationWithAuth` 3 of 3 passes. Its new case reads the details response of a follower with credentials and checks that the password is absent ([test](https://github.com/nick-boss-tech/solr/blob/e4f5e941cd8e88524196b03f2022261c2215c3ba/solr/core/src/test/org/apache/solr/handler/TestUserManagedReplicationWithAuth.java#L188-L221)).

## Limits

**Two warnings and the client's error text can still show the leader URL.**

- The "Leader at ... is not available" warnings print the leader URL as configured ([IndexFetcher.java](https://github.com/nick-boss-tech/solr/blob/e4f5e941cd8e88524196b03f2022261c2215c3ba/solr/core/src/java/org/apache/solr/handler/IndexFetcher.java#L501-L510)). The HTTP client's connection and timeout errors can carry the same URL, and those errors are printed in these warnings. This change does not cover them.
- The helper looks for user-info only after `://`, so a value with no scheme comes back unchanged. A URL whose password has a raw `/` or `?` also comes back unchanged, because that character ends the user-info for the helper. A unit test checks that case ([test](https://github.com/nick-boss-tech/solr/blob/e4f5e941cd8e88524196b03f2022261c2215c3ba/solr/solrj/src/test/org/apache/solr/common/util/URLUtilTest.java#L143-L160)).
- If you want these warnings and client errors covered too, a follow-up ticket and pull request can add that.
