## What happens today

**After a standalone core restore, the update log still holds updates made before the restore.**

A standalone restore (replication handler `command=restore`) replaces the index, but the update log keeps the updates logged before it. Realtime get can then return a document that is not in the restored index, and a restart replays the logged updates on top of the restored index. SOLR-17287 reports this, with a test where a realtime get returns a document added after the backup.

## What this change does

**A successful standalone restore now clears the update log.**

After the index switch and the cleanup of old index files, a standalone core clears the update log ([RestoreCore.java lines 250-255](https://github.com/nick-boss-tech/solr/blob/6957daf82610d6f09c533297cceec173a46e82a7/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L250-L255)). The clear drops the current, previous and older transaction logs, the buffered log and the lookup maps, and leaves the log active ([UpdateLog.java lines 2037-2072](https://github.com/nick-boss-tech/solr/blob/6957daf82610d6f09c533297cceec173a46e82a7/solr/core/src/java/org/apache/solr/update/UpdateLog.java#L2037-L2072)). A log file that a reader still holds stays on disk until the reader releases it, and is deleted then.

This also touches [UpdateLog.java](https://github.com/nick-boss-tech/solr/blob/6957daf82610d6f09c533297cceec173a46e82a7/solr/core/src/java/org/apache/solr/update/UpdateLog.java), so the change is cross-filed under Update processing and atomic updates. It adds two methods, the public `clearAndActivate` and the private helper `discardLog`, and changes no existing method. The public method has one caller, this restore path.

## Proof

**`TestRestoreCore.testRestoreClearsUpdateLog` fails on the base code and passes with this change.**

The [test](https://github.com/nick-boss-tech/solr/blob/6957daf82610d6f09c533297cceec173a46e82a7/solr/core/src/test/org/apache/solr/handler/TestRestoreCore.java#L173-L253) adds a document after the backup without committing it, then restores. On the base code the document is still returned by realtime get after the restore, and the test fails at its check that the update log was cleared. The test also restarts the core and checks that the document is not replayed.

[`UpdateLogTest.testClearAndActivateKeepsReferencedLogsAlive`](https://github.com/nick-boss-tech/solr/blob/6957daf82610d6f09c533297cceec173a46e82a7/solr/core/src/test/org/apache/solr/update/UpdateLogTest.java#L244-L277) tests the new method, so it cannot fail on the base code. It is a new-API test. It checks that a log file a reader still references stays on disk until the reader releases it.

## A choice to check

**Should SolrCloud restores clear the update log too? This change clears it for standalone cores only.**

Two routes were considered. The first route is this change. The second also clears it on SolrCloud restores. SolrCloud already leaves the log buffered, and the caller applies the buffered updates once the restore completes, so this change leaves that path alone. Was leaving SolrCloud unchanged the right call?

## Limits

**SolrCloud is not covered, a failed cleanup after the switch skips the clear, and concurrent updates are untested.**

- The clear runs after the cleanup of old index files. If that cleanup throws after the switch, the clear is skipped.
- No concurrency test was run for updates that arrive during the clear.
