## What happens today

**Each file stream gets its own throttle, so N replicas at one rate can use N times that rate.**

The file endpoint reads `maxWriteMBPerSec` from each request. The base code then builds a new rate limiter for every file stream at that rate ([ReplicationAPIBase.java at the base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/admin/api/ReplicationAPIBase.java#L308-L313)). When several replicas recover at the same time, each one gets the full rate. The ticket describes the same gap: the limit applies per request, not per node.

## What this change does

**File streams that ask for the same rate now share one limiter on the node, for up to 64 distinct rate values.**

The change keeps one shared limiter for each rate value, up to 64 distinct values ([ReplicationAPIBase.java](https://github.com/nick-boss-tech/solr/blob/0d64c35c5a7d3caffa9981fd1e1a61e1d818edf5/solr/core/src/java/org/apache/solr/handler/admin/api/ReplicationAPIBase.java#L98-L119)). A rate of 0 still means no throttle, and unthrottled streams share one unlimited limiter until the map is full. The request parameter and the response are unchanged. Concurrent transfers at the same rate now share that rate, so each transfer can be slower when several run together. Streams at different rates keep separate limiters. The map holds at most 64 rate values, so a client cannot grow it without limit.

## Proof

**The new test calls a helper that the base code does not have, so it does not compile on the base code.**

`ReplicationRateLimiterTest` 4/4 at `0d64c35c5a7d3caffa9981fd1e1a61e1d818edf5`, verified 2026-10-12. The tests check that two streams at the same rate get one limiter, that different rates get different limiters, that rate 0 gives an unlimited limiter, and that rates past the cap of 64 get their own limiter. On the pre-cap code at `49af21be58927a62b50bd7ba1df1688110fba63e`, with the new test kept and a test-only hook added, the cap test fails at its cap assertion. The base-code leg is a compile failure, so it is inconclusive by construction. A separate behavior check, not included in this change, ran one test against the base code and passed at `49af21be58927a62b50bd7ba1df1688110fba63e` on 2026-10-07. It failed on "two concurrent streams at the same configured rate must share one throttle." It has not been run at the gated head.

## A choice to check

**One limiter per rate value, or one limiter for the whole node?**

The ticket asks for a limit per node. This change keeps one limiter per rate value, up to 64 distinct values. That never overrides a rate that a replica asked for, but streams at different rates are not capped together. The other option is one limiter for the whole node, with its rate taken from the lowest request. That caps the node total, but a replica that asked for a higher rate gets a lower one. Was one limiter per rate value the right call, or should the whole node share one limiter?

## Limits

**Streams at different rates are not capped together, and transfer speed is not measured.**

- Past 64 distinct rate values, a new stream gets its own limiter and is not shared.
- No test measures transfer speed during a real replication.
- The follower side and the index fetch path are not changed.
