## What happens today

**Each file stream gets its own throttle, so N replicas at one rate can use N times that rate.**

The file endpoint reads `maxWriteMBPerSec` from each request. The base code then builds a new rate limiter for every file stream at that rate ([ReplicationAPIBase.java](https://github.com/apache/solr/blob/8e62c2686882aa704480ab13b6a60ee8f7b5c8af/solr/core/src/java/org/apache/solr/handler/admin/api/ReplicationAPIBase.java#L308-L313)). When several replicas recover at the same time, each one gets the full rate. The ticket describes the same gap: the limit applies per request, not per node.

## What this change does

**File streams that ask for the same rate now share one limiter on the node.**

The change keeps one shared limiter for each rate value ([ReplicationAPIBase.java](https://github.com/nick-boss-tech/solr/blob/49af21be58927a62b50bd7ba1df1688110fba63e/solr/core/src/java/org/apache/solr/handler/admin/api/ReplicationAPIBase.java#L98-L110)). A rate of 0 still means no throttle, and unthrottled streams share one unlimited limiter. The request parameter and the response are unchanged. Concurrent transfers at the same rate now share that rate, so each transfer can be slower when several run together. Streams at different rates keep separate limiters.

## Proof

**The new test calls a helper that the base code does not have, so it does not compile on the base code.**

`ReplicationRateLimiterTest` 3/3 at `49af21be58927a62b50bd7ba1df1688110fba63e`, verified 2026-10-07. The tests check that two streams at the same rate get one limiter, that different rates get different limiters, and that rate 0 gives an unlimited limiter. On the base code the test fails to compile, because `rateLimiterFor` is added by this change. This is a new-API check, so it is inconclusive by construction. A separate behavior check, not included in this change, ran one test against the base code. It failed on "two concurrent streams at the same configured rate must share one throttle" and passed at this head.

## A choice to check

**One limiter per rate value, or one limiter for the whole node?**

The ticket asks for a limit per node. This change keeps one limiter per rate value. That never overrides a rate that a replica asked for, but streams at different rates are not capped together. The other option is one limiter for the whole node, with its rate taken from the lowest request. That caps the node total, but a replica that asked for a higher rate gets a lower one. Was one limiter per rate value the right call, or should the whole node share one limiter?

## Limits

**Streams at different rates are not capped together, and transfer speed is not measured.**

- Limiters stay in memory for the life of the node, one for each rate value that a request has used.
- No test measures transfer speed during a real replication.
- The follower side and the index fetch path are not changed.
