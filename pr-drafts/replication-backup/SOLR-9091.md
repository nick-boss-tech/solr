## What happens today

**On the restore path, a file copied from the backup is not checked, and a failed checksum read counts as no checksum.**

On the merge-base commit, a file the restore copies from the backup goes into the restore directory with no check ([RestoreCore.java](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L169-L175)). A corrupt backup file is accepted, and the restore switches the index to it. When the backup-side checksum read fails, the error is logged and no checksum is returned, and the restore goes on ([RestoreCore.java](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L316-L327)).

## What this change does

**Each file copied from the backup is read in full and checked against the checksum in its own footer.**

The check is `CodecUtil.checksumEntireFile` in `verifyRestoredFile` ([RestoreCore.java](https://github.com/nick-boss-tech/solr/blob/e6bfa5c626812f1452ed8c0158697ab8653a40d2/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L104-L108)). It runs after both copy paths that use the backup, at lines 180 and 187 ([RestoreCore.java](https://github.com/nick-boss-tech/solr/blob/e6bfa5c626812f1452ed8c0158697ab8653a40d2/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L180-L187)). A mismatch throws, so the restore fails before the index is switched, and the live index stays in place.

This is a behavior change: each copied file is read once more in full, so a restore takes longer.

## Proof

**The new test fails on the base code and passes with this change.**

`TestRestoreCore` passes 4 of 4 at head `e6bfa5c626812f1452ed8c0158697ab8653a40d2`, verified 2026-10-10, with no failures, errors or skips. The new test flips one byte in the largest file of a backup and expects the restore to be reported as failed ([TestRestoreCore.java](https://github.com/nick-boss-tech/solr/blob/e6bfa5c626812f1452ed8c0158697ab8653a40d2/solr/core/src/test/org/apache/solr/handler/TestRestoreCore.java#L234-L297)). On the base `RestoreCore.java`, with the new test kept, it fails with "Expected exception AssertionError but no exception was thrown" at [line 284](https://github.com/nick-boss-tech/solr/blob/e6bfa5c626812f1452ed8c0158697ab8653a40d2/solr/core/src/test/org/apache/solr/handler/TestRestoreCore.java#L284). With this change it passes.

## Limits

**The check covers only files copied from the backup. The backup-side checksum read is not changed.**

- Files the restore takes from the live index are not read again.
- The check uses each file's own footer. It does not compare a file with a checksum recorded in the backup, and the backup-side read still logs and returns no checksum ([RestoreCore.java](https://github.com/nick-boss-tech/solr/blob/e6bfa5c626812f1452ed8c0158697ab8653a40d2/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L335-L338)). We can open a follow-up ticket and pull request for that on request.
- The test damages one file in one backup.
