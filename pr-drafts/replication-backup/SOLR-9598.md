## What happens today

**RESTORE returns before the restored collection is ready to use.**

RESTORE creates the new collection, requests its replicas, and sets the alias, without waiting for those replicas to become active ([RestoreCmd.java](https://github.com/apache/solr/blob/8e62c2686882aa704480ab13b6a60ee8f7b5c8af/solr/core/src/java/org/apache/solr/cloud/api/collections/RestoreCmd.java#L301-L306)). Until recovery finishes, the collection may not be ready for queries or updates. The ticket asks for this check inside RESTORE, so clients do not have to make it.

## What this change does

**RESTORE waits, by default, until every replica of the restored collection is active.**

After it requests the replicas, RESTORE waits until every replica of every shard is active, and only then sets the alias ([RestoreCmd.java](https://github.com/nick-boss-tech/solr/blob/c8407773f76ca49711b5777ff9f69736d87b1e90/solr/core/src/java/org/apache/solr/cloud/api/collections/RestoreCmd.java#L308-L348)). The wait uses the same 10 minute default as ADDREPLICA. On timeout, RESTORE returns a server error that names the collection. The request option `waitForFinalState=false` skips the wait ([RestoreCollectionRequestBody.java](https://github.com/nick-boss-tech/solr/blob/c8407773f76ca49711b5777ff9f69736d87b1e90/solr/api/src/java/org/apache/solr/client/api/model/RestoreCollectionRequestBody.java#L41-L45)). This changes the default for existing RESTORE calls, which can now take longer or fail with the timeout error.

## Proof

**The new check is timing-dependent, so the base failure is not deterministic.**

The shared backup test case now checks that every replica is active as soon as RESTORE returns ([AbstractCloudBackupRestoreTestCase.java](https://github.com/nick-boss-tech/solr/blob/c8407773f76ca49711b5777ff9f69736d87b1e90/solr/test-framework/src/java/org/apache/solr/cloud/api/collections/AbstractCloudBackupRestoreTestCase.java#L378-L390)). On the base code that check failed in one of five runs of `TestLocalFSCloudBackupRestore`, and four runs passed. The result depends on timing, so the base failure is not deterministic, and this proof does not claim one.

At `c8407773f76ca49711b5777ff9f69736d87b1e90`, run finished 2026-10-05: `TestLocalFSCloudBackupRestore` 2/2, `RestoreCollectionAPITest` 7/7, `BackupRestoreApiErrorConditionsTest` 4/4. `TestLocalFSCloudBackupRestore` passed three times at this head, including the randomized setup that failed on the base code.

## A choice to check

**Should RESTORE wait by default with an opt-out, or always wait, as SOLR-17712 moves other commands?**

(1) Wait by default, and let `waitForFinalState=false` opt out. This change does that. (2) Always wait, with no opt-out. SOLR-17712 moves commands that take `waitForFinalState` toward this, and deprecates the option on CREATE for that reason. (3) Do not wait by default, as CREATE does today. Existing callers see no change, but the gap stays for callers that do not opt in. This change takes option 1. Was a default wait with an opt-out the right call, or should RESTORE follow option 2 ([SOLR-17712](https://issues.apache.org/jira/browse/SOLR-17712))?

## Limits

**A timed-out RESTORE leaves the restored collection in place, without its alias.**

- Cleanup after a failed RESTORE is not changed here. Restore cleanup is a separate question ([SOLR-12651](https://issues.apache.org/jira/browse/SOLR-12651)).
- If a replica cannot become active, the wait runs to the timeout.
- Other commands keep their own defaults.
