## What happens today

**A failed restore can leave the core on the wrong index directory.**

A standalone restore writes a new index.properties that points at a `restore.<timestamp>` directory, then opens that index. If opening the restored index fails, the rollback deletes index.properties. Without that file, the core falls back to the default `index` directory, not to the directory it was using before the restore. After one successful restore, a failed second restore therefore brings back an older directory. SOLR-9865 gives the case: with directories `index`, `index.timestamp1` and `index.timestamp2`, deleting the file "would roll you back to index instead of index.timestamp1".

## What this change does

**The rollback writes back the directory that index.properties named before the restore.**

RestoreCore records the directory name before the switch ([RestoreCore.java line 210](https://github.com/nick-boss-tech/solr/blob/4937608bb181efae104c0d6f0257f445af50bf52/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L210)). On a failed switch it deletes index.properties only when the previous directory is the default `index` ([lines 232-233](https://github.com/nick-boss-tech/solr/blob/4937608bb181efae104c0d6f0257f445af50bf52/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L232-L233)). Otherwise it writes the previous directory name back ([line 235](https://github.com/nick-boss-tech/solr/blob/4937608bb181efae104c0d6f0257f445af50bf52/solr/core/src/java/org/apache/solr/handler/RestoreCore.java#L235)). A successful restore is unchanged, and so is a restore that fails before the switch.

## Proof

**`TestRestoreCore.testFailedRestoreAfterSuccessfulRestoreKeepsCurrentIndex` fails on the base code and passes with this change.**

The [test](https://github.com/nick-boss-tech/solr/blob/4937608bb181efae104c0d6f0257f445af50bf52/solr/core/src/test/org/apache/solr/handler/TestRestoreCore.java#L182-L243) runs a restore that succeeds, then a second restore whose backup is missing a segments file, so the second restore fails and rolls back. The test then checks that the core still serves the documents from the first restore.

A first version of the test had no reload step, and it passed on the base code too, so it did not show the bug. The test now reloads the core before the final check, so that check reads index.properties on a fresh open. No assertion changed. With the reload, the base code fails the final check (expected 70 documents, found 0), and this change passes it.

## A choice to check

**Should the rollback write back the previous directory name? This change writes it back.**

Two routes were considered. The first route is this change. The second picks the newest index directory on disk when index.properties is missing, as the ticket suggests. The second changes how every core without index.properties starts, and it needs a rule for choosing the newest directory. This change takes the narrower route. Was writing back the previous name the right call?

## Limits

**The SolrCloud restore gets the same rollback without a test, and a restore that fails during the copy is not changed.**

- The SolrCloud restore calls the same method.
- The rollback stores the last path element of the previous index directory. index.properties already names directories inside the data directory, so this is the only form it can hold.
- A restore that fails while it copies files never reaches the switch, and is not changed.
