## What happens today

**A UUID field accepts a 36-character value that has non-hex characters.**

The check in `UUIDField.toInternal` tests only the length and the dashes at positions 8, 13, 18 and 23 ([lines 79 to 85 at the base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/schema/UUIDField.java#L79-L85)). A value such as `zzzzzzzz-zzzz-zzzz-zzzz-zzzzzzzzzzzz` passes and is indexed as given.

The ticket title reports a 500 for a short value. That no longer happens at the base commit. `FieldType.createField` rethrows a `SolrException` unchanged ([lines 306 to 307 at the base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/schema/FieldType.java#L306-L307)), so the 400 from the length check reaches the client.

## What this change does

**A 36-character value with a non-hex character now gets a 400 error.**

The check now tests each character. The four UUID positions must be dashes, and every other position must be a hex digit, in either case ([lines 89 to 104 at the head](https://github.com/nick-boss-tech/solr/blob/fd495167cd096334434dbb602d7bbefcf212a5d5/solr/core/src/java/org/apache/solr/schema/UUIDField.java#L89-L104)). Full-width digits, such as U+FF14, are rejected even though Java counts them as digits.

Behavior changes wider than writes:
- Term and range queries use the same check. A query with such a value now gets a 400 error. It used to look for that exact value.
- Writes that the base accepted now fail, so re-indexing documents that hold such values will fail.

## Proof

**The new test fails on the base code and passes with this change.**

Verified 2026-10-09 at head fd495167cd0:
- On the base code, with this branch's test in place, `UUIDFieldTest` runs 3 tests with 1 failure, `testNonHexCharactersAreRejected`. The base accepts the first bad value, so the expected exception never comes.
- With this change, `UUIDFieldTest` runs 3 of 3 and passes.

## A choice to check

**The rule applies to queries as well as writes.**

The options are to reject non-hex values on every path, which this change does, or to reject them only on writes. The second keeps queries as they were, with no new 400 errors for them. Was it right to apply the rule to queries too?
