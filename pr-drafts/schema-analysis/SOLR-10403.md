## What happens today

**A currency conversion cuts off the fraction instead of rounding it.**

`CurrencyValue.convertAmount` multiplies by the exchange rate, shifts the decimal point by repeated multiplication by 0.1 or 10, and casts the result to `long`, which drops the fraction ([lines 137 to 152 at the base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/schema/CurrencyValue.java#L137-L152)). For 2554.55 in a 2-digit currency converted to a 0-digit currency, the result is 2554, not 2555. The ticket reports a conversion that comes out low.

## What this change does

**Conversions round to the nearest minor unit.**

The shift is now one division or multiplication by an exact power of ten, and the result goes through `Math.round` ([lines 140 to 146 at the head](https://github.com/nick-boss-tech/solr/blob/d8e03755cb5d3d8bc990cdb49a6bc1d11ac8583c/solr/core/src/java/org/apache/solr/schema/CurrencyValue.java#L140-L146)).

Behavior changes wider than the ticket:
- Stored amounts do not change. Index-time code keeps the amount as entered ([CurrencyFieldType.java line 182 at the base commit](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/schema/CurrencyFieldType.java#L182)).
- Conversions run at query time, in range queries, sorting, function queries and range facets. Their results can move by one minor unit.
- A tie rounds up, toward positive infinity.

## Proof

**The new test fails on the base code and passes with this change.**

Verified 2026-10-09 at head d8e03755cb5:
- On the base code, with this branch's test in place, `CurrencyFieldTypeTest` runs 45 tests with 21 skipped and 3 failures. The class runs each test once per exchange-rate provider, and the 3 failures are the 3 variants of `testConvertAmountRoundsInsteadOfTruncating`, each expecting 2555 and getting 2554.
- With this change, `CurrencyFieldTypeTest` runs 45 tests with 21 skipped and 0 failures. The skipped tests depend on the machine's locale.

The same test also checks a second case: 2555 units of a 0-digit currency, at 1116.071429 per USD, should come to 229 cents. The base run stops at the first failing assertion, so that case is not shown on the base code.

## A choice to check

**Ties round up.**

The options are to round ties up, which `Math.round` does and this change uses, or to round ties to the even digit, a common rule for money. The two differ only on an exact half, such as 2554.5. No test in this change covers an exact half. Was rounding ties up the right rule?

## Limits

**The ticket's wider point is not addressed.**

The ticket says precision should apply only at the end of a calculation. This change rounds each conversion. It does not change how a calculation with several steps is staged, and no test sums converted values. The query paths are read from the code and not run.
