## What happens today

**A docValues setting on a CurrencyFieldType sub-field is ignored.**

CurrencyFieldType writes its amount and currency code sub-fields with the single value `createField` call. That call never returns docValues. A sub-field type configured with `docValues="true"` therefore gets an indexed field without docValues, so a sort on that sub-field cannot use docValues.

## What this change does

**The amount and currency code sub-fields are built with `createFields`, so their docValues are written.**

Both calls switch to `createFields` ([CurrencyFieldType.java L182-L184](https://github.com/nick-boss-tech/solr/blob/cbb345f2e7df452e20036d357c82cc63db96ffd3/solr/core/src/java/org/apache/solr/schema/CurrencyFieldType.java#L182-L184)). A sub-field without docValues produces the same field as before. Documents indexed before this change have no docValues for these sub-fields until they are reindexed.

With the default docValues as stored setting (schema version 1.6 and later), a docValues field that is not stored can be returned as a stored value. So `fl=*` searches and real-time gets can now return these sub-fields for currency documents.

Both failures are the missing sub-field docValues this change adds.

CurrencyFieldTypeTest reported no failures on that tree as well (42 tests, 21 skipped by its currency locale assumption, 0 failures), in the same run at head `cbb345f2e7df452e20036d357c82cc63db96ffd3`, recorded 2026-10-12.

## A choice to check

**Sub-fields with docValues are returned as stored values by default on schema version 1.6 and later.**

Options considered: (a) keep the default, so these sub-fields follow the rule for any docValues field and can appear in `fl=*` results; (b) turn off docValues as stored for the sub-field types, so `fl=*` does not return them by default, at the cost of extra configuration on each type. Should these sub-fields follow the default, or be hidden by default?

## Limits

**Real-time get and `fl=*` output for currency documents are not tested.**
- No test checks real-time get or `fl=*` output with these sub-fields. SOLR-15357 changes copyField target checks, not the docValues path, so this change alone decides what those requests return.
- Documents indexed before this change have no sub-field docValues until they are reindexed. The changelog says so.
- CurrencyFieldTypeTest now accepts 3 or 4 fields, depending on the amount docValues setting. Its test schema has no docValues on the amount sub-field, so only the 3 field branch runs there.
- Land SOLR-15357 first. Without its copy target change, an atomic update could carry the derived currency values into the document it sends back.
- A sub-field type that cannot write docValues now throws at index time when docValues is set on it. Before this change, the setting was dropped silently. Not tested.
