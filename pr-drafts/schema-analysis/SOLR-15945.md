## What happens today

**A `DateRangeField` or `SpatialRecursivePrefixTreeFieldType` field with `indexed="false"` stops the core from loading.**

With this schema, from the ticket:

```xml
<fieldType name="rdate" class="solr.DateRangeField" sortMissingLast="true"/>
<field name="date" type="rdate" indexed="false" stored="true"/>
```

the core fails with `date of type DateRangeField is incompatible with omitNorms=false; hardcoded behavior is omitNorms=true.  Remove specification in schema`. The check is in [`AbstractSpatialPrefixTreeFieldType.checkSchemaField`](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/schema/AbstractSpatialPrefixTreeFieldType.java#L149-L158). The same method also rejects index options other than `DOCS` ([lines 159-167](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/schema/AbstractSpatialPrefixTreeFieldType.java#L159-L167)). A field with `indexed="false"` reports `IndexOptions.NONE` ([`SchemaField.indexOptions`](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/schema/SchemaField.java#L513-L516)), so the second check fails too.

## What this change does

**For a field with `indexed="false"`, the norms check and the index-options check are skipped.**

The superclass checks still run first. For a field that is not indexed, the method then returns ([code](https://github.com/nick-boss-tech/solr/blob/adb0fd450c06c07f49ccd187c3d810410a76c5b3/solr/core/src/java/org/apache/solr/schema/AbstractSpatialPrefixTreeFieldType.java#L146-L152)). Indexed fields run the same checks as before.

Behavior change: a stored-only `DateRangeField` or `SpatialRecursivePrefixTreeFieldType` field now loads, and its values come back in results. The field is not indexed, so a query cannot search it.

On the base code the schema does not load, so the test fails in its setup with the omitNorms error above.

## A choice to check

**Options: load stored-only spatial fields (implemented), or keep refusing them with a clearer error.**

This change loads a stored-only spatial field. The other option keeps the refusal and changes the message to say the field must be indexed. Loading lets a stored-only field into a schema that cannot search it. Refusing keeps the load failure, with a clearer message. Was it right to load stored-only spatial fields, or should the schema keep refusing them with a message that says they must be indexed?

## Limits

**Only stored-only fields are covered.**

- A field with `indexed="false"` and `docValues="true"` still fails. The base `FieldType.checkSchemaField` calls `checkSupportsDocValues` for any field with docValues ([base code](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/schema/FieldType.java#L1194-L1197)), and neither type overrides it. Supporting docValues-only spatial fields is a separate change. A follow-up ticket and PR can be opened for it on request.
- The test checks that both stored values are present. It does not compare their exact text.
- SOLR-15403 describes the same index-options check on this path, and this change covers that check. Whether the two tickets are duplicates is for maintainers to decide.
