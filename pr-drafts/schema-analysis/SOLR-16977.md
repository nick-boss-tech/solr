## What happens today

**A KNN query with an all-zero vector fails with an unclear server error when the field uses cosine similarity.**

The ticket reports this on Solr 9.2.1. A request with `q={!knn f=vector topK=1}[0.0, 0.0, 0.0, 0.0]` against a DenseVectorField that uses cosine similarity returns HTTP 500. The error is a Lucene `docID must be >= 0` message raised while the matching documents are written. Cosine similarity divides by the vector norm, and the norm of an all-zero vector is zero.

## What this change does

**A KNN query with an all-zero vector now fails with HTTP 400 when the field uses cosine similarity.**

The check runs in [`getKnnVectorQuery`](https://github.com/nick-boss-tech/solr/blob/1142f9563abe13aea113bd80d241db770fd6cdb6/solr/core/src/java/org/apache/solr/schema/DenseVectorField.java#L503-L524) before the query object is built. The helper, [`checkQueryVectorUsableForCosine`](https://github.com/nick-boss-tech/solr/blob/1142f9563abe13aea113bd80d241db770fd6cdb6/solr/core/src/java/org/apache/solr/schema/DenseVectorField.java#L573-L597), looks for a non-zero value in a float or byte vector. If none is found, it throws `BAD_REQUEST`. Fields with other similarity functions still accept a zero query vector, because those functions are defined for it.

Requests that the ticket reports as HTTP 500 now return HTTP 400.

## Proof

**One new test fails on the base code. Two guard cases that must not change.**

Run at head `1142f9563abe`, verified 2026-10-07. [DenseVectorFieldTest](https://github.com/nick-boss-tech/solr/blob/1142f9563abe13aea113bd80d241db770fd6cdb6/solr/core/src/test/org/apache/solr/schema/DenseVectorFieldTest.java#L1316-L1357) passes 51 tests, 2 skipped, 0 failures. On base `14c7aac0d15`, the three new tests run with the head test file, and one fails: `zeroQueryVector_cosineSimilarity_shouldBeRejected`. The base builds the query without an error, so the expected `SolrException` is never thrown. `zeroQueryVector_nonCosineSimilarity_shouldBeAccepted` and `nonZeroQueryVector_cosineSimilarity_shouldBeAccepted` pass on base and with this change.

## Limits

- **Stored vectors.** The ticket also reports an all-zero vector stored in a document. That case fails the same way at query time, and this change does not cover it. I can open a follow-up ticket and PR for it on request.
- **Other query paths.** The check covers the `{!knn}` parser only, at [KnnQParser](https://github.com/nick-boss-tech/solr/blob/1142f9563abe13aea113bd80d241db770fd6cdb6/solr/core/src/java/org/apache/solr/search/vector/KnnQParser.java#L179). The [`vectorSimilarity` query parser](https://github.com/nick-boss-tech/solr/blob/1142f9563abe13aea113bd80d241db770fd6cdb6/solr/core/src/java/org/apache/solr/search/vector/VectorSimilarityQParser.java#L45-L75) builds its own vector and does not call the check, so a zero vector reaches it unchanged. The `vectorSimilarity()` function is unchanged too.
- **Unit level only.** The tests call `getKnnVectorQuery` directly. No test sends an HTTP request.
