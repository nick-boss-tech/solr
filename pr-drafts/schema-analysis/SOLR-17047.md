## What happens today

**Bad KNN settings on a DenseVectorField load without error, and fail later, at the first segment flush.**

With the default codec (`SchemaCodecFactory`), a field type with `knnAlgorithm="typo"` or `hnswM="0"` loads. The error appears only when a segment is first written, because the vectors format is built per field at that point ([SchemaCodecFactory](https://github.com/nick-boss-tech/solr/blob/1ba7e33bfe7b86c147f2cd22d6ba517aaa5cbb00/solr/core/src/java/org/apache/solr/core/SchemaCodecFactory.java#L126-L139)). With a codec factory that does not support these options, the core loads and ignores them with no message. The ticket asks for these settings to fail at core init unless the codec honors them.

## What this change does

**Core init now checks each DenseVectorField's KNN settings and fails the core when a setting cannot be honored.**

- With `SchemaCodecFactory`, core init rejects an unsupported `knnAlgorithm` and builds each vectors format, so an invalid HNSW value fails at init ([checks](https://github.com/nick-boss-tech/solr/blob/1ba7e33bfe7b86c147f2cd22d6ba517aaa5cbb00/solr/core/src/java/org/apache/solr/core/SchemaCodecFactory.java#L140-L180)). Lucene's HNSW format throws IllegalArgumentException for `hnswM="0"` in both the 9.12 and 10.4 lines.
- For a codec factory that is not `SolrCoreAware`, a DenseVectorField setting that differs from the default fails core load. Postings and docValues formats already work this way ([SolrCore](https://github.com/nick-boss-tech/solr/blob/1ba7e33bfe7b86c147f2cd22d6ba517aaa5cbb00/solr/core/src/java/org/apache/solr/core/SolrCore.java#L1603-L1611)).
- Wider than the narrowest reading:
  - Quantized field types always count as a setting that differs from the default ([ScalarQuantized](https://github.com/nick-boss-tech/solr/blob/1ba7e33bfe7b86c147f2cd22d6ba517aaa5cbb00/solr/core/src/java/org/apache/solr/schema/ScalarQuantizedDenseVectorField.java#L124-L128)). With a codec factory that cannot apply quantization, such a core now fails to load.
  - Field types that no field uses are checked too.
  - Under the default codec, `knnAlgorithm="cagra_hnsw"` now fails at core load. Before, it failed at the first flush.

## A choice to check

**Quantized fields now fail to load under a codec factory that cannot apply quantization. The alternative keeps loading them with the setting ignored.**

Quantization counts as a KNN setting here, as postings and docValues formats do. A custom codec setup that loaded before now fails at startup. The other route checks only the algorithm and the HNSW values. Was failing the load the right call?

## Limits

- Only an exact `SchemaCodecFactory` gets the eager check. [`CuVSCodecFactory`](https://github.com/nick-boss-tech/solr/blob/1ba7e33bfe7b86c147f2cd22d6ba517aaa5cbb00/solr/modules/cuvs/src/java/org/apache/solr/cuvs/CuVSCodecFactory.java#L27-L36) wraps one but is not one, so cuVS users keep the lazy error.
- The cuVS settings are not checked under `SchemaCodecFactory`. Only the cuVS codec reads them ([CuVSCodec](https://github.com/nick-boss-tech/solr/blob/1ba7e33bfe7b86c147f2cd22d6ba517aaa5cbb00/solr/modules/cuvs/src/java/org/apache/solr/cuvs/CuVSCodec.java#L66-L73)), so the default codec still ignores them.
- A field type added through the Schema API is checked at the next core load, not when it is added. Until then, the first segment flush reports it.
