## What happens today

**On Lucene 10, a phrase query on `ancestor_path` does not match documents stored at an ancestor path.**

The shipped `ancestor_path` type indexes each path as one keyword and queries with `PathHierarchyTokenizer` ([_default schema](https://github.com/nick-boss-tech/solr/blob/c5a0bdb21e862ec403b37c51c39070d952b972d8/solr/server/solr/configsets/_default/conf/managed-schema.xml#L513-L520)). The field query parser, as in `{!field f=cat_ancestor}Books/NonFic/Science`, turns the query into a phrase over the path prefixes. Lucene 10 gives those prefixes consecutive positions. A phrase over consecutive positions cannot match one keyword, so a document stored at `Books/NonFic` is not found. Quoted text takes the same phrase path. Unquoted text in the standard parser builds a SHOULD query on schema version 1.4 or later, so it is not on this path.

## What this change does

**The query analyzer adds `ZeroPositionIncrementFilter`, which puts the path prefixes at one position so they match as alternatives.**

- New filter [`ZeroPositionIncrementFilter`](https://github.com/nick-boss-tech/solr/blob/c5a0bdb21e862ec403b37c51c39070d952b972d8/solr/core/src/java/org/apache/solr/analysis/ZeroPositionIncrementFilter.java#L24-L59) and factory `solr.ZeroPositionIncrementFilterFactory` ([factory](https://github.com/nick-boss-tech/solr/blob/c5a0bdb21e862ec403b37c51c39070d952b972d8/solr/core/src/java/org/apache/solr/analysis/ZeroPositionIncrementFilterFactory.java#L23-L65)). The first token keeps its position. Later tokens get position increment 0.
- The shipped `_default` and `sample_techproducts_configs` configsets add the filter to the query analyzer of `ancestor_path` ([_default](https://github.com/nick-boss-tech/solr/blob/c5a0bdb21e862ec403b37c51c39070d952b972d8/solr/server/solr/configsets/_default/conf/managed-schema.xml#L513-L520), [sample_techproducts](https://github.com/nick-boss-tech/solr/blob/c5a0bdb21e862ec403b37c51c39070d952b972d8/solr/server/solr/configsets/sample_techproducts_configs/conf/managed-schema.xml#L678-L686)).
- The core test schema now indexes `ancestor_path` values with a keyword tokenizer, as the shipped configsets do. It used PathHierarchy on both sides before ([test schema](https://github.com/nick-boss-tech/solr/blob/c5a0bdb21e862ec403b37c51c39070d952b972d8/solr/core/src/test-files/solr/collection1/conf/schema.xml#L474-L486)).
- A new filter section in the reference guide, and an updated upgrade note. Users who indexed with PathHierarchy on both sides must reindex with the keyword index.
- Lucene 9.x already emits overlapping prefixes, so the filter changes nothing there.

## A choice to check

**Ship this Solr filter now, or wait for a Lucene fix?**

Option one is this change. Its cost is a Solr filter that does nothing once Lucene restores overlapping prefixes, at which point Solr can remove it. Option two is to wait for [Lucene issue 15769](https://github.com/apache/lucene/issues/15769). Its cost is that `ancestor_path` phrase queries stay broken on Lucene 10 releases until that fix ships. This change takes option one. Was shipping the Solr filter now the right call?

## Limits

- The unit tests cover the field query parser path only. The test schema uses schema version 1.0, where the standard parser also builds phrases. The shipped configsets use version 1.7, and no test runs them.
- Quoted text takes the same phrase path, and no test covers it.
- Existing schemas must add the filter to the query analyzer. Schemas that use PathHierarchy on both sides must also reindex. The upgrade note says so.
