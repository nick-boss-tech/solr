## What happens today

**The Schema API accepts a request to delete the uniqueKey field.**

`ManagedIndexSchema.deleteFields` checks copy field sources and destinations, but it does not check the uniqueKey field. The request goes through. The failure shows up later as a server error from the persist step ("Unable to persist managed schema"), not as a clear refusal. The ticket reports that after `id` was deleted this way, SolrCloud collections stopped working.

## What this change does

**The Schema API now refuses to delete the uniqueKey field with a 400 error.**

In `ManagedIndexSchema.deleteFields`, a field whose name equals the schema's uniqueKey field name is refused before the copy field checks run. The error text is "Can't delete field 'id' because it is the uniqueKey field." Other fields are not affected. The check runs only for a field that exists in the schema.

## Proof

`TestBulkSchemaAPI.testDeleteUniqueKeyFieldRefused` fails on the base code. On base, the delete request returns a server error ("Unable to persist managed schema") instead of the refusal, so the assertion on the error text fails. It passes with this change.

## Limits

- The copy field source and destination checks were already in place. This change covers only the uniqueKey field.
- Other references are not covered. A field used as `df` or `qf` in a request handler still deletes without a refusal. The ticket comments name this case. I can open a follow-up ticket and pull request for it on request.
- Changing the uniqueKey through the Schema API is not covered here.
