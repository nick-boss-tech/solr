## What happens today

**With LTR, an elevated document can end up below documents it should beat.**

With `elevateIds` and an `rq` rerank, the elevated document should stay on top of the rerank window, and it does not always do so. The boost loop in `ReRankCollector.BoostedComp` stops at the first document in the window that is not elevated ([base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/search/ReRankCollector.java#L327-L334)). With LTR, `LTRRescorer.getFirstPassDocsRanked` also sorts the window by internal document id before that loop runs ([source](https://github.com/nick-boss-tech/solr/blob/e38ddec5279c465f65a2fa2de22ee9c92e0f5e31/solr/modules/ltr/src/java/org/apache/solr/ltr/LTRRescorer.java#L146-L148)). An elevated document that is not first by id is never boosted. The ticket's comment describes an elevated worst document landing last in the reranked list.

## What this change does

**Every elevated document in the rerank window gets the boost, not only a leading run.**

The loop in `BoostedComp` now checks every document in the window ([source](https://github.com/nick-boss-tech/solr/blob/e38ddec5279c465f65a2fa2de22ee9c92e0f5e31/solr/core/src/java/org/apache/solr/search/ReRankCollector.java#L324-L333)). Each elevated document sorts above the rest of the window, in elevation priority order. Documents outside the rerank window do not move. Behavior changes, stated openly:

- The fix is in the shared rerank collector. It applies to every `rq` rerank with an elevation match, not only LTR.
- Before this change, the boost applied only to a leading run of elevated documents, whatever the sort. Now a field-sorted window also gets the boost when `forceElevation` is off. Elevated documents from anywhere in the window are sorted to the top before the page is cut, so one can enter the first page even when the reranker scored it low.

## A choice to check

**Should a field-sorted rerank window also boost elevated documents when `forceElevation` is off?**

Options considered:

1. Boost every elevated document in the window, as this change does. This fixes LTR for every sort. The cost is that a field-sorted rerank moves elevated documents to the top of the window without `forceElevation`, which the elevation component does not do on its own.
2. Boost the whole window only when the elevation component also adds its own sort (a score sort, or `forceElevation=true`), and keep the leading-run rule for other sorts. This leaves field-sorted rerank as it is today, but it needs a flag passed through the request context, and LTR with a field sort stays broken.

Was the first option the right call?

## Limits
