## What happens today

**A field with useDocValuesAsStored=false is dropped when fl also has a glob, even when fl names it.**

With `fl=id,a*,a3`, the response has `id`, `a1` and `a2`, but not `a3`. In the test schema, `a3` has `stored=false`, `docValues=true` and `useDocValuesAsStored=false` ([schema](https://github.com/nick-boss-tech/solr/blob/562d3e7e685a06acd1fbe3baf2fd3bf168979067/solr/core/src/test/org/apache/solr/schema/TestUseDocValuesAsStored2.java#L69-L76)). The glob `a*` skips it, because the glob only matches stored fields and fields with useDocValuesAsStored=true. The explicit name is ignored too.

## What this change does

**When fl has a glob, a field named by its own name in fl is now returned, even if it has useDocValuesAsStored=false.**

The pattern-matching branch of `calcDocValueFieldsForReturn` now also adds each requested name that is a non-stored docValues field ([lines 883-892](https://github.com/nick-boss-tech/solr/blob/562d3e7e685a06acd1fbe3baf2fd3bf168979067/solr/core/src/java/org/apache/solr/search/SolrDocumentFetcher.java#L883-L892)). Glob matches behave as before. The glob alone still does not return `a3`.

## Limits

- A field named through an alias, such as `fl=alias:a3`, is still not returned when fl also has a glob. A follow-up can cover aliases. I can open a ticket and PR for that on request.
- An alias such as `fl=a3:a1` is treated as a requested name `a3`. If `a1` is missing from a document and `a3` is present, the raw `a3` value can be returned under the name `a3`. No test covers this case.
- Only the standard select path has a test here. Other response writers were not checked.
