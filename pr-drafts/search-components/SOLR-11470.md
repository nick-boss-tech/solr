## What happens today

**A pure negative main query returns no results when a rank query is also sent.**

The ticket's example is `q=NOT foo` on the techproducts sample. It returns 52 documents alone, and none when `rq={!rerank reRankQuery=bar}` is added. The lucene query parser already makes a pure negative query searchable, but only when `luceneMatchVersion` is 10.2.0 or later ([SolrQueryParser.java](https://github.com/apache/solr/blob/8e62c2686882aa704480ab13b6a60ee8f7b5c8af/solr/core/src/java/org/apache/solr/search/SolrQueryParser.java#L31-L35), [QParser.java](https://github.com/apache/solr/blob/8e62c2686882aa704480ab13b6a60ee8f7b5c8af/solr/core/src/java/org/apache/solr/search/QParser.java#L113-L118)). The `{!bool}` parser builds the same kind of query without that step ([BoolQParserPlugin.java](https://github.com/apache/solr/blob/8e62c2686882aa704480ab13b6a60ee8f7b5c8af/solr/core/src/java/org/apache/solr/search/BoolQParserPlugin.java)), so `q={!bool must_not=term_s:ZZZZ}` with `rq` returns no documents on the base code.

## What this change does

**The main query is made searchable before the rank query wraps it.**

`ResponseBuilder.wrap` now passes the main query through `QueryUtils.makeQueryable` when a rank query is set ([ResponseBuilder.java lines 480-488](https://github.com/nick-boss-tech/solr/blob/f44c294da37452462541771c48b2d85132cf5a16/solr/core/src/java/org/apache/solr/handler/component/ResponseBuilder.java#L480-L488)). It is the same helper the lucene parser already uses.

The change is wider than negative queries. With a rank query set, every main query goes through `makeQueryable`. That call also unwraps a wrapped query, so a main query that carries local params such as `cache` or `cost` loses that wrapper under a rank query. Queries that are not negative are otherwise unchanged. No test covers the wrapper case.

The ticket suggests a `RankQuery#getMainQuery` accessor. This change adds no new API.

## Proof

**A new `{!bool}` test fails on the base code and passes with this change.**

[TestReRankQParserPlugin](https://github.com/nick-boss-tech/solr/blob/f44c294da37452462541771c48b2d85132cf5a16/solr/core/src/test/org/apache/solr/search/TestReRankQParserPlugin.java#L303-L335) 13 of 13 passes at head f44c294da37, verified 2026-10-05. `testReRankWithPureNegativeMainQueryFromBoolParser` fails on the base code with no results, as the ticket describes, and passes with this change. The other 12 tests pass on the base code and with this change. A lucene parser test in the same file also passes on the base code, because the parser already fixes that query, so the `{!bool}` test is the one that shows the change.

`QueryEqualityTest` 113 of 113 passes at the same head.

## A choice to check

**The fix sits in `ResponseBuilder.wrap`, not in a new accessor on the rank query.**

The ticket proposes `RankQuery#getMainQuery`, used inside `QueryUtils.makeQueryable`. This change calls `makeQueryable` once, in `ResponseBuilder.wrap`. That needs no new API, but it runs for every main query when a rank query is set, including the wrapper case above. Was this the right call, or should the fix go through a rank query accessor?

## Limits

- The `luceneMatchVersion` before 10.2.0 path has no test. The version check was made on main. The 9.x branch has no such check in its query parser.
- The wrapper case (`cache` or `cost` on a main query under a rank query) has no test.
