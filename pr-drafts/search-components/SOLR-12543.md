## What happens today

**An /export request with no sort, or with no fl, returns HTTP 200 with the error inside the body.**

The body says `"responseHeader":{"status":400}` and holds an `EXCEPTION` document. The writer builds that body in [ExportWriter.java](https://github.com/nick-boss-tech/solr/blob/88d236db6b7d4a538248b915447ea02e31ac83cf/solr/core/src/java/org/apache/solr/handler/export/ExportWriter.java#L176-L192). The no-sort check ([lines 221-225](https://github.com/nick-boss-tech/solr/blob/88d236db6b7d4a538248b915447ea02e31ac83cf/solr/core/src/java/org/apache/solr/handler/export/ExportWriter.java#L221-L225)) and the no-fl check ([lines 275-280](https://github.com/nick-boss-tech/solr/blob/88d236db6b7d4a538248b915447ea02e31ac83cf/solr/core/src/java/org/apache/solr/handler/export/ExportWriter.java#L275-L280)) both use it.

## What this change does

**The handler now rejects an /export request with no sort, or with no fl, with HTTP 400.**

The check runs in [ExportHandler.java](https://github.com/nick-boss-tech/solr/blob/88d236db6b7d4a538248b915447ea02e31ac83cf/solr/core/src/java/org/apache/solr/handler/ExportHandler.java#L135-L155), before the writer starts. A sort given as a local parameter on q counts, as it does in the writer. Clients that look for an `EXCEPTION` document in a 200 response will now get an HTTP error.

## A choice to check

**The sort and fl checks sit in the handler. The writer already has the same rules.**

- Implemented: the handler runs the two checks before the writer starts, and returns HTTP 400. The writer keeps its own checks.
- Other route: leave the checks in the writer, and set the 400 status where the writer reports these errors.

Cost of the implemented route: the same two rules exist in two places and must stay in step. Cost of the other route: it changes how the writer reports errors. Was the check in the handler the right call?
