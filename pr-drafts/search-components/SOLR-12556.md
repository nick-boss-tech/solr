## What happens today

**With `processEmpty:true`, a bucket can be returned with partial stats after refinement re-sorts it.**

With `refine:true` and `processEmpty:true`, refinement asks shards for buckets they did not return, even without `more:true`. After refinement a bucket can sort differently. The completeness check ignored `processEmpty` and only looked at shards that reported `more:true`, so an incomplete bucket can be returned with partial stats.

## What this change does

**Buckets known before refinement follow the `processEmpty` rule. Buckets first seen during refinement keep the old rule.**

[`FacetModule`](https://github.com/nick-boss-tech/solr/blob/033ec65a0e1bc12fd16d65b77a5b19458c837040/solr/core/src/java/org/apache/solr/search/facet/FacetModule.java#L195-L200) records the bucket count before any refinement response is merged. [`FacetMerger.Context`](https://github.com/nick-boss-tech/solr/blob/033ec65a0e1bc12fd16d65b77a5b19458c837040/solr/core/src/java/org/apache/solr/search/facet/FacetMerger.java#L59-L62) keeps that boundary, so mergers created during refinement see it too.

[`isBucketComplete`](https://github.com/nick-boss-tech/solr/blob/033ec65a0e1bc12fd16d65b77a5b19458c837040/solr/core/src/java/org/apache/solr/search/facet/FacetRequestSortedMerger.java#L160-L180) judges a bucket known before refinement by every shard that returned the facet. A shard that returned the facet and did not return the bucket makes it incomplete, and [`FacetFieldMerger`](https://github.com/nick-boss-tech/solr/blob/033ec65a0e1bc12fd16d65b77a5b19458c837040/solr/core/src/java/org/apache/solr/search/facet/FacetFieldMerger.java#L122-L124) then leaves it out of the response. A bucket first seen in a refinement response uses the old rule ([L189-L191](https://github.com/nick-boss-tech/solr/blob/033ec65a0e1bc12fd16d65b77a5b19458c837040/solr/core/src/java/org/apache/solr/search/facet/FacetRequestSortedMerger.java#L189-L191)), since no shard can be asked about it again.

## A choice to check

**Buckets first seen during refinement keep the base behavior. They come back with stats from the shards that answered.**

The other route applies the `processEmpty` rule to them too. Then such a bucket is dropped unless every shard that returned the facet also answered for it. That drops buckets whose counts from the shard that has them are correct. This change keeps them, as base does. Was keeping them with partial stats the right call?

## Limits

**Only field (terms) facets with `refine:true` use this check, and one stronger expectation is still open.**

- Buckets first seen during refinement come back with stats from the shards that answered, as before.
- `testSortedSubFacetRefinementWhenParentOnlyReturnedByOneShardProcessEmpty` stays `@AwaitsFix`. It expects every shard to contribute to every bucket, which needs a refinement protocol change. A follow-up can be opened on request.
