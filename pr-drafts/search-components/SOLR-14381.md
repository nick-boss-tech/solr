## What happens today

**Distributed grouped counts overflow when a total passes Integer.MAX_VALUE.**

Grouped counts (matches, ngroups, and numFound in the simple format) are held as `int` in the grouping code. A grouped search over more than 2,147,483,647 matching documents can report a wrapped or negative count. At the merge-base, the int fields were in [`Grouping.java`](https://github.com/nick-boss-tech/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/search/Grouping.java), [`ResponseBuilder.java`](https://github.com/nick-boss-tech/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/handler/component/ResponseBuilder.java), and the SolrJ [`GroupCommand.java`](https://github.com/nick-boss-tech/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/solrj/src/java/org/apache/solr/client/solrj/response/GroupCommand.java).

## What this change does

**Grouping counts are long values through the grouping code and the final response. Shards send a count as Integer whenever it fits.**

`TopGroupsResultTransformer.boxCount` ([source](https://github.com/nick-boss-tech/solr/blob/7caf8d33d3bf29d38e3f16c38a01282982329e90/solr/core/src/java/org/apache/solr/search/grouping/distributed/shardresultserializer/TopGroupsResultTransformer.java#L340-L346)) writes an Integer when the value fits and a Long only above the int range. An older coordinator reads the top-level `totalHitCount` and the shard `matches` with `(Integer)` casts, so it keeps working for every count that fits.

Behavior changes, stated openly:

- Every grouped response types `matches` and `ngroups` as `long` in XML output, not only counts above the int range. The XML assertions in TestGroupingSearch and TestMissingGroups change from `int` to `long`.
- SolrJ `GroupCommand.getMatches()` now returns `long`, and `getNGroups()` returns `Long`.

## A choice to check

**The implemented route changes the SolrJ getter return types. The other route keeps them.**

`GroupCommand.getMatches()` now returns `long`, and `getNGroups()` returns `Long`. Keeping both getters unchanged would mean adding long-returning accessors beside them. Changing the type breaks source compatibility for callers. Adding accessors leaves the old getters returning truncated values for large counts. Was changing the return types the right call?

## Proof

**The compat tests pass at the current head and fail on the code from before the boxing change.**

TopGroupsResultTransformerCompatTest 2 of 2 and QueryResponseSectionParityTest 9 of 9, verified 2026-10-07 at head `a28b3f672cb4daa7cc32833082b0f499f41e3a85`. The head above, `7caf8d33d3bf29d38e3f16c38a01282982329e90`, changes only the changelog title, so these counts hold there.

On the merge-base `b5c71bc5573c4e31b4cee5a7965d73587fc0ae58` production code, both compat test methods fail with `ClassCastException: Long cannot be cast to Integer` (verified 2026-10-07).

At the earlier head `dd8d16441dc`, verified 2026-10-03: GroupingWideCountsTest 2 of 2, TestGroupingSearch 17 of 17, TestMissingGroups 1 of 1. Later commits changed TopGroupsResultTransformer.java and QueryComponent.java, so those three counts come from that earlier head.

## Limits

**Two tests are not yet checked, and mixed-version clusters still fail for large counts.**

- A mixed-version cluster still fails for a count above Integer.MAX_VALUE, because an older coordinator casts it to Integer. The rolling-upgrade claim covers counts that fit.
- TestDistributedGrouping is edited here (count types only) and has not been run at this head.
- GroupingWideCountsTest has not been checked against the base code.
