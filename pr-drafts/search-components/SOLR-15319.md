## What happens today

**With distributed IDF, a query across several collections can score with one collection's statistics.**

A query such as `/solr/collection1,collection2/query?q=fulltext:shark` should score each document with the term statistics of every collection it searches. Instead, each shard's statistics are stored under its bare shard name, such as `shard1`. Two collections that each have a `shard1` share one entry, so the second overwrites the first.

The coordinator also builds the shard names it looks up from the collection of the core that received the request. A shard it cannot name is skipped with a warning. The scores can then match one collection's document frequencies, as the Jira ticket reports.

## What this change does

**Each shard's statistics are keyed by its collection and shard name. The coordinator uses the keys that the shards send.**

- Each shard adds its collection name to its statistics response under a new key, `shard.collection` ([ExactStatsCache.java](https://github.com/nick-boss-tech/solr/blob/4bda91f46fc18142809c919d7c563129fdf7fb96/solr/core/src/java/org/apache/solr/search/stats/ExactStatsCache.java#L228)).
- The coordinator stores each shard's statistics under `collection!shard` ([L319-L326](https://github.com/nick-boss-tech/solr/blob/4bda91f46fc18142809c919d7c563129fdf7fb96/solr/core/src/java/org/apache/solr/search/stats/ExactStatsCache.java#L319-L326)). A shard that sends no collection name, as an older version does during a rolling upgrade, is keyed by its shard URL. Two older shards with the same name then stay apart.
- The coordinator no longer derives shard names from its own collection ([L264-L270](https://github.com/nick-boss-tech/solr/blob/4bda91f46fc18142809c919d7c563129fdf7fb96/solr/core/src/java/org/apache/solr/search/stats/ExactStatsCache.java#L264-L270)). The "Can't determine shard" warning is gone. A shard with no statistics still contributes none.
- The change adds one key to the statistics response. No existing key changes.

## A choice to check

**Keys use the collection and shard name, with the shard URL as the fallback. The other route keys every shard by its URL.**

The URL route needs no new response key and no second key format. This change adds the `shard.collection` key and a second key format for older shards. Was adding that key the right call, or is the shard URL enough as the only key?

## Limits

**SOLR-8051 lands first, and this branch follows it.**

- Not run at this head: the tests of the two subclasses, `ExactSharedStatsCache` and `LRUStatsCache`, and their cloud tests. Both use the same keys.
- Not covered: a shard response with no body still throws at the exception check in [ExactStatsCache.java line 120](https://github.com/nick-boss-tech/solr/blob/4bda91f46fc18142809c919d7c563129fdf7fb96/solr/core/src/java/org/apache/solr/search/stats/ExactStatsCache.java#L120). This change leaves that path as it is. The same path fails in [SOLR-8051](https://issues.apache.org/jira/browse/SOLR-8051). The SOLR-8051 test ExactStatsCacheMergeTest fails at this head with a NullPointerException at line 120, thrown by SolrResponse.getException on a null response. The SOLR-8051 branch fixes this shared merge path by moving the null-response skip ahead of the exception check. This change does not include that fix. Where the two edits to ExactStatsCache overlap, this change is reworked on top of the SOLR-8051 fix.
- Mixed-version behavior is checked by a unit test of the key function. No cluster runs two versions.
- `StatsUtil.shardUrlToShard` has no callers now. It stays in place.
