## What happens today

**On Windows, creating a managed resource whose id has a colon in it succeeds, but the words are never saved and the resource cannot be deleted.**

The Jira report creates the resource `/schema/analysis/stopwords/test : list`. The stored file name contains a colon, which Windows does not allow. The file is left empty, and words added later are not written to disk. A later DELETE fails with HTTP 500 and `java.nio.file.InvalidPathException: Illegal char <:>`.

## What this change does

**A create request now checks the id against the file storage first, and returns 400 when the file cannot be named.**

`FileStorageIO` gets a `validateStoredResourceId` check. It builds the path with the same path rules that delete uses. It rejects a name that is not a valid path, or that does not map to a single file in the storage directory ([FileStorageIO](https://github.com/nick-boss-tech/solr/blob/02930909397ad52c5c7c61279152b07f2c4ae98d/solr/core/src/java/org/apache/solr/rest/ManagedResourceStorage.java#L195-L215)). The create path runs the check before any data is stored ([RestManager](https://github.com/nick-boss-tech/solr/blob/02930909397ad52c5c7c61279152b07f2c4ae98d/solr/core/src/java/org/apache/solr/rest/RestManager.java#L474)). Other storage types use the default in the interface, which accepts every id ([default](https://github.com/nick-boss-tech/solr/blob/02930909397ad52c5c7c61279152b07f2c4ae98d/solr/core/src/java/org/apache/solr/rest/ManagedResourceStorage.java#L82-L86)).

Behavior changes, stated openly:

- On Windows, a create with a colon or a backslash in the id now returns 400 and stores nothing.
- On Linux and macOS, those ids are legal file names, so the check accepts them. The new test checks that they still work there.
- Registration at startup and from the schema does not run the check.
- Resources that already exist with such ids are not changed. Their DELETE still fails.

## A choice to check

**Two ways exist to decide which ids are safe. This change asks the file system.**

1. Ask the file system the server runs on. This change does that. Each platform rejects only what its own file system rejects.
2. Keep one fixed list of characters that Windows rejects, and apply it on every platform. The result is the same everywhere. The cost is that Linux and macOS would reject ids they store without trouble.

This change takes the first route. Was checking the file system the right call over a fixed list?

## Proof

**Counts are recorded at this head. The new test cannot show a failure on the base code.**

At head `02930909397`, verified 2026-10-03: `TestManagedFileStorage` 2 of 2 and `TestRestManager` 5 of 5. The tidy check and the Error Prone compile also passed.

This proof is inconclusive by construction. The new `TestManagedFileStorage` test calls `validateStoredResourceId`, which the base code does not have. So the test cannot compile on the base, and a run there cannot show a failure. The Windows branch of the test is the one that covers this bug.

The new `TestRestManager` test checks that registration still accepts such an id. It passes with or without this change, so it guards the design. It does not prove the fix.

## Limits

**Two gaps remain, and each can get a follow-up.**

- No test calls the REST endpoint. The 400 status follows from the error type in the create path.
- Resources that already exist with such ids are not repaired. Their DELETE still fails, and the write path is unchanged. A follow-up ticket and PR for cleanup can be opened on request.
- Updates to an existing id, and managed handles declared in the schema, do not run the check. A follow-up can cover them on request.
