## What happens today

**A failed document add puts field values, and sometimes the whole document, into the error message.**

A document that fails to index returns an error to the client. The javabin loader adds the whole document to its message, so every field value appears ([JavabinLoader, base commit `14c7aac0d151`, line 126](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/handler/loader/JavabinLoader.java#L126)). `DocumentBuilder` puts the field value into its field errors and copies up to 256 characters of values into the multi-value error ([base commit, lines 166 to 180](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/update/DocumentBuilder.java#L166-L180)). The copy-field error adds the original value too ([base commit, lines 378 to 381](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/update/DocumentBuilder.java#L378-L381)).

## What this change does

**Error messages now name the document id and the field, not the values.**

- The javabin loader reports the unique key only, for example `ERROR adding document [doc=7]` ([head `0881de1ed68`](https://github.com/nick-boss-tech/solr/blob/0881de1ed68b847c781abd7ccb56196cdbf15ecd/solr/core/src/java/org/apache/solr/handler/loader/JavabinLoader.java#L148-L155)).
- Field errors keep the document id and the field name. They drop the value and the exception text ([head, lines 100 to 110 and 281 to 289](https://github.com/nick-boss-tech/solr/blob/0881de1ed68b847c781abd7ccb56196cdbf15ecd/solr/core/src/java/org/apache/solr/update/DocumentBuilder.java#L100-L110)). The exception stays attached as the cause.
- The multi-value and copy-field errors name the field only. The 256-character limit on values is removed.
- Field errors still write the value to the log at TRACE level.

Behavior change, stated openly: a field error no longer repeats the underlying exception text. An error that said `For input string: "b"` now names only the field. Code that matched the old text can read the cause instead.

## A choice to check

**Field values now go to the log only at TRACE level. The other route keeps them out of the logs altogether.**

1. Values at TRACE (this change). Someone debugging a bad field can still see the value by turning on TRACE for the document builder's logger. The cost is that TRACE logs can hold sensitive values.
2. No values in any log. This is the strictest choice. The cost is that a bad field value is harder to find when debugging.

Was TRACE the right place for the values, or should they stay out of the logs too?

## Proof

**The message checks fail on the base code and pass with this change.**

At head `0881de1ed68`, the three test classes pass in GitHub test runs with this change, recorded 2026-10-04: `JavabinLoaderTest` 3 of 3, `DocumentBuilderTest` 17 of 17, and `TolerantUpdateProcessorTest` 11 of 11. The same classes fail at the focused test step on the base code. The failures are in the message assertions this change touches. The count of failing tests per class on the base code is not recorded here.

## Limits

**The proof covers three test classes, and the new messages reach every update format.**

- `DocumentBuilder` is shared. `AddUpdateCommand.makeLuceneDocs` builds each indexed document through it ([head, line 213](https://github.com/nick-boss-tech/solr/blob/0881de1ed68b847c781abd7ccb56196cdbf15ecd/solr/core/src/java/org/apache/solr/update/AddUpdateCommand.java#L213)), and the normal add path reaches it through `updateDocOrDocValues` ([line 1175](https://github.com/nick-boss-tech/solr/blob/0881de1ed68b847c781abd7ccb56196cdbf15ecd/solr/core/src/java/org/apache/solr/update/DirectUpdateHandler2.java#L1175)). XML, JSON and CSV updates therefore get the new field messages too. Their tests are not part of this proof.
- Upstream [PR #1151](https://github.com/apache/solr/pull/1151) covers this ticket with a wider scope.
