## What happens today

**With a `mincount` above 1, a JSON facet terms request still returns a `missing` bucket whose count is below that `mincount`.**

The reporter sends `mincount: 500` and `missing: true`. The field has 497 documents without a value, and the response still contains `"missing":{"count":497}` while smaller term buckets are left out. The base code adds the missing bucket whenever `missing` is set ([FacetFieldProcessor.java](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/search/facet/FacetFieldProcessor.java#L470)), and the merger adds it whenever a shard returned one ([FacetFieldMerger.java](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/search/facet/FacetFieldMerger.java#L139-L141)).

## What this change does

**A missing bucket below a `mincount` above 1 is left out of the response. At the default `mincount`, nothing changes.**

- Single node: the processor removes the `missing` entry when its count is below `mincount`, and only when `mincount` is above 1 ([FacetFieldProcessor.java](https://github.com/nick-boss-tech/solr/blob/148544e9ed54a7c6dd6714197d3bf74b06fff1ca/solr/core/src/java/org/apache/solr/search/facet/FacetFieldProcessor.java#L534-L542)).
- Distributed: shards still return the missing bucket, so shard responses are unchanged. The coordinator adds the shard counts and leaves the bucket out when the total is below `mincount` ([FacetFieldMerger.java](https://github.com/nick-boss-tech/solr/blob/148544e9ed54a7c6dd6714197d3bf74b06fff1ca/solr/core/src/java/org/apache/solr/search/facet/FacetFieldMerger.java#L139-L145)).
- At a `mincount` of 1 or lower, the bucket is returned as before, even with a count of 0.
- Behavior change: for a request with `mincount` above 1 and `missing` set, the `missing` key can now be absent. Clients that read `missing.count` without checking for the key will see this.

## A choice to check

**Only a `mincount` above 1 drops the missing bucket. The default keeps the existing rule.**

Options considered:

1. Keep the old rule for every request. This does not fix the reported case, where 497 is returned for a `mincount` of 500.
2. Apply `mincount` to the missing bucket the same way as term buckets, including the default of 1. A zero-count bucket would then be left out by default, which changes the default response shape.
3. Apply the rule only above a `mincount` of 1. This is what the change does.

Option 3 keeps the default response shape and fixes the reported case. Was that the right call, or should the default contract change too?

## Limits

- Sub-facets under the missing bucket are still computed before the bucket is dropped. Only the output changes.
- Range facets are not changed. The ticket is about terms facets.
- The JSON Facet API reference page does not describe the new rule yet.
- The distributed run sums the counts across shards only as far as the test data happens to split. No test sets up a case such as two shards with 400 documents each and a `mincount` of 500. A fixture for that case can go in this PR, or in a follow-up on request.
