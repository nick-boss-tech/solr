## What happens today

**A distributed `{!knn}` query can report more hits than its topK, because each shard returns up to topK hits.**

With `{!knn f=vector topK=3}` on three shards, each shard returns up to three hits. At the base commit `97d973814336`, the coordinator adds the shard counts together, so `numFound` is 9 where the query asks for 3 ([merge queue sized from start and rows, base line 1016](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1016); [shard counts added, base line 1171](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1171)).

## What this change does

**For a knn query in score order, the coordinator keeps at most topK hits and reports at most topK.**

- The merge queue holds at most topK hits when the request has no sort ([head `c2396f425fa2`, lines 1018 to 1024](https://github.com/nick-boss-tech/solr/blob/c2396f425fa2a67a40fea7afee341840c3896358/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1018-L1024)).
- `numFound` is capped at topK for every knn request ([lines 1238 to 1240](https://github.com/nick-boss-tech/solr/blob/c2396f425fa2a67a40fea7afee341840c3896358/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1238-L1240)).
- Two accessors, `getTopK()`, are added to the float and byte knn query classes ([float](https://github.com/nick-boss-tech/solr/blob/c2396f425fa2a67a40fea7afee341840c3896358/solr/core/src/java/org/apache/solr/search/vector/SolrKnnFloatVectorQuery.java#L48-L51), [byte](https://github.com/nick-boss-tech/solr/blob/c2396f425fa2a67a40fea7afee341840c3896358/solr/core/src/java/org/apache/solr/search/vector/SolrKnnByteVectorQuery.java#L47-L50)).

Behavior change, stated openly: for a distributed knn query, `numFound` can now be lower than the shard counts added together. It is never higher than topK.

## Proof

**The new test fails on the base code and passes with this change.**

`DistributedKnnTopKTest` passes 1 of 1 at head `c2396f425fa2`, recorded 2026-10-10. With production code reverted to the base commit `97d973814336`, the test fails with `numFound` 9 where it expects 3. The sort case has no fail-before result yet (see Limits).

## Limits

**An explicit sort on a field other than score is not trimmed yet, so the list can hold more than topK hits.**

- With a sort on another field, the merge queue still keeps start plus rows ([head, line 1020](https://github.com/nick-boss-tech/solr/blob/c2396f425fa2a67a40fea7afee341840c3896358/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1020)). A test run on this head, outside the branch, returned 9 documents in the list for `topK=3`, three shards and `sort=id asc` (run 2026-10-14). A single node returned 3 for the same query. That run did not record `numFound`. Reading the code, `numFound` is still capped at topK for these requests ([lines 1238 to 1240](https://github.com/nick-boss-tech/solr/blob/c2396f425fa2a67a40fea7afee341840c3896358/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1238-L1240)).
- The test covers the default score order only ([test, line 59](https://github.com/nick-boss-tech/solr/blob/c2396f425fa2a67a40fea7afee341840c3896358/solr/core/src/test/org/apache/solr/handler/component/DistributedKnnTopKTest.java#L59)). The sort case has no fail-before run yet. The run is pending at the parent of the fix commit, `c2396f425fa2`, with the fix's test files in place.
