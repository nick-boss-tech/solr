## What happens today

**A distributed grouped search fails with a NullPointerException when the unique key is not stored.**

The second phase writes each group document's id by reading the unique key from the stored-field fetch. When the unique key is stored off and has docValues, the fetch returns no value for it, and the transformer passes null to `toExternal`. The Jira stack trace ends in `TopGroupsResultTransformer.serializeTopGroups`.

## What this change does

**The unique key is read from its stored value, or from docValues when it is not stored.**

`retrieveUniqueKey` ([source](https://github.com/nick-boss-tech/solr/blob/1413237f7a75b8b3da946401d12bcd0e29917581/solr/core/src/java/org/apache/solr/search/grouping/distributed/shardresultserializer/TopGroupsResultTransformer.java#L343-L366)) reads the stored value first. When there is none, it reads the docValues into a new `SolrDocument`, so the shared document cache entry is never changed.

Behavior change, stated openly: when the unique key has neither a stored value nor docValues, the request now fails with a `SolrException` of type SERVER_ERROR that names the field and the document. It used to fail with a NullPointerException.

## Proof

TopGroupsResultTransformerTest 1 of 1 at head `1413237f7a75b8b3da946401d12bcd0e29917581`, verified 2026-10-05. The test stores the unique key with docValues only, runs a second-phase grouped request with three documents, and checks that all three ids come back.

On base code `14c7aac0d15`, with the same test, it fails with a server NullPointerException.

## Limits

- Only string unique keys are tested. On the docValues path the value is converted with `toString()`, which I have not checked against other field types.
- The SERVER_ERROR case for a unique key with neither a stored value nor docValues has no test.
