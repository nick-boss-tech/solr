## What happens today

**With `shards.info` set, a failed shard can make `QueryComponent.returnFields` throw a NullPointerException.**

The ticket reports this error when some shards are down and `shards.info` is set. The code has two routes to it:

- A one-pass query (`distrib.singlePass=true`, or a request whose `fl` needs only the id and score) with `shards.tolerant=true`. A slice with no live replica gives a failed response with an empty shard name. The id merge records that shard as `unknown_shard_N`. The field step then looks up the empty name, finds no entry, and dereferences null.
- A failed shard whose error has no cause. The Solr client raises such an error when it finds no live server and has no earlier exception to attach. The field step calls `getCause()` and then dereferences the null result.

## What this change does

**The field step skips a failed shard that has no name, and it keeps the error when the exception has no cause.**

- A failed shard with no name is skipped in this step. The id merge already recorded it under `unknown_shard_N` ([QueryComponent.java L1094-L1098](https://github.com/nick-boss-tech/solr/blob/dfacaf347668e43a433baef650268b281649c6fc/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1094-L1098)).
- An error with no cause is reported as itself. The id merge already does the same ([L1043](https://github.com/nick-boss-tech/solr/blob/dfacaf347668e43a433baef650268b281649c6fc/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1043), [L1496-L1498](https://github.com/nick-boss-tech/solr/blob/dfacaf347668e43a433baef650268b281649c6fc/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1496-L1498)).
- A named shard with no `shards.info` entry gets one, so its error is listed ([L1487-L1492](https://github.com/nick-boss-tech/solr/blob/dfacaf347668e43a433baef650268b281649c6fc/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1487-L1492)). See the choice below.
- Behavior change: a one-pass query with `shards.info` and a failed shard no longer fails with a 500 error. It returns the results, lists the failed shard in `shards.info`, and keeps the partial-results flag that the id merge sets.

## Proof

**The single-pass case fails on the base code with the NullPointerException and passes with this change.**

- `TestShardsInfoResponse` gains a single-pass query against a two-node cluster with two failed shards. On the base code it fails with the NullPointerException. It passes at `dfacaf347668e43a433baef650268b281649c6fc`, recorded 2026-10-04.
- `TestShardsInfoErrorRecording` 4 of 4 pass at this head, recorded 2026-10-04. On the base code three of the four fail with the same NullPointerException. The fourth, which keeps an existing error entry, passes on both.
- No test covers an error with no cause on a shard that already has an entry.

## A choice to check

**This change adds a `shards.info` entry for a named failed shard that has none. The other route leaves `shards.info` as the id merge left it.**

The other route is smaller. It skips the empty-name case only, so a named failed shard with no entry would show no error line. The current query paths do not reach a missing entry, because the id merge records every failed response under its name. Was adding the entry the right call, or should this change stay with the empty-name skip?

## Limits

- The ticket does not say which query shape produced the error. This change covers the one-pass case with an unnamed failed shard, and the error with no cause. Other shapes were not reproduced.
- The new test checks the response and the entries. It does not check the partial-results flag.
- The entry-creation branch is tested by calling `returnFields` directly.
