## What happens today

**A PUT or POST to `/schema/feature-store/<storeName>` puts features that have no `store` attribute in the default store.**

The Jira report sends features to `/schema/feature-store/store1` and finds them under `_DEFAULT_`. The guide's upload example also sends to `/schema/feature-store` and shows the result under `_DEFAULT_`. It does not say what a store name in the URL does.

## What this change does

**A store name in the URL now becomes the store for features in that request that have no `store` attribute.**

The dispatcher passes the URL child id to PUT and POST ([RestManager](https://github.com/nick-boss-tech/solr/blob/a39c1c9737667e4ab935a9c498648bdb9f4507c1/solr/core/src/java/org/apache/solr/rest/RestManager.java#L341-L346)). `ManagedFeatureStore` sets the `store` attribute from that id when the attribute is missing, and keeps an explicit `store` value ([ManagedFeatureStore](https://github.com/nick-boss-tech/solr/blob/a39c1c9737667e4ab935a9c498648bdb9f4507c1/solr/modules/ltr/src/java/org/apache/solr/ltr/store/rest/ManagedFeatureStore.java#L162-L198)). A store that does not exist yet is created, as it is for an explicit store name. POST behaves like PUT for this resource, as before.

Behavior change, stated openly: uploads that name a store in the URL, with no `store` attribute, now go to that store and not to `_DEFAULT_`. Models that read from the default store will not see features uploaded this way. The upgrade note says so ([upgrade note](https://github.com/nick-boss-tech/solr/blob/a39c1c9737667e4ab935a9c498648bdb9f4507c1/solr/solr-ref-guide/modules/upgrade-notes/pages/major-changes-in-solr-11.adoc#L45-L51)). The guide now describes the URL store name ([guide](https://github.com/nick-boss-tech/solr/blob/a39c1c9737667e4ab935a9c498648bdb9f4507c1/solr/solr-ref-guide/modules/query-guide/pages/learning-to-rank.adoc#L294)).

## A choice to check

**Two ways exist to pass the URL id to the resource. This change adds overloads to the base class.**

1. Two new public overloads on `ManagedResource`, one for PUT and one for POST, that take the child id. The defaults call the existing methods, so other resources keep working. This change takes this route. The cost is two more public methods on the base class.
2. A child-id getter on the request endpoint, which resources read inside the existing methods. No new overloads. Each resource that needs the id reads it itself.

Was adding overloads to `ManagedResource` the right call over a getter on the endpoint?

## Proof

**The REST tests show the bug on the base code. The four unit tests cannot run on the base.**

At head `a39c1c97376`, verified 2026-10-05:

- `TestManagedFeatureStoreRest` 2 of 2. These tests send requests through the REST layer. On the base code, both fail on the named-store check: the feature lands in `_DEFAULT_`.
- `TestManagedFeatureStore` 10 of 10. Four of these tests are new. They call the new overloads, so they cannot compile on the base code. This part is inconclusive by construction, and it does not show a failure before the change.
- `TestModelManager` 3 of 3. This branch does not change it. It runs as a regression check.

The tidy check and the Error Prone compile passed for core and the LTR module, and both module checks passed.

## Limits

**Only the feature store changes. Features already uploaded to `_DEFAULT_` stay where they are.**

- Model stores and the other child resources receive the id through the new overload and ignore it, so their behavior is unchanged.
- Features already in `_DEFAULT_` from earlier uploads stay there. A helper to move them can be a follow-up ticket and PR on request.
