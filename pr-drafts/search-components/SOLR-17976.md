## What happens today

**Documents with equal scores can come back in a different order for the same query.**

When two shards return documents with the same score, the merge breaks the tie by comparing the shard address. In SolrCloud, the address is the list of replica URLs for the shard, joined with `|`. That list order depends on which replicas serve the request. By default, the replica order is random, and `shards.preference` changes it too. The same query can therefore rank tied documents differently from one request to the next. The ticket gives a two-shard, two-node example.

## What this change does

**Ties are broken by the SolrCloud shard name, so the order no longer depends on which replicas answer.**

- Each merged document gets its shard name from the request's own slice list ([QueryComponent.java L971-L989](https://github.com/nick-boss-tech/solr/blob/56ea43c448ed4fea75131d34c390d11233bab5cb/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L971-L989), set at [L1232](https://github.com/nick-boss-tech/solr/blob/56ea43c448ed4fea75131d34c390d11233bab5cb/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java#L1232)).
- The combined query component sets the name the same way ([CombinedQueryComponent.java L323](https://github.com/nick-boss-tech/solr/blob/56ea43c448ed4fea75131d34c390d11233bab5cb/solr/core/src/java/org/apache/solr/handler/component/CombinedQueryComponent.java#L323), [L424](https://github.com/nick-boss-tech/solr/blob/56ea43c448ed4fea75131d34c390d11233bab5cb/solr/core/src/java/org/apache/solr/handler/component/CombinedQueryComponent.java#L424)).
- The comparator uses the shard name when it is set, and the shard address when it is not ([ShardFieldSortedHitQueue.java L104-L118](https://github.com/nick-boss-tech/solr/blob/56ea43c448ed4fea75131d34c390d11233bab5cb/solr/core/src/java/org/apache/solr/handler/component/ShardFieldSortedHitQueue.java#L104-L118)).
- Behavior change: for every SolrCloud request, the order of tied documents changes once. This includes single-replica collections. Standalone requests and explicit shard URLs have no shard names, so they keep the address order.
- `ShardDoc` gets a new public field, `shardName` ([ShardDoc.java L30-L33](https://github.com/nick-boss-tech/solr/blob/56ea43c448ed4fea75131d34c390d11233bab5cb/solr/core/src/java/org/apache/solr/handler/component/ShardDoc.java#L30-L33)). Code that builds a `ShardDoc` without setting it keeps the address order.

## Limits

- No test checks tie order on the combined query path. The existing combined tests pass, but none checks the order of tied documents.
- The cluster test uses two shards on two nodes. It does not cover more shards or nodes.
- Code that builds a `ShardDoc` without `shardName` keeps the old order. The field is public, so other code can rely on it.
