## What happens today

**The expand search never calls `complete()` on its post filter, so that filter's final step is skipped.**

With `expand=true`, `ExpandComponent` runs a second search for the expanded groups. Unless `expand.fq` is given, that search reuses the query's filters, except collapse filters ([ExpandComponent.java lines 186-194 at the merge-base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/component/ExpandComponent.java#L186-L194)). When one of those filters is a post filter, the search runs its collector chain. At the merge-base, the search is followed directly by the exit check, with no `complete()` call between them ([lines 441-448 at the merge-base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/component/ExpandComponent.java#L441-L448)). A collapse filter given in `expand.fq` finishes its last segment in `complete()` ([CollapsingQParserPlugin.java lines 794-827](https://github.com/nick-boss-tech/solr/blob/680044f1d2a6a36b4543f4d52bb552e32b142919/solr/core/src/java/org/apache/solr/search/CollapsingQParserPlugin.java#L794-L827)), so its last group can be missing from the expanded section.

## What this change does

**The expand search now calls `complete()` on its collector chain after the search.**

- The call runs only when the search has a post filter chain ([ExpandComponent.java lines 450-453](https://github.com/nick-boss-tech/solr/blob/680044f1d2a6a36b4543f4d52bb552e32b142919/solr/core/src/java/org/apache/solr/handler/component/ExpandComponent.java#L450-L453)). Without one, the code path is unchanged.
- The main search already makes this call, inside a finally block ([SolrIndexSearcher.java lines 327-336](https://github.com/nick-boss-tech/solr/blob/680044f1d2a6a36b4543f4d52bb552e32b142919/solr/core/src/java/org/apache/solr/search/SolrIndexSearcher.java#L327-L336)). The expand search now makes it too, inside a finally block, so the call also runs when the search exits early.

## Proof

**A new test fails on the base code and passes with this change.**

- `TestExpandComponent.testExpandCompletesPostFilterCollectors` ([test lines 949-975](https://github.com/nick-boss-tech/solr/blob/680044f1d2a6a36b4543f4d52bb552e32b142919/solr/core/src/test/org/apache/solr/handler/component/TestExpandComponent.java#L949-L975)) runs an expand query with a test-only post filter ([CompleteTrackingQParserPlugin.java](https://github.com/nick-boss-tech/solr/blob/680044f1d2a6a36b4543f4d52bb552e32b142919/solr/core/src/test/org/apache/solr/handler/component/CompleteTrackingQParserPlugin.java)). The post filter counts the collectors it creates and the ones that get `complete()`. On the base code one collector is never completed.
- Verified 2026-10-15 at head 680044f1d2: TestExpandComponent 10 of 10. On the base code, with these tests in place, the class runs 10 tests and one fails: this test, on the completion counts (expected 2, was 1).
- A second test, `testExpandCompletesPostFilterCollectorsWhenQueryLimitExceeded`, trips an injected query limit inside the expand search and asserts the response is marked partial and every post filter collector is completed. It passes on the base code too: the limit stops the search through the searcher's partial-results exit, which completes the collector chain itself, so this test pins the limit scenario rather than discriminating for the change.

## Limits

**The test checks the `complete()` calls, not the expanded output.**

- The test's post filter keeps every document. On the base code the failing check is the call count, not the expanded groups.
- The test does not run a collapse filter through the expand search. The collapse case rests on reading the code.
- The call sits in a finally block, so it also runs when the expand search exits early. No test drives a search that actually throws out of the expand search; the query-limit test stops through the partial-results exit instead.
- The reporter's own case is not reproduced. The ticket describes an empty expand section. The reporter's post filter is an access-control filter that sends documents only in its finish step. The test uses a counting filter instead, so it does not cover that case.
