## What happens today

**Pivot faceting keeps building pivot values after the request's query limits are exceeded, and distributed pivot refinement keeps requesting refinements after a shard has answered with partial results.**

Other components check `timeAllowed`, `cpuAllowed` and `memAllowed` between units of work, for example [QueryComponent](https://github.com/nick-boss-tech/solr/blob/2ee19dc646329f21ef630df33ae9ebab7e239cbc/solr/core/src/java/org/apache/solr/handler/component/QueryComponent.java) and [FacetComponent](https://github.com/nick-boss-tech/solr/blob/2ee19dc646329f21ef630df33ae9ebab7e239cbc/solr/core/src/java/org/apache/solr/handler/component/FacetComponent.java). Pivot faceting did not check limits inside its value loop. The ticket reports that after `timeAllowed` trips, pivot building keeps running lookups that fail, for a long time. At the merge-base commit `97d973814336`, the value loop in [`doPivots`](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/core/src/java/org/apache/solr/handler/component/PivotFacetProcessor.java#L328-L345) runs a subset search for every value at every level.

In a distributed request there is a second gap: when a shard answers a pivot refinement request with partial results, the coordinator goes on to queue the next level of refinement requests, even though the counts it already holds are incomplete.

## What this change does

**The pivot loop checks the query limits before each value and stops at the first limit that has tripped, and the coordinator stops pivot refinement once a shard refinement answer is partial.**

[`doPivots`](https://github.com/nick-boss-tech/solr/blob/2ee19dc646329f21ef630df33ae9ebab7e239cbc/solr/core/src/java/org/apache/solr/handler/component/PivotFacetProcessor.java#L328-L333) reads the request's limits once and checks them before each value. When a limit has tripped, the loop stops and returns the values built so far. The response is marked partial, with the detail "Faceting pivots". The check runs at every level, because `doPivots` calls itself for sub-pivots.

In [`refinePivotFacets`](https://github.com/nick-boss-tech/solr/blob/2ee19dc646329f21ef630df33ae9ebab7e239cbc/solr/core/src/java/org/apache/solr/handler/component/FacetComponent.java#L1023-L1070), when any shard's refinement answer carries the partial marker, the coordinator marks its own response partial and does not queue further refinement requests.

Behavior change, stated openly: the check covers every limit the shared code knows, so `memAllowed` is included, not only `timeAllowed` and `cpuAllowed`. With `partialResults=false`, a tripped limit is reported in the response header as "omitted" and no pivot data is returned, so partial pivots are not handed back as if they were usable results.

**`TestQueryLimits` passes 7 of 7 at head `2ee19dc646329f21ef630df33ae9ebab7e239cbc`, and each production change has a test that fails without it.**

With the refinement change reverted (head `ae76f048005`, the same tests), `TestQueryLimits` runs 7 tests with exactly 1 failure: [`testPivotFacetRefinementStopsWhenPartial`](https://github.com/nick-boss-tech/solr/blob/2ee19dc646329f21ef630df33ae9ebab7e239cbc/solr/core/src/test/org/apache/solr/search/TestQueryLimits.java#L262-L298) sees a second round of refinement requests sent after the partial answers (5 tripped refinement requests against the asserted bound of 3, one per shard in the first round). At this head the second round is not sent and the test passes. Verified 2026-10-15 at this head.

[`testPivotFacetTruncatesWhenLimitsTrip`](https://github.com/nick-boss-tech/solr/blob/2ee19dc646329f21ef630df33ae9ebab7e239cbc/solr/core/src/test/org/apache/solr/search/TestQueryLimits.java#L142-L194) covers the loop check: on base production code it fails (the partial response carries no pivot data at all), and with the check it passes; that pair was verified on 2026-10-14 at the earlier head `24bd15ebb84e`.

`testPivotFacetOmitsResultsWhenPartialResultsDisallowed` passes with and without the refinement change. It pins the `partialResults=false` contract stated above: the header reports "omitted", the detail names the pivot limit check, and no pivot data is returned. `testPivotFacetRespectsLimits` also passes with and without this change; it checks the partial marker and the trip detail only. The limit trips are injected through test hooks (`CallerSpecificQueryLimit` and a refinement counting limit), not a real `timeAllowed` or `cpuAllowed` run.

## Limits

**The check runs between values. A limit that trips inside one value's search is not stopped sooner.**

- A limit that trips inside one value's subset search ends that search as before. This change does not stop it earlier.
- The refinement stop reads the partial marker on shard refinement answers. With `partialResults=false` those answers are marked "omitted" instead, so the early stop does not apply there; the final response still reports the omission in its header.
- The ticket points at the searcher's exception handling. This change does not touch that code. A follow-up in the searcher can be opened on request.
- No test measures how many lookups are saved. The tests check the response shape and the request counts at the trip point.
