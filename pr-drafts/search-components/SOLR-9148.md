## What happens today

**Filter queries sent to `/sql` are dropped, so they never reach the Solr queries that a SQL statement becomes.**

A caller can send `fq` values with the request, for example a geo filter such as `fq={!geofilt ...}` or an access filter. The SQL handler forwards only a fixed list of connection settings ([SQLHandler.java L121-L127](https://github.com/nick-boss-tech/solr/blob/30f0d7a42d501316bd9d5336fe564608e78bfbba/solr/modules/sql/src/java/org/apache/solr/handler/sql/SQLHandler.java#L121-L127)). The `fq` values are not among them, so the rows come back unfiltered.

## What this change does

**Each `fq` value is passed to every Solr query that the statement becomes.**

- `SQLHandler` stores the request's `fq` values as connection properties named `solr.sql.fq.0`, `solr.sql.fq.1`, and so on ([SQLHandler.java L133-L139](https://github.com/nick-boss-tech/solr/blob/30f0d7a42d501316bd9d5336fe564608e78bfbba/solr/modules/sql/src/java/org/apache/solr/handler/sql/SQLHandler.java#L133-L139)).
- `SolrTable` adds them to the parameters of each query it builds. The five builders are select, stats, facet group by, map_reduce group by, and select distinct under map_reduce ([SolrTable.java L313](https://github.com/nick-boss-tech/solr/blob/30f0d7a42d501316bd9d5336fe564608e78bfbba/solr/modules/sql/src/java/org/apache/solr/handler/sql/SolrTable.java#L313), [L544](https://github.com/nick-boss-tech/solr/blob/30f0d7a42d501316bd9d5336fe564608e78bfbba/solr/modules/sql/src/java/org/apache/solr/handler/sql/SolrTable.java#L544), [L663](https://github.com/nick-boss-tech/solr/blob/30f0d7a42d501316bd9d5336fe564608e78bfbba/solr/modules/sql/src/java/org/apache/solr/handler/sql/SolrTable.java#L663), [L805](https://github.com/nick-boss-tech/solr/blob/30f0d7a42d501316bd9d5336fe564608e78bfbba/solr/modules/sql/src/java/org/apache/solr/handler/sql/SolrTable.java#L805), [L897](https://github.com/nick-boss-tech/solr/blob/30f0d7a42d501316bd9d5336fe564608e78bfbba/solr/modules/sql/src/java/org/apache/solr/handler/sql/SolrTable.java#L897)).

Behavior change: a statement sent with `fq` values now runs with those filters in every plan shape above. Requests without `fq` are unchanged.

## Limits

**The select distinct path under map_reduce has no test.**

- The select distinct path under `aggregationMode=map_reduce` passes `fq` through the same helper. No test in this PR runs it. A test for it is a possible follow-up, and a PR for it can be opened on request.
- The `fq` values filter results. They do not authenticate the caller, and a caller who sends the request can leave them out.
- The JDBC driver adds no filter queries of its own.
