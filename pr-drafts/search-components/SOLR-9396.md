## What happens today

**A `[subquery]` fails when it reads a `$row.` field that the outer `fl` does not list.**

A subquery can read a value from the parent document with a reference such as `depts.q={!term f=dept_id_s v=$row.dept_id}`. The transformer does not ask the index for `dept_id`. If the outer `fl` does not list it, the field is missing from the document, and the transformer fails with `while invoking depts:[subquery] on doc=...` ([SubQueryAugmenterFactory.java L375-L396](https://github.com/nick-boss-tech/solr/blob/a5ab2eda4e6a9bcad5668653e80c0d0b510e6388/solr/core/src/java/org/apache/solr/response/transform/SubQueryAugmenterFactory.java#L375-L396)). The ticket's example fails with the same message. Its workaround is to list every referenced field in `fl`, or to use `fl=*`.

## What this change does

**The transformer asks the index for the fields its subquery references.**

When the transformer is created, it scans the subquery's own parameter values for `$row.field` references and adds those field names to the fields the request reads ([SubQueryAugmenterFactory.java L307-L362](https://github.com/nick-boss-tech/solr/blob/a5ab2eda4e6a9bcad5668653e80c0d0b510e6388/solr/core/src/java/org/apache/solr/response/transform/SubQueryAugmenterFactory.java#L307-L362)). The response shape does not change. A field that `fl` does not list is read for the subquery but is still not written to the response ([TestSubQueryTransformer.java L257-L283](https://github.com/nick-boss-tech/solr/blob/a5ab2eda4e6a9bcad5668653e80c0d0b510e6388/solr/core/src/test/org/apache/solr/response/transform/TestSubQueryTransformer.java#L257-L283)). A request that already lists the field sees no change. The cost is one extra field read for each referenced field that `fl` did not name.

## Proof

The base run used the base `SubQueryAugmenterFactory.java` with this test file. In that run the new test was the only failure in TestSubQueryTransformer: 1 of 11 failed, and the other 10 passed.
- At head a5ab2eda4e6a9bcad5668653e80c0d0b510e6388, verified 2026-10-05: TestSubQueryTransformer 11 of 11, TestSubQueryTransformerCrossCore 3 of 3, TestSubQueryTransformerDistrib 1 of 1, and TestChildDocTransformer 2 of 2 pass.

## A choice to check

**The transformer reads `$row.` names from the subquery's own parameters, not from every field of the request.**

Options considered: scan the subquery's parameter values for `$row.field` references (implemented), or read every field whenever a `[subquery]` is present. The scan reads only the fields a subquery names. It cannot see a reference that reaches the subquery through another request parameter (see Limits). Reading every field needs no scan, but then every subquery reads every field. Was the scan the right call?

## Limits

- Only a `$row.field` reference written in the subquery's own parameters is scanned. A reference that reaches the subquery through another request parameter is not scanned, so that field must still be listed in `fl`.
- The real-time get path (`/get`) uses the same field parsing, but no test covers it.
