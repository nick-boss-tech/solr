## What happens today

**HTTPS fails when a keystore's key password differs from its store password.**

The ticket reports that Solr fails to read the certificate when the store and key passwords differ. The default setup in `solr/server/etc/jetty-ssl.xml` passes only the keystore password and the truststore password to Jetty ([lines 14-19 at the merge-base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/server/etc/jetty-ssl.xml#L14-L19)). Solr does not pass a separate key password to Jetty, so a key whose password differs from the keystore password cannot be opened.

## What this change does

**It adds a setting for the key password and passes it to Jetty.**

A new environment variable, `SOLR_SSL_KEY_MANAGER_PASSWORD`, sets the Java property `solr.jetty.keymanager.password`. `SSLConfigurations` reads it through the existing credential providers ([line 37](https://github.com/nick-boss-tech/solr/blob/611eae2464536fdae61b8cae32abac97ee3a453b/solr/core/src/java/org/apache/solr/util/configuration/SSLConfigurations.java#L37), [lines 92-98](https://github.com/nick-boss-tech/solr/blob/611eae2464536fdae61b8cae32abac97ee3a453b/solr/core/src/java/org/apache/solr/util/configuration/SSLConfigurations.java#L92-L98)). `jetty-ssl.xml` passes the value to Jetty as `KeyManagerPassword` ([lines 17-21](https://github.com/nick-boss-tech/solr/blob/611eae2464536fdae61b8cae32abac97ee3a453b/solr/server/etc/jetty-ssl.xml#L17-L21)).

The setting is optional. When SSL is enabled, `bin/solr` exports the variable if it is set ([lines 229-231](https://github.com/nick-boss-tech/solr/blob/611eae2464536fdae61b8cae32abac97ee3a453b/solr/bin/solr#L229-L231)). The sample `solr.in.sh` and `solr.in.cmd` files list it as a commented line ([solr.in.sh lines 164-165](https://github.com/nick-boss-tech/solr/blob/611eae2464536fdae61b8cae32abac97ee3a453b/solr/bin/solr.in.sh#L164-L165), [solr.in.cmd lines 149-150](https://github.com/nick-boss-tech/solr/blob/611eae2464536fdae61b8cae32abac97ee3a453b/solr/bin/solr.in.cmd#L149-L150)).

## Proof

**A standalone Jetty run shows the mechanism, and the focused tests pass at this head.**

- Standalone run, outside Solr, on vm2 on 2026-10-11: a keystore whose key password differs from its store password could not be loaded with the keystore password alone (`UnrecoverableKeyException: Cannot recover key`). It loaded once the key manager password was set. Nothing from this run is on the branch.
- Focused tests at packaged head `611eae2464536fdae61b8cae32abac97ee3a453b` (the fork branch tip `55d8cd189d15` plus one commit that removes a root-level file): `SSLConfigurationsTest` 20 tests run, 0 failures, 0 errors, 0 skipped ([new tests at lines 184-199](https://github.com/nick-boss-tech/solr/blob/611eae2464536fdae61b8cae32abac97ee3a453b/solr/core/src/test/org/apache/solr/util/configuration/SSLConfigurationsTest.java#L184-L199)). `EnvSSLCredentialProviderTest` 2 tests, 0 failures. `SysPropSSLCredentialProviderTest` 2 tests, 0 failures.

## Limits

**The change is not run in a live server, and several parts are unverified.**

- The `jetty-ssl.xml` change was not run in a live Solr server. The standalone run shows the Jetty mechanism only, and the focused tests do not load `jetty-ssl.xml`.
- The unset case depends on Jetty accepting an empty reference in `jetty-ssl.xml`. That was not verified.
- Jetty may also read the JVM property `org.eclipse.jetty.ssl.keypassword` when the new setting is empty. That reading comes from the Jetty classes, not from a run.
- The reference guide page on enabling SSL (`enabling-ssl.adoc`) is not updated.
- `solr.cmd`, the Windows start script, was not checked.
- Server side only. SolrJ clients and the test framework have no key password setting in this change. A client setting would need its own ticket, and a follow-up can be opened on request.
