## What happens today

**HTTPS fails when a keystore's key password differs from its store password.**

The ticket reports that Solr fails to read the certificate when the store and key passwords differ. The default setup in `solr/server/etc/jetty-ssl.xml` passes only the keystore password and the truststore password to Jetty ([lines 14 to 21 at the merge-base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/server/etc/jetty-ssl.xml#L14-L21)). Solr does not pass a separate key password to Jetty, so a key whose password differs from the keystore password cannot be opened.

## What this change does

**It adds a setting for the key password and passes it to Jetty.**

A new environment variable, `SOLR_SSL_KEY_MANAGER_PASSWORD`, is read by the environment credential provider. The Java property `solr.jetty.keymanager.password` is read by the system property provider. `SSLConfigurations` reads both through the existing credential providers ([line 37](https://github.com/nick-boss-tech/solr/blob/2c68a83c64ee8d4e8bece83392ad4cf28eb5b55b/solr/core/src/java/org/apache/solr/util/configuration/SSLConfigurations.java#L37), [lines 92-98](https://github.com/nick-boss-tech/solr/blob/2c68a83c64ee8d4e8bece83392ad4cf28eb5b55b/solr/core/src/java/org/apache/solr/util/configuration/SSLConfigurations.java#L92-L98)). `jetty-ssl.xml` passes the value to Jetty as `KeyManagerPassword` ([lines 17-21](https://github.com/nick-boss-tech/solr/blob/2c68a83c64ee8d4e8bece83392ad4cf28eb5b55b/solr/server/etc/jetty-ssl.xml#L17-L21)). The variable maps to nothing in `EnvToSyspropMappings.properties`, as the other SSL password variables do, so it is not copied to a system property.

The setting is optional. When SSL is enabled, `bin/solr` exports the variable if it is set ([lines 229-231](https://github.com/nick-boss-tech/solr/blob/2c68a83c64ee8d4e8bece83392ad4cf28eb5b55b/solr/bin/solr#L229-L231)). The sample `solr.in.sh` and `solr.in.cmd` files list it as a commented line ([solr.in.sh lines 164-165](https://github.com/nick-boss-tech/solr/blob/2c68a83c64ee8d4e8bece83392ad4cf28eb5b55b/solr/bin/solr.in.sh#L164-L165), [solr.in.cmd lines 149-150](https://github.com/nick-boss-tech/solr/blob/2c68a83c64ee8d4e8bece83392ad4cf28eb5b55b/solr/bin/solr.in.cmd#L149-L150)).

## Limits

- **The standalone run used a JKS keystore.** A PKCS12 keystore cannot carry a key password that differs from its store password, so the run does not cover PKCS12.

**The change is not run in a live server, and several parts are unverified.**

- The `jetty-ssl.xml` change was not run in a live Solr server. The standalone run shows the Jetty mechanism only, and the focused tests do not load `jetty-ssl.xml`.
- The unset case depends on Jetty accepting an empty reference in `jetty-ssl.xml`. That was not verified.
- Jetty may also read the JVM property `org.eclipse.jetty.ssl.keypassword` when the new setting is empty. That reading comes from the Jetty classes, not from a run.
- The reference guide page on enabling SSL (`enabling-ssl.adoc`) is not updated.
- `solr.cmd`, the Windows start script, was not checked.
- Server side only. SolrJ clients and the test framework have no key password setting in this change. A client setting would need its own ticket, and a follow-up can be opened on request.
- **Custom `class://` credential providers receive the new credential type.** They load at every server start and get the new type unchanged. None of them has key manager support, and this change does not alter them.
