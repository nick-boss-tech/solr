## What happens today

**`SSLConfigurationsFactory.current()` checks a static field twice, and the first check runs outside the lock. The field is not `volatile`.**

The first check is at [line 32](https://github.com/nick-boss-tech/solr/blob/9b3a84b1c460981eab09d8ffaef776acc4a184f8/solr/core/src/java/org/apache/solr/util/configuration/SSLConfigurationsFactory.java#L32-L33) of the base commit, and the field is declared at [line 23](https://github.com/nick-boss-tech/solr/blob/9b3a84b1c460981eab09d8ffaef776acc4a184f8/solr/core/src/java/org/apache/solr/util/configuration/SSLConfigurationsFactory.java#L23). Java does not guarantee that a thread reading a non-volatile field outside the lock sees a fully built `SSLConfigurations` object. The ticket's title is "Double-checked Locking Should Not be Used".

## What this change does

**It makes the field `volatile`. That is the only production change.**

- The field is declared `volatile` ([line 23 at the head](https://github.com/nick-boss-tech/solr/blob/73504e7a8dcb58e8f77c976d98db600af6fc5ced/solr/core/src/java/org/apache/solr/util/configuration/SSLConfigurationsFactory.java#L23)).
- The change adds `SSLConfigurationsFactoryTest` with two tests. [testLazilyInitializedSingletonIsVolatile](https://github.com/nick-boss-tech/solr/blob/73504e7a8dcb58e8f77c976d98db600af6fc5ced/solr/core/src/test/org/apache/solr/util/configuration/SSLConfigurationsFactoryTest.java#L33-L39) reads the field's modifier by reflection. [testConcurrentCurrentReturnsSingleInstance](https://github.com/nick-boss-tech/solr/blob/73504e7a8dcb58e8f77c976d98db600af6fc5ced/solr/core/src/test/org/apache/solr/util/configuration/SSLConfigurationsFactoryTest.java#L41-L69) starts eight threads that call `current()` together and checks that they all get the same instance.

## Proof

**The reflection test fails on the base code, and the test class passes at this head.**

- `SSLConfigurationsFactoryTest` at head `73504e7a8dcb`: 2 tests, 0 failures, 0 errors, 0 skipped (verified 2026-10-11).
- Base commit `9b3a84b1c460`, with only the test file added: 2 tests, 1 failure, 0 errors. `testLazilyInitializedSingletonIsVolatile` fails with "double-checked locking requires a volatile field". `testConcurrentCurrentReturnsSingleInstance` passes on the base code too.

## Limits

**The proof checks the field's declaration. It does not show a runtime failure.**

- No failure has been seen at this site in practice. The change follows the Java memory model rule for this pattern.
- The concurrency test passes without the change, so it does not show the race happening.
- An instance field named `apis` in `SecurityConfHandler` uses the same unsynchronized first check ([base commit, lines 284 and 289-292](https://github.com/nick-boss-tech/solr/blob/9b3a84b1c460981eab09d8ffaef776acc4a184f8/solr/core/src/java/org/apache/solr/handler/admin/SecurityConfHandler.java#L284-L292)).
