## What happens today

**Multi-node cloud tests run under Lucene's HandleLimitFS, which caps open files for the whole JVM.**

The links in this section go to the merge-base, `cabedd1d968`. [SolrCloudTestCase](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/test-framework/src/java/org/apache/solr/cloud/SolrCloudTestCase.java#L86) and [BaseDistributedSearchTestCase](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/test-framework/src/java/org/apache/solr/BaseDistributedSearchTestCase.java#L109) inherit only the ExtrasFS suppression from [SolrTestCaseJ4](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/test-framework/src/java/org/apache/solr/SolrTestCaseJ4.java#L150-L153). So HandleLimitFS applies to them. It allows a fixed number of open files for the whole JVM, and a test that starts several nodes in one JVM can exceed that number.

## What this change does

**The two multi-node base classes now suppress HandleLimitFS as well as ExtrasFS. This changes test base classes only.**

[SolrCloudTestCase](https://github.com/nick-boss-tech/solr/blob/8745afd00cf99597c24ee12764fc7b3d7dc7870e/solr/test-framework/src/java/org/apache/solr/cloud/SolrCloudTestCase.java#L86-L89) and [BaseDistributedSearchTestCase](https://github.com/nick-boss-tech/solr/blob/8745afd00cf99597c24ee12764fc7b3d7dc7870e/solr/test-framework/src/java/org/apache/solr/BaseDistributedSearchTestCase.java#L110-L113) each declare `@SuppressFileSystems({"ExtrasFS", "HandleLimitFS"})`. A subclass annotation replaces the one it inherits, so both classes repeat ExtrasFS. Every cloud test that extends them inherits the change. No server code changes.

Behavior change: cloud tests no longer run under the handle-limit file system, so a test that opens too many files no longer fails for that reason.

## A choice to check

**The change suppresses the handle limit on every cloud base class. The alternative is a per-node limit, which needs a change in Lucene.**

The implemented route is the simpler one, and its cost is that every cloud test loses the handle limit. The other route keeps a limit, but it counts open files per node, and that needs a change in Lucene's test framework. Was suppressing the limit on the base classes the right call?

## Proof

**The new test reads the annotations, so it fails on the base code and passes with this change. It does not start a cluster.**

[`CloudTestBaseFileSystemsTest`](https://github.com/nick-boss-tech/solr/blob/8745afd00cf99597c24ee12764fc7b3d7dc7870e/solr/core/src/test/org/apache/solr/cloud/CloudTestBaseFileSystemsTest.java#L31-L45) passes 1 of 1 at head `8745afd00c`, verified 2026-10-14. The check covers three classes: SolrCloudTestCase, BaseDistributedSearchTestCase, and AbstractFullDistribZkTestBase, which declares no annotation of its own. On the base code, with the two base classes reverted to the merge base and the test kept, the run gives 1 test and 1 failure: "SolrCloudTestCase [ExtrasFS]". That run was verified 2026-10-12 at head `eb8c4060d9`. The test file is the same at `8745afd00c`. The check fails at its first assertion, because HandleLimitFS is missing from that list.

At head `8745afd00c`, the formatting check makes no changes, Error Prone compiles, and the module check passes.

## Limits

**The test shows that the suppression is declared on three base classes. It does not show that cloud tests stay under the limit.**

- The test reads the annotations by reflection and starts no cluster.
- It does not reproduce the handle limit itself.
