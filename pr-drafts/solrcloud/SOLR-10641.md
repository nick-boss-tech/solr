## What happens today

**Finishing a synchronous overseer task takes two separate ZooKeeper calls, and nothing ties them together.**

When the caller waits for the result, `OverseerTaskQueue.remove` writes the response node with `setData`, then deletes the request node with `delete` ([OverseerTaskQueue.java L118-L134](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/cloud/OverseerTaskQueue.java#L118-L134)). That link goes to the merge-base, the code before this change. Each call is its own round trip to ZooKeeper. If the response node is already gone, the write is skipped with an info log, and the delete still runs.

## What this change does

**The response write and the request delete now go in one ZooKeeper multi transaction.**

For a synchronous task, `remove` first tries one multi that sets the response data and deletes the request node, both with version -1 ([OverseerTaskQueue.java L123-L125](https://github.com/nick-boss-tech/solr/blob/fbc1f47b280843278a6c9ddbc8d6dbd1fe37cdc0/solr/core/src/java/org/apache/solr/cloud/OverseerTaskQueue.java#L123-L125); the helper is at [L151-L163](https://github.com/nick-boss-tech/solr/blob/fbc1f47b280843278a6c9ddbc8d6dbd1fe37cdc0/solr/core/src/java/org/apache/solr/cloud/OverseerTaskQueue.java#L151-L163)). If the multi does not apply, for example because the response node is already gone, the code runs the two calls it made before, so those cases behave as they did. Asynchronous tasks, which write no response, still only delete the request node.

On the normal path, the two writes now land together. A reader can no longer see the response written while the request node still exists.

## Proof

**OverseerTaskQueueTest passes 9 of 9 at head fbc1f47b2808, verified 2026-10-11. This proof cannot tell the change apart from the old code.**

The two new tests, [testRemoveSetsResponseAndDeletesRequest and testRemoveWithMissingResponseNodeStillDeletesRequest](https://github.com/nick-boss-tech/solr/blob/fbc1f47b280843278a6c9ddbc8d6dbd1fe37cdc0/solr/core/src/test/org/apache/solr/cloud/OverseerTaskQueueTest.java#L41-L73), check the behavior the old code already has. On the base code (merge-base `cabedd1d968`, with the branch's tests kept), verified 2026-10-11, the class runs 9 tests with 0 failures, so both new tests pass there too.

## Limits

**The tests check behavior, not speed. Reads and the batched deletes are not changed.**

- The tests do not measure round trips. The saving of one round trip per synchronous task follows from the calls, but it is not measured here.
- Deleting many queue items in one multi is already in place, in batches of 1000 ([ZkDistributedQueue.java L213-L232 at the merge-base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/cloud/ZkDistributedQueue.java#L213-L232)). This change does not touch that path.
- Reads of the queue, including `getData`, are not changed.
