## What happens today

**ADDREPLICA fails when the request sets `property.coreNodeName`.**

The ticket reports that a Collections API `ADDREPLICA` request with `property.coreNodeName=foo` fails with "coreNodeName user_assigned_node_name does not exist in shard shard1". The base code reads the replica's name only from `coreNodeName` ([merge-base, line 352](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/cloud/api/collections/AddReplicaCmd.java#L352)).

## What this change does

**It uses `property.coreNodeName` as the replica's name for one replica. For several replicas, it returns a 400 error.**

- With no `coreNodeName`, the replica takes its name from `property.coreNodeName` ([lines 360-363 at the head](https://github.com/nick-boss-tech/solr/blob/6f739cfbbd383f08e7393ea38358b7fc77254e58/solr/core/src/java/org/apache/solr/cloud/api/collections/AddReplicaCmd.java#L360-L363)). If both are set for one replica, `coreNodeName` wins.
- The existing several-replica check now also refuses `property.coreNodeName`. Its message names both parameters ([lines 141-149 at the head](https://github.com/nick-boss-tech/solr/blob/6f739cfbbd383f08e7393ea38358b7fc77254e58/solr/core/src/java/org/apache/solr/cloud/api/collections/AddReplicaCmd.java#L141-L149)).

## Proof

**The two new tests fail on the base code and pass with this change.**

- `CollectionsAPISolrJTest` at head `360dca60fcfa`, verified 2026-10-11. The branch tip `6f739cfbbd3` has the same file contents (checked 2026-10-13): 26 tests, 0 failures, 0 errors, 1 conditional skip (`testCreateAndDeleteShard`, an existing assumption tied to SOLR-13021). Both new tests pass.
- Base commit `cabedd1d9680`, with the branch's tests in place, verified 2026-10-11: both new tests fail, 2 failures and 0 errors. `testAddReplicaWithCoreNodeNameProperty` fails with "ADDREPLICA failed to create replica". `testAddReplicaWithCoreNodeNamePropertyRejectsMultipleReplicas` gets HTTP 500 where this change returns 400.

## A choice to check

**Several replicas are refused rather than given derived names.**

1. Implemented: refuse several replicas. The shard keeps its replicas in a map keyed by name ([Slice.java, line 91 at the head](https://github.com/nick-boss-tech/solr/blob/6f739cfbbd383f08e7393ea38358b7fc77254e58/solr/solrj/src/java/org/apache/solr/common/cloud/Slice.java#L91)), so one name cannot stand for several replicas.
2. Derive a distinct name for each replica from the given value. This would need a naming rule the ticket does not define, plus tests for it.

Was refusing several replicas the right call, or should each replica get a derived name?

## Limits

**Only the ADDREPLICA path changes. Other Collections API commands are not covered.**

- The ticket covers one replica. For several replicas, this change returns HTTP 400 where the base code returned HTTP 500. The ticket does not cover that case.
- No test in this branch sets both `coreNodeName` and `property.coreNodeName` on one request.
- Landing order: this PR opens only after [SOLR-15035](https://issues.apache.org/jira/browse/SOLR-15035), and lands after it. That change also edits `AddReplicaCmd.java` at another spot. This branch is not rebased onto it.
