## What happens today

**A RESTORE that fails after it creates the new collection leaves that collection in place, with copied data that cannot be read.**

A restore creates the target collection, uploads the collection properties, creates one replica per shard, and copies the index files into those replicas. If a step fails, nothing removes the collection. The ticket reports a restore into a Solr 7.x node that failed this way and left a collection that could not be read.

## What this change does

**A failure before the restored shards become active now deletes the new collection.**

The cleanup covers the property upload, the replica setup, and the copy of the index files ([RestoreCmd.java](https://github.com/nick-boss-tech/solr/blob/f3131d1ee8463388c68f18deab3c4ac3262ead83/solr/core/src/java/org/apache/solr/cloud/api/collections/RestoreCmd.java#L265-L316)). If the cleanup fails too, its error is attached to the restore error, and the restore error is still thrown.

Behavior change: a failed restore no longer leaves its target collection behind for these steps, so the collection name is free again for a new attempt.

## A choice to check

**The implemented route deletes the new collection on failure, and the alternative keeps it so a retry can resume.**

Options considered: delete the new collection when a restore fails (implemented), or keep the partly restored collection so that a retry can pick up where the failed one stopped. A comment on the ticket asks whether cleanup should be optional for that reason. Deleting costs a retry its progress on a large restore. Keeping leaves a half-built collection in the cluster until someone removes it.

Was deleting on failure the right call, or should cleanup be optional so that a retry can resume?

## Limits

**Failures after the shards are active do not delete the collection.**

- Adding the remaining replicas and restoring the alias happen after the shards are active. A failure there leaves the restored collection in place, as before. A follow-up can cover those steps on request.
- A restore that runs asynchronously does not delete the collection when a shard copy fails, because that failure shows only in the async status. A follow-up can add that check on request.
