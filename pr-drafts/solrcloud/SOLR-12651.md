## What happens today

**A RESTORE that throws an error after it creates the new collection leaves that collection in place.**

A restore creates the target collection, uploads the collection properties, creates one replica per shard, and copies the index files into those replicas. If a step throws an error, nothing removes the collection. The ticket reports a restore into a Solr 7.x node that failed this way and left a collection that could not be read.

## What this change does

**A failure before the restored shards become active now deletes the new collection, except a failed shard copy in an async restore.**

The cleanup covers the property upload, the replica setup, and the copy of the index files ([RestoreCmd.java](https://github.com/nick-boss-tech/solr/blob/404f13b501c97d6c6b65743a27f54f4f38363afa/solr/core/src/java/org/apache/solr/cloud/api/collections/RestoreCmd.java#L265-L316)). If the cleanup fails too, its error is attached to the restore error, and the restore error is still thrown.

Behavior change: a failed restore no longer leaves its target collection behind for these steps, so the collection name is free again for a new attempt.

## A choice to check

**The implemented route deletes the new collection on failure, and the alternative keeps it so a retry can resume.**

Options considered: delete the new collection when a restore fails (implemented), keep the partly restored collection so that a retry can pick up where the failed one stopped, or make cleanup optional, with delete as the default. Tomas Lobbe asked on the ticket whether cleanup should be optional, even if it stays the default. Deleting costs a retry its progress on a large restore. Keeping leaves a half-built collection in the cluster until someone removes it.

Was deleting on failure the right call, or should cleanup be optional, even as the default, so that a retry can resume?

## Limits

**Failures after the shards are active still leave the collection in place, and so does a failed shard copy in an async restore.**

- Adding the remaining replicas and restoring the alias happen after the shards are active, so a failure there is not cleaned up. A follow-up can cover those steps on request.
- An async restore does not delete the collection when a shard copy fails, because that failure shows only in the async status. A follow-up can add that check on request.
- The ticket asks that the per-file copy messages be DEBUG. Those messages are not in the current restore code. This change adds one ERROR line for the cleanup and changes no existing log level.
