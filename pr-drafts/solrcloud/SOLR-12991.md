## What happens today

**When a recovering replica cannot reach its leader, the log line leaves out the cause.**

In [pingLeader](https://github.com/apache/solr/blob/97d973814336101e12475558d7419321c743de79/solr/core/src/java/org/apache/solr/cloud/RecoveryStrategy.java#L829-L836), both connect-failure catches log "Failed to connect leader {} on recovery, try again" at ERROR. The exception is not passed to the logger, so the log shows the leader URL and no reason. The Jira report asks for the root cause in this message.

## What this change does

**Both connect-failure messages now include the exception, at WARN level.**

The two catches in [pingLeader](https://github.com/nick-boss-tech/solr/blob/1a86966179e1817e4572fb0008a3b82a7c14184f/solr/core/src/java/org/apache/solr/cloud/RecoveryStrategy.java#L829-L837) pass the exception to the logger and log at WARN. Each failed attempt now writes a stack trace.

## Proof

**RecoveryStrategyLeaderUnreachableLogTest passes 1 of 1 at head 1a86966179e, verified 2026-10-06.**

The test points the leader's base_url at a port with nothing listening, then asks the follower to recover. It waits up to 60 seconds for a WARN from RecoveryStrategy that carries the exception, and checks that an IOException is in the cause chain. On the base code the message is logged at ERROR, so no WARN arrives and the test fails.

## A choice to check

**The message moves from ERROR to WARN. The ticket asks for WARN or ERROR, and ERROR is already there. Was WARN the right level?**

Keeping ERROR and adding the cause would also meet the ticket as written. A 2018 comment on the ticket says a failed connection during a cluster change is normal, and it sounds more like information than a warning.

## Limits

**Only two catches change, each retry logs more text, and the test simulates the leader rather than stopping it.**

- Only the two connect catches in pingLeader change. Other recovery log lines are unchanged.
- Each retry now writes a stack trace, so a long outage writes more log text.
- The test simulates an unreachable leader by changing its base_url in the collection state. It does not stop a node, so leader election timing is not covered.
