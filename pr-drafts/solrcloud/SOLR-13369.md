## What happens today

**The TriLevelCompositeIdRoutingTest check assumes one route prefix never spans two shards, and the test was disabled for this ticket.**

The test checks that each route prefix, such as `app9/2!user32`, appears in one shard only. The ticket records a failing run where that prefix was found in two shards. The reporter's reading is that a bit-masked prefix fixes only the leading bits of the hash, so its hash range can cross a shard boundary.

## What this change does

**The test accepts a prefix in several shards when the router searches all of those shards for that prefix.**

For each prefix, the test records every shard that holds it. It then checks that the router's search slices for that prefix include each of those shards ([TriLevelCompositeIdRoutingTest.java](https://github.com/nick-boss-tech/solr/blob/dfa0db5bdf96d119d985a8b895ff90c4d783ad47/solr/core/src/test/org/apache/solr/cloud/TriLevelCompositeIdRoutingTest.java#L143-L157)). The missing and duplicate document checks stay. The `@AwaitsFix` marker is removed, so the test runs again. The change touches the test and its changelog only.

## Proof

**No run has shown the old failure. The proof is inconclusive by construction.**

`TriLevelCompositeIdRoutingTest` 1 of 1 at head `dfa0db5bdf96`, recorded 2026-10-07. On the base code, the same test passes 1 of 1 at this head, recorded 2026-10-07, because no route prefix spanned two shards in that run. The evidence rests on the ticket's recorded failure and on the router's search code. No run has shown this test failing without the change.

## A choice to check

**The test's rule changed, and the router did not.**

The reporter suspected the bit-mask prefix handling from SOLR-13210 is the bug, and a later comment agrees that with a bit mask, neither the app prefix nor the app!user prefix is guaranteed to stay in one shard. This change keeps the router and changes the test to match the router's search. The other route changes the router so that a prefix stays in one shard. That changes where new documents are placed, and documents already indexed stay where they are. Was it right to change the test rather than the router?

## Limits

**The test cannot catch a routing bug that both the router and the test share.**

- The change does not alter routing. The test checks the router against the router's own search.
- The reporter asked whether the test or the router is at fault. This change takes the test side. It does not decide whether the router should keep a bit-masked prefix in one shard.
