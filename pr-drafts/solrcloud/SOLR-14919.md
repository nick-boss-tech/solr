## What happens today

**Solr's own internal commits can be rejected when IgnoreCommitOptimizeUpdateProcessorFactory is in the update chain.**

A replica's recovery commit to its leader carries no marker. The processor treats it as a client commit and rejects it with the configured status, 403 by default ([IgnoreCommitOptimizeUpdateProcessorFactory.java](https://github.com/nick-boss-tech/solr/blob/84e7bcaeb57d88e1d9d519389d96ff14a66acb6e/solr/core/src/java/org/apache/solr/update/processor/IgnoreCommitOptimizeUpdateProcessorFactory.java#L64)). Commits that Solr forwards between nodes carry the values `leaders` and `replicas` ([DistributedZkUpdateProcessor.java](https://github.com/nick-boss-tech/solr/blob/84e7bcaeb57d88e1d9d519389d96ff14a66acb6e/solr/core/src/java/org/apache/solr/update/processor/DistributedZkUpdateProcessor.java#L218)). The processor reads that marker as a boolean, so those values fail with `400 invalid boolean value`.

## What this change does

**The processor accepts the internal markers, and recovery commits now send one.**

The processor treats `true`, `leaders`, and `replicas` as internal ([IgnoreCommitOptimizeUpdateProcessorFactory.java](https://github.com/nick-boss-tech/solr/blob/84e7bcaeb57d88e1d9d519389d96ff14a66acb6e/solr/core/src/java/org/apache/solr/update/processor/IgnoreCommitOptimizeUpdateProcessorFactory.java#L117-L130)). Any other value now takes the client path, where it used to fail with 400. Recovery commits now set `commit_end_point=true` ([RecoveryStrategy.java](https://github.com/nick-boss-tech/solr/blob/84e7bcaeb57d88e1d9d519389d96ff14a66acb6e/solr/core/src/java/org/apache/solr/cloud/RecoveryStrategy.java#L302-L304)).

The recovery change affects every cluster, not only chains with this processor. The leader now commits itself and forwards only to its own shard's replicas. Before, the commit also went to the leader of every other shard ([DistributedZkUpdateProcessor.java](https://github.com/nick-boss-tech/solr/blob/84e7bcaeb57d88e1d9d519389d96ff14a66acb6e/solr/core/src/java/org/apache/solr/update/processor/DistributedZkUpdateProcessor.java#L215-L219)).

## Proof

**The processor test fails on the base processor and passes with this change. The recovery change has no test.**

`IgnoreCommitOptimizeUpdateProcessorFactoryTest` 1 of 1 at head `84e7bcaeb57`, recorded 2026-10-03. The new loop sends `leaders` and `replicas` ([test](https://github.com/nick-boss-tech/solr/blob/84e7bcaeb57d88e1d9d519389d96ff14a66acb6e/solr/core/src/test/org/apache/solr/update/processor/IgnoreCommitOptimizeUpdateProcessorFactoryTest.java#L63-L76)). On the base processor it fails with `invalid boolean value: leaders`. With this change it passes. The test calls the processor directly. No test runs a replica recovery or a distributed commit on a cluster.

## A choice to check

**Should the recovery marker ship in this change?**

Upstream commented out the recovery marker in [75b183196798](https://github.com/apache/solr/commit/75b183196798232aa6f2dcaaaab117f309119053), a commit that also lists SOLR-12933, "Fix SolrCloud distributed commit." Without the marker, a recovering replica's commit still reaches the processor as a client commit. The other route is to ship the processor change alone and move the recovery marker to its own ticket with its own test. This branch keeps the marker, which changes which shards receive the recovery commit. Was it right to re-enable the marker in this change?

## Limits

- Any client can send `commit_end_point`, and the processor does not check where a request came from. This was already true for `true`. The change adds `leaders` and `replicas`. If the processor is meant to block client commits, a provenance check is a separate change. A follow-up can take that on if you want it.
- The distributed path is not tested on a cluster.
- Marker values the processor does not recognize now take the client path, where they used to fail with 400.
