## What happens today

**Commits that Solr forwards between nodes fail when IgnoreCommitOptimizeUpdateProcessorFactory is in the update chain.**

The distributed update processor sets `commit_end_point` to `leaders` or `replicas` when it forwards a commit ([DistributedZkUpdateProcessor.java L218-L235](https://github.com/nick-boss-tech/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/update/processor/DistributedZkUpdateProcessor.java#L218-L235), code at merge-base b5c71bc5573c, before this change). The processor reads that value as a boolean, so the forwarded commit fails with `400 invalid boolean value`.

The ticket also reports replica recovery failing on a status other than 200.
## What this change does

**The processor accepts the forwarded values `leaders` and `replicas` as internal commits.**

The processor treats `true`, `leaders`, and `replicas` as internal ([IgnoreCommitOptimizeUpdateProcessorFactory.java L117-L130](https://github.com/nick-boss-tech/solr/blob/483b3885f6439391a3128e6c61be34fc47122514/solr/core/src/java/org/apache/solr/update/processor/IgnoreCommitOptimizeUpdateProcessorFactory.java#L117-L130)). Any other non-boolean value now takes the client path, where it used to fail with 400. The change is the processor only.

## Proof

**The processor test fails on the base processor and passes with this change.**

`IgnoreCommitOptimizeUpdateProcessorFactoryTest` 1 of 1, 0 failures, 0 errors, 0 skipped; verified 2026-10-14 at head 483b3885f643. The [test](https://github.com/nick-boss-tech/solr/blob/483b3885f6439391a3128e6c61be34fc47122514/solr/core/src/test/org/apache/solr/update/processor/IgnoreCommitOptimizeUpdateProcessorFactoryTest.java#L63-L75) sends `leaders` and `replicas`. On the base processor (merge-base b5c71bc5573c) it fails with `invalid boolean value: leaders`. With this change it passes.

## Limits

**The replication failure in the ticket is not fixed here.**

- A replica's recovery commit carries no marker. The processor treats it as a client commit and rejects it with the configured status, 403 by default ([IgnoreCommitOptimizeUpdateProcessorFactory.java L63](https://github.com/nick-boss-tech/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/update/processor/IgnoreCommitOptimizeUpdateProcessorFactory.java#L63), code at merge-base b5c71bc5573c, before this change). The recovery marker that would set `commit_end_point=true` on recovery commits changes which shards receive the commit. It needs its own ticket and test. A follow-up ticket and PR can cover it on request. Upstream commit [75b183196798](https://github.com/apache/solr/commit/75b183196798232aa6f2dcaaaab117f309119053) (SOLR-12933) changed the forwarded values to `leaders` and `replicas`, and commented out the marker that `RecoveryStrategy` set on recovery commits. Its message gives no reason for that.
- Any client can send `commit_end_point`. The processor does not check the source, which was already true for `true`. A follow-up can add a provenance check if you want one.
- The distributed path is not tested on a cluster.
