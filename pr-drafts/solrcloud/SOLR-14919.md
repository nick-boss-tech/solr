## What happens today

**Commits that Solr forwards between nodes fail when IgnoreCommitOptimizeUpdateProcessorFactory is in the update chain.**

The distributed update processor sets `commit_end_point` to `leaders` or `replicas` when it forwards a commit ([DistributedZkUpdateProcessor.java L218-L235](https://github.com/nick-boss-tech/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/update/processor/DistributedZkUpdateProcessor.java#L218-L235), code before this change). The processor reads that value as a boolean, so the forwarded commit fails with `400 invalid boolean value`.

## What this change does

**The processor accepts the forwarded values `leaders` and `replicas` as internal commits.**

The processor treats `true`, `leaders`, and `replicas` as internal ([IgnoreCommitOptimizeUpdateProcessorFactory.java L117-L130](https://github.com/nick-boss-tech/solr/blob/c1fa37e33c1e00ab06ed59646b6a739facf50017/solr/core/src/java/org/apache/solr/update/processor/IgnoreCommitOptimizeUpdateProcessorFactory.java#L117-L130)). Any other value now takes the client path, where it used to fail with 400. The change is the processor only. Replica recovery commits are not changed; see Limits.

## Proof

**The processor test fails on the base processor and passes with this change.**

`IgnoreCommitOptimizeUpdateProcessorFactoryTest` 1 of 1 at head 84e7bcaeb57. The processor code is unchanged since that head. Only its javadoc changed. The loop sends `leaders` and `replicas` ([test](https://github.com/nick-boss-tech/solr/blob/c1fa37e33c1e00ab06ed59646b6a739facf50017/solr/core/src/test/org/apache/solr/update/processor/IgnoreCommitOptimizeUpdateProcessorFactoryTest.java#L63-L75)). On the base processor it fails with `invalid boolean value: leaders`. With this change it passes. The test calls the processor directly. No test runs a replica recovery or a distributed commit on a cluster.

## Limits

**Recovery commits still carry no marker, and a client can still send these values.**

- A replica's recovery commit carries no marker. The processor treats it as a client commit and rejects it with the configured status, 403 by default, when the processor is in the chain ([IgnoreCommitOptimizeUpdateProcessorFactory.java L63](https://github.com/nick-boss-tech/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/update/processor/IgnoreCommitOptimizeUpdateProcessorFactory.java#L63), code before this change). This change does not fix that. The recovery marker that would set `commit_end_point=true` on recovery commits changes which shards receive the commit. It needs its own ticket and test. Upstream commented that marker out in [75b183196798](https://github.com/apache/solr/commit/75b183196798232aa6f2dcaaaab117f309119053), a commit that also lists SOLR-12933. The reason for that change has not been read yet.
- Any client can send `commit_end_point`, and the processor does not check where a request came from. This was already true for `true`. The change adds `leaders` and `replicas`. If the processor is meant to block client commits, a provenance check is a separate change. A follow-up can take that on if you want it.
- Marker values the processor does not recognize now take the client path, where they used to fail with 400.
- The distributed path is not tested on a cluster.
