## What happens today

**A replica added with ADDREPLICA has no numShards entry in its core.properties. A replica created with CREATE has one.**

The ADDREPLICA request builds the create parameters without the shard count, so the core.properties it writes lacks the entry that CREATE writes.

## What this change does

**ADDREPLICA now sends the collection's shard count with its create request, and the v2 create path keeps it.**

The count is the number of slices in the collection's cluster state at that moment ([AddReplicaCmd.java](https://github.com/nick-boss-tech/solr/blob/12d7491e82cd660ad55063cb85633b7e05e1918c/solr/core/src/java/org/apache/solr/cloud/api/collections/AddReplicaCmd.java#L305)). The CoreAdmin create mapping now copies that value into the core properties ([CoreAdminHandler.java](https://github.com/nick-boss-tech/solr/blob/12d7491e82cd660ad55063cb85633b7e05e1918c/solr/core/src/java/org/apache/solr/handler/admin/CoreAdminHandler.java#L250)).

## Proof

**The new test fails with the ADDREPLICA change alone, and passes with the full change.**

- AddReplicaTest 4 of 4 at 12d7491e82c, recorded 2026-10-03. The new test is [testAddReplicaPersistsNumShardsInCoreProperties](https://github.com/nick-boss-tech/solr/blob/12d7491e82cd660ad55063cb85633b7e05e1918c/solr/core/src/test/org/apache/solr/cloud/AddReplicaTest.java#L238-L265). On the base code, ADDREPLICA sends no shard count, so the new core has no numShards entry in core.properties.
- Sending the count from ADDREPLICA alone is not enough, recorded 2026-10-03. The v2 create path (`CreateCore`) copies only the parameters on its allowlist ([paramToProp](https://github.com/nick-boss-tech/solr/blob/12d7491e82cd660ad55063cb85633b7e05e1918c/solr/core/src/java/org/apache/solr/handler/admin/CoreAdminHandler.java#L239-L251)). The count was not on that list, so the test failed. The list entry is required.
- Adjacent suites at the same head, same date: CoreAdminHandlerTest 8 of 8 and CoreAdminOperationTest 44 of 44.

## A choice to check

**The implemented route records every slice. The reporter asked whether the entry should exist at all.**

The reporter asked whether numShards belongs in core.properties, and wanted the two routes consistent. Two other routes exist. Counting only active slices (`getActiveSlices()`) needs a filter in AddReplicaCmd and a test on a split collection. Dropping numShards from both routes changes the files CREATE writes today. Was recording every slice the right call, or should the count follow the active shards, or the entry go?

## Limits

**The count is the current slice count, so after a shard split it can be higher than the shard count the collection was created with.**

- After a split, the inactive parent shard stays in the cluster state and is counted. A replica added after a split can therefore record a higher number than the original shard count. The test does not cover a split collection.
- Replicas created before this change keep their existing core.properties.
