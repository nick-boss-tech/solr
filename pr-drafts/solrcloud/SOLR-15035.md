## What happens today

**A replica added with ADDREPLICA has no numShards entry in its core.properties. A replica created with CREATE has one.**

The ticket summary describes this difference. The ADDREPLICA request builds the create parameters for the new core without the shard count, so the core.properties file it writes lacks the entry that CREATE writes.

## What this change does

**ADDREPLICA now sends the collection's shard count with its create request, and the CoreAdmin create path keeps it.**

The count is the number of slices in the collection's cluster state at that moment ([AddReplicaCmd.java](https://github.com/nick-boss-tech/solr/blob/12d7491e82cd660ad55063cb85633b7e05e1918c/solr/core/src/java/org/apache/solr/cloud/api/collections/AddReplicaCmd.java#L305)). The CoreAdmin create mapping now copies that value into the core properties ([CoreAdminHandler.java](https://github.com/nick-boss-tech/solr/blob/12d7491e82cd660ad55063cb85633b7e05e1918c/solr/core/src/java/org/apache/solr/handler/admin/CoreAdminHandler.java#L250)).

## Proof

**The new test fails on the base code and passes with this change.**

- AddReplicaTest 4 of 4 at 12d7491e82c, verified 2026-10-03. The new test is [testAddReplicaPersistsNumShardsInCoreProperties](https://github.com/nick-boss-tech/solr/blob/12d7491e82cd660ad55063cb85633b7e05e1918c/solr/core/src/test/org/apache/solr/cloud/AddReplicaTest.java#L238-L278). On the base code it fails with [the observed failure line, to be copied from the run output before opening].
- Sending the count from ADDREPLICA alone is not enough. The CoreAdmin create path copies only the parameters on its list, and the count was not on that list, so the test still failed. The list entry is required.
- Adjacent suites at the same head: CoreAdminHandlerTest 8 of 8 and CoreAdminOperationTest 44 of 44.

## Limits

**The count is the current slice count, so after a shard split it can be higher than the shard count the collection was created with.**

- After a split, the parent shard stays in the cluster state as inactive, and the count includes it. A replica added after a split can therefore record a higher number than the original shard count. The test does not cover a split collection.
- Replicas created before this change keep their existing core.properties.
