## What happens today

**An Overseer keeps leadership after its collection processor thread stops on its own, and the Collection API queue is no longer read.**

The Overseer runs a state updater thread and a collection and config set processor thread. If the processor thread ends and no one asked it to stop, the state updater keeps running, the node stays Overseer, and nothing reads the Collection API queue. The ticket reports more than 1200 queued messages during a ZooKeeper outage. After ZooKeeper came back, the state updater queue drained, but the Collection API queue stayed stuck.

## What this change does

**When the processor thread ends without a stop request, the Overseer stops its state updater. The node then gives up leadership and rejoins the election.**

The run method stops the state updater unless the Overseer asked for the stop ([run method](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L768-L780), [stop](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L831-L846)). When the state updater exits, the node deletes the leader node it still holds, then rejoins the election unless it is shutting down ([exit](https://github.com/nick-boss-tech/solr/blob/9b3a84b1c460981eab09d8ffaef776acc4a184f8/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L451-L492), merge-base link, unchanged by this branch). An Overseer-requested stop skips this path ([stop flag](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L654-L668)).

The path applies to any unrequested end of the processor thread, not only a ZooKeeper session expiry. That includes the early returns in some startup and error cases ([early return](https://github.com/nick-boss-tech/solr/blob/9b3a84b1c460981eab09d8ffaef776acc4a184f8/solr/core/src/java/org/apache/solr/cloud/OverseerTaskProcessor.java#L185-L186), merge-base link, unchanged by this branch). A test accessor, `getCollectionProcessorThread()`, is added and marked `@lucene.internal`.

## Proof

**One new test passes with this change. At the merge base the test does not compile, because the base has no `getCollectionProcessorThread()` method.**

- `OverseerProcessorExitTest` 1 of 1 at head `40b7e5d0efa`, run 2026-10-13 ([test](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/test/org/apache/solr/cloud/OverseerProcessorExitTest.java#L34-L59)). The test calls `getCollectionProcessorThread()`, which this change adds ([accessor](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L827-L829)), so the base code cannot compile it. The proof is inconclusive by construction.

## A choice to check

**The title asks that the thread not return. This change keeps every return and gives up leadership instead.**

The other route keeps the processor thread alive through each return, so the node stays Overseer and keeps reading the queue. Its cost is a retry path for each return, and a thread that stays alive but stalled would still hold the node in charge. The cost of the route taken is a leadership change on every unrequested exit, including the startup and error cases. Was giving up leadership the right call, or should the thread stay up?

## Limits

**The ZooKeeper outage in the ticket is not reproduced, and the session-expiry race is not covered.**

- The race between a processor exit and a ZooKeeper session expiry is not covered. The test ends the processor thread directly. A follow-up ticket and PR can cover it on request.
- The test does not use a real session expiry or a multi-node failure.
- The early-return paths are not tested on their own. The returns and interrupts after the runner start, which the report names, are not changed in OverseerTaskProcessor.java.
