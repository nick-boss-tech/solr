## What happens today

**An Overseer keeps leadership after its collection processor thread stops on its own, and the Collection API queue is no longer read.**

The Overseer runs a state updater thread and a collection and config set processor thread. If the processor thread ends and no one asked it to stop, the state updater keeps running, the node stays Overseer, and nothing reads the Collection API queue. The ticket reports more than 1200 queued messages during a ZooKeeper outage. After ZooKeeper came back, the state updater queue drained, but the Collection API queue stayed stuck.

## What this change does

**When the processor thread ends without a stop request, the Overseer stops its state updater. The node then gives up leadership and rejoins the election.**

The processor thread's run method checks whether the Overseer asked for the stop. If it did not, the run method stops the state updater ([run method](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L768-L780), [stop](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L831-L846)). When the state updater exits, it deletes the leader node if this node still holds it. It then rejoins the election unless the node is shutting down ([exit](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L451-L492)). A stop that the Overseer requested does not take this path ([stop flag](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L654-L668)).

Behavior change: the path applies to any unrequested end of the processor thread, not only a ZooKeeper session expiry. The processor also returns early in some startup and error cases ([early return](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/java/org/apache/solr/cloud/OverseerTaskProcessor.java#L185-L186)), and those cases now give up leadership the same way. A test accessor, `getCollectionProcessorThread()`, is added and marked `@lucene.internal`.

## Proof

**One new test fails on the base code and passes with this change.**

- `OverseerProcessorExitTest` 1 of 1 at head 40b7e5d0efa, verified on [date to confirm] ([test](https://github.com/nick-boss-tech/solr/blob/40b7e5d0efa70d61b74b9fa9ac04beb1ed397637/solr/core/src/test/org/apache/solr/cloud/OverseerProcessorExitTest.java#L34-L58)). The test ends the processor loop directly, waits up to 60 seconds for a new live processor thread, and then creates a collection. On the base code no new processor thread starts, so the test fails at its assertion that a new processor exists. With this change the new processor starts, and the collection is created and becomes active.

## Limits

- The race between a processor exit and a ZooKeeper session expiry is not covered. The test ends the processor thread directly and does not simulate that race. A follow-up ticket and PR can cover it on request.
- The test does not use a real session expiry or a multi-node failure.
- The early-return paths in the processor are not tested on their own.
