## What happens today

**A shutdown DOWNNODE message can mark a restarted node's replicas DOWN.**

A node sends a DOWNNODE message to the Overseer on shutdown. If the node restarts before the Overseer applies it, the message still marks the node's replicas DOWN. They return to ACTIVE only after a shard leader election, and the ticket describes a restart where no election ran.

## What this change does

**The shutdown message now carries a flag. The Overseer skips a flagged message when the node is live at the time the message is applied.**

- The shutdown path sends the flag ([shutdown call](https://github.com/nick-boss-tech/solr/blob/ca8cb61ee957ed728034a2e6c90532e6082ef3ff/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L845-L848)). The queued message carries it ([queued message](https://github.com/nick-boss-tech/solr/blob/ca8cb61ee957ed728034a2e6c90532e6082ef3ff/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L3082-L3086)).
- `NodeMutator.downNode` returns no changes for a flagged message when the node is live ([guard](https://github.com/nick-boss-tech/solr/blob/ca8cb61ee957ed728034a2e6c90532e6082ef3ff/solr/core/src/java/org/apache/solr/cloud/overseer/NodeMutator.java#L58-L61)).
- The one-argument `publishNodeAsDown` still sends an unflagged message, so its callers see no change ([public method](https://github.com/nick-boss-tech/solr/blob/ca8cb61ee957ed728034a2e6c90532e6082ef3ff/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L3029-L3031)).

Behavior change, stated openly: a shutdown DOWNNODE that reaches the Overseer after the node is live again is skipped. Nothing else in the message handling changes.

## Proof

**The unit tests cover the guard. The delayed-message sequence is not covered end to end, so the proof is inconclusive by construction.**

- `NodeMutatorTest` passes 3 of 3 at head ca8cb61ee957, with 0 skipped, verified 2026-10-13. `testConditionalDownNodeSkippedWhenNodeIsLiveAgain` ([test](https://github.com/nick-boss-tech/solr/blob/ca8cb61ee957ed728034a2e6c90532e6082ef3ff/solr/core/src/test/org/apache/solr/cloud/overseer/NodeMutatorTest.java#L77-L82)) checks that a flagged message is skipped when the node is live. The other two tests check the unchanged paths.
- That test uses the new flag constant, which does not exist on the base code. So no base failure is shown.

## A choice to check

**The guard checks the Overseer's cached live node list once, when the message is applied.**

The implemented route is that single check. It is small and uses state the Overseer already holds, but it trusts the cache to be current when the message runs. The first alternative, from the ticket comments, checks again after the update is computed. Its cost: both checks read the same cache, so a restart between the second check and the write is still missed. The second alternative is a conditional ZooKeeper update tied to the live nodes. Its cost: live node entries carry no data, so a version check cannot see a restart.

Is one check against the cached live node list enough, or should the Overseer also check after it computes the update?

## Limits

**The guard has no end-to-end test, does not run on the distributed path, and an older Overseer ignores it.**

- No test runs a delayed queue or live node watch lag.
- The distributed cluster state path does not send this message. It marks the node down during shutdown without the queue ([distributed path](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L3043-L3050), at the merge-base, unchanged here), so the guard does not run there.
- In a mixed-version cluster, an older Overseer ignores the flag and applies the message as before.
- David Smiley's broader idea is not in this change: a replica's liveness would also depend on `live_nodes`, so an absent node overrules its replicas' state (ticket comment, 2021-04-30). A follow-up ticket and PR can be opened on request.
