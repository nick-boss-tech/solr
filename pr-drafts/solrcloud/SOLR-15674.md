## What happens today

**After a collection is deleted and created again with a different schema, a node can keep serving the old schema.**

The Jira report describes this case. The old schema still shows in the schema API and the admin UI, and edits to its fields fail with a 500 error.

SolrCloud caches the schema and solrconfig.xml of a core. The cache entry is checked against the data version of the znode, in [IndexSchemaFactory.java](https://github.com/apache/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/schema/IndexSchemaFactory.java#L178-L182) and [SolrConfig.java](https://github.com/apache/solr/blob/b5c71bc5573c4e31b4cee5a7965d73587fc0ae58/solr/core/src/java/org/apache/solr/core/SolrConfig.java#L199-L209). A new znode starts that version over at 0. An old entry with the same version then matches the new znode, and the old config stays in use.

## What this change does

**The cache check now compares the znode's mzxid instead of its data version.**

The mzxid is the ZooKeeper ID of the last change to the znode. ZooKeeper does not reuse this ID, so a recreated znode gets a new cache key. The schema and solrconfig.xml caches store the mzxid and compare it ([IndexSchemaFactory.java L149-L150](https://github.com/nick-boss-tech/solr/blob/ba01c83d4c5ad03c7af63fd4061df119a8146d49/solr/core/src/java/org/apache/solr/schema/IndexSchemaFactory.java#L149-L150), [L187](https://github.com/nick-boss-tech/solr/blob/ba01c83d4c5ad03c7af63fd4061df119a8146d49/solr/core/src/java/org/apache/solr/schema/IndexSchemaFactory.java#L187), [SolrConfig.java L161, L170, L387-L389](https://github.com/nick-boss-tech/solr/blob/ba01c83d4c5ad03c7af63fd4061df119a8146d49/solr/core/src/java/org/apache/solr/core/SolrConfig.java#L161-L170)). The znode lookup returns its Stat ([ZkSolrResourceLoader.java L56-L61](https://github.com/nick-boss-tech/solr/blob/ba01c83d4c5ad03c7af63fd4061df119a8146d49/solr/core/src/java/org/apache/solr/cloud/ZkSolrResourceLoader.java#L56-L61)).

Any write changes both numbers, so an edited file reloads as before. The only new reload is a recreated znode. The data version is still stored and reported. The public `VersionedConfig` constructor and the `getZkResourceInfo` return type change; the in-repo callers are updated.

## Proof

**IndexSchemaFactoryCacheTest passes 1 of 1 at head ba01c83d4c5, verified 2026-10-03.**

The test uses a mocked loader. It checks that an unchanged znode is served from the cache, that a znode recreated with the same data version is loaded again, and that a data change is loaded again.

This proof is inconclusive by construction. The test calls the new constructor and the new return type, so it does not compile against the unpatched code and cannot show a failure there.

## A choice to check

**The check uses the mzxid alone. An earlier version of this branch used the creation ID with the data version.**

The creation ID with the data version covers the same two cases with two numbers. The mzxid is one number and changes on both a write and a recreate. Was the mzxid alone the right call?

## Limits

**Three paths are outside this change: the configset cache, the core config watcher, and the managed-schema fallback.**

- Covered: SolrCloud loads of schema and solrconfig.xml through the object cache. Not covered: the configset cache that `shareSchema` enables. [SOLR-15478](https://issues.apache.org/jira/browse/SOLR-15478) changes that cache in its own PR.
- The test covers the schema cache rule with a mocked loader. It does not cover the solrconfig path, and it does not run a delete and recreate in a cluster.
- The config watcher in SolrCore decides to reload by comparing data versions. If a node is deleted and created again before the watcher runs, and the new version is not higher, the watcher does not reload. This change does not touch that check. A core that loads its config after this change reads the current znode.
- One fallback path in ManagedIndexSchemaFactory loads a plain stream with no mzxid. That schema is parsed on each load and is not cached.
