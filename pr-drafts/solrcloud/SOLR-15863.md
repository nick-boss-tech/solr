## What happens today

**An incremental backup records the running Solr build's Lucene version in backup_N.properties, not the version the index was written with.**

The ticket shows a collection created on Solr 8.10.1 and backed up by Solr 8.11.0. The backup properties then say indexVersion 8.11.0, which tells a reader nothing about the segments that were actually copied.

## What this change does

**Each shard reports the oldest Lucene version among its segments, and the backup records the oldest of those values.**

Each incremental shard backup reads the version of its oldest segment ([IncrementalShardBackup.java](https://github.com/nick-boss-tech/solr/blob/f381fd8d4dd1cc82f2bb899f11fdb02c2c62ccc5/solr/core/src/java/org/apache/solr/handler/IncrementalShardBackup.java#L182-L187)). The backup command takes the oldest value across the shards and writes it to the backup properties ([BackupCmd.java](https://github.com/nick-boss-tech/solr/blob/f381fd8d4dd1cc82f2bb899f11fdb02c2c62ccc5/solr/core/src/java/org/apache/solr/cloud/api/collections/BackupCmd.java#L345-L351)).

Behavior change: the recorded value now depends on the index files, not on the Solr build that ran the backup. Backups that are not incremental keep the old value.

## Proof

**The new tests pass with this change. On the base code they do not compile, so the base result comes from an earlier run.**

- BackupCoreAPITest 6 of 6, BackupCmdTest 4 of 4, and LocalFSCloudIncrementalBackupTest 7 of 7 at f381fd8d4dd, verified 2026-10-08.
- The new check is [testIncrementalBackupReportsSegmentLuceneVersion](https://github.com/nick-boss-tech/solr/blob/f381fd8d4dd1cc82f2bb899f11fdb02c2c62ccc5/solr/core/src/test/org/apache/solr/handler/admin/api/BackupCoreAPITest.java#L138-L158). The base code has neither its new field nor the BackupCmdTest helper, so a base run cannot compile. That leg is inconclusive by construction.
- An earlier head, 8f5e94cf314, ran the segment check on the base code. It expected the running Lucene version and got no value, so it failed.

## A choice to check

**The implemented route records the oldest segment version in indexVersion, and a separate field is the alternative.**

Options considered: the oldest segment version (implemented), the Lucene version that wrote the latest commit, or a new field, with indexVersion left as it was. The ticket thread asks whether indexVersion was meant as a backup-format version, which points toward a new field. The cost of the implemented route is that an existing field changes its meaning for anyone who reads backup_N.properties.

Was the oldest segment version the right value for indexVersion, or should the backup carry a separate field?

## Limits

**The change covers only the version field of the ticket.**

- The file count and size fields in the same ticket are not changed here. A follow-up can address them on request.
- Restore does not check this value yet. A restore into an older Lucene could fail early with a clear error. A follow-up can add that on request.
- A shard that reports no version is skipped. In a mixed-version cluster an older node may not report one, so the recorded value can be newer than the oldest segment. If no shard reports a value, the running version is recorded, as before.
- An index with no segments reports no version, so the running version is recorded.
- The incremental backup test base is shared with the S3 and GCS module tests. Those tests were not run for this change.
