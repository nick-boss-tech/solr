## What happens today

**Stopping a node can end its ZooKeeper session before its Overseer has finished closing.**

The links go to the merge-base, `14c7aac0d151`. In [ZkController.close(), lines 883 to 918](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L883-L918), the Overseer close is queued on a background thread at line 883 and is not waited on. The state reader and the ZooKeeper client close at lines 904 and 910. The queued close is awaited only at pool shutdown, line 918, after the client has closed. If the session ends first, the election nodes can be released while the Overseer is still closing.

## What this change does

**The Overseer finishes closing before the session ends, and an interrupt does not cut that wait short.**

[ZkController.close()](https://github.com/nick-boss-tech/solr/blob/408317d7e241c62a3eba9b1115dbac62292b49a7/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L883-L944) now runs in this order:

1. The Overseer close starts on a pool thread. The election context closes, then the Overseer.
2. The other election contexts and the clients close on the pool.
3. The shutdown thread waits for the Overseer close.
4. The state reader and the ZooKeeper client close. Ending the session releases the ephemeral election nodes.
5. The Overseer closes again, the pool shuts down, and any interrupt is restored.

An interrupt that arrives while the wait is blocked is held until the state reader and the ZooKeeper client have closed, so those closes run without it. The caller still gets its interrupt status back. Stopping a node can take longer, because `close()` waits for the Overseer close.

## A choice to check

**The implemented route waits on a pool thread. The alternative closes the Overseer serially, on the shutdown thread.**

A ticket comment suggests the serial close the code used before the thread pool existed. That route closes the Overseer on the shutdown thread. Its cost: `Overseer.close()` ignores an interrupt while it joins its threads ([Overseer.java, doClose](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L827-L851), at the merge-base, unchanged by this branch). On an interrupted thread the join stops early, so close can return while an overseer thread still runs. The same comment says the pool was added for test speed.

Was waiting on the pool the right call, or should close go back to serial?
