## What happens today

**Today an unknown collection, shard or replica still gets HTTP 200.**

The command queues the change and reports success. The state updater then looks up the collection and replica, and throws when it cannot find them. The Overseer, or the distributed state updater, logs that error and skips the message, so the caller never sees it. The code is in [ReplicaMutator.java L162-L175](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/cloud/overseer/ReplicaMutator.java#L162-L175), [Overseer.java L436-L439](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L436-L439) and [DistributedClusterStateUpdater.java L819-L830](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/cloud/DistributedClusterStateUpdater.java#L819-L830). All three go to the merge-base.

## What this change does

**ADDREPLICAPROP now returns HTTP 400 and changes nothing when the collection, the shard or the replica in that shard is not found.**

Before queuing, the command looks up the collection, the shard, then the replica inside that shard ([CollApiCmds.java L345-L351](https://github.com/nick-boss-tech/solr/blob/a23f770e4b9587acbd14fcdbaae2047bd5c727c4/solr/core/src/java/org/apache/solr/cloud/api/collections/CollApiCmds.java#L345-L351)). If one is missing, it throws HTTP 400 and queues nothing. The message names all three ([L352-L362](https://github.com/nick-boss-tech/solr/blob/a23f770e4b9587acbd14fcdbaae2047bd5c727c4/solr/core/src/java/org/apache/solr/cloud/api/collections/CollApiCmds.java#L352-L362)).

Behavior change: a valid replica name given with the wrong shard is now rejected with HTTP 400. Before, that request returned 200 and set the property on no replica. For preferredleader, the old update could also clear the property on the named shard's replicas. The old code finds a replica by name in any shard ([DocCollection.java L382-L391](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/solrj/src/java/org/apache/solr/common/cloud/DocCollection.java#L382-L391)). It updates only the named shard ([ReplicaMutator.java L184-L195](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/cloud/overseer/ReplicaMutator.java#L184-L195)). Both links go to the merge-base.

## A choice to check

**A maintainer could prefer the other route for a wrong-shard replica name.**

This change rejects that request with HTTP 400. The other route keeps the lookup across all shards and applies the property in the shard where the replica lives. That is kinder to callers. Its cost is a change to the update path ([ReplicaMutator.java L184-L195](https://github.com/nick-boss-tech/solr/blob/e2cdb2d7e8ae0be4cf6cf0606206c67d89e7278f/solr/core/src/java/org/apache/solr/cloud/overseer/ReplicaMutator.java#L184-L195), base commit), which this change leaves alone. Was rejecting it the right call?
