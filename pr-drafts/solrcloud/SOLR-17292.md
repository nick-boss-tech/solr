## What happens today

**When every retry of a per-replica state write fails, persist returns without writing and without an error.**

[PerReplicaStatesOps.persist](https://github.com/apache/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj-zookeeper/src/java/org/apache/solr/common/cloud/PerReplicaStatesOps.java#L131-L147) retries while the state is stale. When the last attempt also fails, the loop ends and the method returns. The caller gets no signal. The Jira report describes this and asks for the relevant exception to be thrown.

## What this change does

**When the last attempt fails, persist throws the last KeeperException.**

The last attempt no longer re-reads the state before it gives up. Callers that used to get a silent return now see the failure, at these call sites:

- Overseer state flush ([ZkStateWriter.java L274](https://github.com/nick-boss-tech/solr/blob/e43200b0fb6da9c5f443b9368628e5f2103f8e31/solr/core/src/java/org/apache/solr/cloud/overseer/ZkStateWriter.java#L274)): the flush stops and the updates stay queued. The Overseer loop logs the error and retries ([Overseer.java L387-L390](https://github.com/nick-boss-tech/solr/blob/e43200b0fb6da9c5f443b9368628e5f2103f8e31/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L387-L390)).
- Distributed state update ([DistributedClusterStateUpdater.java L467](https://github.com/nick-boss-tech/solr/blob/e43200b0fb6da9c5f443b9368628e5f2103f8e31/solr/core/src/java/org/apache/solr/cloud/DistributedClusterStateUpdater.java#L467)): the update stops before state.json is written.
- Leader election ([ShardLeaderElectionContextBase.java L241](https://github.com/nick-boss-tech/solr/blob/e43200b0fb6da9c5f443b9368628e5f2103f8e31/solr/core/src/java/org/apache/solr/cloud/ShardLeaderElectionContextBase.java#L241)) and replica publish or unregister ([ZkController.java L1968](https://github.com/nick-boss-tech/solr/blob/e43200b0fb6da9c5f443b9368628e5f2103f8e31/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1968), [L2064](https://github.com/nick-boss-tech/solr/blob/e43200b0fb6da9c5f443b9368628e5f2103f8e31/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L2064)): the exception goes up to the caller.
- Node-down publish, when distributed state updates are off ([ZkController.java L3064](https://github.com/nick-boss-tech/solr/blob/e43200b0fb6da9c5f443b9368628e5f2103f8e31/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L3064)): the failure is logged as a warning, and the node-down message is still sent ([L3070-L3075](https://github.com/nick-boss-tech/solr/blob/e43200b0fb6da9c5f443b9368628e5f2103f8e31/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L3070-L3075)).

## Proof

**TestPerReplicaStates passed 4 of 4 at head e43200b0fb6 on 2026-10-04. That run is before the node-down change, so a run at the current head is owed before opening.**

The new test checks two cases. A write that is stale on the first attempt succeeds on retry. A write that is stale on every attempt throws NodeExistsException. On the base code, the second case fails, because persist returns without throwing.

## Limits

**The test covers persist alone, and the callers and sustained contention are not tested.**

- The number of attempts is unchanged. Only what happens after the last failed attempt changes.
- An Overseer message that keeps losing the race is retried, not dropped. That is not tested under sustained contention.
- The new error log line is written at ERROR. Callers that log the exception again will log it twice.
- It does not run the Overseer or the callers listed above.
