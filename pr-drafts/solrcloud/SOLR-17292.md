## What happens today

**When every retry of a per-replica state write fails, persist returns without writing and without an error.**

[PerReplicaStatesOps.persist](https://github.com/apache/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj-zookeeper/src/java/org/apache/solr/common/cloud/PerReplicaStatesOps.java#L131-L147) retries while the state is stale. When the last attempt also fails, the loop ends and the method returns. The caller gets no signal. The Jira report describes this and asks for the relevant exception to be thrown.

## What this change does

**When the last attempt fails, persist throws the last KeeperException.**

The last attempt no longer re-reads the state before it gives up ([PerReplicaStatesOps.java L132-L158](https://github.com/nick-boss-tech/solr/blob/f614a42fbc8046e47cb7ed216f6b52b8a01f594c/solr/solrj-zookeeper/src/java/org/apache/solr/common/cloud/PerReplicaStatesOps.java#L132-L158)). Callers that relied on the silent return now get the exception, which is a behavior change for them. These are the call sites:

- Overseer state flush ([ZkStateWriter.java L274](https://github.com/nick-boss-tech/solr/blob/f614a42fbc8046e47cb7ed216f6b52b8a01f594c/solr/core/src/java/org/apache/solr/cloud/overseer/ZkStateWriter.java#L274)): the flush stops and the updates stay queued. The Overseer loop logs the error and retries ([Overseer.java L387-L390](https://github.com/nick-boss-tech/solr/blob/f614a42fbc8046e47cb7ed216f6b52b8a01f594c/solr/core/src/java/org/apache/solr/cloud/Overseer.java#L387-L390)).
- Distributed state update ([DistributedClusterStateUpdater.java L467](https://github.com/nick-boss-tech/solr/blob/f614a42fbc8046e47cb7ed216f6b52b8a01f594c/solr/core/src/java/org/apache/solr/cloud/DistributedClusterStateUpdater.java#L467)): the update stops before state.json is written.
- Leader election ([ShardLeaderElectionContextBase.java L241](https://github.com/nick-boss-tech/solr/blob/f614a42fbc8046e47cb7ed216f6b52b8a01f594c/solr/core/src/java/org/apache/solr/cloud/ShardLeaderElectionContextBase.java#L241)) and replica publish or unregister ([ZkController.java L1968](https://github.com/nick-boss-tech/solr/blob/f614a42fbc8046e47cb7ed216f6b52b8a01f594c/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1968), [L2064](https://github.com/nick-boss-tech/solr/blob/f614a42fbc8046e47cb7ed216f6b52b8a01f594c/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L2064)): the exception goes up to the caller.
- Node-down publish, when distributed state updates are off ([ZkController.java L3058-L3068](https://github.com/nick-boss-tech/solr/blob/f614a42fbc8046e47cb7ed216f6b52b8a01f594c/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L3058-L3068)): the failure to persist one collection's replica states is logged, and the loop moves on to the next collection. persist logs an ERROR first, and this call site logs a warning. The node-down message is now sent after any persist KeeperException, not only after the last stale-state retry ([L3074-L3079](https://github.com/nick-boss-tech/solr/blob/f614a42fbc8046e47cb7ed216f6b52b8a01f594c/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L3074-L3079)). Before this change, a KeeperException from persist, for example a lost ZooKeeper connection, skipped that message.

## Proof

**TestPerReplicaStates passes 4 of 4 at head f614a42fbc80, verified 2026-10-10.**

With PerReplicaStatesOps.java and ZkController.java reverted to the merge-base, the class runs 4 tests with exactly 1 failure.

The new test checks two cases. A write that is stale on the first attempt succeeds on retry. A write that is stale on every attempt throws NodeExistsException. On the base code, the second case fails, because persist returns without throwing.

## Limits

**The test covers persist alone, and the callers and sustained contention are not tested.**

- The number of attempts is unchanged. Only what happens after the last failed attempt changes.
- An Overseer message that keeps losing the race is retried, not dropped. That is not tested under sustained contention.
- persist writes an ERROR line when it gives up. The Overseer loop logs the same exception again at ERROR, so that failure appears twice at that level. The node-down call site logs it again as a warning.
- It does not run the Overseer or the callers listed above.
