## What happens today

**The public cluster DELETE of a file returns a 500 when the file has a ZooKeeper entry.**

`DELETE /cluster/filestore/files/{file}` runs the local delete first. The local delete refuses any file that has a ZooKeeper entry, with a 400 and the message "The path exist ZK, delete and retry" ([DistribFileStore.java](https://github.com/nick-boss-tech/solr/blob/56ec140e3636d5f4150fa87fbf7103529536ac99/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L513-L518)). The cluster call wraps that failure as a server error ([ClusterFileStore.java](https://github.com/nick-boss-tech/solr/blob/56ec140e3636d5f4150fa87fbf7103529536ac99/solr/core/src/java/org/apache/solr/filestore/ClusterFileStore.java#L283-L299)). The links point to the merge-base commit, the code before this change.

## What this change does

**The public cluster DELETE removes the file's ZooKeeper entry first, so callers no longer need to.**

- The cluster delete removes the shared entry if one exists, deletes the local copy, and asks the other nodes to delete theirs ([DistribFileStore.java L488-L512](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L488-L512)). A caller that deletes the entry first still works, because the entry check finds nothing ([L519-L530](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L519-L530)).
- A local-only delete (`localDelete=true`) still refuses a file that has an entry. The jar-in-use check still refuses a jar that a package uses ([ClusterFileStore.java L325-L327](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/ClusterFileStore.java#L325-L327)).
- Behavior change: if the local copy of a file with an entry cannot be deleted, the entry is already gone. The error is logged, not raised ([L162-L168](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L162-L168)), so the call returns success and the file stays on disk.

## Proof

**testFileStoreManagement fails on the base code and passes with this change.**

`TestDistribFileStore` runs 1 test with 0 failures at head 636196b7954, verified 2026-10-13 04:07 UTC. With the base production file and this test, the cluster DELETE returns 500 where the test expects 200 (expected:<200> but was:<500>). With this change it returns 200, and the entry and the file are gone on every node ([TestDistribFileStore.java L201-L219](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/test/org/apache/solr/filestore/TestDistribFileStore.java#L201-L219)). The test also checks that a local-only delete still returns 400.

## A choice to check

**Three routes were possible for a file that has a ZooKeeper entry.**

The public DELETE removes the entry itself (implemented here). One call then works, but a local delete failure returns success. The other routes are: keep the old rule and return 400 instead of 500, so the caller removes the entry in a second call; or return 501 for a registered file, so it cannot be deleted through this API at all. Was it right to have DELETE remove the entry itself?

## Limits

**Remote and local delete failures are not reported, and the sync call is not changed.**

- Remote deletes are asynchronous. A remote node that fails to delete does not report the failure to the caller ([DistribFileStore.java L496-L510](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L496-L510)). The test covers neither failure.
- The ticket also reports that POST sync returns 500 when the node already exists in ZooKeeper, and asks whether it should return 501. We did not reproduce that 500. This change does not touch sync, and it does not decide whether sync should return 501.
