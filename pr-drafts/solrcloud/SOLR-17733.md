## What happens today

**The public cluster DELETE of a file returns a 500 when the file has a ZooKeeper entry.**

`DELETE /cluster/filestore/files/{file}` runs the local delete first. The local delete refuses any file that has a ZooKeeper entry, with a 400 and the message "The path exist ZK, delete and retry" ([DistribFileStore.java](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L532-L538)). The cluster call wraps that failure as a server error ([ClusterFileStore.java](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/ClusterFileStore.java#L283-L299)).

## What this change does

**The public cluster DELETE removes the file's ZooKeeper entry first, so callers no longer need to.**

The cluster delete removes the shared entry if one exists, deletes the local copy, and asks the other nodes to delete theirs ([DistribFileStore.java](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L488-L511)). This is a contract change. A caller that deletes the entry first still works, because the entry check finds nothing ([DistribFileStore.java](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L514-L530)). A local-only delete (`localDelete=true`) still refuses a file that has an entry. The jar-in-use check still refuses a jar that a package uses ([ClusterFileStore.java](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/ClusterFileStore.java#L325-L327)).

## Proof

**testFileStoreManagement fails on the base code and passes with this change.**

`TestDistribFileStore` 1 of 1 at head `636196b7954`, recorded 2026-10-04. With the base production file and this test, the cluster DELETE returns 500 where the test expects 200. With this change it returns 200, and the entry and the file are gone on every node ([TestDistribFileStore.java](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/test/org/apache/solr/filestore/TestDistribFileStore.java#L201-L219)). The test also checks that a local-only delete still returns 400.

## A choice to check

**The public DELETE now owns the shared cleanup.**

The other route keeps the old rule and returns a 400 that tells the caller to delete the entry first. That stops the 500, but the caller still makes two calls. This change makes one call work. Was it right to have DELETE remove the entry itself?

## Limits

**A failed remote or local delete still returns success, and the test covers only the normal path.**

- Remote deletes are asynchronous. A remote node that fails to delete does not report the failure to the caller ([DistribFileStore.java](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L496-L511)).
- If the local copy cannot be deleted, the entry is already gone and the call still returns success. The local delete logs the error and does not raise it ([DistribFileStore.java](https://github.com/nick-boss-tech/solr/blob/636196b7954af6b34efad54bd0cda2330ef8c7a4/solr/core/src/java/org/apache/solr/filestore/DistribFileStore.java#L162-L168)).
- The ticket also reports that the sync call fails with a 500. That failure was not reproduced, and this change does not touch sync.
