## What happens today

**A host setting that is only a URL scheme, such as `http://`, registers an empty host name.**

The links in this section go to the merge-base, `cabedd1d968`. [`normalizeHostName`](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1007-L1017) removes the scheme and returns what is left. For `http://` that is an empty string. The [controller uses the returned value as its host name](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L314). An empty setting, where no host is configured, takes a different route: it falls back to the advertised address. The ticket's empty value therefore already falls back on main.

## What this change does

**A host setting that resolves to an empty name now stops node startup with an error.**

[`normalizeHostName`](https://github.com/nick-boss-tech/solr/blob/e4ea4bfde80ea027f005fe138b0285f6c2e5a689/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1007-L1023) becomes static and throws a `SolrException` when its result is null or blank. The controller calls it while it is built at startup, so the node does not start. The ticket's empty value is unchanged. It still falls back to the advertised address, so this change does not fix the reported symptom for that value.

## A choice to check

**A scheme-only setting stops startup. The alternative is to fall back to the advertised address, as an empty setting does.**

The change fails startup with an error. The other route would treat a scheme-only setting like an empty one. That route starts the node, but it registers an address the operator did not set, and nothing in the startup shows that the setting was wrong. Was failing at startup the right call?

## Proof

**The test cannot fail on the merge base, because it calls a method that is private there. The fail-before result is inconclusive by construction.**

[`ZkControllerTest.testNormalizeHostName`](https://github.com/nick-boss-tech/solr/blob/e4ea4bfde80ea027f005fe138b0285f6c2e5a689/solr/core/src/test/org/apache/solr/cloud/ZkControllerTest.java#L81-L90) passes 1 of 1 at head `e4ea4bfde80e`, verified 2026-10-11. The test checks that a plain host passes through, that a URL scheme is removed, that null and empty input give a name that is not blank, and that `http://` and `https://` throw a `SolrException`. On the merge base the method is private and not static, so the test file does not compile there. The compiler reports six errors, all of the form "normalizeHostName(String) has private access in ZkController". That shows the method is not reachable on the base. It does not show how the base behaves.

At head, the changelog parses, the formatting check makes no changes, Error Prone compiles, and the module check passes.

## Limits

- The test calls the helper directly. It does not start a node, so the startup failure is not tested end to end.
- The premise for the scheme-only case is read from the code. No run on the merge base has yet shown a node with `solr.host.advertise=http://` registering an empty name.
