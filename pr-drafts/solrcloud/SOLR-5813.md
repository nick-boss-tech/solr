## What happens today

**A core created with an empty collection name registers under an empty collection name.**

When the `collection` property is missing, the core takes its core name. When it is present but empty, the empty value is kept, in [CloudDescriptor.java L53](https://github.com/apache/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/cloud/CloudDescriptor.java#L53). The 2014 ticket comment reproduces this from the core admin page with the defaults. It says the create fails with an IllegalArgumentException about a path that ends in "/", but only after a poison pill state is published to the Overseer queue. The ticket links the follow-on problems to SOLR-5811.

## What this change does

**An empty collection name now defaults to the core name, the same as a missing one.**

The fix is one line in [CloudDescriptor.java L54](https://github.com/nick-boss-tech/solr/blob/90b8baa08aefd83cbee7e6e17ca9c59fcc93b30f/solr/core/src/java/org/apache/solr/cloud/CloudDescriptor.java#L54). The change also reaches cores that already have an empty `collection` value in their core.properties file. Those cores now load under their core name. The constructor is called from [CoreDescriptor.java L209](https://github.com/nick-boss-tech/solr/blob/90b8baa08aefd83cbee7e6e17ca9c59fcc93b30f/solr/core/src/java/org/apache/solr/core/CoreDescriptor.java#L209). That path is not tested.

## Proof

**CloudDescriptorTest passes 3 of 3 at head 90b8baa08ae, verified 2026-10-07.**

Before the change, [testEmptyCollectionNameDefaultsToCoreName](https://github.com/nick-boss-tech/solr/blob/90b8baa08aefd83cbee7e6e17ca9c59fcc93b30f/solr/core/src/test/org/apache/solr/cloud/CloudDescriptorTest.java#L33-L38) fails, because the empty name comes back as an empty string. The missing-name test and the explicit-name test pass before and after the change.

## A choice to check

**This change defaults the empty name. The alternative is to reject it when the core is created.**

The ticket title asks for a clean failure. The 2014 commit messages describe the tests as checking for a default to the core name. Rejecting the name would give callers a clear error. It would also change what `collection=` returns, and it needs an error path that this change does not add. Was defaulting the right call?

## Limits

- Not covered: SOLR-5811. The ticket says failures reached the Overseer queue because of SOLR-5811. This change does not touch that path.
- Existing core.properties files with an empty `collection` value now load under the core name. This is not tested.
- The public `setCollectionName` setter has no guard. Its only caller in the main source is `reload`, which already skips empty values ([CloudDescriptor.java L128-L131](https://github.com/nick-boss-tech/solr/blob/90b8baa08aefd83cbee7e6e17ca9c59fcc93b30f/solr/core/src/java/org/apache/solr/cloud/CloudDescriptor.java#L128-L131)).
