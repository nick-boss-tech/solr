## What happens today

**An interrupt during the leader lookup is wrapped in a generic error, and the interrupt status is cleared.**

On the merge-base, the code before this change, `getLeader` catches every exception except IllegalStateException. It logs the failure at ERROR and throws a SolrException that says only that the leader lookup failed for a shard ([generic catch](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1725-L1730)). An InterruptedException goes through the same catch. The ticket says `getLeader` "does not handle InterruptedException, and instead rethrows it as a SolrException." The message does not say the thread was interrupted.

## What this change does

**An interrupt reaches the caller as an InterruptedException, which `getLeader` now declares. Other failures still come out as a SolrException, with a clearer message.**

- The signature declares `throws InterruptedException` ([L1675](https://github.com/nick-boss-tech/solr/blob/29bf373828994c622ac478a968d6cff4f4c45fa5/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1675)). A separate catch rethrows it unchanged ([L1725-L1726](https://github.com/nick-boss-tech/solr/blob/29bf373828994c622ac478a968d6cff4f4c45fa5/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1725-L1726)).
- The generic catch still logs at ERROR, as before. Its message names the collection and points to ZooKeeper and the shard's elected leader ([L1727-L1736](https://github.com/nick-boss-tech/solr/blob/29bf373828994c622ac478a968d6cff4f4c45fa5/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1727-L1736)).
- `getLeader` is package-private instead of private, so the same-package test can call it.
- Behavior change: the interrupt status stays cleared, as Java does when it throws. The [register path](https://github.com/nick-boss-tech/solr/blob/29bf373828994c622ac478a968d6cff4f4c45fa5/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1485) declares `throws Exception`, so the exception reaches its caller. The [rejoin path](https://github.com/nick-boss-tech/solr/blob/29bf373828994c622ac478a968d6cff4f4c45fa5/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L2605-L2606) wraps it in "Unable to rejoin election" and does not restore the flag, as on the base code.

## A choice to check

**The interrupt is declared on `getLeader`. The other route keeps the wrapping and restores the flag.**

Options: declare InterruptedException on `getLeader` (implemented at this head), or keep the SolrException and restore the flag, as earlier commits on the branch did. The ticket names the wrapping as the gap, not a fix. The declared route costs a checked exception that callers must handle. The wrapping route costs visibility: a caller sees an interrupt only through the cause of a SolrException. Was declaring the exception the right call, or should `getLeader` keep the wrapping and restore the flag?

## Limits

**Not covered: flow control and the rejoin flag.**

- The ticket lists not using exceptions for flow control. The conflicting-leader check still throws inside the try block, and the generic catch wraps it again ([L1695-L1702](https://github.com/nick-boss-tech/solr/blob/29bf373828994c622ac478a968d6cff4f4c45fa5/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1695-L1702)). A follow-up ticket and PR can cover it on request.
- The rejoin path does not restore the flag. A follow-up can change that on request.
- A ticket comment from mdrob (2016) asks for better ops logging. The generic catch keeps its ERROR line from the base code, and this change adds no new log line.
- The generic message also covers the conflicting-leader case. The cause keeps the specific text.
- The test interrupts the thread before the call. It does not cover an interrupt that arrives during the wait.
