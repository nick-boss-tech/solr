## What happens today

**An interrupt during the leader lookup is wrapped in a generic error, and the interrupt status is cleared.**

On the base code, `getLeader` catches every exception except IllegalStateException, which it rethrows. It logs the failure at ERROR and throws a SolrException that says only that the leader lookup failed for a shard ([generic catch, at the merge-base](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1725-L1730)). An InterruptedException goes through the same catch. The ticket says `getLeader` "does not handle InterruptedException, and instead rethrows it as a SolrException". The message does not say that the thread was interrupted, and the interrupt status is lost.

## What this change does

**An interrupt now reaches the caller as an InterruptedException, which `getLeader` declares. Other failures keep their type and get a clearer message.**

- `getLeader` declares `throws InterruptedException` ([signature](https://github.com/nick-boss-tech/solr/blob/dbd88c84ff246631875afc010c1c4dff4e50c28a/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1675)). A separate catch rethrows it unchanged ([catch](https://github.com/nick-boss-tech/solr/blob/dbd88c84ff246631875afc010c1c4dff4e50c28a/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1725-L1726)).
- The generic catch no longer logs. Its message names the collection and suggests checking ZooKeeper and the shard's elected leader ([message](https://github.com/nick-boss-tech/solr/blob/dbd88c84ff246631875afc010c1c4dff4e50c28a/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1727-L1735)).
- `getLeader` is package-private instead of private, so the same-package test can call it.

Behavior changes, stated openly: an InterruptedException leaves `getLeader` with the interrupt status cleared, as Java does when it throws the exception. Two callers are in that position. The [register path](https://github.com/nick-boss-tech/solr/blob/dbd88c84ff246631875afc010c1c4dff4e50c28a/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1485) declares `Exception`, so the interrupt goes to its caller. The [rejoin path](https://github.com/nick-boss-tech/solr/blob/dbd88c84ff246631875afc010c1c4dff4e50c28a/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L2604-L2605) wraps it in "Unable to rejoin election" and does not restore the flag, as on the base code. The ERROR log line is removed. The cause stays in the exception chain.

## A choice to check

**The interrupt is declared on `getLeader`, and both callers already handle it. The other route keeps the wrapping and restores the flag.**

Options considered: keep the SolrException and restore the interrupt flag, which was the earlier version of this change, or declare InterruptedException on `getLeader`, which is implemented. The ticket says `getLeader` "rethrows it as a SolrException", which points to the declared route. The cost is a checked exception the callers must handle. The register path already declares `Exception`, and the rejoin path already catches it. Was declaring the exception the right call, or should `getLeader` keep the wrapping and restore the flag?

## Limits

**Two things remain: exceptions still drive the conflict check, and the rejoin path does not restore the flag.**

- The ticket's point about exceptions used for flow control is not addressed. The conflicting-leader check still throws inside the try block, and the generic catch wraps it again ([conflict check](https://github.com/nick-boss-tech/solr/blob/dbd88c84ff246631875afc010c1c4dff4e50c28a/solr/core/src/java/org/apache/solr/cloud/ZkController.java#L1695-L1702)). A follow-up ticket and PR can cover it on request.
- The rejoin path wraps an interrupt in its own error and does not restore the flag. A follow-up can change that on request.
- The generic message also covers the conflicting-leader case, where ZooKeeper may be reachable. The cause keeps the specific message.
- The test interrupts the thread before the call. It covers the first blocking step, not an interrupt that arrives while the lookup waits.
