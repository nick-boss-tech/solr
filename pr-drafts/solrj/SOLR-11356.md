## What happens today

**Queued requests with different credentials can share one HTTP stream, so a document can go out under another identity.**

A queued request joins an open stream when the collection and the parameters match. The check does not look at the user, the password or the headers. The stream's HTTP request is decorated with the credentials of the request that opened it ([line 209](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj-jetty/src/java/org/apache/solr/client/solrj/jetty/ConcurrentUpdateJettySolrClient.java#L209)), so a later document from another user goes out under that user. The old match is at [lines 126-129](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj-jetty/src/java/org/apache/solr/client/solrj/jetty/ConcurrentUpdateJettySolrClient.java#L126-L129). Both links are at the base commit the branch starts from, `cabedd1d968059215188f4e7563fb303241899ed`.

## What this change does

**Each stream keeps the credentials and headers of the request that opened it, and only matching requests join it.**

The stream records the user, the password and the headers of the opening request, and the match checks all of them ([lines 126-144 at this head](https://github.com/nick-boss-tech/solr/blob/6120dae28d04a07763f44d4bc5e9d9793af025f6/solr/solrj-jetty/src/java/org/apache/solr/client/solrj/jetty/ConcurrentUpdateJettySolrClient.java#L126-L144)). Requests with other credentials or headers open a separate stream.

This is a behavior change. A client that alternates identities now opens more streams than before.

## Proof

**A new shared test fails on the base and passes with this change.**

The test is `testRequestsWithDifferentCredentialsAreNotSentOnOneStream`, in [ConcurrentUpdateSolrClientTestBase](https://github.com/nick-boss-tech/solr/blob/6120dae28d04a07763f44d4bc5e9d9793af025f6/solr/solrj/src/test/org/apache/solr/client/solrj/impl/ConcurrentUpdateSolrClientTestBase.java#L300-L333). It runs through `ConcurrentUpdateJettySolrClientTest`. It queues 20 documents from two users, alternating, on one client.

- This head (`6120dae28d04a07763f44d4bc5e9d9793af025f6`): `ConcurrentUpdateJettySolrClientTest`, 12 tests, 0 failures.

## Limits

**The test depends on timing, and two parts of the match are still open: the headers and the user principal.**

- The test depends on timing. It needs several queued updates to meet on one stream. Each side was run once, and no repeat runs were made to check for flakiness.
- The stream stores a live view of the opening request's headers, not a copy. `SolrRequest.getHeaders()` returns an unmodifiable view of the request's own map ([lines 374-377 at the base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj/src/java/org/apache/solr/client/solrj/SolrRequest.java#L374-L377)). If that request's headers change after it is queued, the match changes too. This change does not copy them, and no test covers it.
- The per-request user principal is not part of the match. Whether it reaches the wire on a shared stream was not checked.
- The same shared test also runs in the JDK client suite (`ConcurrentUpdateJdkSolrClientTest`). That suite was not part of this run.
