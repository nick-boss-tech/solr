## What happens today

**In split mode, a mapped field that comes after the split records is left out of every record, and nothing reports it.**

With a split on `/exams`, a JSON document with a top-level `after` field after the `exams` array loses `after` from each record, even when `/after` is mapped. The ticket describes the same loss ([Jira](https://issues.apache.org/jira/browse/SOLR-12094)). The new test uses this layout ([test, lines 250-282](https://github.com/nick-boss-tech/solr/blob/8d957a73f4fb1e8e6e72e53df4faa14266702e53/solr/solrj/src/test/org/apache/solr/common/util/TestJsonRecordReader.java#L250-L282)). On the base code, the value is stored with no check, and nothing reports that the record was already emitted ([base code, lines 401-405](https://github.com/nick-boss-tech/solr/blob/c3cdf7b46e8cfff3673f76d881f32cf8e7b00622/solr/solrj/src/java/org/apache/solr/common/util/JsonRecordReader.java#L401-L405)).

## What this change does

**A mapped field that follows the split records now raises an error that names the field.**

- The reader records when a split record has been emitted below the current object ([lines 313-315](https://github.com/nick-boss-tech/solr/blob/8d957a73f4fb1e8e6e72e53df4faa14266702e53/solr/solrj/src/java/org/apache/solr/common/util/JsonRecordReader.java#L313-L315), [lines 370-379](https://github.com/nick-boss-tech/solr/blob/8d957a73f4fb1e8e6e72e53df4faa14266702e53/solr/solrj/src/java/org/apache/solr/common/util/JsonRecordReader.java#L370-L379)). A mapped field in that object that follows such a record raises the error ([lines 415-422](https://github.com/nick-boss-tech/solr/blob/8d957a73f4fb1e8e6e72e53df4faa14266702e53/solr/solrj/src/java/org/apache/solr/common/util/JsonRecordReader.java#L415-L422)). The message names the field and asks for it to be moved before the split node.
- Fields before the split are not affected.
- This is a behavior change. The update request that used to succeed without the field now fails with the error. It reaches `/update/json/docs` in split mode, which calls this reader ([JsonLoader.java line 262](https://github.com/nick-boss-tech/solr/blob/8d957a73f4fb1e8e6e72e53df4faa14266702e53/solr/core/src/java/org/apache/solr/handler/loader/JsonLoader.java#L262)). The ticket discussion calls the silent drop wrong, and says an error is an acceptable result ([Jira comments](https://issues.apache.org/jira/browse/SOLR-12094)).

## Proof

**The new test fails on the base code and passes with this change.**

- `TestJsonRecordReader` (solrj): 10 of 10 pass at head `8d957a73f4fb1e8e6e72e53df4faa14266702e53`, verified 2026-10-05.
- On the base code, 1 of the 10 fails: `testMappedFieldAfterSplitIsRejected`. The base reader returns the records and raises no error, so the expected exception never occurs.
- The JSON loader, which calls this reader, passes its 31 tests at the same head (`JsonLoaderTest`, core module).

## Limits

**This changes behavior for some callers, the relaxed mode is not built, and unmapped fields are still dropped.**

- Callers of `/update/json/docs` in split mode who relied on the silent drop now get an error for documents where a mapped field follows the split.
- The ticket also asked for an opt-in relaxed mode that holds such fields until the record can be emitted. That needs buffering, and this change does not add it. On request, a follow-up ticket and pull request can add that mode.
- Unmapped fields after the split are still left out without an error, as before ([test, lines 273-281](https://github.com/nick-boss-tech/solr/blob/8d957a73f4fb1e8e6e72e53df4faa14266702e53/solr/solrj/src/test/org/apache/solr/common/util/TestJsonRecordReader.java#L273-L281)).
- The reader streams. It cannot add a field to a record it has already emitted, so for such input the choice is an error or buffering.
