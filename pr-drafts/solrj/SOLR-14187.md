Title: SolrJ CollectionAdminRequest.waitForAsyncRequest has an overload taking per-request basic auth credentials, used for the REQUESTSTATUS polls and the final DELETESTATUS.

https://issues.apache.org/jira/browse/SOLR-14187

## What happens today

**The three-argument `waitForAsyncRequest` sends no credentials.**

The static helper `CollectionAdminRequest.waitForAsyncRequest(requestId, client, timeout)` has no way to take a user or password. Its REQUESTSTATUS polls and its final DELETESTATUS go out with no basic-auth user, so a secured cluster sees them without the caller's identity. The helper is at [lines 1829-1832](https://github.com/nick-boss-tech/solr/blob/e044bf20b405b8ca985730be3553d77d1fc8ff31/solr/solrj/src/java/org/apache/solr/client/solrj/request/CollectionAdminRequest.java#L1829-L1832) at the merge-base.

The instance paths already carry credentials, at the merge-base too. [processAndWait](https://github.com/nick-boss-tech/solr/blob/e044bf20b405b8ca985730be3553d77d1fc8ff31/solr/solrj/src/java/org/apache/solr/client/solrj/request/CollectionAdminRequest.java#L260) copies the caller's credentials to its status request. [RequestStatus.waitFor](https://github.com/nick-boss-tech/solr/blob/e044bf20b405b8ca985730be3553d77d1fc8ff31/solr/solrj/src/java/org/apache/solr/client/solrj/request/CollectionAdminRequest.java#L1874) copies them to the final delete.

## What this change does

**A five-argument overload sends the caller's credentials on every status call.**

The new `waitForAsyncRequest(requestId, client, timeout, basicAuthUser, basicAuthPassword)` sets the credentials on the status request, then waits. The polls carry them. The final delete does too, because `waitFor` already copies the status request's credentials to the delete. The [overload is at lines 1834-1848](https://github.com/nick-boss-tech/solr/blob/29023ec1ecabc2cd0a87675bdcdccf5d71e719b8/solr/solrj/src/java/org/apache/solr/client/solrj/request/CollectionAdminRequest.java#L1834-L1848). The three-argument form is unchanged.

## Proof

**The branch test cannot run on the base code, so the base behavior is shown by a separate scratch test.**

The [branch test](https://github.com/nick-boss-tech/solr/blob/29023ec1ecabc2cd0a87675bdcdccf5d71e719b8/solr/solrj/src/test/org/apache/solr/client/solrj/request/CollectionAdminRequestAsyncAuthTest.java#L48-L58), `CollectionAdminRequestAsyncAuthTest`, calls the five-argument overload. The base code does not have that overload, so the test does not compile there and cannot fail there. At this head it passes: 2 tests, 0 failures.

A scratch test, not part of this change, ran against the base production code with the branch test left out. It ran 2 tests, 0 failures. It shows that the three-argument helper sends the poll and the delete with no user, and that a status request with credentials set sends them on both calls.

Verified at head `29023ec1ecabc2cd0a87675bdcdccf5d71e719b8`.

## A choice to check

**The new overload wraps a path that already sends the credentials. Was adding it the right call?**

Two routes were open. The one implemented adds a five-argument static overload, so a caller can pass a user and password to the one-line helper. The other adds no method. A caller who needs credentials uses `requestStatus(id)`, then `setBasicAuthCredentials(user, password)`, then `waitFor(client, timeout)`. That path already sends the credentials on the poll and the delete.

The cost of the second route is that the three-argument helper stays as it is. Callers who use it still send no credentials, and they must learn the longer path. The cost of the first is one more public overload to keep.

Was a new public overload the right call, or should the existing path be the answer, with the three-argument helper documented as sending no credentials?

## Limits

- The test uses a stub client that records each request. It does not run against a secured cluster.
- The three-argument helper is unchanged, so code that still calls it sends no credentials. The existing test callers were not moved to the overload.
