## What happens today

**The periodic check that tests a down server looks like user queries in the server logs.**

When a server is marked down, `LBSolrClient` sends it a check query: a match-all query with zero rows, sorted by `_docid_`, not distributed ([static query setup, lines 162-176](https://github.com/nick-boss-tech/solr/blob/67e75ea1eea4433d3b9fe8bb97b32bbc38ad373c/solr/solrj/src/java/org/apache/solr/client/solrj/impl/LBSolrClient.java#L162-L176); [the check, lines 756-760](https://github.com/nick-boss-tech/solr/blob/67e75ea1eea4433d3b9fe8bb97b32bbc38ad373c/solr/solrj/src/java/org/apache/solr/client/solrj/impl/LBSolrClient.java#L756-L760)). Nothing in that request marks it as a check. It is hard to tell apart from user queries in the logs.

## What this change does

**The check adds `_zombieservercheck=true`, so its requests can be found in the logs.**

The parameter is set on the query the check sends ([lines 157-175](https://github.com/nick-boss-tech/solr/blob/67e75ea1eea4433d3b9fe8bb97b32bbc38ad373c/solr/solrj/src/java/org/apache/solr/client/solrj/impl/LBSolrClient.java#L157-L175)). The query is otherwise unchanged. Solr does not act on the parameter. It appears in the request parameters that Solr writes to its logs, such as the slow-request log. Only the alive check sends it.

## Proof

**The new test fails when the tag line is removed. The base code has no helper that the test calls, so a base run cannot check it.**

- [LBSolrClientTest](https://github.com/nick-boss-tech/solr/blob/67e75ea1eea4433d3b9fe8bb97b32bbc38ad373c/solr/solrj/src/test/org/apache/solr/client/solrj/impl/LBSolrClientTest.java#L54-L61): 9/9 at head 67e75ea1eea4, including the new `testZombieCheckQueryIsTraceable`. Run recorded 2026-10-06.
- With only the line that sets the tag removed and the new test kept, LBSolrClientTest fails 1 of 9: the new test.
- The solrj check task, with tests excluded, passed at this head.

## A choice to check

**The tag is the smallest way to make the check visible. The ticket suggests two other routes.**

- **The tag, as implemented.** The existing query carries one more parameter. The check itself stays the same, so it costs the same as before.
- **A ping route.** David Smiley suggested calling the core's ping handler. That is easier to observe, and the handler can be set up to run any query. No SolrJ change is needed. The cost is that the check then depends on how each server's ping handler is set up.
- **A settable check query.** Noble Paul suggested letting the application set the check query in SolrJ. That allows a cheaper query. The cost is a new client setting that users must choose well.

Was the tag the right first step, or should the check move to a ping route or a settable query?

## Limits

**The tag makes the check easy to find. It does not make the check cheaper.**

- The ticket reports that these checks can take many seconds on a very large shard ([ticket](https://issues.apache.org/jira/browse/SOLR-14298)). This change leaves that cost in place. Cheaper checks are a follow-up that we can open on request.
- The new test checks the query object that the client builds. It does not capture the HTTP request that goes out.
