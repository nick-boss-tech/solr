## What happens today

**`GenericSolrRequest.process(client, collection)` drops the collection on clients that build their URL from a root URL.**

The URL builder appends the collection only when `requiresCollection()` is true ([base, line 65](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/solrj/src/java/org/apache/solr/client/solrj/util/ClientUtils.java#L65)). A request that never called `setRequiresCollection(true)` returns false, so it goes to `/solr/select`, not `/solr/coll1/select`.

## What this change does

**A named collection now makes a `GenericSolrRequest` collection-aware, unless the caller set `setRequiresCollection` explicitly.**

`SolrRequest.process` calls a new protected hook, `collectionProvided`, before sending ([lines 308-312](https://github.com/nick-boss-tech/solr/blob/3f9367d796a6446fa2f0549d8e9763e07831e6e8/solr/solrj/src/java/org/apache/solr/client/solrj/SolrRequest.java#L308-L312)). `GenericSolrRequest` sets `requiresCollection` in that hook when `setRequiresCollection` was not called ([lines 109-113](https://github.com/nick-boss-tech/solr/blob/3f9367d796a6446fa2f0549d8e9763e07831e6e8/solr/solrj/src/java/org/apache/solr/client/solrj/request/GenericSolrRequest.java#L109-L113)). The public field's javadoc names the setter as the tracked way to change it ([lines 34-39](https://github.com/nick-boss-tech/solr/blob/3f9367d796a6446fa2f0549d8e9763e07831e6e8/solr/solrj/src/java/org/apache/solr/client/solrj/request/GenericSolrRequest.java#L34-L39)).

Behavior beyond the ticket: the flag stays set on the request object. The cloud client's admin check reads it ([line 639](https://github.com/nick-boss-tech/solr/blob/3f9367d796a6446fa2f0549d8e9763e07831e6e8/solr/solrj/src/java/org/apache/solr/client/solrj/impl/CloudSolrClient.java#L639)), and so does the load-balancing client's retry decision ([line 575](https://github.com/nick-boss-tech/solr/blob/3f9367d796a6446fa2f0549d8e9763e07831e6e8/solr/solrj/src/java/org/apache/solr/client/solrj/impl/LBSolrClient.java#L575)).

## A choice to check

**The fix keeps the public field and documents the setter. The other option makes the field private.**

Implemented: the public `requiresCollection` field stays, and its javadoc names `setRequiresCollection` as the tracked way to set it. `testDirectFieldWriteFalseDoesNotOptOut` pins that a direct write of `false` does not opt out. The cost is that a direct write still skips tracking.

Not implemented: a private field, so only the setter changes it. The cost is a breaking SolrJ API change for code that reads or writes the field. The ticket comments also discuss a constructor that takes the flag. Was keeping the public field with a documented setter the right call?

## Limits

**The tests check a URL and send no request. Two side effects are not tested.**

- The tests check the URL that `ClientUtils.buildRequestUrl` builds. No request reaches a server.
- A wrapped request is not covered. `WrappedSolrRequest` does not pass the hook to the request it wraps. A follow-up can add that on request.
- The flag stays set, so a later call on the same object with no collection takes the collection path. On clients that apply a default collection, that call uses the default ([HttpJdkSolrClient, line 234](https://github.com/nick-boss-tech/solr/blob/3f9367d796a6446fa2f0549d8e9763e07831e6e8/solr/solrj/src/java/org/apache/solr/client/solrj/impl/HttpJdkSolrClient.java#L234)). Not tested.
- Admin-typed requests that name a collection now take the collection path in the cloud and load-balancing clients. Not tested.
