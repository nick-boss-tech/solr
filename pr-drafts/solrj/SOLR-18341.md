## What happens today

**The two retry layers decide from different signals, so they can disagree about replaying the same update.**

`LBSolrClient` retries an update only after a connection failure, where nothing was sent ([base lines 675-680](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj/src/java/org/apache/solr/client/solrj/impl/LBSolrClient.java#L675-L680)). `CloudSolrClient` retries any communication error by sending the whole request again ([base lines 725-727](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj/src/java/org/apache/solr/client/solrj/impl/CloudSolrClient.java#L725-L727)). A connection reset can come after the server applied the update, so an atomic `inc` sent again adds its value twice. The ticket describes this case.

A separate open change, [apache/solr PR 4829](https://github.com/apache/solr/pull/4829), touches the same retry boundary and makes different choices for stale-state retries.

## What this change does

**Each request says whether it may be retried, and both clients ask it.**

- `SolrRequest.isRetriable()` is a new public method. It is true only for queries, unless a subclass overrides it. The HTTP method is not consulted ([lines 253-255](https://github.com/nick-boss-tech/solr/blob/458b098719d7ac988c47942eee05dbc2a83e7707/solr/solrj/src/java/org/apache/solr/client/solrj/SolrRequest.java#L253-L255)).
- `UpdateRequest` walks its documents, including child documents and nested atomic operators. Full adds, deletes, commits, `set`, child-document `add`, `add-distinct`, `remove` and `removeregex` may be retried. `inc`, scalar `add`, unknown operators, `overwrite=false` and document iterators may not. A `_version_` above 0 may be retried, because a replay then fails with a 409 ([lines 412-505](https://github.com/nick-boss-tech/solr/blob/458b098719d7ac988c47942eee05dbc2a83e7707/solr/solrj/src/java/org/apache/solr/client/solrj/request/UpdateRequest.java#L412-L505)).
- Both load balancer clients use this answer in place of their type checks. A request that may not be retried fails over only when the HTTP client shows that nothing was sent ([lines 654-694](https://github.com/nick-boss-tech/solr/blob/458b098719d7ac988c47942eee05dbc2a83e7707/solr/solrj/src/java/org/apache/solr/client/solrj/impl/LBSolrClient.java#L654-L694)).
- `CloudSolrClient` replays a whole request only when the answer is yes, and never replays an update after a 503 route error. It still marks cached state stale after a communication error, even when it does not replay ([lines 717-753](https://github.com/nick-boss-tech/solr/blob/458b098719d7ac988c47942eee05dbc2a83e7707/solr/solrj/src/java/org/apache/solr/client/solrj/impl/CloudSolrClient.java#L717-L753)).
- The transport checks move to `HttpSolrClient` ([lines 393-405](https://github.com/nick-boss-tech/solr/blob/458b098719d7ac988c47942eee05dbc2a83e7707/solr/solrj/src/java/org/apache/solr/client/solrj/impl/HttpSolrClient.java#L393-L405)).

Behavior changes, stated openly:

- Cloud: a non-retriable update (for example `inc`) is not replayed after a communication error. That includes a refused connection, a reset, a broken pipe and an unknown host. It was replayed before. The unknown-host case is the conservative choice.
- Cloud: an update after a 503 route error is not replayed. It was replayed before.
- Cloud: a non-retriable update after an invalid-state or 404 error is not replayed, and cached collection state is not cleared. It was refreshed and replayed before.
- Load balancer: an idempotent update after a 500, 503, timeout or reset now fails over. Before, only connection failures did. This is wider than the ticket's text.
- Load balancer: admin requests tied to a collection, generic requests with no type, security requests and streaming requests are no longer retried. They were retried before. The ticket says these stay as they are. For the load balancer they do not.
- Load balancer, synchronous client: any `IOException` now fails over for a retriable request, as the async client already did.
- Cloud: JDK connect timeouts, and Jetty end-of-stream or closed-channel errors, now count as communication errors. Queries are replayed after them.

## Choices to check

**Five calls where a maintainer may want a different answer.** Each one is a behavior change listed above.

1. **A 503 route error blocks replay of updates, even idempotent ones.** The error is raised after every shard's result has been collected, and one shard may already have applied its part. The code never replays an update after it, even when the request's answer is yes. The cost: during a rolling restart, idempotent updates fail that the answer would allow. The other route is to let the answer decide. Was blocking that replay the right call?

2. **Only queries are retriable by default.** The ticket says admin, security and unspecified requests keep today's behavior. For the load balancer they do not. The other route keeps today's load balancer failover for those requests. Its cost is that an update sent without a type keeps being retried. Was the stricter default right?

3. **Stale-state errors do not replay a non-retriable update.** Such an update gets the error at once. Its cached state stays until it expires ([default time to live](https://github.com/nick-boss-tech/solr/blob/458b098719d7ac988c47942eee05dbc2a83e7707/solr/solrj/src/java/org/apache/solr/client/solrj/impl/CloudSolrClient.java#L1646)). The server seems to reject these requests before it applies them, but that is not confirmed for each path. The other route is to replay anyway. The cost of the chosen route: an `inc` with stale cached state fails instead of succeeding after a refresh. Was waiting the right call?

4. **`wasCommError` is removed from `CloudSolrClient`.** The check moved to `HttpSolrClient`. A subclass that overrode the old method no longer affects those decisions. HTTP clients also no longer consult `LBSolrClient.isConnectException`. The other route is a deprecated method that calls the new check. Its cost is two places answering one question. Was removal the right call?

5. **The refused-connection exemption applies only to the load balancer.** When an endpoint refuses the connection, nothing was sent, so the load balancer may try another server even for an `inc`. Cloud does not replay a non-retriable request on that basis. The base code did. The other route is to replay when the transport shows that one route was never sent. Its cost: a route error can cover several shards, so proof for one route says nothing about the others. Was the narrow rule right?

On choices 2 and 5, we are willing to take the broader route in this PR if maintainers prefer it.

## Limits

**Not in this PR: the mid-request fault tests from the ticket, and a shared cause-chain helper.**

- The `SocketProxy` integration tests named in the ticket are not included. The new tests use stubbed clients and constructed exceptions, not a live server. The fault tests are later confirmation.
- No test checks this error text. When nothing was sent, its error text now reads "Connection failed before the request was sent to" instead of "Connection lost at" ([lines 525-530](https://github.com/nick-boss-tech/solr/blob/458b098719d7ac988c47942eee05dbc2a83e7707/solr/solrj-jetty/src/java/org/apache/solr/client/solrj/jetty/HttpJettySolrClient.java#L525-L530)).
- New protected methods: `LBSolrClient.mayFailOver`, and `HttpSolrClient.wasRequestUnsent` and `wasCommError`.
- A shared cause-chain helper for `wasCommError` and `isConnectException` is a follow-up. We can open it on request.
- Correcting the HTTP methods of admin requests is a separate change. The retry policy does not depend on it.
