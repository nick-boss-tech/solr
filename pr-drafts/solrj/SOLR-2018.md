## What happens today

**The `waitFlush` flag on commit and optimize has no effect, but the SolrJ javadoc says it blocks until index changes are flushed to disk.**

The SolrJ commit and optimize methods take a `waitFlush` argument, and its javadoc says it blocks until index changes are flushed to disk ([SolrClient.java line 454 (base)](https://github.com/apache/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj/src/java/org/apache/solr/client/solrj/SolrClient.java#L454)). The value never reaches the request. The shared request code sets the commit or optimize parameter, the soft-commit and segment settings, and `waitSearcher`. It never sets `waitFlush` ([AbstractUpdateRequest.java lines 53-64 (base)](https://github.com/apache/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj/src/java/org/apache/solr/client/solrj/request/AbstractUpdateRequest.java#L53-L64)). No server code reads `waitFlush`. The commit stream decorator passes its option through the same method ([CommitStream.java line 294 (base)](https://github.com/apache/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/CommitStream.java#L294)). SOLR-2018 reports that Solr does not pay attention to this option.

## What this change does

**The branch documents that `waitFlush` is ignored. It does not change how the flag behaves.**

- The eight `@param waitFlush` lines on the commit and optimize methods in [SolrClient.java](https://github.com/nick-boss-tech/solr/blob/213457aa91fd6d4809094d80dd9c8d312c0a6d3b/solr/solrj/src/java/org/apache/solr/client/solrj/SolrClient.java) now say the option is ignored and kept for compatibility.
- The commit stream reference page now says that Solr ignores the option ([stream-decorator-reference.adoc line 446](https://github.com/nick-boss-tech/solr/blob/213457aa91fd6d4809094d80dd9c8d312c0a6d3b/solr/solr-ref-guide/modules/query-guide/pages/stream-decorator-reference.adoc#L446)).
- No signature or code changes. Existing callers compile unchanged.

## Limits

**Covered: the javadoc and one line of the reference guide. Not covered: how the flag works.**

- The flag still does nothing. Making it work, or removing it from the signatures, would change the API. That is a separate change. A follow-up is possible if maintainers want it.
- Four notes on the commit and optimize methods still say that `waitFlush=true` matches the plain HTTP defaults ([SolrClient.java lines 409, 429, 543 and 560](https://github.com/nick-boss-tech/solr/blob/213457aa91fd6d4809094d80dd9c8d312c0a6d3b/solr/solrj/src/java/org/apache/solr/client/solrj/SolrClient.java#L409)). They are unchanged here.
- A comment in [RequestHandlerUtils.java line 50 (base)](https://github.com/apache/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/RequestHandlerUtils.java#L50) still lists `waitFlush` among the parameters the handler checks. It is unchanged here.
