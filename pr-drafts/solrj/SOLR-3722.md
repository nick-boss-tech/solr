## What happens today

**A null element in the array given to the NamedList constructor throws a NullPointerException.**

The ticket reports it with `debugQuery=true` on a distributed request. The stack trace runs from `DebugComponent.finishStage` through the `SimpleOrderedMap` constructor into `NamedList.nameValueMapToList`. In the base code, that method calls `getKey()` on each element with no null check ([base](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/solrj/src/java/org/apache/solr/common/util/NamedList.java#L144-L151)). The ticket ties the null to a mismatch between the shard result list and the per-shard score explanations. It says the root cause is not yet understood.

## What this change does

**NamedList skips null elements in the constructor that takes a `Map.Entry` array. SimpleOrderedMap gets the same behavior.**

The change is in [`nameValueMapToList`](https://github.com/nick-boss-tech/solr/blob/f9d3dda1d3de8d9724a9dc47b7368d378306e01c/solr/solrj/src/java/org/apache/solr/common/util/NamedList.java#L145-L155), which both constructors call. The constructor's javadoc says so ([constructor](https://github.com/nick-boss-tech/solr/blob/f9d3dda1d3de8d9724a9dc47b7368d378306e01c/solr/solrj/src/java/org/apache/solr/common/util/NamedList.java#L80-L92)). The other entries keep their order. Nothing is logged.

## Proof

**The new test fails on the base code and passes with this change.**

- `NamedListTest` 6/6 at head `f9d3dda1d3de`, including `testEntryArrayWithNullElements`. On the base code that test fails with a `NullPointerException` on `ent.getKey()` when the list contains a null element.
- `SimpleOrderedMapTest` 18/18 and `TestNamedListCodec` 4/4 at the same head.
- The module check task, without tests, passed.

Verified 2026-10-06 at this head.

## A choice to check

**Skipping was chosen over failing with a clear error.**

The ticket suggests ignoring nulls in the constructor, so that is the route implemented. The failing path is debug output. A request that asks for debug output should still return its results when one shard's explanation entry is missing. The other route throws an error that names the position of the null element. That still stops the request, but with a clearer message. The cost of skipping is that a short list stays quiet, so the mismatch the ticket describes is never reported.

Was skipping the right call, or should the constructor fail with a clear error?

## Limits

**Only the `Map.Entry` array constructors change.**

No component is changed. The ticket also suggests that the components reading these arrays log a warning or put a placeholder value in the response. This change does neither. A follow-up ticket and pull request for those components can be opened on request. The shard mismatch itself is not investigated here. A null key or a null value inside an entry is not covered by the new test.
