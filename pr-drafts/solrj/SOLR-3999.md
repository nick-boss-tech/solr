## What happens today

**Java-serialized SolrJ documents fail to read between builds, because the four document classes have no fixed serialVersionUID.**

Java serialization stamps each class with a version number, the serialVersionUID. A class that declares none gets a number computed from its shape, such as its non-private methods. A reader rejects a stream whose number differs from its own, with `InvalidClassException: local class incompatible`. SOLR-3999 reports this for `SolrInputDocument` and `SolrInputField` between a client and a server on different versions. On the base code none of the four classes declares a number ([SolrInputField.java line 29 (base)](https://github.com/apache/solr/blob/b6b2b8f10e9827e3b86e44649fb7966ce646c185/solr/solrj/src/java/org/apache/solr/common/SolrInputField.java#L29), and the same is true of the other three).

## What this change does

**Each of the four classes now declares `serialVersionUID = 1L`, so the number no longer follows the class's shape.**

The declarations are at [SolrDocumentBase.java line 26](https://github.com/nick-boss-tech/solr/blob/e3af6f36e3120536bd7edccc779d34ea4b2b467b/solr/solrj/src/java/org/apache/solr/common/SolrDocumentBase.java#L26), [SolrDocument.java line 44](https://github.com/nick-boss-tech/solr/blob/e3af6f36e3120536bd7edccc779d34ea4b2b467b/solr/solrj/src/java/org/apache/solr/common/SolrDocument.java#L44), [SolrInputDocument.java line 38](https://github.com/nick-boss-tech/solr/blob/e3af6f36e3120536bd7edccc779d34ea4b2b467b/solr/solrj/src/java/org/apache/solr/common/SolrInputDocument.java#L38), and [SolrInputField.java line 30](https://github.com/nick-boss-tech/solr/blob/e3af6f36e3120536bd7edccc779d34ea4b2b467b/solr/solrj/src/java/org/apache/solr/common/SolrInputField.java#L30). Builds that declare 1L accept each other's streams, as long as the stored fields stay compatible.

## Proof

**The new test fails on the base code and passes with this change.**

`SolrDocumentSerialVersionTest`: 2 of 2 pass at head `e3af6f36e312`, verified 2026-10-06. On the base code, one of the two tests fails: `testExplicitSerialVersionUid`, with `NoSuchFieldException: serialVersionUID`. That test checks that each of the four classes declares a private, static, final `long` named `serialVersionUID` with the value 1L, and that the serialization runtime uses 1L for each class. With this change it passes.

## Limits

**The number fixes the declared version. It does not make older streams readable.**

- Streams from builds that declare no number carry the computed number. A build with 1L still rejects them. The ticket's own case, a server on an older build, still fails.
- The number helps only between builds that use 1L. Later builds read streams from this version only if they keep 1L.
- Declaring the number is a promise that the maintainers keep the stored fields compatible. The runtime does not check that. Changes to the fields still need care under the Java serialization rules.
- Values inside a document are written by their own classes, with their own version numbers. This change covers the four document classes only.
- `SolrDocumentList`, which extends `ArrayList<SolrDocument>`, declares no number and is not changed here.
