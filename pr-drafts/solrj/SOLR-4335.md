## What happens today

**SolrJ writes U+FFFE and U+FFFF into update XML unchanged, and the server then reports an error for the request.**

The ticket quotes the server error `Invalid UTF-8 character 0xffff`. The escape routine copies every character that has no escape entry unchanged, and U+FFFE and U+FFFF have no entry. Neither character is legal in XML 1.0. The same routine already replaces other illegal control characters. For example, U+0000 becomes `#0;`, so the handling is inconsistent ([base code](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/solrj/src/java/org/apache/solr/common/util/XML.java#L133-L145), [Jira](https://issues.apache.org/jira/browse/SOLR-4335)).

## What this change does

**Each of the two characters is written as the text `#65534;` or `#65535;`, the way the existing control characters are written.**

- A new branch in the escape routine writes the text for these two characters ([lines 142-146](https://github.com/nick-boss-tech/solr/blob/8f6e267d6482516e9853df69da630e4f0142c72a/solr/solrj/src/java/org/apache/solr/common/util/XML.java#L142-L146)). `escapeCharData` and `escapeAttributeValue` both use that routine ([lines 75-81](https://github.com/nick-boss-tech/solr/blob/8f6e267d6482516e9853df69da630e4f0142c72a/solr/solrj/src/java/org/apache/solr/common/util/XML.java#L75-L81)).
- The text has no ampersand. It is plain text, not a character reference. The note in the table's source says invalid characters are written this way, because a real `&#nn;` reference makes strict parsers fail ([lines 58-59](https://github.com/nick-boss-tech/solr/blob/8f6e267d6482516e9853df69da630e4f0142c72a/solr/solrj/src/java/org/apache/solr/common/util/XML.java#L58-L59)).
- The substitution is lossy by design. A reader gets the text `#65535;` where the character was. Nothing in the document shows where the character was.
- The same two helpers serve other output, so those paths change too. That covers the XML response writer ([line 405](https://github.com/nick-boss-tech/solr/blob/8f6e267d6482516e9853df69da630e4f0142c72a/solr/core/src/java/org/apache/solr/response/XMLWriter.java#L405)), the schema XML writer ([line 475](https://github.com/nick-boss-tech/solr/blob/8f6e267d6482516e9853df69da630e4f0142c72a/solr/core/src/java/org/apache/solr/response/SchemaXmlWriter.java#L475)), and the XML request writer for delete-by-id and delete-by-query ([lines 141 and 148](https://github.com/nick-boss-tech/solr/blob/8f6e267d6482516e9853df69da630e4f0142c72a/solr/solrj/src/java/org/apache/solr/client/solrj/request/XMLRequestWriter.java#L141-L148)). The ticket is about SolrJ update requests, so these paths reach beyond it.

## Limits

**The substitution loses the character, and unpaired surrogates are not covered.**

- Lossy, as described above. Code that needs the exact character cannot recover it from this XML.
- Unpaired surrogates (U+D800 to U+DFFF) are also illegal in XML. They still pass through unchanged. On request, a follow-up ticket and pull request can cover them.
- The JSON and javabin request writers are not changed by this branch.
- No test sends a document with these characters through an update request. The tests cover the escape routine only.
