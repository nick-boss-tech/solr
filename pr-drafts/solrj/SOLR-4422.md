## What happens today

**A bean's dynamic-field Map comes back in hash order, not in the order of the document's fields.**

A bean field with a dynamic pattern, such as `@Field("ord_*") Map<String, String>`, gets its values from a `SolrDocument` through `DocumentObjectBinder`. The binder collects them in a `HashMap` ([DocumentObjectBinder.java line 419 (base)](https://github.com/apache/solr/blob/97d973814336101e12475558d7419321c743de79/solr/solrj/src/java/org/apache/solr/client/solrj/beans/DocumentObjectBinder.java#L419)). A `HashMap` iterates in hash order, which depends on the key names. The document keeps its fields in insertion order ([SolrDocument.java line 49 (base)](https://github.com/apache/solr/blob/97d973814336101e12475558d7419321c743de79/solr/solrj/src/java/org/apache/solr/common/SolrDocument.java#L49)), so the bound map loses an order the document had. SOLR-4422 reports this.

## What this change does

**The binder collects dynamic-field values into a `LinkedHashMap`, so the bound map keeps the document's field order.**

The change is one line in `getFieldValue` ([DocumentObjectBinder.java line 420](https://github.com/nick-boss-tech/solr/blob/3e5b7afecddbe93eeea3b2cd468c2836091392a8/solr/solrj/src/java/org/apache/solr/client/solrj/beans/DocumentObjectBinder.java#L420)), plus the import for `LinkedHashMap`. The list form of a dynamic field already keeps order, because it uses an `ArrayList`, so it is not changed.

Behavior change: every bean with a dynamic-field `Map` now gets a `LinkedHashMap` in document order. The keys and values stay the same. Only the iteration order changes.

## Proof

**The new test fails on the base code and passes with this change.**

[`TestDocumentObjectBinder`](https://github.com/nick-boss-tech/solr/blob/3e5b7afecddbe93eeea3b2cd468c2836091392a8/solr/solrj/src/test/org/apache/solr/client/solrj/beans/TestDocumentObjectBinder.java#L82-L101): 6 of 6 pass at head `3e5b7afecddb`, verified 2026-10-06. The new test, `testDynamicFieldMapKeepsDocumentOrder`, adds 40 fields in descending name order and checks that the bound map's keys follow the insertion order. On the base code it fails: the keys come back in hash order. With this change it passes.

## Limits

**Covered: dynamic-field `Map` bindings. Not covered: other binder paths.**

- The binder still builds a new map and sets it on the bean. If matching fields exist, a map the bean's constructor already filled is replaced. If nothing matches, the bean keeps its own value. The ticket also suggests filling the bean's existing map. This change does not do that. A follow-up is possible if maintainers want it.
- The test checks key order for `Map<String, String>` with single values. It does not cover `Map<String, List<...>>` bindings.
