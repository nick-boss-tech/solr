## What happens today

**A solrconfig.xml parameter with no name attribute loads without any error.**

The ticket's example is `<str Name="df">name</str>` in a request handler's `defaults` list. The attribute is spelled `Name`, so the element has no `name` attribute, and a lookup for `df` finds nothing. In the base code, [`NamedList.toSolrParams`](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/solrj/src/java/org/apache/solr/common/util/NamedList.java#L349-L356) (base) accepts such an entry without complaint and stores it under a null name.

## What this change does

**`NamedList.toSolrParams` throws a `SolrException` for an entry with no name.**

The exception uses the server error code and names the value, for example `Parameter without a name (missing 'name' attribute?), with value: name`. The check is in [`toSolrParams`](https://github.com/nick-boss-tech/solr/blob/2e947b7f622c6c530350ecef3679b01e1b004cde/solr/solrj/src/java/org/apache/solr/common/util/NamedList.java#L349-L361). Entries with a name convert as before.

## Proof

**The new test fails on the base code and passes with this change.**

- `NamedListTest` 6/6 at head `2e947b7f622c`, including `testToSolrParamsRejectsUnnamedEntry`. On the base code that test fails because the unnamed entry converts without an exception.
- The module check task, without tests, passed.

Verified 2026-10-06 at this head.

## A choice to check

**The check runs when a list is converted to parameters, not when solrconfig.xml is read.**

The implemented check covers every list that becomes parameters, such as handler defaults, appends and invariants. The ticket places the check where solrconfig.xml is read. That check could name the element, but it would reject unnamed elements in lists that are never used as parameters, although a list does not require names. It would also need an exception for children of an `arr` element, which are read without names.

Should the check move to the config reader, as the ticket suggests, or stay where a list becomes parameters?

## Limits

**The check runs only where a list becomes parameters.**

In this tree the check runs in 29 non-test source files that call `toSolrParams`, in `solr/core`, `solr/solrj` and `solr/modules`. The handler defaults, appends and invariants path (`getSolrParamsFromNamedList` in [`RequestHandlerBase.java`](https://github.com/nick-boss-tech/solr/blob/2e947b7f622c6c530350ecef3679b01e1b004cde/solr/core/src/java/org/apache/solr/handler/RequestHandlerBase.java#L217-L221)) is one of them, and so are the javabin update reader in [`JavabinLoader.java`](https://github.com/nick-boss-tech/solr/blob/2e947b7f622c6c530350ecef3679b01e1b004cde/solr/core/src/java/org/apache/solr/handler/loader/JavabinLoader.java#L165) and the javabin update request codec in [`JavaBinUpdateRequestCodec.java`](https://github.com/nick-boss-tech/solr/blob/2e947b7f622c6c530350ecef3679b01e1b004cde/solr/solrj/src/java/org/apache/solr/client/solrj/request/JavaBinUpdateRequestCodec.java#L122). No code that reads a response calls `toSolrParams` here, so an unnamed entry in a response list does not throw.

An empty name (`name=""`) is not rejected, because the parser keeps the empty string as the name ([`getAttr`](https://github.com/nick-boss-tech/solr/blob/2e947b7f622c6c530350ecef3679b01e1b004cde/solr/solrj/src/java/org/apache/solr/common/util/DOMUtil.java#L80-L88)). For an array value, the message shows the Java object text. The error uses the server error code even for a client's javabin update request. A follow-up for the empty-name case can be opened on request.
