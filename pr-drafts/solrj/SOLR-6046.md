## What happens today

**An atomic update whose value is a Java array is written as the array's `toString()`, so the field holds text such as `[Ljava.lang.String;@162d4ea3`.**

The XML update writer expands a `Collection` operand into one field element per value. An `Object[]` operand is not a `Collection`, so it falls through to the single-value path, which writes `toString()` ([base code](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/solrj/src/java/org/apache/solr/client/solrj/util/ClientUtils.java#L111-L116)). The ticket's example puts a `String[]` under `set`. The ticket reports that a `List` with the same values works with this writer, and that the binary writer works too ([Jira](https://issues.apache.org/jira/browse/SOLR-6046)).

## What this change does

**The XML writer expands an `Object[]` operand into one field element per element, the same way it already expands a `Collection`.**

- The new branch calls the same single-value writer for each element ([lines 115-118](https://github.com/nick-boss-tech/solr/blob/3b833e369a0bf5fc06c976c7e1febe17694223c4/solr/solrj/src/java/org/apache/solr/client/solrj/util/ClientUtils.java#L115-L118)). A `String[]` under `set` becomes two `<field update="set">` elements.
- The server joins repeated elements that share a field name and update key into one operation whose value is the list of both values ([XMLLoader.java lines 381-398](https://github.com/nick-boss-tech/solr/blob/3b833e369a0bf5fc06c976c7e1febe17694223c4/solr/core/src/java/org/apache/solr/handler/loader/XMLLoader.java#L381-L398)). So `set` receives both values, as it does for a `List`.
- Each element's text goes through `XML.escapeCharData` ([line 162](https://github.com/nick-boss-tech/solr/blob/3b833e369a0bf5fc06c976c7e1febe17694223c4/solr/solrj/src/java/org/apache/solr/client/solrj/util/ClientUtils.java#L162)). That is the routine that [SOLR-4335](https://issues.apache.org/jira/browse/SOLR-4335) changes.
- The branch applies to every `Object[]` under an update key, not only `String[]`. An `Integer[]` is expanded too.
- [SOLR-6045](https://issues.apache.org/jira/browse/SOLR-6045) covers the server side of the same shape, on the javabin path. Its pull request is [#5077](https://github.com/apache/solr/pull/5077). The two belong to the same pair. This change does not need SOLR-6045. The XML loader builds one operation per field before update processing sees it, so the repeated-operation case from SOLR-6045 does not come from this path.

## Limits

**Primitive arrays are not expanded, and the combination with SOLR-4335 has no test.**

- Primitive arrays such as `int[]` are not `Object[]`. They still go through `toString()`.
- The test uses `String[]` only. A null element is written as a null field element, the same way a null in a `List` is written, but no test covers that.
- No test combines an array element with a character that [SOLR-4335](https://issues.apache.org/jira/browse/SOLR-4335) changes. The two changes meet in the same escaping routine, which was checked by reading the code.
- The JSON and javabin request writers are not changed by this branch.
