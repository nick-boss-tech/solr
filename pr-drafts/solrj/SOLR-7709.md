## What happens today

**A javabin document that repeats a field name keeps only the last value.**

The ticket's example sends `field_2` three times. The javabin reader returns `[value_3]`, while the same input sent as XML keeps all three values. In the base code, both document readers call `setField` for each field entry, so a repeated name replaces the one before ([SolrDocument reader](https://github.com/nick-boss-tech/solr/blob/c3cdf7b46e8cfff3673f76d881f32cf8e7b00622/solr/solrj/src/java/org/apache/solr/common/util/JavaBinCodec.java#L734) and [SolrInputDocument reader](https://github.com/nick-boss-tech/solr/blob/c3cdf7b46e8cfff3673f76d881f32cf8e7b00622/solr/solrj/src/java/org/apache/solr/common/util/JavaBinCodec.java#L804), both base). The XML update reader adds each repeated field element with `addField` ([XMLLoader.java](https://github.com/nick-boss-tech/solr/blob/501078f22203f636c171ec90f63d746896365593/solr/core/src/java/org/apache/solr/handler/loader/XMLLoader.java#L403-L405)).

## What this change does

**Both document readers add repeated fields in stream order, as the XML reader does.**

When a name is already present, the reader calls `addField`. Otherwise it calls `setField`. The change is in [`readSolrDocument`](https://github.com/nick-boss-tech/solr/blob/501078f22203f636c171ec90f63d746896365593/solr/solrj/src/java/org/apache/solr/common/util/JavaBinCodec.java#L734-L739) and [`readSolrInputDocument`](https://github.com/nick-boss-tech/solr/blob/501078f22203f636c171ec90f63d746896365593/solr/solrj/src/java/org/apache/solr/common/util/JavaBinCodec.java#L809-L814).

This is a behavior change. A sender that repeats a field name in a javabin stream, expecting the last value to win, now gets every value. Such a sender has to send each field once.

## Limits

**Only the two document readers change.**

The ticket names these two readers, and the other readers in `JavaBinCodec` are not changed. A stream that sends each field name once reads as before.
