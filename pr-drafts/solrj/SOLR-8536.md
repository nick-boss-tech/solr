## What happens today

**Every MDC value of the submitting thread goes into the worker thread's name unchanged, so a value with a line break puts that break into the log output.**

`MDCAwareThreadPoolExecutor.execute` joins the values of the submitting thread's MDC into one string ([base code, lines 339-343](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj/src/java/org/apache/solr/common/util/ExecutorUtil.java#L339-L343)). The joined string is used in the thread name with only `/` doubled and no control characters removed ([base code, line 349](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj/src/java/org/apache/solr/common/util/ExecutorUtil.java#L349)). The ticket reports Solr log output split across lines because an application MDC value contained line breaks ([Jira](https://issues.apache.org/jira/browse/SOLR-8536)).

## What this change does

**Control characters are replaced with spaces in the joined string, before the thread name is built.**

- One `replaceAll` on the joined string does the replacement ([lines 349-350](https://github.com/nick-boss-tech/solr/blob/28552ddc26eb30df5c9bfcd612bbac3698372442/solr/solrj/src/java/org/apache/solr/common/util/ExecutorUtil.java#L349-L350)). It runs before the string is cut to the 512-character limit.
- Java's `\p{Cntrl}` matches U+0000 to U+001F and U+007F. Each of those characters becomes one space. The value `line1\nline2\tx` gives the name text `line1 line2 x` ([test, lines 48-65](https://github.com/nick-boss-tech/solr/blob/28552ddc26eb30df5c9bfcd612bbac3698372442/solr/solrj/src/test/org/apache/solr/common/util/ExecutorUtilTest.java#L48-L65)).
- Every MDC value is kept. Values are not filtered by key. Filtering by key is the alternative below.

## Proof

**The new test fails on the base code and passes with this change.**

- `ExecutorUtilTest`: 7 of 7 pass at head `28552ddc26eb30df5c9bfcd612bbac3698372442`, verified 2026-10-05. `StallDetectionTest` in the same module: 13 of 13 pass at that head.
- On the base code, 1 of the 7 fails: `testMdcControlCharactersNotInThreadName`. The name keeps the line break and the tab, so the name check fails.

## A choice to check

**Thread names keep the application's values, with control characters replaced. The alternative builds the name only from Solr's own MDC keys.**

- Option 1, implemented here: keep every MDC value and replace control characters with spaces. Application text still appears in thread names. A newline or carriage return can no longer split a log line that shows a name.
- Option 2, the reporter's suggestion: build the name only from MDC keys with Solr's prefixes. Application values would not appear in thread names at all. The cost is a prefix list that must cover every key Solr sets, and a change in what names show for anyone who reads application values there today.
- Was this the right call?

## Limits

**Only ASCII control characters are replaced, and values that are not Strings still fail.**

- Characters above ASCII are not replaced, including U+0080 to U+009F, U+2028 and U+2029.
- The loop that builds the string reads each MDC value as a String ([line 341](https://github.com/nick-boss-tech/solr/blob/28552ddc26eb30df5c9bfcd612bbac3698372442/solr/solrj/src/java/org/apache/solr/common/util/ExecutorUtil.java#L341)). A value of another type, such as an Integer stored in MDC through a logging API, still fails there with a ClassCastException, as a comment on the ticket reports for SolrJ 7.7. This change does not touch that loop. On request, a follow-up ticket and pull request can cover it.
