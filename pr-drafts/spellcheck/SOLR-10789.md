## What happens today

**A `spellcheck.collateParam.*` override for `tie`, `pf`, `pf2`, `pf3`, `bq` or `bf` is dropped before the collation check runs.**

When a spellcheck collation is verified, Solr runs the corrected query again. Each `spellcheck.collateParam.<name>` setting is copied into that query. Then Solr removes the scoring parameters that a DisMax or eDisMax query does not need for the check. The removal runs after the copy, so an override for one of those six parameters never reaches the query. For example, with `defType=edismax` and `spellcheck.collateParam.bq=teststop:political`, the boost query is dropped. Nothing in the log says so.

At the merge-base, the copy is at [L110-L123](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/spelling/SpellCheckCollator.java#L110-L123) and the removal is at [L136-L142](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/spelling/SpellCheckCollator.java#L136-L142).

## What this change does

**The scoring parameters are removed first, and the overrides are copied in after that.**

An override for `tie`, `pf`, `pf2`, `pf3`, `bq` or `bf` now reaches the check query. The example above now adds the boost query to the check. Scoring parameters from the original request are still removed for the check, as before. Only an explicit override can set them back ([L110-L131](https://github.com/nick-boss-tech/solr/blob/d9077048d74dc302127cf87af0b83b3d661871d4/solr/core/src/java/org/apache/solr/spelling/SpellCheckCollator.java#L110-L131)). The change touches only `SpellCheckCollator.java`, its test and a changelog entry.

This is a behavior change for anyone who sets these overrides. An override that does not parse now makes the check query fail. Solr logs a WARN for that candidate, counts it as having no hits, and offers no collation for it. The search itself still succeeds.

## Proof

**The new test fails on the base code and passes with this change.**

- `SpellCheckCollatorTest` passes 13 of 13 tests at head `d9077048d74`. The counts come from fresh JUnit XML, verified 2026-10-09.
- On the base code, [`testCollateParamOverrideOfScoringParams`](https://github.com/nick-boss-tech/solr/blob/d9077048d74dc302127cf87af0b83b3d661871d4/solr/core/src/test/org/apache/solr/spelling/SpellCheckCollatorTest.java#L279-L331) fails. That result is from 2026-10-09, with random seed `10789C0FFEE10789`, so the run can be repeated.
- The test has two checks, and both set `bq` through `spellcheck.collateParam.bq`. Both run through `/spellCheckCompRH` with the `direct` dictionary and `defType=edismax`. A valid boost query yields the collation `parisian political machine`. An unparseable one yields no collation.

## Limits

**Only `bq` has a test, and a bad override is logged, not returned as an error.**

- The test sets `bq` only. `tie`, `pf`, `pf2`, `pf3` and `bf` take the same path, but no test sets them.
- The overrides change only the collation check query. The main query is not affected.
- An unparseable override is handled the way a failed check query already is: a WARN in the log, and no collation for that candidate. The search does not fail. Returning a visible error to the client is not part of this change.
