## What happens today

**A build or reload that names an unknown dictionary fails with a NullPointerException, not a clear "does not exist" error.**

The handler looks up the dictionary, then calls `build` or `reload` on the result. An unknown name gives no dictionary, so the call fails on a null ([merge-base code](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L115-L117)).

With several dictionary names, one unknown name is added to the chain as a null. The chain then fails with a NullPointerException ([merge-base code](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L594), [merge-base addChecker](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/spelling/ConjunctionSolrSpellChecker.java#L49-L55)).

A query with the same unknown name gets a clear NOT_FOUND message ([merge-base code](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L234-L240)). Build and reload did not.

## What this change does

**An unknown dictionary name now gets the same NOT_FOUND error that a query gets.**

- The handler checks for a missing dictionary before build or reload ([code](https://github.com/nick-boss-tech/solr/blob/558864454f7f63e73293f77b85dbd3a89bb0c98a/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L115-L121)). It returns the same NOT_FOUND message as a query ([code](https://github.com/nick-boss-tech/solr/blob/558864454f7f63e73293f77b85dbd3a89bb0c98a/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L245-L250)).
- With several names, a missing one makes the lookup return nothing, so the same error follows ([code](https://github.com/nick-boss-tech/solr/blob/558864454f7f63e73293f77b85dbd3a89bb0c98a/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L604-L607)).
- Build and reload with no spellcheckers configured now return 200 with no action. The response has no `command` entry. A query on a handler with no spellcheckers also returns quietly ([code](https://github.com/nick-boss-tech/solr/blob/558864454f7f63e73293f77b85dbd3a89bb0c98a/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L138-L140)). Before this change, the same build or reload request failed.

## Proof

- `SpellCheckComponentTest` runs 15 of 15 at head `558864454f7f`, checked 2026-10-09. The new test is `testInvalidDictionaryWithBuildOrReload` ([SpellCheckComponentTest.java L283-L316](https://github.com/nick-boss-tech/solr/blob/558864454f7f63e73293f77b85dbd3a89bb0c98a/solr/core/src/test/org/apache/solr/handler/component/SpellCheckComponentTest.java#L283-L316)).
- A run on the merge-base code made the new test fail, as expected.

## A choice to check

**With no spellcheckers configured, build and reload return quietly. The other route is an error.**

- The quiet 200 matches how a query behaves with no spellcheckers. A reload script that runs on every server keeps working.
- The other route is a NOT_FOUND error for build and reload. Then the same script fails on any server that has no spellchecker.

Was quiet success the right call?

## Limits

**A distributed request on a handler with no spellchecker still fails with a NullPointerException.**

- The coordinator calls the lookup result without a null check, both when it changes shard requests and when it merges replies ([code](https://github.com/nick-boss-tech/solr/blob/558864454f7f63e73293f77b85dbd3a89bb0c98a/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L391), [code](https://github.com/nick-boss-tech/solr/blob/558864454f7f63e73293f77b85dbd3a89bb0c98a/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L450-L451)). The same code is on upstream main. A fix for that path can be opened as a follow-up on request.
- The new test covers an unknown name with spellcheckers configured. It does not cover the no-spellcheckers case or a distributed request.
