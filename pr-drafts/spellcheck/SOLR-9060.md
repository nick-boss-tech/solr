## What happens today

**Distributed spellcheck can return equally close suggestions in the wrong order, because shards leave out frequencies.**

A shard adds frequency data to its reply only when the request sets `spellcheck.extendedResults` ([merge-base code](https://github.com/nick-boss-tech/solr/blob/e432df19c4a50b9d54d7fba545397b859cc54f98/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L159)). The coordinator merges the shard replies. It breaks ties between equally close suggestions by frequency ([merge-base code](https://github.com/nick-boss-tech/solr/blob/e432df19c4a50b9d54d7fba545397b859cc54f98/solr/core/src/java/org/apache/solr/spelling/SolrSpellChecker.java#L118)). Without frequency data, every tie looks the same. The merged order then does not follow frequency.

## What this change does

**Shards always report frequencies, so the coordinator can break ties by frequency.**

- Shards report frequencies on every distributed spellcheck request ([code](https://github.com/nick-boss-tech/solr/blob/49040cb7b88ec62cc30523e16d2301c4fbd1fcc8/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L159-L161)).
- The coordinator's merge already uses frequency as the tie-break. It now receives the data it needs ([code](https://github.com/nick-boss-tech/solr/blob/49040cb7b88ec62cc30523e16d2301c4fbd1fcc8/solr/core/src/java/org/apache/solr/spelling/SolrSpellChecker.java#L118-L122)).
- The reply to the client does not change shape. Frequency fields appear only when the client asks for extended results ([code](https://github.com/nick-boss-tech/solr/blob/49040cb7b88ec62cc30523e16d2301c4fbd1fcc8/solr/core/src/java/org/apache/solr/handler/component/SpellCheckComponent.java#L664-L672)).
- Cost: every distributed spellcheck request now carries frequency values from each shard, even when the client did not ask for them. The only visible client change is the order of tied suggestions.

## Proof

**The new test passes with this change. With the shard change reverted, it fails on tie order.**

- The test indexes four words of one length. They tie on distance and have different frequencies. It compares a distributed query with a single-node query ([DistributedSpellCheckComponentTest.java L417-L455](https://github.com/nick-boss-tech/solr/blob/49040cb7b88ec62cc30523e16d2301c4fbd1fcc8/solr/core/src/test/org/apache/solr/handler/component/DistributedSpellCheckComponentTest.java#L417-L455)).
- At head `49040cb7b88`, verified 2026-10-14: `testShardMergeRanksTiesByFrequency` 1 of 1 passes (1 test, 0 failures, 0 errors, 0 skipped).
- With `SpellCheckComponent.java` reverted to the merge-base code and the test kept, verified 2026-10-14: 1 failure. The first suggestion differs (`zarnt` against `zornt`). That is a tie-order difference, not a count.

## A choice to check

**Shards send frequencies on every request. The other route was to leave shard replies as they are.**

- Sending frequencies makes tied suggestions follow frequency in every distributed query. The cost is a larger shard reply.
- Leaving shard replies alone keeps the payload the same. Tied suggestions then keep their current order.

Was the extra data on every distributed request worth the better tie order?

## Limits

**Frequency only breaks ties. The coordinator still ignores `comparatorClass`.**

- The coordinator merge uses the default queue, so `comparatorClass=freq` is not honored there. Honoring it is a larger change. A follow-up can be opened on request.
- Frequency does not rank suggestions overall. Only equally close suggestions are affected.
