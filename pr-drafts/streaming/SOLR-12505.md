## What happens today

**fetch() returns the tuples without the fetched fields when the target handler's default query parser is not lucene.**

fetch() sends its batch as `{! df=<join field> q.op=OR cache=false }` followed by the escaped key values. It sends no `defType`, so the handler's default parser reads the batch. Solr reads the `{!` prefix only when that default is lucene or func ([QParser.java lines 387 to 396, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/search/QParser.java#L387-L396)). With another default, the batch is read as plain query text and the fetched fields are missing. The ticket's assignee, Eric Pugh, found that removing `defType=edismax` from the `/select` handler fixed it.

The batch is built at [FetchStream.java lines 239 to 246](https://github.com/apache/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FetchStream.java#L239-L246) (base, at the merge-base; current main has the same lines).

## What this change does

**fetch() sends `defType=lucene` with every batch, so the prefix is read whatever the handler's default is.**

[FetchStream.java lines 255 to 257](https://github.com/nick-boss-tech/solr/blob/1a1875d95f3680c20447006efc3c949c57f5135f/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FetchStream.java#L255-L257) add the parameter. Behavior change: a `defType` default on the handler no longer applies to fetch batches. A handler with the lucene default, which is Solr's default and the test setup, sends the same batch as before.

**fetch() also rejects a join field name that would break its batch query.**

A join field name containing whitespace, braces, `!`, quotes or a backslash now fails when the expression is built, and the error names the field ([FetchStream.java lines 153 to 159](https://github.com/nick-boss-tech/solr/blob/1a1875d95f3680c20447006efc3c949c57f5135f/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FetchStream.java#L153-L159)). Before, such a name ended the `df=` value early in the batch query and corrupted the fetched-field list. The name is rejected rather than escaped: escaping would let the batch accept a name that is not in the schema, while the check fails with a message that says what is wrong.

## Proof

**The new test fails on the base FetchStream and passes with this change.**

[`testFetchStreamWithNonLuceneDefaultDefType`](https://github.com/nick-boss-tech/solr/blob/1a1875d95f3680c20447006efc3c949c57f5135f/solr/solrj-streaming/src/test/org/apache/solr/client/solrj/io/stream/StreamDecoratorTest.java#L951-L1006) sets the test collection's `/select` default to edismax. With the base FetchStream, it fails with `ComparisonFailure: expected:<alpha> but was:<null>`.

With this change, StreamDecoratorTest runs 57 tests, 5 skipped, 0 failures at head `1a1875d95f3680c20447006efc3c949c57f5135f`, verified 2026-10-13. That includes the two existing fetch tests, which use the default parser and do not change.

[`testFetchStreamRejectsJoinFieldNameThatBreaksLocalParams`](https://github.com/nick-boss-tech/solr/blob/1a1875d95f3680c20447006efc3c949c57f5135f/solr/solrj-streaming/src/test/org/apache/solr/client/solrj/io/stream/StreamDecoratorTest.java#L1009-L1046) sends the join field name `a i`. On the base FetchStream the drain fails with the server's parser error, `invalid query parser 'i'`, which does not name the join field. With this change it fails at construction with the clear error.

## A choice to check

**The batch sets `defType=lucene`. The ticket thread also named the terms query parser.**

Joel Bernstein proposed setting the parameter, and David Smiley agreed ([his comment](https://issues.apache.org/jira/browse/SOLR-12505?focusedCommentId=16519637)). Smiley also suggested the terms parser ([plugin name, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/search/TermsQParserPlugin.java#L74), [comma separator, base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/search/TermsQParserPlugin.java#L150)). That alternative sets `defType=terms` with the keys as the query. It changes the query text of every batch, and the keys would need the terms separator instead of the escaping the batch uses now.

Was setting `defType` on the batch the right call, or should the batch use the terms parser?

## Limits

**Covered: fetch batches on a handler with any non-lucene default. The test uses edismax only. Not covered: the realtime get endpoint.**

- Only the batch request and the join field check change. The search side of the expression is untouched.
- The realtime get endpoint, which the ticket raised, works only when the join field is the uniqueKey. It is not used here.
- Base: this change is written against merge-base 14c7aac0d151402b00259e2fb9bf5eed7049ec5d, which is 72 commits behind upstream main. It has not been rebased.
