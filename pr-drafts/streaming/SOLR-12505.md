## What happens today

**fetch() returns the tuples without the fetched fields when the target handler's default query parser is not lucene.**

fetch() sends its batch as `{! df=<join field> q.op=OR cache=false }` followed by the escaped key values. It sends no `defType`, so the handler's default parser reads the batch. Solr reads the `{!` prefix only when that default is lucene or func ([QParser.java lines 387 to 396, merge-base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/search/QParser.java#L387-L396)). With another default, the batch is read as plain query text and the fetched fields are missing. The ticket's assignee, Eric Pugh, found that removing `defType=edismax` from the `/select` handler fixed it.

The batch is built at [FetchStream.java lines 239 to 246](https://github.com/apache/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FetchStream.java#L239-L246) (merge-base; current main has the same lines).

## What this change does

**fetch() sends `defType=lucene` with every batch, so the prefix is read whatever the handler's default is.**

[FetchStream.java lines 273 to 276](https://github.com/nick-boss-tech/solr/blob/bd6c16d9164fb923991c3aed0732bbb31186d0ff/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FetchStream.java#L273-L276) add the parameter. Behavior change: a `defType` default on the handler no longer applies to fetch batches. A handler with the lucene default, which is Solr's default and the test setup, sends the same batch as before.

**fetch() also rejects a join field name that would break its batch query.**

A join field name that would break the batch query now fails when the expression is built, and the error names the field ([FetchStream.java lines 153 to 187](https://github.com/nick-boss-tech/solr/blob/bd6c16d9164fb923991c3aed0732bbb31186d0ff/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FetchStream.java#L153-L187)). The batch sends the name as an unquoted value, which the local-params reader ends at whitespace or `}`, so both are rejected anywhere in the name. A leading quote would switch the reader to a quoted string, and a leading `$` would be read as a reference to a request parameter, so both are rejected at the start of the name. The whitespace in that check is `Character.isWhitespace`, the same definition the local-params reader splits on, so Unicode spaces are rejected as well as ASCII ones. Before, a name with whitespace or `}` ended the `df=` value early in the batch query and corrupted the fetched-field list, and a name starting with `$` sent the batch looking up the wrong field. The name is rejected rather than escaped: escaping would let the batch accept a name that is not in the schema, while the check fails with a message that says what is wrong.

[`testFetchStreamRejectsJoinFieldNameThatBreaksLocalParams`](https://github.com/nick-boss-tech/solr/blob/bd6c16d9164fb923991c3aed0732bbb31186d0ff/solr/solrj-streaming/src/test/org/apache/solr/client/solrj/io/stream/StreamDecoratorTest.java#L1009-L1036) sends the join field name `a i`. [`testFetchStreamRejectsJoinFieldNameWithUnicodeSpace`](https://github.com/nick-boss-tech/solr/blob/bd6c16d9164fb923991c3aed0732bbb31186d0ff/solr/solrj-streaming/src/test/org/apache/solr/client/solrj/io/stream/StreamDecoratorTest.java#L1039-L1069) sends the join field name `a\u2003i`, with an em space (U+2003) instead of an ASCII space; the local-params reader splits on that character too. On the head before the leading-`$` rejection, nothing rejects the name: the batch is sent, `$a_i` is read as a parameter reference, and the server answers that parameter `a_i` is missing.

## A choice to check

**The batch sets `defType=lucene`. The ticket thread also named the terms query parser.**

Joel Bernstein proposed setting the parameter, and David Smiley agreed ([his comment](https://issues.apache.org/jira/browse/SOLR-12505?focusedCommentId=16519637)). Smiley also suggested the terms parser ([plugin name, merge-base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/search/TermsQParserPlugin.java#L74), [comma separator, merge-base](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/core/src/java/org/apache/solr/search/TermsQParserPlugin.java#L150)). That alternative sets `defType=terms` with the keys as the query. It changes the query text of every batch, and the keys would need the terms separator instead of the escaping the batch uses now.

Was setting `defType` on the batch the right call, or should the batch use the terms parser?

One difference matters at scale: the batch ORs one clause per key value, so a batch holding more key values than the handler's `maxBooleanClauses` (1024 by default) would fail under lucene. The terms parser has no such limit.

## Limits

**The batch no longer depends on a handler's default defType. The test uses edismax only. Not covered: the realtime get endpoint, or a handler that pins defType under invariants.**

- Only the batch request and the join field check change. The search side of the expression is untouched.
- StreamFactory reports only a generic message for a constructor failure, so the check's message sits on the cause chain. Fixing that is outside this change; a follow-up ticket and PR can be opened on request.
- The rejection tests use three bad names: an ASCII space, an em space, and `$a_i` for the leading-dollar case. Names containing `{`, `!` or a backslash are not rejected, because the reader treats them as ordinary characters.
- A handler that pins `defType` under `invariants` still overrides the batch's `defType=lucene`, because request parameters do not override invariants. The new test covers a handler `defaults` entry; the invariants configuration is not covered.
- The realtime get endpoint, which the ticket raised, works only when the join field is the uniqueKey. It is not used here.
- Base: this change is written against merge-base 14c7aac0d151402b00259e2fb9bf5eed7049ec5d, which is 77 commits behind upstream main at d38e0f16237, as counted on 2026-10-13. It has not been rebased.
