## What happens today

**fetch() returns the tuples without the fetched fields when the target handler's default query parser is not lucene.**

fetch() sends its batch as `{! df=<key> q.op=OR cache=false }` followed by the escaped keys. It sends no `defType`, so the handler's default parser reads the batch. Solr reads the `{!` prefix only when that default is lucene or func ([QParser.java lines 387 to 396](https://github.com/nick-boss-tech/solr/blob/5f20e1171bc890509d76e4f5f7defcc4fc8c102c/solr/core/src/java/org/apache/solr/search/QParser.java#L387-L396)). With another default, the batch is read as plain query text and the fetched fields are missing. The ticket reporter found that setting the `/select` default to lucene fixed it.

The batch is built at [FetchStream.java lines 239 to 246](https://github.com/apache/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FetchStream.java#L239-L246) (base, at the merge-base; current main has the same lines).

## What this change does

**fetch() sends `defType=lucene` with every batch, so the prefix is read whatever the handler's default is.**

[FetchStream.java lines 247 to 249](https://github.com/nick-boss-tech/solr/blob/5f20e1171bc890509d76e4f5f7defcc4fc8c102c/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FetchStream.java#L247-L249) add the parameter. Behavior change: a `defType` default on the handler no longer applies to fetch batches. A handler with the lucene default, which is Solr's default and the test setup, sends the same batch as before.

## Proof

**The new test fails on the base FetchStream and passes with this change.**

[`testFetchStreamWithNonLuceneDefaultDefType`](https://github.com/nick-boss-tech/solr/blob/5f20e1171bc890509d76e4f5f7defcc4fc8c102c/solr/solrj-streaming/src/test/org/apache/solr/client/solrj/io/stream/StreamDecoratorTest.java#L946-L1006) sets the test collection's `/select` default to edismax. With the base FetchStream, it fails with `ComparisonFailure: expected:<alpha> but was:<null>`.

With this change, StreamDecoratorTest runs 56 tests, 5 skipped, 0 failures at head `5f20e1171bc890509d76e4f5f7defcc4fc8c102c`, verified 2026-10-04. That includes the two existing fetch tests, which use the default parser and do not change.

## A choice to check

**The batch sets `defType=lucene`. The ticket thread also named the terms query parser.**

Joel Bernstein proposed setting the parameter, and David Smiley agreed ([his comment](https://issues.apache.org/jira/browse/SOLR-12505?focusedCommentId=16519637)). Smiley also suggested the terms parser ([plugin name](https://github.com/nick-boss-tech/solr/blob/5f20e1171bc890509d76e4f5f7defcc4fc8c102c/solr/core/src/java/org/apache/solr/search/TermsQParserPlugin.java#L74), [comma separator](https://github.com/nick-boss-tech/solr/blob/5f20e1171bc890509d76e4f5f7defcc4fc8c102c/solr/core/src/java/org/apache/solr/search/TermsQParserPlugin.java#L150)). That alternative sets `defType=terms` with the keys as the query. It changes the query text of every batch, and the keys would need the terms separator instead of the escaping the batch uses now.

Was setting `defType` on the batch the right call, or should the batch use the terms parser?

## Limits

**Covered: fetch batches on a handler with a non-lucene default. Not covered: other default parsers, and the realtime get endpoint.**

- Only the batch request changes. The search side of the expression is untouched.
- The realtime get endpoint, which the ticket raised, works only when the join field is the uniqueKey. It is not used here.
