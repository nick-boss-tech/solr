## What happens today

**A min or max on a date field makes facet() fail with a ClassCastException.**

The facet() expression casts each metric value to a Number. A date is not a Number, so the stream fails in `FacetStream.open` with `java.util.Date cannot be cast to java.lang.Number`, as the ticket shows. The cast is at [FacetStream.java line 951](https://github.com/apache/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FacetStream.java#L951) (base, at the merge-base; current main has the same line). A bucket with no value for the metric field fails with a NullPointerException when the stream reads that value.

## What this change does

**Date min and max come back as ISO-8601 strings, and min and max over string fields return strings too.**

- A metric value that is not a Number is kept as it is. A Date becomes its ISO-8601 instant, such as `2018-01-01T00:00:00Z` ([FacetStream.java lines 953 to 958](https://github.com/nick-boss-tech/solr/blob/16a0a69e8398079cceb4bec4bd7e0f6bcf02c469/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/FacetStream.java#L953-L958)).
- [MinMetric.java](https://github.com/nick-boss-tech/solr/blob/16a0a69e8398079cceb4bec4bd7e0f6bcf02c469/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/metrics/MinMetric.java#L71-L74) and [MaxMetric.java](https://github.com/nick-boss-tech/solr/blob/16a0a69e8398079cceb4bec4bd7e0f6bcf02c469/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/metrics/MaxMetric.java#L65-L68) keep the smallest or largest string they see. The parallel (rollup) path uses this to combine the per-collection values.
- A bucket with no value for the metric field now gets a null for that metric.
- API change: `Metric.getValue()` returns `Object`, not `Number` ([Metric.java line 75](https://github.com/nick-boss-tech/solr/blob/16a0a69e8398079cceb4bec4bd7e0f6bcf02c469/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/metrics/Metric.java#L75)). Callers that assign the result to a Number need a cast.

## Proof

**Both new tests fail on the base code and pass with this change.**

[StreamExpressionTest.java lines 1421 to 1530](https://github.com/nick-boss-tech/solr/blob/16a0a69e8398079cceb4bec4bd7e0f6bcf02c469/solr/solrj-streaming/src/test/org/apache/solr/client/solrj/io/stream/StreamExpressionTest.java#L1421-L1530) holds `testFacetStreamMinMaxOnDateField` and `testFacetStreamMinMaxOnDateFieldParallelRollup`.

- On the base FacetStream and base metrics, both fail with the ClassCastException from the ticket.
- With only the FacetStream change, the parallel test fails: the rollup returns 1.7976931348623157E308 where it should return `2018-01-01T00:00:00Z`. So the metric change is needed too.
- With this change, StreamExpressionTest passes 35 of 35 at head `16a0a69e8398079cceb4bec4bd7e0f6bcf02c469`: the 33 existing tests and the 2 new ones. Verified 2026-10-07.

## Limits

**Min and max on dates compare text, which matches time order only when the fractional digits match.**

Solr writes only the fractional digits a value needs. As text, `2018-03-01T10:00:00Z` sorts after `2018-03-01T10:00:00.250Z`, though it is the earlier time. So the parallel rollup can return the wrong min or max when values from the same second have different numbers of fractional digits. The tests use whole seconds only. The direct facet path takes min and max from Solr, so it is not affected.

- String min and max use plain text order (`String.compareTo`).
- The parallel test uses one alias over two collections. Fractional seconds are not tested.
