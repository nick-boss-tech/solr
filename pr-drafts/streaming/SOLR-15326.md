## What happens today

**The /export sort goes out exactly as the caller wrote it, so documents that tie on that sort come back in no defined order.**

`CloudSolrStream.open` sends the caller's sort and nothing else ([merge base, lines 314-319](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/CloudSolrStream.java#L314-L319)). The merge of shard results compares only those sort fields. The order of tied documents is therefore not fixed by the request. The ticket reports records missing from a parallel `gatherNodes` expression.

## What this change does

**When the /export sort lacks the unique key, the stream appends it as a final ascending sort.**

- `open` runs this check first ([lines 316-321](https://github.com/nick-boss-tech/solr/blob/dab6a466316940ea643c22dd9e56c9a63c0cb7fb/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/CloudSolrStream.java#L316-L321)). It does nothing unless the request has parameters, uses `qt=/export`, and sets a sort ([L599-L608](https://github.com/nick-boss-tech/solr/blob/dab6a466316940ea643c22dd9e56c9a63c0cb7fb/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/CloudSolrStream.java#L599-L608)).
- The unique key is read with one schema request during `open`, for every /export request that has a sort. If that request fails, `open` throws an `IOException` that says the unique key could not be resolved ([L622-L642](https://github.com/nick-boss-tech/solr/blob/dab6a466316940ea643c22dd9e56c9a63c0cb7fb/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/CloudSolrStream.java#L622-L642)).
- The sort sent to the export handler and the merge comparator both gain the unique key ([L615-L619](https://github.com/nick-boss-tech/solr/blob/dab6a466316940ea643c22dd9e56c9a63c0cb7fb/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/stream/CloudSolrStream.java#L615-L619)).
- Behavior change: tied documents now come back in unique-key order instead of arrival order. A sort that already contains the unique key is unchanged.

## Proof

**`testCloudStreamExportSortAddsUniqueKeyTieBreaker` fails on the base code and passes with this change.**

- On the base code, the test fails with its message, "Export sort should include the unique key as a stable tie-breaker: a_i asc". It is the only failing test in that run, with the base code in place of this change and the tests kept (run 37178321158).
- With this change: `StreamingTest` 35 tests, 1 skipped, 0 failures; verified 2026-10-04 at `dab6a466316` (run 37178940561).

## Limits

**The test checks the sort string the stream sends, not the order of the documents it returns.**

- In a run on the base code (2026-10-04), the ticket's query shapes returned every expected document exactly once, so the missing-record symptom did not reproduce on current main. This change adds a fixed order for ties. It does not fix a loss of records that has been shown.
- Each /export open with a sort makes one extra schema request, including sorts that already contain the unique key.
