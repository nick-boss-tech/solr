## What happens today

**At the base commit, a stream from a default client stops after 600 seconds in total, not 60.**

The ticket reports a 60-second limit. That matches SolrJ 9.4 to 9.6, where the cache's default idle timeout was its 60-second floor ([SolrClientCache.java lines 193 and 197 at release 9.6.0](https://github.com/nick-boss-tech/solr/blob/f8e5a93c11267e13b7b43005a428bfb910ac6e57/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/SolrClientCache.java#L193-L197)). Commit [dd89cd604a6](https://github.com/nick-boss-tech/solr/commit/dd89cd604a6dd563f15dfcec4f7a9ce5076b2410) (SOLR-17776) changed the cache so that an unset idle timeout takes the 600-second builder default. The base commit includes that change. With no request timeout set, the request timeout falls back to the idle timeout ([HttpSolrClient.java lines 597 to 601](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj/src/java/org/apache/solr/client/solrj/impl/HttpSolrClient.java#L597-L601)). The Jetty client applies that total to each request ([HttpJettySolrClient.java line 649](https://github.com/nick-boss-tech/solr/blob/14c7aac0d151402b00259e2fb9bf5eed7049ec5d/solr/solrj-jetty/src/java/org/apache/solr/client/solrj/jetty/HttpJettySolrClient.java#L649)).

## What this change does

**Clients that the stream cache builds get no total time limit.**

After its idle floor, the cache sets the request timeout to `Long.MAX_VALUE` ([SolrClientCache.java lines 166 to 169 at the head](https://github.com/nick-boss-tech/solr/blob/42b6c4fc9158524ceb6b91aa2f4c6583a387c6f9/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/SolrClientCache.java#L166-L169)). This covers the default caches that `SolrStream` and `CloudSolrStream` create, and the clients a Solr node builds through its internal cache when no open connection matches.

Behavior changes wider than the ticket:
- The JDK client has no other bound. Its idle timeout does not apply, so a stalled request on that path does not end.
- On the Jetty path, a stalled request still ends after the 600-second idle timeout.
- A request timeout set on a seed client is replaced for cache clients. A test asserts this.
- The floors become per instance, and two new constructors accept custom floors. Those constructors do not clamp the connection floor to 60 seconds. They are the SOLR-17143 part of this branch ([SOLR-17143](https://issues.apache.org/jira/browse/SOLR-17143)).

## A choice to check

**The unlimited timeout is set in the stream cache, not in the HTTP client.**

The reporter suggested no timeout at all while a stream keeps returning content. The ticket discussion proposes another route: a default request timeout of -1 in `HttpSolrClient`, which the JDK client would read as no timeout. That route reaches every client, not only cache clients, and the Jetty and JDK clients must agree on it. This change limits the change to the cache. Was the cache the right place for it?
