## What happens today

**DatabaseMetaData.getColumns returns null, and getTypeInfo throws UnsupportedOperationException.**

getColumns gives `null` where a `ResultSet` is expected. getTypeInfo throws a runtime exception, not the `SQLException` that JDBC specifies for an unsupported feature ([DatabaseMetaDataImpl.java lines 755 to 758](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/sql/DatabaseMetaDataImpl.java#L755-L758) and [lines 816 to 817](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/sql/DatabaseMetaDataImpl.java#L816-L817)). Links here point to the merge-base commit.

## What this change does

**getColumns now returns the columns that match its patterns, and getTypeInfo throws the standard JDBC exception.**

getColumns queries `metadata.COLUMNS` with the schema, table and column patterns and selects 18 columns ([DatabaseMetaDataImpl.java lines 755 to 777](https://github.com/nick-boss-tech/solr/blob/5fe174425514852da8a949ecc7e6502274d3edb3/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/sql/DatabaseMetaDataImpl.java#L755-L777)). getTypeInfo throws `SQLFeatureNotSupportedException` ([lines 833 to 836](https://github.com/nick-boss-tech/solr/blob/5fe174425514852da8a949ecc7e6502274d3edb3/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/sql/DatabaseMetaDataImpl.java#L833-L836)). Behavior change: getColumns no longer returns null.

## A choice to check

**The new columns use the driver's camelCase labels, as getTables does. The JDBC names are the other route.**

The query labels its columns `tableName`, `columnName` and so on ([lines 760 to 762](https://github.com/nick-boss-tech/solr/blob/5fe174425514852da8a949ecc7e6502274d3edb3/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/sql/DatabaseMetaDataImpl.java#L760-L762)). JDBC names them `TABLE_NAME` and `COLUMN_NAME`. A lookup by label is a key match ([ResultSetImpl.java lines 439 to 449, merge-base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/sql/ResultSetImpl.java#L439-L449)), so asking for `COLUMN_NAME` returns `null`. JDBC names would match the specification but differ from getTables. Was camelCase the right call, or should getColumns use the JDBC names?

## Limits

**getTypeInfo still throws, and a metadata call closes the result set of the call before it.**

Only the getTypeInfo exception class changed. Metadata calls share one statement, and each new query closes the result set still open on it ([ConnectionImpl.java lines 73 to 74](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/sql/ConnectionImpl.java#L73-L74) and [StatementImpl.java lines 55 to 60](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/solrj-streaming/src/java/org/apache/solr/client/solrj/io/sql/StatementImpl.java#L55-L60), merge-base). A caller that reads a getTables or getColumns result while making another metadata call loses it. The test reads each result before the next call, so it does not cover this. The rows have no ORDER BY, though JDBC specifies one, and the catalog argument is unused.
