## What happens today

**A suggester build can fail with "No space left on device" when the JVM temp directory is full.**

The reporter saw this error on core load, while the data disk had about 600 GB free. The stack trace goes through `AnalyzingSuggester.build` and Lucene's `OfflineSorter` ([JIRA](https://issues.apache.org/jira/browse/SOLR-10937)). The error does not name the temp path. The ref guide did not say that these builds use that directory.

## What this change does

**The ref guide now says which suggesters use the JVM temp directory.**

- A NOTE at the top of "Lookup Implementations" names five lookups: `AnalyzingLookupFactory`, `FuzzyLookupFactory`, `FSTLookupFactory`, `WFSTLookupFactory`, and `TSTLookupFactory`. It says their builds write to `java.io.tmpdir`, not the core's data directory. It also shows how to point that property at a larger volume ([NOTE](https://github.com/nick-boss-tech/solr/blob/7d0cd11bafdce4a258b8758a34b9ccca364e4023/solr/solr-ref-guide/modules/query-guide/pages/suggester.adoc#L204-L207)).
- Docs only. No code or error text changes.

## Proof

**Docs only, with no test. The five-lookup list was checked in Lucene's bytecode.**

- There is no test and no failing-before run, because this is a docs change.
- The pinned Lucene 10.4.0 `lucene-suggest` jar was read with `javap -c -p`. Each of the five builds reaches `OfflineSorter` with the temp directory. Fuzzy inherits the build from Analyzing.
- Checked 2026-10-09.

## Limits

**The path-naming follow-up is not in this PR.**

- The build error still does not name the temp path. Naming it is a possible follow-up. A PR for it can be opened on request.
- The check read bytecode, not Lucene source. No sources jar was available locally.
