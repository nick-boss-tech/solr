## What happens today

**A suggester configured with `allTermsRequired=false` still requires every term when a request has a context filter.**

`SuggestComponent` defaults `suggest.allTermsRequired` to `true` and always passes that value on ([base code](https://github.com/nick-boss-tech/solr/blob/9b3a84b1c460981eab09d8ffaef776acc4a184f8/solr/core/src/java/org/apache/solr/handler/component/SuggestComponent.java#L270)). The request default overrides the configured value on this path, so a partial match is not returned.

## What this change does

**On context-filtered requests, the suggester's configured `allTermsRequired` now applies unless the request sets `suggest.allTermsRequired`.**

- `SuggestComponent` no longer defaults the request value, so an omitted parameter stays `null` ([L270](https://github.com/nick-boss-tech/solr/blob/faa262eedc554109123106b4f26a4ad9ad063a76/solr/core/src/java/org/apache/solr/handler/component/SuggestComponent.java#L270)).
- `SolrSuggester` reads the configured value in `init` ([L108-L110](https://github.com/nick-boss-tech/solr/blob/faa262eedc554109123106b4f26a4ad9ad063a76/solr/core/src/java/org/apache/solr/spelling/suggest/SolrSuggester.java#L108-L110)). A request value wins when present. Otherwise the configured value applies ([L244-L247](https://github.com/nick-boss-tech/solr/blob/faa262eedc554109123106b4f26a4ad9ad063a76/solr/core/src/java/org/apache/solr/spelling/suggest/SolrSuggester.java#L244-L247)).
- Suggesters without the setting keep `true`. Only suggesters configured with `false` that also receive a context filter change behavior.
- Requests without a context filter are unchanged.

## A choice to check

**The fallback is a literal `true` in `SolrSuggester`. The alternative reads the lookup's own default.**

- Implemented: `true` is written in `SolrSuggester` ([L93](https://github.com/nick-boss-tech/solr/blob/faa262eedc554109123106b4f26a4ad9ad063a76/solr/core/src/java/org/apache/solr/spelling/suggest/SolrSuggester.java#L93)). It applies when the suggester does not configure the value.
- Alternative: take the default from the lookup factory. When the value is unset, the factories use Lucene's `AnalyzingInfixSuggester.DEFAULT_ALL_TERMS_REQUIRED` ([AnalyzingInfixLookupFactory L100-L103](https://github.com/nick-boss-tech/solr/blob/faa262eedc554109123106b4f26a4ad9ad063a76/solr/core/src/java/org/apache/solr/spelling/suggest/fst/AnalyzingInfixLookupFactory.java#L100-L103)). In Lucene 10.4.0 that constant is `true`, so both sources agree today. The choice matters only if one of them changes.

Was a literal `true` the right fallback, or should the lookup's own default decide it?

## Limits

**Configured `true` gives different answers on the two paths. That split predates this change and is not fixed here.**

- The lookup factories read the configured value with `Boolean.getBoolean`. That reads the value as the name of a system property, so a configured `true` gives `false` on the path without a context filter, unless a system property named `true` is set. The context path reads the same setting as `true`. The base code already had this split, because the context path always used `true`.
- The test covers configured `false` and an explicit request `true`. It does not cover configured `true`.
- A follow-up fix for the factory parsing can be opened as its own ticket and PR, on request.
