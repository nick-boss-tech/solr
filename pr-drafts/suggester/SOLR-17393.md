## What happens today

**The distributed merge keeps the first equal-weight candidate that arrives, so the result follows shard order.**

The coordinator merges shard results through a queue of size `count` that compares weight only ([base code](https://github.com/nick-boss-tech/solr/blob/c3cdf7b46e8cfff3673f76d881f32cf8e7b00622/solr/core/src/java/org/apache/solr/handler/component/SuggestComponent.java#L346-L378)). When the queue is full, a candidate whose weight is not above the lowest kept weight is dropped. So the equal-weight suggestions that survive depend on the order in which the shards answered.

## What this change does

**The merge now sorts every shard candidate by weight, then by suggestion text, before it cuts to `count`.**

- The sort key is weight, highest first, then suggestion text ([L78-L82](https://github.com/nick-boss-tech/solr/blob/626241e647e5fcc5ac6cc485f6a96d4ffe12e00a/solr/core/src/java/org/apache/solr/handler/component/SuggestComponent.java#L78-L82)).
- For each suggester and token, the merge collects all shard candidates, sorts them, and keeps the first `count` ([L368-L378](https://github.com/nick-boss-tech/solr/blob/626241e647e5fcc5ac6cc485f6a96d4ffe12e00a/solr/core/src/java/org/apache/solr/handler/component/SuggestComponent.java#L368-L378)).
- `merge` is now package-private, so a unit test can call it ([L352](https://github.com/nick-boss-tech/solr/blob/626241e647e5fcc5ac6cc485f6a96d4ffe12e00a/solr/core/src/java/org/apache/solr/handler/component/SuggestComponent.java#L352)).
- The shard side is unchanged. Each shard still receives `count` ([L273](https://github.com/nick-boss-tech/solr/blob/626241e647e5fcc5ac6cc485f6a96d4ffe12e00a/solr/core/src/java/org/apache/solr/handler/component/SuggestComponent.java#L273)).

## Limits

**The merge orders what the shards return. It does not change which candidates a shard returns.**

- Each shard cuts to its own top `count` before the merge sees anything. At `count` 1 with equal weights, a shard can return a different candidate than the merge would have chosen. So the reporter's symptom can persist. The per-shard fix is a planned follow-up submission.
- The only test is a unit test of `merge`. No distributed test covers this change.
- Payload is not part of the order. The stable order applies to distinct suggestion text. Duplicate text with different payloads is out of scope.
- Memory: before, the merge kept `count` candidates per token and suggester. Now it holds up to `count` times the shard count while it sorts, because each shard returns at most `count` candidates.
