## What happens today

**A `#` in a context value splits the value, so a suggestion can match the wrong context.**

Context filter queries (`suggest.cfq`) are always analyzed with the standard tokenizer. The base code hard-wires it in `SolrSuggester.init` ([base code](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/core/src/java/org/apache/solr/spelling/suggest/SolrSuggester.java#L111)). That tokenizer splits `c#x` into `c` and `x`. In the new test's fixture, a query with context `c#x` returns the wrong suggestion on the base code. A filter that fails to parse reads `Failed to parse query: null`, because the message prints a variable that is still null when the parser throws ([base code](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/core/src/java/org/apache/solr/spelling/suggest/SolrSuggester.java#L267-L268)).

## What this change does

**A new suggester option sets the tokenizer for context values. The default stays `standard`.**

- `contextFilterQueryTokenizer` names a tokenizer by its SPI name. Init creates it with no arguments ([init](https://github.com/nick-boss-tech/solr/blob/c31d2ff1a3fd967d4f51931073c8641fc1435e64/solr/core/src/java/org/apache/solr/spelling/suggest/SolrSuggester.java#L119-L127)). An unknown name fails at init ([test](https://github.com/nick-boss-tech/solr/blob/c31d2ff1a3fd967d4f51931073c8641fc1435e64/solr/core/src/test/org/apache/solr/handler/component/SuggestComponentContextFilterQueryTest.java#L155-L171)).
- With `keyword`, a character such as `#` stays inside one term. The value is still parsed as a query, so whitespace separates terms and query syntax still applies ([parse](https://github.com/nick-boss-tech/solr/blob/c31d2ff1a3fd967d4f51931073c8641fc1435e64/solr/core/src/java/org/apache/solr/spelling/suggest/SolrSuggester.java#L269-L287)).
- A parse failure now throws an `IllegalArgumentException` that names the query and keeps the cause ([L283-L285](https://github.com/nick-boss-tech/solr/blob/c31d2ff1a3fd967d4f51931073c8641fc1435e64/solr/core/src/java/org/apache/solr/spelling/suggest/SolrSuggester.java#L283-L285)).
- The ref guide documents the option and its limits ([suggester.adoc](https://github.com/nick-boss-tech/solr/blob/c31d2ff1a3fd967d4f51931073c8641fc1435e64/solr/solr-ref-guide/modules/query-guide/pages/suggester.adoc#L933-L944)).

## A choice to check

**The option sets the tokenizer for each suggester. The alternative reads the context field's schema analyzer.**

- Implemented: an opt-in option. Suggesters that do not set it keep today's tokens.
- Alternative: use the context field's schema analyzer, with no new setting. Existing suggesters could then see different tokens, because all of them use the standard tokenizer now.

Was an opt-in tokenizer option the right call, rather than reading the context field's schema analyzer?

## Limits

**Only `keyword` is tested as a working non-default tokenizer. Two later tests have no pre-fix run on record.**

- The bad-name test checks init failure only. No test runs a second tokenizer.
- Factories that need constructor arguments cannot be configured, and token filters cannot be set. The ref guide says so.
- No pre-fix run is on record for `testBadContextFilterQueryTokenizerFailsAtInit` or `testUnparseableContextFilterQueryReportsQueryAndCause`.
