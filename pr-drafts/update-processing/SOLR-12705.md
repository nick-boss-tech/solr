## What happens today

**A field mutating update processor does not touch the value inside an atomic update.**

For example, ParseDateFieldUpdateProcessorFactory skips an update such as `{"set": "2010-11-12T13:14:15.168Z"}`. The value is a map, not a string, so the processor leaves the field unchanged. The date parser never runs on the operand ([ParseDateFieldUpdateProcessorFactory.java#L113-L120](https://github.com/nick-boss-tech/solr/blob/aa56b7b1be4c5491723c58f296e20c906d7b7334/solr/core/src/java/org/apache/solr/update/processor/ParseDateFieldUpdateProcessorFactory.java#L113-L120)).

## What this change does

**The set, add, add-distinct and remove operations of an atomic update now go through the mutator. Other operations are left as they are.**

- If a field's only value is an operation map, `processAdd` runs `mutate` on the operand of each set, add, add-distinct and remove operation ([FieldMutatingUpdateProcessor.java#L109-L111](https://github.com/nick-boss-tech/solr/blob/aa56b7b1be4c5491723c58f296e20c906d7b7334/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L109-L111), [#L151-L182](https://github.com/nick-boss-tech/solr/blob/aa56b7b1be4c5491723c58f296e20c906d7b7334/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L151-L182)). Operations such as `inc` keep their operands. An update with only those operations is handled as before.
- This is wider than the ticket's narrowest reading. By default, every subclass of `FieldMutatingUpdateProcessor` mutates atomic operands, not only the date parser.
- A subclass opts out by overriding the new protected method `mutateAtomicOperands()` to return `false`. The base method returns `true`, which is the default ([L74-L86](https://github.com/nick-boss-tech/solr/blob/aa56b7b1be4c5491723c58f296e20c906d7b7334/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L74-L86)). A new public overload, `mutator(selector, next, fun, applyToAtomicOperands)`, sets the same switch ([L358-L374](https://github.com/nick-boss-tech/solr/blob/aa56b7b1be4c5491723c58f296e20c906d7b7334/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L358-L374)).
- `CountFieldValuesUpdateProcessorFactory` opts out ([L67-L75](https://github.com/nick-boss-tech/solr/blob/aa56b7b1be4c5491723c58f296e20c906d7b7334/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L67-L75)). Counted fields follow the rule in [SOLR-7504](https://issues.apache.org/jira/browse/SOLR-7504), which lands first.

## Limits

**A few cases are untested, one behavior is missing from the changelog, and two changes land first.**

- The date-parse test does not cover `add-distinct` or `remove`. No test checks the case where the processor returns nothing for an operand, so that operation is dropped.
- A field with several operation maps in one update is passed to `mutate` unchanged. This limit was already there. It is not a regression.
- If the mutator returns nothing for every value operation in an atomic update, and no other operation remains, `processAdd` removes the whole field from the update ([L118-L120](https://github.com/nick-boss-tech/solr/blob/aa56b7b1be4c5491723c58f296e20c906d7b7334/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L118-L120), [L176-L177](https://github.com/nick-boss-tech/solr/blob/aa56b7b1be4c5491723c58f296e20c906d7b7334/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L176-L177)). The changelog does not mention this.
- Landing order. [SOLR-7504](https://issues.apache.org/jira/browse/SOLR-7504) and [SOLR-16655](https://issues.apache.org/jira/browse/SOLR-16655) land before this change. The combined run above is the reason SOLR-7504 goes first. SOLR-16655 changes only `processAdd`, `mutateDocument` and the imports in `FieldMutatingUpdateProcessor.java`. It moves the field loop into `mutateDocument`, adds the child-document descent, and mutates each document once. This change is the broader atomic operands rework in the same file, and it rebases onto SOLR-16655. The two conflict twice in `FieldMutatingUpdateProcessor.java`. SOLR-7504 also conflicts with this change in two hunks, both in one import block of `FieldMutatingUpdateProcessorTest.java`.
- A follow-up submission is planned to add the add-distinct, remove and dropped-operand cases.
