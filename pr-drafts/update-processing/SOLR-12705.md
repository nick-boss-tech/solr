## What happens today

**A field mutating update processor does not touch the value inside an atomic update.**

For example, ParseDateFieldUpdateProcessorFactory skips an update such as `{"set": "2010-11-12T13:14:15.168Z"}`. The value is a map, not a string, so the processor leaves the field unchanged. The date parser never runs on the operand ([ParseDateFieldUpdateProcessorFactory.java#L113-L120](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/java/org/apache/solr/update/processor/ParseDateFieldUpdateProcessorFactory.java#L113-L120)).

## What this change does

**The set, add, add-distinct and remove operations of an atomic update now go through the mutator. Other operations are left as they are.**

- If a field's only value is an operation map, `processAdd` runs `mutate` on the operand of each set, add, add-distinct and remove operation ([FieldMutatingUpdateProcessor.java#L109-L111](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L109-L111), [#L151-L182](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L151-L182)). Operations such as `inc` keep their operands. An update with only those operations is handled as before.
- This is wider than the ticket's narrowest reading. It applies to every subclass of `FieldMutatingUpdateProcessor`, not only the date parser.
- A subclass can opt out by overriding the new protected method `mutateAtomicOperands()`, which returns true by default ([L74-L86](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L74-L86)). A new public overload, `mutator(selector, next, fun, applyToAtomicOperands)`, sets the same switch ([L358-L374](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L358-L374)).
- `CountFieldValuesUpdateProcessorFactory` opts out ([L67-L75](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L67-L75)). An atomic update on a counted field is still counted as one value.

## Proof

**The gate at this head passed, and the new tests fail on the code without the change.**

- On the pre-fix head `b053944b127`, the counting processor counted the operand itself. `{"add": "aaa"}` came back as `{add=1}`. On a single-valued field holding 3, the appended `{"add": 1}` failed the whole update with "multiple values encountered for non multiValued field price".
- New test [testCountValuesAtomicUpdate](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/test/org/apache/solr/update/processor/FieldMutatingUpdateProcessorTest.java#L806-L827) pins `{add}`, `{remove}`, and a multi-value `{set}` on the counting processor. Each returns a count of 1.
- New test [testParseDateInAtomicUpdateOperations](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/test/org/apache/solr/update/processor/ParsingFieldUpdateProcessorsTest.java#L68-L99) checks that the `set` and `add` operands are parsed as dates, that `inc` is untouched, and that a field the selector skips keeps its string.
- Gate at `8624b7c3238b`, 2026-10-09: the fail-before check passed. `FieldMutatingUpdateProcessorTest` 25 of 25, `ParsingFieldUpdateProcessorsTest` 43 of 43, `NestedAtomicUpdateTest` 15 of 15, and `AtomicUpdatesTest` 26, with 1 skipped. The module check is clean.

## Limits

**A few cases are untested, and one behavior is missing from the changelog.**

- The date-parse test does not cover `add-distinct` or `remove`. No test checks the case where the processor returns nothing for an operand, so that operation is dropped.
- A field with several operation maps in one update is passed to `mutate` unchanged. This limit was already there. It is not a regression.
- If the mutator returns nothing for every value operation in an atomic update, `processAdd` removes the whole field from the update ([L118-L120](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L118-L120), [L176-L177](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L176-L177)). The changelog does not mention this.
- SOLR-16655 changes the same file, `FieldMutatingUpdateProcessor.java`, and the two changes conflict there. The two PRs must be sequenced, not merged independently.
