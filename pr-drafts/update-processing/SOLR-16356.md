## What happens today

**A delete-by-query on a closing core logs an ERROR with a stack trace.**

A delete-by-query can ask the update log to open a new realtime searcher ([UpdateLog.java](https://github.com/nick-boss-tech/solr/blob/39c0585072f0eacc0767a173bab3f1d528db64f7/solr/core/src/java/org/apache/solr/update/UpdateLog.java#L919-L925)). When the core is already closed, that open fails with a closed-core exception. The update log logs "Error opening realtime searcher" at ERROR with the stack trace ([catch block](https://github.com/nick-boss-tech/solr/blob/39c0585072f0eacc0767a173bab3f1d528db64f7/solr/core/src/java/org/apache/solr/update/UpdateLog.java#L953-L955)). The core is closing, so no new searcher can open. The ERROR is logged anyway.

## What this change does

**A closed-core failure is logged at debug, not ERROR, in two places in the update log.**

- In `openRealtimeSearcher`, the closed-core exception is logged at debug, and the method returns. The id caches are kept, as for any other failure ([lines](https://github.com/nick-boss-tech/solr/blob/39c0585072f0eacc0767a173bab3f1d528db64f7/solr/core/src/java/org/apache/solr/update/UpdateLog.java#L949-L952)).
- In `deleteAll`, the same exception is logged at debug. The method then clears its caches as before. The code comment marks `deleteAll` as for testing only ([lines](https://github.com/nick-boss-tech/solr/blob/39c0585072f0eacc0767a173bab3f1d528db64f7/solr/core/src/java/org/apache/solr/update/UpdateLog.java#L964-L971)).

Any other failure still logs at ERROR.
