## What happens today

**Field mutating update processors skip child documents, so child fields keep the values they were sent with.**

These processors change only the fields of the root document. Child documents are skipped, both anonymous children and child documents given as a field value. So a trim, regex replace, remove-blank or date parse step does not run on a child's field.

## What this change does

**The processors now walk child documents at any depth and change their fields the same way as the root.**

The processor walks the root document, then descends into child documents given as field values and into anonymous child documents, at every depth ([FieldMutatingUpdateProcessor.java](https://github.com/nick-boss-tech/solr/blob/aa7898d972a7802588d9cf94ea1ee874323abac9/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L90-L150)). The field selector decides which field names change, in each child as in the root. A document reachable by two paths is changed once, since not every mutation is safe to repeat.

Wider effect: the walk into a child runs even when the field holding that child is not selected. The selector still decides which field names change inside that child ([same file](https://github.com/nick-boss-tech/solr/blob/aa7898d972a7802588d9cf94ea1ee874323abac9/solr/core/src/java/org/apache/solr/update/processor/FieldMutatingUpdateProcessor.java#L128-L141)).

Upgrade note: after upgrading, pipelines that send child documents will see these processors change child field values. Examples are trim, regex replace, remove-blank and date parsing. Check the chains that send child documents before upgrading.
