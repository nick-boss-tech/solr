Title: The Parse{Int,Long,Float,Double}FieldUpdateProcessorFactory classes no longer fail with a NullPointerException on an empty string value

## What happens today

**An empty string in a Parse{Int,Long,Float,Double}FieldUpdateProcessorFactory field throws a NullPointerException.**

`NumberFormat.parse` returns null for an empty string. The bounds check still passes, because the parse position and the string length are both 0. The code then calls a method on the null result, for example `number.intValue()` in [ParseIntFieldUpdateProcessorFactory.java](https://github.com/nick-boss-tech/solr/blob/d7170b12f312b364cb280b943a042707e553ea64/solr/core/src/java/org/apache/solr/update/processor/ParseIntFieldUpdateProcessorFactory.java#L101).

## What this change does

**An empty string that does not parse is skipped, so the value stays as it was.**

Each of the four factories treats a null parse result as unparseable. The check is now `number == null || pos.getIndex() != stringVal.length()` in [Int](https://github.com/nick-boss-tech/solr/blob/d7170b12f312b364cb280b943a042707e553ea64/solr/core/src/java/org/apache/solr/update/processor/ParseIntFieldUpdateProcessorFactory.java#L93), [Long](https://github.com/nick-boss-tech/solr/blob/d7170b12f312b364cb280b943a042707e553ea64/solr/core/src/java/org/apache/solr/update/processor/ParseLongFieldUpdateProcessorFactory.java#L104), [Float](https://github.com/nick-boss-tech/solr/blob/d7170b12f312b364cb280b943a042707e553ea64/solr/core/src/java/org/apache/solr/update/processor/ParseFloatFieldUpdateProcessorFactory.java#L96), and [Double](https://github.com/nick-boss-tech/solr/blob/d7170b12f312b364cb280b943a042707e553ea64/solr/core/src/java/org/apache/solr/update/processor/ParseDoubleFieldUpdateProcessorFactory.java#L107). The value is then kept. The Long and Double changes also reach Schema Designer's type guess, in [DefaultSchemaSuggester.isIntOrLong](https://github.com/nick-boss-tech/solr/blob/d7170b12f312b364cb280b943a042707e553ea64/solr/core/src/java/org/apache/solr/handler/designer/DefaultSchemaSuggester.java#L338) and in the [float and double check](https://github.com/nick-boss-tech/solr/blob/d7170b12f312b364cb280b943a042707e553ea64/solr/core/src/java/org/apache/solr/handler/designer/DefaultSchemaSuggester.java#L300). In that path an empty value no longer throws. It counts as not a number, and the guess moves on to the other type checks.

## Limits

**The Schema Designer path and the other errors in the ticket sample are not covered.**

- The test calls the four processor chains. It does not run the Schema Designer path, where [DefaultSchemaSuggester.isIntOrLong](https://github.com/nick-boss-tech/solr/blob/d7170b12f312b364cb280b943a042707e553ea64/solr/core/src/java/org/apache/solr/handler/designer/DefaultSchemaSuggester.java#L338) calls the Long parser. The ticket reports Schema Designer failures on empty values. The link between the two is not tested here.
- The same ticket sample also hits a non-string unique key and child-document `_root_` type errors. This change does not touch them. A follow-up submission is planned to cover them.
