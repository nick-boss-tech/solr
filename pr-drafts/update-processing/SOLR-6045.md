## What happens today

**An atomic update that adds one field twice does not apply its operations. The maps are indexed as text.**

The ticket reports that with the javabin writer, two `addField` calls with operation maps for one field leave the index holding `{set=new_value1}` and `{set=new_value2}`, not the set. The field's value is then a list of maps. The factory wraps that whole list in one operation ([AtomicUpdateProcessorFactory.java#L139](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateProcessorFactory.java#L139)). Before this change, the merger checked only the whole field value. That value is a list here, so the merger did not find an operation map ([AtomicUpdateDocumentMerger.java#L88-L97](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L88-L97)).

## What this change does

**Repeated operation maps are recognized, and each map is applied in the order the fields were added.**

- The factory leaves a field alone when its values are all operation maps ([line 133](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateProcessorFactory.java#L133), [helper](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateProcessorFactory.java#L161-L177)).
- The merger treats a field as atomic when its first value is an operation map. It then applies each map on the field ([atomic check](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L88-L97), [operations](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L103-L118), [merge](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L179-L180)).
- Child documents are not operations. A child document is also a map, so the merger now skips child documents in both places ([operations](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L107), [merge](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L179)). A list of child documents is set as plain values, as it was on base. On base, a single child document in an update that also has operations was read field by field as operation names. That fails with "Unknown operation" ([default branch](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L202-L208)). It is now set as a plain value.
- Behavior change wider than the ticket: a JSON array of operation objects is now applied as atomic operations. On base, the objects were stored as values. The array becomes a list of maps ([JsonLoader.java#L637-L648](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/handler/loader/JsonLoader.java#L637-L648)). The changelog does not say so.

## Limits

**Some cases are not covered: mixed values, the XML writer path, and in-place updates.**

- Mixed values. A field with an operation map first and a plain value after it now returns 400, and the message lists the field's values ([check](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L106-L113)). A plain value first is not treated as atomic, so the map is stored as a value ([first-value check](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L179-L180)). No test covers either case.
- Order. Operations apply in the order the `addField` calls ran. One test checks one order.
- XML writer. The test comments describe how the XML writer shapes repeated fields. That path was not traced.
- In-place updates. The in-place check still reads the whole field value ([line 273](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L273)). A repeated-operation field takes the full atomic path.
- Sequencing. [SOLR-12703](https://issues.apache.org/jira/browse/SOLR-12703) also changes `mergeDocHavingSameId`. The two merge cleanly, but their combined behavior is not tested here. Apply them in sequence.
