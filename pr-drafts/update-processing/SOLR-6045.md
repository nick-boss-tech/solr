## What happens today

**An atomic update that adds one field twice does not apply its operations. The maps are indexed as text.**

With the javabin writer, two `addField` calls with operation maps for one field leave `{set=new_value1}` and `{set=new_value2}` in the index. The factory wraps the whole list in one operation ([factory](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateProcessorFactory.java#L139)). The merger checks only the whole field value, a list here, so it finds no operation map ([check](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L88-L97)).

## What this change does

**Repeated operation maps are recognized and applied in the order the fields were added.**

- The factory leaves a field alone when all its values are operation maps ([helper](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateProcessorFactory.java#L161-L177)).
- The merger treats a field as atomic when its first value is an operation map, then applies each map in turn ([atomic check](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L88-L97), [operations](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L103-L118)).
- A child document is a map too. The merger does not read it as an operation map ([first-value check](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L179)). A child document in a field that also has operation maps is rejected as mixed values ([check](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L107)).
- On base, a single child document in an update with operations failed with "Unknown operation" ([default branch](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L202-L208)). It is now a plain value, as a list of child documents already was.
- A JSON array of operation objects is now applied as atomic operations. On base the objects were stored as values ([array parser](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/handler/loader/JsonLoader.java#L637-L648)). This is wider than the ticket, and the changelog does not say so.

## Limits

**Mixed values, JSON arrays, the XML writer and in-place updates are not covered by tests.**

- Mixed values. An operation map first and a plain value after it now return 400, and the message lists the field's values ([check](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L106-L113)). A plain value first is not atomic, so the map is stored as a value ([first-value check](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L179-L180)). No test covers either case.
- JSON arrays. No test covers the array behavior described above.
- Order. Operations apply in the order the `addField` calls ran. One test checks one order.
- XML writer. The test comments describe how the XML writer shapes repeated fields. That path was not traced.
- In-place updates. The in-place check still reads the whole field value ([line 273](https://github.com/nick-boss-tech/solr/blob/e4b77fa7ae53d363e8869e1073a800c324fd6972/solr/core/src/java/org/apache/solr/update/processor/AtomicUpdateDocumentMerger.java#L273)). A repeated-operation field takes the full atomic path.
- Sequencing. [SOLR-12703](https://issues.apache.org/jira/browse/SOLR-12703) also changes `mergeDocHavingSameId`. The two merge cleanly, but their combined behavior is not tested here. Apply them in sequence.
