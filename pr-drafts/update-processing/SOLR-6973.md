## What happens today

**With `overwriteDupes` and a `fields` list, a partial update with no signature fields can delete unrelated documents.**

With a `fields` list, the processor's loop throws only if a signature field is present in the partial update ([SignatureUpdateProcessorFactory.java on the merge-base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/update/processor/SignatureUpdateProcessorFactory.java#L169-L178)). A partial update that sets other fields passes the loop with an empty signature. The processor writes that signature to `signatureField` and sets `updateTerm` to it ([SignatureUpdateProcessorFactory.java on the merge-base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/update/processor/SignatureUpdateProcessorFactory.java#L200-L204)). `updateDocuments` deletes every document that matches `updateTerm` ([DirectUpdateHandler2.java on the merge-base](https://github.com/nick-boss-tech/solr/blob/cabedd1d968059215188f4e7563fb303241899ed/solr/core/src/java/org/apache/solr/update/DirectUpdateHandler2.java#L1177-L1180)).

## What this change does

**A partial update with no signature fields skips the signature step.**

It goes to the next processor unchanged. Partial updates with a signature field still fail, and requests without `fields` still reject partial updates ([SignatureUpdateProcessorFactory.java](https://github.com/nick-boss-tech/solr/blob/51fcd05e695ae1a5983ed69a3d2afc50e7f7bc1e/solr/core/src/java/org/apache/solr/update/processor/SignatureUpdateProcessorFactory.java#L146-L182)).

Behavior change: a partial update with no signature fields no longer gets an empty signature. This covers new documents and existing ones. A new document is stored without `signatureField`. An existing document keeps its stored `signatureField`, and the update no longer deletes other documents that share the empty signature.

## Proof

**The new test fails on the base code and passes with this change.**

The test is [SignatureUpdateProcessorFactoryTest.java](https://github.com/nick-boss-tech/solr/blob/51fcd05e695ae1a5983ed69a3d2afc50e7f7bc1e/solr/core/src/test/org/apache/solr/update/processor/SignatureUpdateProcessorFactoryTest.java#L205-L236). It checks that `signatureField` is absent and `updateTerm` is null. On the merge-base production code, with this branch's test file added, the same class ran 7 tests with 1 failure (gate 2026-10-08, head `fa5b59ba07b4`). Reading the base code, the failing test is the new test: the base code sets both values it checks for absence (base lines 199 to 203).

With this change, the focused `SignatureUpdateProcessorFactoryTest` ran 7 of 7, verified 2026-10-09 at head `51fcd05e695`. The same 7 tests and the same base failure were re-verified at this head.

## A choice to check

**The update passes through. The other option is to reject it.**

The no-`fields` setup already rejects partial updates with an error. This change passes them through, so the update works and no signature is stored. Rejecting would make the failure visible but would stop the update. Was pass-through the right call?
