## What happens today

**A partial update with explicit `fields` can delete unrelated documents.**

`SignatureUpdateProcessorFactory` checks a partial update for signature fields inside its loop. The loop throws only when a signature field is present. A partial update that sets some other field (for example `set` on `name`) passes the loop with nothing in the signature. The processor writes the empty signature into `signatureField` and, with `overwriteDupes`, sets `updateTerm` to it. Every such update gets the same signature, so the term matches unrelated documents, and `updateDocuments` deletes them.

## What this change does

**Partial updates with no signature fields skip the signature step.**

They go to the next processor unchanged. Partial updates that include a signature field still fail as before. Requests without `fields` still reject partial updates as before.

Behavior change: a partial update that creates a new document now stores it with no `signatureField`. The old code gave it the shared empty signature, which was the collision. Neither result identifies the document.

The new test, `SignatureUpdateProcessorFactoryTest.testPartialUpdateWithoutSignatureFieldsIsPassedThrough`, asserts that `signatureField` is absent and `updateTerm` is null. The base code sets both, so the test should fail there. This was checked by reading only.

## A choice to check

**The update is passed through. The other option is to reject it.**

The no-`fields` setup already rejects partial updates with an error. This change passes them through instead, so the update keeps working and no signature is stored. Rejecting would make the failure visible but would stop the update. Was pass-through the right call?
