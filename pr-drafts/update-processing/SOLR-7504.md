## What happens today

**An atomic update on the counted field is counted as one value.**

Before this change, the counter replaces the field's values with their number ([counter](https://github.com/nick-boss-tech/solr/blob/97d973814336101e12475558d7419321c743de79/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L70-L74)). An atomic update reaches it as a map of operations. The whole map counts as one value, so a `set` of two values counts as 1.

## What this change does

**The counter counts a `set` operand. Every other atomic operation on the counted field is rejected.**

- A `set` operand counts its elements when it is a collection or an array, duplicates included. A single value counts as 1. A null operand counts as 0 ([operand count](https://github.com/nick-boss-tech/solr/blob/2fe06bfd917f193b3591dfa4c088ef0994279ed6/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L138-L148)). The counter reads the field's values once and treats null as no values, so a field whose value is null also counts as 0 ([values read once](https://github.com/nick-boss-tech/solr/blob/2fe06bfd917f193b3591dfa4c088ef0994279ed6/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L78-L85)).
- Several operation maps apply in order, and the last `set` decides the count ([count rule](https://github.com/nick-boss-tech/solr/blob/2fe06bfd917f193b3591dfa4c088ef0994279ed6/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L91-L136)).
- `add`, `remove`, `inc`, `add-distinct` and `removeregex` on the counted field now fail with BAD_REQUEST. Before this change, such a request succeeded and stored a count of 1.
- A plain value in the same field as an operation map is also rejected now, with BAD_REQUEST. Before this change, the counter counted it. The check reads every value, so a plain value first is rejected too ([scan](https://github.com/nick-boss-tech/solr/blob/2fe06bfd917f193b3591dfa4c088ef0994279ed6/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L78-L84)).
- A field with no `set` in any of its operation maps is rejected with BAD_REQUEST, for example one empty operation map. An empty map next to a `set` is accepted ([count rule](https://github.com/nick-boss-tech/solr/blob/2fe06bfd917f193b3591dfa4c088ef0994279ed6/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L127-L133)).

## Limits

**Only updates that carry the counted field are covered. The chain placement is unchanged.**

- The counter runs only when the source field is in the update. An update that leaves the source field out is not covered. A trailing `DefaultValue` after the counter would then write a plain 0, which an atomic update applies as a `set`. This is a reading of the chain, not a run, and the chain is not changed here.
- The changelog title covers only updates that carry the counted field.
- The tests call the counter directly. No end-to-end atomic update is run.
- SOLR-6045 applies the same rule in `AtomicUpdateDocumentMerger`: a plain value mixed with an operation map is rejected in either order. The two checks sit in different files.
- SOLR-7504 lands before SOLR-12705. SOLR-12705 changes the field mutating base class. At their heads the two branches conflict in one import block of `FieldMutatingUpdateProcessorTest.java`, so SOLR-12705 needs that block merged by hand. A combined run with SOLR-12705 passed on 2026-10-09 at the pre-fix head [22b77196e662](https://github.com/nick-boss-tech/solr/commit/22b77196e662e93aca6ddc926c6738fb69c817fb), before the null fix. The null fix is not in that run. SOLR-12705's counting test now pins only the atomic-operand opt-out, not counted-field outcomes, so the rejection above governs counted fields.
- A follow-up submission is planned to add an end-to-end atomic update test.
