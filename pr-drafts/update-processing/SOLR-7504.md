## What happens today

**An atomic update on the counted field is counted as one value.**

The counter replaces the field's values with their number ([counter](https://github.com/nick-boss-tech/solr/blob/22b77196e662e93aca6ddc926c6738fb69c817fb/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L76-L85)). An atomic update reaches the counter as a map of operations, and the whole map counts as one value. A `set` of two values therefore counts as 1.

## What this change does

**The counter counts a `set` operand. Every other atomic operation on the counted field is rejected.**

- A `set` operand counts by its elements when it is a collection or an array, including duplicates. A single value counts as 1, and a null counts as 0 ([count](https://github.com/nick-boss-tech/solr/blob/22b77196e662e93aca6ddc926c6738fb69c817fb/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L134-L144)).
- When an update carries several operation maps, they apply in order, and the last `set` decides the count ([helper](https://github.com/nick-boss-tech/solr/blob/22b77196e662e93aca6ddc926c6738fb69c817fb/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L88-L132)).
- Only `set` can be counted. `add`, `remove`, `inc`, `add-distinct` and `removeregex` on the counted field now fail the request with BAD_REQUEST. Before this change, such a request succeeded and stored a count of 1. This is the one behavior change for existing updates.
- A plain value in the same field as an operation map is rejected with BAD_REQUEST. The check looks at every value, so a plain value first is rejected too ([scan](https://github.com/nick-boss-tech/solr/blob/22b77196e662e93aca6ddc926c6738fb69c817fb/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L78-L82)).
- An operation map with no operation is rejected with BAD_REQUEST.

## Limits

**Only updates that carry the counted field are covered. The chain placement is unchanged.**

- The counter runs only when the source field is in the update. An update that leaves the source field out is not covered. A trailing `DefaultValue` after the counter would then write a plain 0, which an atomic update applies as a `set`. This is a reading of the chain, not a run, and the chain is not changed here.
- The changelog title covers only updates that carry the counted field.
- The tests call the counter directly. No end-to-end atomic update is run.
- SOLR-6045 adds a similar check to `AtomicUpdateDocumentMerger`, for mixed plain and operation values. If both land, the two checks should share one helper.
- SOLR-12705 changes the field mutating base class. The two branches merge without conflicts at their heads, and SOLR-12705 keeps this counter on the whole field, so the rejection still applies ([counter](https://github.com/nick-boss-tech/solr/blob/8624b7c3238b5ca35b448e0d6d62fb7789dad0cd/solr/core/src/java/org/apache/solr/update/processor/CountFieldValuesUpdateProcessorFactory.java#L70-L75)). Neither combined tree has been run.
