## Fallback path trace (2026-10-12)

Investigation job gates/SOLR-15615-fallback-trace.md, run by vm1. The branch's fallback (the code that fetches the MLT source document from another collection when the local real-time get misses) traced end to end in the branch tree at the gated head be77267bf554. All citations are file and line at that head. The draft describes the fallback as asking the collections one at a time; the code matches that shape.

### 1. Entry

- CloudMLTQParser.parse() calls getDocument(id) (solr/core/src/java/org/apache/solr/search/mlt/CloudMLTQParser.java:61).
- getDocument (lines 110-123) first runs an in-process real-time get against the core handling the request: it builds a SolrQueryRequestBase on that core and calls the core's "/get" handler directly (lines 116-121). Only when that returns no document does the fallback enter: line 122, `return doc != null ? doc : getDocumentFromOtherCollections(core, id);`
- The local get therefore covers the collection of the core handling the request; the fallback covers the other collections named by the request's `collection` param, which HttpSolrCall sets to the alias-resolved collection list (solr/core/src/java/org/apache/solr/servlet/HttpSolrCall.java:338, addCollectionParamIfNeeded at line 783).

### 2. The per-collection sequence

- getDocumentFromOtherCollections (CloudMLTQParser.java:131-153): returns null at once if the `collection` param is absent or the container is not ZooKeeper-aware (lines 134-136). It then walks the param's comma-separated list in order (StrUtils.splitSmart, line 138), skipping blank entries and the handling core's own collection (lines 137-141).
- Each step is one SolrClient.getById(collection, id) call (lines 143-144), which issues a real-time get (qt=/get) for that collection (solr/solrj/src/java/org/apache/solr/client/solrj/SolrClient.java:1048-1051, 1076-1085, and 1145-1158 with QT set at line 1151) and returns null when the collection holds no such document.
- The sequence stops at the first non-null document, which is returned at once (lines 145-147). If the list is exhausted, the method returns null (line 152).

### 3. Client and credentials

- The client is the cluster's own CloudSolrClient: coreContainer.getZkController().getSolrClient() (CloudMLTQParser.java:144; solr/core/src/java/org/apache/solr/cloud/ZkController.java:681-682), built as a CloudJettySolrClient over a ZkClientClusterStateProvider, with CoreContainer's default HTTP client underneath (ZkController.java:996-999). CloudSolrClient.sendRequest resolves the target collection's live, active replicas from cluster state and sends the request node-to-node over HTTP through the load-balancing client (solr/solrj/src/java/org/apache/solr/client/solrj/impl/CloudSolrClient.java:898-1054). No shard machinery (HttpShardHandler) is involved; this is a SolrJ client call that happens to originate inside a node.
- The default HTTP client is an HttpJettySolrClient built with a dedicated security listener factory (solr/core/src/java/org/apache/solr/core/HttpSolrClientProvider.java:42, 51), and CoreContainer registers the PKI authentication plugin's builder into that factory whenever an authentication plugin is set up: "Always register PKI auth interceptor" (solr/core/src/java/org/apache/solr/core/CoreContainer.java:599-608, the solrClientProvider.setSecurityBuilder call at line 606; the client itself at getDefaultHttpSolrClient, lines 2458-2460).

### 4. Authorization: whose identity the fallback carries

- Client side (solr/core/src/java/org/apache/solr/security/PKIAuthenticationPlugin.java, setup at lines 315-365): when the configured authentication plugin does not secure internode requests itself (the default; AuthenticationPlugin.java:134-136 returns true only for plugins that are client builders, and BasicAuthPlugin.java:215 forwards credentials itself only when its forwardCredentials option is set), the PKI listener reads the user from the current request's SolrRequestInfo in the submitting thread (lines 332-337) and adds a SolrAuthV2 header: a token signed with this node's private key asserting that user (onBegin at lines 348-356; generateTokenV2 at lines 400-408). The fallback runs synchronously inside the original request (it is called from parse()), so the identity available to assert is the original requester's.
- getUser (lines 375-398) settles the branches: with a request context and an authenticated principal, the asserted user is that principal's name (lines 377-387). With a request context but no principal (the original request was not authenticated), it returns empty and no header is added (lines 380-383). The node-itself identity "$" (NODE_IS_USER, line 437) is asserted only when there is no request context or the server token was explicitly requested (lines 388-397); nothing in the MLT path requests it.
- Receiving side: a request carrying a SolrAuthV2 header is authenticated by the PKI plugin rather than the configured plugin (solr/core/src/java/org/apache/solr/servlet/AuthenticationFilter.java:100-103, isInternodePKI at lines 154-157). PKIAuthenticationPlugin.doAuthenticate (lines 130-165) verifies the signature against the sending node's public key and sets the principal to the asserted user name, or to CLUSTER_MEMBER_NODE when the asserted user is "$" (lines 157-160).
- Authorization then runs against that principal: HttpSolrCall.shouldAuthorize (HttpSolrCall.java:607-619) skips authorization only when PKIAuthenticationPlugin.needsAuthorization is false, and that is false only for the CLUSTER_MEMBER_NODE principal (PKIAuthenticationPlugin.java:370-373). So for a fallback fetch made under an authenticated original request, the receiving collection's authorization check runs against the original user. For an unauthenticated original request, no identity is asserted and the receiving node treats the fetch as an ordinary unauthenticated request under its configured plugin. When no authentication plugin is configured at all, the listener adds nothing (setup, lines 322-325) and no authentication or authorization runs anywhere on the path.

### 5. Exit and mid-sequence errors

- Final error: when every step returns null, parse() throws SolrException with ErrorCode.BAD_REQUEST (400), "Error completing MLT request. Could not fetch document with id [...]" (CloudMLTQParser.java:62-66). The draft's 400 is confirmed.
- Mid-sequence errors split by type. The fallback catches SolrServerException and IOException around each getById, logs a warning, and continues with the next collection (CloudMLTQParser.java:148-150). That catch absorbs the load-balancing client's exhausted-retries failure, which is a SolrServerException whose cause is the last replica's error (solr/solrj/src/java/org/apache/solr/client/solrj/impl/LBSolrClient.java:571-596); responses with codes 404, 403, 503 or 500 take that retry path (RETRY_CODES, lines 132-133; the retry branch at lines 643-656), so an authorization refusal (403) from one collection surfaces to the fallback as a caught SolrServerException: it is logged, the sequence moves on, and if no other collection yields the document the request ends in the 400 above, not in a 403.
- A response whose code is not in RETRY_CODES, notably 401 (authentication rejected, the outcome when no identity was asserted and the receiving node's plugin rejects unauthenticated requests), is rethrown by the load-balancing client as a RemoteSolrException, a SolrException (LBSolrClient.java:643-656, the endpoint loops at lines 862-864 and 909-912), and CloudSolrClient rethrows SolrException unchanged (CloudSolrClient.java:881-887). The fallback's catch does not cover SolrException, so a 401 aborts the sequence and propagates out of parse() with its own code.

### Verdict

The trace supports this Limits sentence for the draft, quoted in full for the main side to place:

"The fallback fetches carry the original requester's identity, not an internal one: each per-collection request is a node-to-node request whose signed header asserts the user who made the MLT request, so a collection that would refuse that user a direct read also refuses the fallback fetch."

No step of the trace was left unestablished; the authorization question is answered by the PKI listener and shouldAuthorize code cited in part 4.
