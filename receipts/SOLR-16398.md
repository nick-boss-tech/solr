## What changed

- The four command resources are registered in `CollectionsHandler.getJerseyResources()` (`SplitShard`, `MoveReplica`, `RebalanceLeaders`, `MigrateDocs`). The rebalance entry is fully qualified because the v1 class `handler.admin.RebalanceLeaders` has the same simple name and the v1 `REBALANCELEADERS` action still uses it. An import here fails to compile (round 2 attempt).
- `rebalance-leaders` was broken, not just unregistered. The resource submitted a top-level `REBALANCELEADERS` overseer message. The overseer's `RebalanceLeadersCmd` needs per-replica params and rejects it: "collection,core,core_node_name,node_name,rejoinAtHead are required params". The v1 action runs the rebalance in-process (`CollectionsHandler`, `REBALANCELEADERS_OP`). The resource now does the same. `handler.admin.RebalanceLeaders` is made public, and the resource passes collection, `maxAtOnce` and `maxWaitSeconds` as request params.
- Removed the `split-shard` and `migrate-docs` mapping cases from `TestCollectionAPIs`. The migration commit states those mapping tests were removed; these cases were left behind and failed with "No handler at path".
- Added `CollectionCommandsV2IntegrationTest` (SolrCloud, four tests): split a shard, move a replica, rebalance leaders, and migrate docs, each through a real V2 HTTP request.

That field is keyed by node elsewhere, so here it is keyed by the v1 summary and shard names. A dedicated field in the response model would be cleaner.
