## PR description draft (not posted)

**Reverse cursor marks now page backwards through Solr results.**

Today a `cursorMark` can only move forward. A client that wants the previous page has to restart from the beginning. The reverse direction needs the boundary, the sort, and the response order to agree across shards.

**This change** completes `SortSpec.reverse()` with the existing Lucene comparators, keeps value selection and missing-value handling, and disables competitive skipping for inverse comparators. Shards keep collector order. The coordinator reverses response positions before choosing the boundary. The zero-row request returns both markers at the supplied boundary. Forward cursor tokens keep their existing encoding. Backward cursors need upgraded nodes in the cluster. SolrJ gains a previous-cursor getter. The guide and changelog are updated.

**Proof.** Counts from the run on `fde070281383f113a331a9ec5ccde173b66fac3c`:
- `SortSpecReverseTest`, `CursorMarkTest`, `CursorPagingTest`, `DistribCursorPagingTest` (seed 5108C0DE): 16 tests, 0 failures.
- `QueryResponseTest` (SolrJ, seed 5108C0DE): 7 tests, 0 failures.
- Reverse tests on seed 17786C0DE: 9 tests, 0 failures.
- With the reversal removed, `DistribCursorPagingTest.testReverseCursorPaging` fails with `expected:<[3, 4, 5]> but was:<[5, 4, 3]>`.
- With the local normalization removed, `CursorPagingTest.testReverseCursorPaging` fails the same way.
- With the zero-row markers restored to one-sided, `CursorMarkTest.testZeroRowCursorMarks` fails on a null marker.

**The choice.** The current branch disables competitive skipping for backward sorts. This is correct but slower. Is that the right trade for now? The alternative is a skipping optimization for inverse comparators, which we have not built. We recommend the disabled version for this change, because it is simpler to verify.

**Limits.** Benchmarks are not run. Lucene issue #14775 is not required by this branch. Only the Linux aarch64 build was run.
