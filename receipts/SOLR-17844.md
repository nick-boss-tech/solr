## What happens today

**TestFieldCacheSortRandom computes the expected sort order and then does not check it: two workaround commits removed the ordering assertions, so the test passes while verifying only the runtime types of its results.**

The test computes expected values ([TestFieldCacheSortRandom.java at the base](https://github.com/nick-boss-tech/solr/blob/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb/solr/core/src/test/org/apache/solr/uninverting/TestFieldCacheSortRandom.java#L202-L231)), but the result check ([same file](https://github.com/nick-boss-tech/solr/blob/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb/solr/core/src/test/org/apache/solr/uninverting/TestFieldCacheSortRandom.java#L268-L289)) verifies each result's runtime type and unconditionally skips the exact ordering comparisons; the hit count is not asserted there either. The ticket says the earlier fix is "likely incorrect" and needs to be looked into.

## What this change does

**The test asserts the hit count, the document order, and the sort values again, deduplicating repeated observations of the same document.**

[TestFieldCacheSortRandom.java](https://github.com/nick-boss-tech/solr/blob/b46e78cb50fea8cf8059bbbdb49815662a197a8e/solr/core/src/test/org/apache/solr/uninverting/TestFieldCacheSortRandom.java) is the only file changed. Lucene 10.4.0 partition dispatch can invoke the full-leaf supplier more than once, so the same global docID can be observed repeatedly; the restored assertions deduplicate the expected observations by docID and assert that repeated observations agree. The expected order is computed by an explicit comparator keyed on the test’s own missing-value setting, not by the sort under test. No expected value is taken from actual search results, and no production code changes.
