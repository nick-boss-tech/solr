## What happens today

**When a request carries a `collection` parameter that disagrees with the collection named in the URL path, HttpSolrCall routes by the parameter, so the request can be served by a collection it was not addressed to.**

[HttpSolrCall](https://github.com/nick-boss-tech/solr/blob/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb/solr/core/src/java/org/apache/solr/servlet/HttpSolrCall.java) resolves the request's collection with the `collection` parameter taking precedence over the path. The ticket says the URL path alone should govern which collection receives a collection-scoped request; the parameter overriding it sends the work to a different collection than the URL names.

## What this change does

**The URL path decides the collection, on the v1 and the V2 entry paths alike; the `collection` parameter no longer overrides the path the request was sent to.**

[HttpSolrCall.java](https://github.com/nick-boss-tech/solr/blob/40e2c40516ff2dfae51c603f10c91dbcfa7a4688/solr/core/src/java/org/apache/solr/servlet/HttpSolrCall.java) keeps routing path-scoped, and [V2HttpCall.java](https://github.com/nick-boss-tech/solr/blob/40e2c40516ff2dfae51c603f10c91dbcfa7a4688/solr/core/src/java/org/apache/solr/api/V2HttpCall.java) now resolves the collection from its path segment instead of the parameter. [HttpSolrCallCloudTest](https://github.com/nick-boss-tech/solr/blob/40e2c40516ff2dfae51c603f10c91dbcfa7a4688/solr/core/src/test/org/apache/solr/servlet/HttpSolrCallCloudTest.java) covers the v1 disagreement case, the narrowing case, and the V2 disagreement case. Four existing tests that relied on the parameter winning (BasicDistributedZkTest, TestDistribIDF, RuleBasedAuthorizationCoreCollectionTest, DistributedQueryComponentOptimizationTest) now put their collections in the path, and AliasIntegrationTest keeps a case where a CloudSolrClient carries the collection only as a parameter, which the client moves into the path. The Ref Guide's distributed-requests page now describes the parameter as narrowing the path, and the Solr 11 major-changes page records the removal. Eleven files change, including the changelog entry.

## Limits

**Requests whose parameter matches their path route as before. Three cases change: a parameter that disagrees with the path, a request with no collection in the path, and a multi-collection path with a non-matching parameter.**

- The precedence change is deliberate and is what the ticket asks for. A client that relied on overriding the path with the `collection` parameter will now be routed by the path.
- A request with no collection segment in the path, such as `/solr/select?collection=c1`, now returns 404 instead of routing by the parameter.
- When the path names several collections (an alias or a comma list), the parameter only narrows the list; a parameter that matches none of them is ignored and the request goes to all of them.
