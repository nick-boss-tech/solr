## What happens today

**When a request carries a `collection` parameter that disagrees with the collection named in the URL path, HttpSolrCall routes by the parameter, so the request can be served by a collection it was not addressed to.**

[HttpSolrCall](https://github.com/nick-boss-tech/solr/blob/b73f03976fa17b857bc0a81bc8af2c6b1c31e0bb/solr/core/src/java/org/apache/solr/servlet/HttpSolrCall.java) resolves the request's collection with the `collection` parameter taking precedence over the path. The ticket reports the path as the address the client chose; the parameter overriding it sends the work to a different collection than the URL names.

## What this change does

**The URL path decides the collection; the `collection` parameter no longer overrides the path the request was sent to.**

[HttpSolrCall.java](https://github.com/nick-boss-tech/solr/blob/bc15134268e2fba2e29fb3fbc62546065906713d/solr/core/src/java/org/apache/solr/servlet/HttpSolrCall.java) keeps routing path-scoped, and [HttpSolrCallCloudTest](https://github.com/nick-boss-tech/solr/blob/bc15134268e2fba2e29fb3fbc62546065906713d/solr/core/src/test/org/apache/solr/servlet/HttpSolrCallCloudTest.java) covers the case where the parameter and the path disagree. AliasIntegrationTest is updated where it relied on the parameter taking precedence. Four files change, including the changelog entry.
