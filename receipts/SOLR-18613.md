## PR description draft (for a later opening, at Nick's direction)

Title: SOLR-18613: Consistently enforce LBSolrClient request attempt limits

🤖 *AI text below* 🤖 *(reviewed by Nick Shanin)*

https://issues.apache.org/jira/browse/SOLR-18613

**What happens today**

**The standalone LB path can spend more attempts than the configured limit, and the async path hides the exhaustion.**

Without a consistent count, a standalone request could continue into zombie fallback after spending `numServersToTry`, and could revisit failed live endpoints when the configured limit exceeded the live snapshot. An async request that ran out of attempts surfaced the preceding transport failure instead of the attempt-limit exhaustion.

**What this change does**

**Live and zombie attempts are counted within one execution, and exhaustion raises a dedicated exception.**

`LBSolrClient` and `LBAsyncSolrClient` count every LB dispatch, including the initial attempt, against the configured maximum. On exhaustion the request fails with `LBSolrClient.AttemptLimitExceededException`, which carries the attempt count, the configured maximum, and the last cause. Behavior with no limit configured is unchanged, and retry eligibility rules are unchanged. The limit covers LB dispatches, not HTTP-client-internal retries.

**Proof**

**The new tests pass at this head, and four of them fail against the original production code for the reasons the ticket describes.**
