## Why the exception is not proof

The JDK 25.0.4.1 server snapshot is `/dev/shm/bats-assertion-hardening-0d7c6f4/solr/packaging/build/test-output/failure-snapshots/5-5/logs/solr.log:15104–15143`. Its stack goes through `CertificateMessage$T13CertificateConsumer.checkClientCerts`, `X509TrustManagerImpl.checkClientTrusted` (`X509TrustManagerImpl.java:138`), and `checkIdentity` (`X509TrustManagerImpl.java:436`). OpenJDK 25’s [`X509TrustManagerImpl.java`](https://github.com/openjdk/jdk25u/blob/master/src/java.base/share/classes/sun/security/ssl/X509TrustManagerImpl.java#L436) reports `Endpoint Identification Algorithm HTTPS is not supported on the server side` for this server-side client-certificate path. [OpenJDK issue JDK-8229972](https://bugs.openjdk.org/browse/JDK-8229972) explains that HTTPS endpoint identification is for clients validating server certificates; server-side client identity checks need a suitable trust-manager mechanism.

**Conclusion:** the test is attempting the intended client-certificate check, but the implementation applies the opposite-direction JSSE HTTPS endpoint-identification setting on the server. The observed unsupported-algorithm exception may mask an identity mismatch; it does not prove that Solr’s intended hostname check works. No test-only correction can honestly validate this behavior while the server implementation/configuration remains this way; production/configuration work is required first.
