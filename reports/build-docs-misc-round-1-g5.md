## SOLR-13705 (double-checked locking in SSLConfigurationsFactory): narrow premise holds; broad premise does not hold by reading

- Diff: 4 files, 4 commits: `SSLConfigurationsFactory.java` (one line), `SSLConfigurationsFactoryTest.java` (new, 70 lines), the TESTING note and the changelog fragment. Merge-base `9b3a84b1c460` matches the receipt. The three touched-path files and the test's helpers are unchanged between the base and main.
- Narrow premise, holds by reading: `SSLConfigurationsFactory.java:23` declares `currentConfigurations` without `volatile`. The double-checked locking is at lines 32-39. On base the reflection test's `Modifier.isVolatile` check fails deterministically. The test compiles on base by reading.
- Broad premise, does not hold by reading as a defect: the object reached through the field has one instance field, `credentialProviders` (`SSLConfigurations.java:32`), declared `final` and assigned once in the constructor (line 52). The constructor does not leak `this`. Under the Java memory model's final-field guarantee, a thread that sees a non-null reference sees the constructed list. The missing volatile is a latent hardening issue, not a shown fault. No test can settle the broad premise.
- Ticket (`research/jira-context/SOLR-13705.json`): "Double-checked Locking Should Not be Used", Open, no comments. It names no class, method or line.
- The register (`research/pipeline/skips.md:643`) says the known DCL sites are already volatile and that SSLConfigurationsFactory has no reproduction. **Contradicted at one site:** `SecurityConfHandler.java:284` declares `private Collection<Api> apis;` (not volatile), with a double-checked read at lines 290-292 and a publish at line 352 of an immutable `List.copyOf` result. A grep sample found the other DCL sites volatile, but the scan was not exhaustive.
- Receipt disagreements: `receipts/SOLR-13705.md:7` repeats the register claim that the known DCL sites are volatile; the SecurityConfHandler site contradicts it. The receipt's "gated, no PR" label is overridden by the receipt itself, and `research/windows-gate-results/batch-001-2026-10-08.md` line 29 says "Gate steps: pending", which agrees with never gated. The takeover log was not opened.
- Owner decision (scope before any gate): (a) close the ticket as not reproduced and retire the branch (a public action); (b) a narrow hardening change on SSLConfigurationsFactory only, with a Linux focused run, described as hardening and not as a bug fix; (c) widen to every non-volatile lazy-init site, at least `SecurityConfHandler.apis`, as a separate scope decision. Recommendation: decide the scope first, correct the register line, and do not run the gate to produce a reproduction; the test checks a declaration.
- Verification owed (Linux lane, if (b) or (c)): focused `SSLConfigurationsFactoryTest` on base with only the test files copied in. Expected by reading: the volatile test fails and the concurrency test passes. Then on head, both pass. The GitHub SUCCESS on head is not a substitute.

## SOLR-17722 (CrossDC mirrors the update `wt` param): premise fails by reading; NOT draftable

- Diff: 3 files, 3 commits: `SolrMessageProcessor.java` (+8), `SolrMessageProcessorTest.java` (+24), `SOLR-17722-TESTING.md` (repo root). Merge-base `56ec140e3636`; no drift on the touched paths. The branch applies cleanly to main. The inventory's `e5c0a64f993` is SOLR-17752's head; the correct tip for this ticket is `fee3a26beb3c`.
- Mechanism claimed by the ticket: the consumer uses the cloud client's default binary parser, so a mirrored `wt=json` reaches the secondary and the consumer misparses JSON as binary.
- Reading on main: `KafkaCrossDcConsumer.java:132` builds a `CloudSolrClient`. The `HttpSolrClient.initializeSolrParams` (`HttpSolrClient.java:153-164`) copies the request's params in, then at line 162 calls `params.set(CommonParams.WT, parserToUse.getWriterType())`. The default parser is `JavaBinResponseParser` (`HttpSolrClient.java:97`). So the outgoing `wt` is javabin whatever the request carried. The same path is in `HttpJdkSolrClient.java:243-244`, and the Jetty client's `makeRequest` (`HttpJettySolrClient.java:703-710`) builds its query from the same params.
- The branch's change (`SolrMessageProcessor.java:281-287`) forces `wt=javabin` on the mirrored params. Step 6 overwrites that value anyway on every client path that calls `initializeSolrParams`, so the branch's write has no effect on the wire.
- History: the overwrite has existed in SolrJ since SOLR-2020 (2012). It predates the ticket (2025-03-27). No commit targets this ticket.
- The branch's unit test asserts only that the mutated mock params hold javabin. It inspects no outgoing request, so it does not test the ticket's mechanism.
- The branch's own note (`SOLR-17722-TESTING.md:9-17`) says the premise is unproven and that if it does not fail, the right outcome is a comment on the ticket. The round-4 review says "likely a no-op ... reproduce on main, else retire".
- Owner decision (not taken): (a) retire the branch now, on the reading; (b) run the wire-level check below on the Linux lane, then retire if it confirms the reading (recommended, then (a)); (c) keep as a hardening no-op. Not recommended: it changes no observable behavior. A ticket comment would be a public action and is not drafted here.
- Verification owed (Linux lane, main-side): a SolrJ-level test on main that sends an `UpdateRequest` with `wt=json` through `CloudHttp2SolrClient` (or `HttpJettySolrClient`) to a local endpoint and asserts the query string has `wt=javabin`. If it does, the premise fails and the branch changes nothing observable.
- Receipt disagreements: `receipts/SOLR-17722.md:6` quotes the register as "Verify the premise during review before hardening"; the text was not found by grep (the branch's note has similar but different wording). `receipts/SOLR-17722.md:7` says the inventory label is "premise-dead; retire call pending". Recommend one label: "unproven until the wire check, then premise-dead if confirmed".
- Interactions: the override lives in SolrJ's `HttpSolrClient`, used by every SolrJ HTTP client; any change there would reach beyond CrossDC. This branch does not change it.
- Not checked: whether any consumer path bypasses `initializeSolrParams` (none found on the default path); the producer and serializer side; `ClientUtils.buildRequestUrl` in full (assumed to build the path only).
