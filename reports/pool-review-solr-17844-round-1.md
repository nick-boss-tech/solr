## Verdict: FIX FIRST

The rework is sound on the point that matters most: the duplicate-observation diagnosis is correct, the dedup is right, the count, order and value assertions are real, and the test discriminates a reversed sort. One thing is not sound. The new expected order delegates both value order and missing-value placement to `SortField.getComparator(...).compareValues`, that is, to the sort under test. The original computed them with an explicit comparator keyed on the test's own `sortMissingLast` variable. As a result, a test input that flips where missing values sort is invisible to the head test (it passes). The change was not needed to fix the 42 against 14 failure, and it is a loss of an assertion the original had. It changes how expectations are computed, so it is not a repair under the assignment's patch loop.

### Fix specified (one)

Restore the original explicit comparator as the single source of expected value order. At `TestFieldCacheSortRandom.java:204-206` replace the `FieldComparator` obtained from `sf.getComparator(1, Pruning.NONE)` with:

```java
final Comparator<BytesRef> valueOrder =
    new Comparator<BytesRef>() {
      @Override
      public int compare(BytesRef a, BytesRef b) {
        if (a == null) {
          if (b == null) {
            return 0;
          }
          return sortMissingLast ? 1 : -1;
        } else if (b == null) {
          return sortMissingLast ? -1 : 1;
        }
        return a.compareTo(b);
      }
    };
```

and use `valueOrder.compare(...)` in the three places that call `fieldComparator.compareValues(...)` (lines 214, 222, 311). Remove the now unused `FieldComparator` and `Pruning` imports (lines 43 and 46). Everything else stays: dedup by global docID, the `reverse` sign flip at 223, the docID tie-break at 225, the count assertion at 274-277, the docID assertion at 281-289. The full patch is `reports/pool-review-solr-17844-round-1-proposed-fix.patch`.

I applied that patch in a scratch worktree and ran it (not committed, worktree discarded). Results at the same seed and on random seeds are in answer 1. I did not run tidy, Error Prone or `:solr:core:check -x test` on the patch, so the gate for the fixed head must run them.

## Answers

### 1. Independent expectations

Where every expected value comes from:

- **The documents and their values.** Generated by the test's own `random()` before any search: `docValues` is filled at lines 91-131, one entry per document, `null` for the missing ones.
- **Which documents match.** `RandomQuery.scorerSupplier` (lines 347-362) draws `new Random(seed ^ context.docBase)` and records `ExpectedHit(docValues.get(id), context.docBase + docID)` for each document it puts in its own bit set. This does not read search results.
- **Count.** `Math.min(hitCount, expected.size())` at line 230, where `hitCount` is the requested top-N (line 179) and `expected` is the deduplicated recorded set.
- **Direction and ties.** `reverse` is the test's own variable (line 159), applied at line 223. Ties break by ascending docID (line 225), which is Lucene's behavior for both `Sort(sf)` and `Sort(sf, FIELD_DOC)`.
- **Value order and missing placement.** From `fieldComparator.compareValues(...)` (lines 204-206, used at 214, 222 and 311), where `fieldComparator` comes from `sf.getComparator(1, Pruning.NONE)`. `sf` is the `SortField` the search runs with (line 165), including its `setMissingValue(STRING_LAST)` (lines 169-171).

So no expectation is read from `hits`, and the count, the order and the sort values are all checked against independently recorded matches. The exception is the one rule in the last bullet, which comes from the component under test.

Evidence that this matters (vm3 runs, seed `1BB02D3762B56611`, logs in `/workspace/gates/logs/vm3/review-17844/`):

| 6b-fix-mut-missing | Proposed fix plus the same flip | 2 tests, 2 failures, `Unexpected document at position 0 in iteration 0` (expected 70 but was 17; expected 32 but was 34). Detected. |

The original test would have caught the flip because its comparator read `sortMissingLast` directly (original lines 200-223). The head test follows whatever the sort is told.

Proposed fix, unmutated: 6a-fix-seed, seed `1BB02D3762B56611`: 2 tests, 0 failures. 6d-fix-random, `-Ptests.iters=10 -Ptests.multiplier=3`, master seed `A372AF18381E4A8B`: 20 executions, 0 failures. ### 2. Deduplication soundness

- **Repeated observations are asserted to agree, not dropped.** Lines 207-216: `putIfAbsent` by docID, and on a repeat the test asserts `compareValues(previous.value, expectedHit.value) == 0` with the message "Different sort values observed for document N". Caveat: `value` is a pure function of the document (`docValues.get(id)`), so repeated observations of one document can never disagree. The check is a sanity check, not a discriminating one. It also uses the comparator discussed in answer 1.
- **A missing or extra document still fails.** The expected set is the recorded matches, not the results. If the actual result omits an expected document, the count assertion fails (`expectedHitCount` against `hits.scoreDocs.length`, lines 274-277), or, when the top-N is truncated, the docID assertion at position `hitIDX` fails (lines 281-289). An extra or duplicated document in the results shifts every later position and fails the same docID assertion. This is derived from the code; I did not run a test that drops a document. The direction mutation does show the order assertion firing (answer 4).
- **What dedup does not hide.** Deduplication collapses how many times a document was recorded, so the test cannot tell how often the supplier ran. That is correct for the purpose: a repeated recording is a property of the test query, not a result.

### 5. First-failure accounting

The receipt records `expected:<42> but was:<14>` for `testRandomStringValSort` at the first candidate `0a7ffa07a4`. I reran that exact commit at the same seed with a one-line `System.out.println` added to `scorerSupplier` (docBase, maxDoc and thread; patch in `4-first-candidate-instrumented.patch` in the log directory, not committed anywhere):

- The failure shape reproduces: `Unexpected number of hits for iteration 0 with sort <string_val: "stringdv"> missingValue=SortField.STRING_LAST expected:<30> but was:<14>`. The returned count is 14 again; the expected count is 30 on this host, not 42.
- In that search, three of the six segments had `scorerSupplier` called three times each, from three threads (the test thread, `LuceneTestCase-1-thread-1`, `LuceneTestCase-1-thread-2`): docBase 0 (maxDoc 28), docBase 41 (maxDoc 45) and docBase 86 (maxDoc 35). The other three segments (docBase 28, 121, 127) were called once.
- `RandomQuery` records every match in the leaf on every call (lines 353-361), so each match in a repeated segment is recorded three times. The first candidate counted observations as hits, so `expected` exceeded the distinct matches.
- `testRandomStringSort` (the STRING variant) called each of its five segments exactly once per iteration (120 iterations) and passed, so only the variant that ran with a partitioned search failed. That fits the receipt, where only `testRandomStringValSort` failed.

42 against 14 is exactly 3 times 14, the value you get if every matching document was recorded three times. 30 against 14 is 14 plus 2 times 8, which is what you get if 8 of the 14 matches are in tripled segments. I did not log matches per segment, so I cannot show the 8 and 6 split directly, and I cannot show why this host got 30 where phone-agent-2 got 42. The segment layout and executor slicing vary between runs and hosts (concurrent merges and the random test executor), so a different split of the same 14 hits is the likely reason; I did not verify it. The fit is strong: the duplicated recording explains an expected count that is above the returned count, with the returned count the same. The head, which dedups, passes this same seed. I found no other explanation that predicts both numbers.
