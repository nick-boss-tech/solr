# SOLR-18439: v2 error-status trace

## Finding

The current Apache Solr `main` source supports the ticket's reported mismatch on two concrete v2 routes. For three caught failure cases, the API builds a normal response object containing legacy `status: ERROR` / `message` fields instead of throwing the failure into the shared exception mapper. A normal entity return uses the HTTP success path (200); the source-level control flow and the ticket description support that behavior, but I did not run a live request or a test under this assignment.

Source snapshot: Apache Solr `main` at `13c693d805f6541f7cec684cd27d28eef7b3b614` (fetched 2026-10-25T02:39Z).

## Two v2 routes, three failure cases

1. **`GET /api/cores/{coreName}/replication/files?generation=...`** is declared by [`ReplicationApis`](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/api/src/java/org/apache/solr/client/api/endpoint/ReplicationApis.java#L37-L70) and implemented by [`CoreReplication.fetchFileList`](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/core/src/java/org/apache/solr/handler/admin/api/CoreReplication.java#L60-L64), which delegates to [`ReplicationAPIBase.getFileList`](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/core/src/java/org/apache/solr/handler/admin/api/ReplicationAPIBase.java#L142-L164).
   - If the requested commit generation is missing or expired, `getFileList` calls `reportErrorOnResponse` with `invalid index generation` and returns the `FileListResponse` normally. The helper sets `status` to `ERROR` and `message`; it does not set `exception` for this case.
   - If reading the index files raises `IOException`, the method sets `status: ERROR`, message `unable to get file names for given index generation`, and the `exception` field, then returns normally ([error branch](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/core/src/java/org/apache/solr/handler/admin/api/ReplicationAPIBase.java#L209-L214), [field setter](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/core/src/java/org/apache/solr/handler/admin/api/ReplicationAPIBase.java#L616-L623)).

   [`FileListResponse`](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/api/src/java/org/apache/solr/client/api/model/FileListResponse.java#L22-L37) defines the legacy `status`, `message`, and `exception` fields. It inherits `responseHeader` and `error`, but these caught paths do not populate the standard `error.code` / `error.msg` structure.

2. **`POST /api/cores/{coreName}/replication/backups`** is declared by [`ReplicationBackupApis`](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/api/src/java/org/apache/solr/client/api/endpoint/ReplicationBackupApis.java#L32-L42). [`SnapshotBackupAPI.createBackup` / `doBackup`](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/core/src/java/org/apache/solr/handler/admin/api/SnapshotBackupAPI.java#L58-L97) rethrows `SolrException`, but catches other `Exception`s from snapshot creation, sets `status: ERROR`, a message prefixed `Error encountered while creating a snapshot: `, and `exception`, then returns the response. [`ReplicationBackupResponse`](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/api/src/java/org/apache/solr/client/api/model/ReplicationBackupResponse.java#L21-L35) exposes those custom fields.

## Why these return on the success path

The v2 [error convention](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/dev-docs/apis-v2-conventions.adoc#L73-L79) says to throw `SolrException` so the HTTP status, `responseHeader.status`, and `error.code` match, with the message in `error.msg`. The shared [`CatchAllExceptionMapper`](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/core/src/java/org/apache/solr/jersey/CatchAllExceptionMapper.java#L105-L124) builds that error object and returns `Response.status(response.error.code)`. In the three cases above, the API methods instead return a response entity, bypassing that mapper path. This is the source-level reason for the ticket's HTTP-200 report; it is not a wire-level reproduction from this task.

The current-main tests do not prove the wire status for these v2 failures: the existing [`TestReplicationHandler` file-list test](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/core/src/test/org/apache/solr/handler/TestReplicationHandler.java#L1488-L1498) asserts only the v1 response body's `status` and `message`, while [`SnapshotBackupAPITest`](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/core/src/test/org/apache/solr/handler/admin/api/SnapshotBackupAPITest.java#L54-L79) covers missing-body and successful backup cases, not the caught generic failure. No build, test, or live Solr request was run.

The history search places these custom response paths in the original v2 API introductions: [file-list API, commit `244a29b`](https://github.com/apache/solr/commit/244a29b39e354a2dabe4a5ad70c5bc148c6f8555) and [backup API, commit `1079589`](https://github.com/apache/solr/commit/107958984333c9650a6124a9751a1ba725baf387). The current main history contains no SOLR-18439 fix; the ticket-linked PR remains open.

## Live ticket context and open decision

The live [SOLR-18439](https://issues.apache.org/jira/browse/SOLR-18439) page is Open, assigned to Eric Pugh, and says failures should be thrown as `SolrException` for the mapper to produce the HTTP status and `error.code` / `error.msg`. Jira currently has no comments. Its linked [PR #4899](https://github.com/apache/solr/pull/4899) is still open and unmerged.

The latest PR discussion is [Jan Høydahl's September 24 comment](https://github.com/apache/solr/pull/4899#issuecomment-5822703480). It points out that the shared file-list path is also reached by v1 `/replication?command=filelist` ([current routing](https://github.com/apache/solr/blob/13c693d805f6541f7cec684cd27d28eef7b3b614/solr/core/src/java/org/apache/solr/handler/ReplicationHandler.java#L304-L308)) and that the existing v1 test expects the legacy `ERROR` / `message` body. The comment also questions 404 versus 409 for a missing generation and recommends considering 409. Its reported 404 request was on the PR branch, not a current-main run. These are open compatibility/status choices; the ticket's broader requirement for a proper non-200 error response is explicit.

**Conclusion:** the ticket is confirmed at source/control-flow level, so a short unposted Jira draft is warranted. The draft asks Eric to settle the missing-generation status and v1 compatibility boundary; it does not endorse the open PR's proposed implementation.
