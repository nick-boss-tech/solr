## SOLR-9852 findings

1. **Premise on main, by reading.** Main `DatabaseMetaDataImpl.java` lines 755 to 758: `getColumns` returns null. Lines 816 to 817: `getTypeInfo` throws. At head `31f58dbe`: `getColumns` is at lines 756 to 771 (query from line 758), `quotePattern` at 772 to 775, and `getTypeInfo` at 832 to 833 throws SQLFeatureNotSupportedException. The report should say `getColumns` now lists the collection's columns, while `getTypeInfo` is still unsupported and only its exception class changed. The ticket's SQuirreL failure at `getTypeInfo` is not fixed by this branch. Whether SQuirreL then continues was not verified.
2. **Query column names are valid for the pinned versions.** The 18 names in the select list (head lines 758 to 762) are all field names of Avatica's `MetaImpl$MetaColumn` in avatica-core 1.29.0 (`libs.versions.toml` line 25). calcite-core 1.42.0 (line 24) `MetadataSchema` references `COLUMNS` and `MetaColumn`. This resolves the TESTING.md guess by a class scan, not by running the query.
3. **Shared statement.** `DatabaseMetaDataImpl` receives the connection's single statement (`ConnectionImpl.java` lines 73 to 74 at main). `StatementImpl.executeQueryImpl` closes the current result set before it runs the next query (`StatementImpl.java` lines 55 to 60 at main). So a `getColumns` call closes a `getTables` or earlier `getColumns` result set that is still being read. `getTables`, `getSchemas` and `getCatalogs` already behave this way (main lines 728 to 746), and `getColumns` inherits it. JdbcTest's blocks (head lines 679 to 707) use try-with-resources and never interleave, so the test does not cover it. The report should claim sequential use only, or carry a Limits line.
4. **Result shape.** Positions 1 to 18 follow the JDBC `getColumns` order, but the labels are the driver's camelCase (`tableCat`, `tableSchem`, `tableName`, `columnName`, and so on), as `getTables` uses, not the JDBC-specified names (`TABLE_CAT`, `COLUMN_NAME`). There is no ORDER BY, though JDBC specifies ordering by TABLE_CAT, TABLE_SCHEM, TABLE_NAME and ORDINAL_POSITION. The report should not claim JDBC-conformant labels or ordering.
5. **Test filter with a wildcard.** `JdbcTest.java` lines 701 to 704 filter `columnName` on "a_s" and assert exactly one row. In LIKE, "_" matches any single character, so the filter also matches any three-character column `a?s`. Low risk: the test is only as exact as the test schema.
6. **Quoting.** `quotePattern` (head lines 772 to 775) doubles single quotes and maps null to "%". `getTables` (main lines 728 to 737) still concatenates raw patterns. That is pre-existing and outside this branch. The report should not say driver metadata is quote-safe overall.
7. **Handoff note.** `SOLR-9852-TESTING.md` is in the branch (added by `31f58dbe8e6`, as the receipt says). Its text ("hypothetical reproduction", "nothing was compiled or run") is internal vocabulary and would ship in the PR diff. SOLR-13524's history removed its own TESTING.md (`8785a202295`) before its PR. Remove it before any PR.
8. **Changelog** (`5074ac2712c`, `changelog/unreleased/SOLR-9852-jdbc-getcolumns.yml`) matches the code. The author is Nick Shanin, with no placeholder. Keep it. The PR title should say `getColumns` is implemented, not that the JDBC metadata gap is closed.
9. **Overlap with SOLR-14200, from 9852's side: none on the code path.** The JDBC driver runs each statement as a SolrStream to one replica's `/sql` handler (`StatementImpl.java` lines 74 to 97 at main), not through SqlStream. 14200 changes `SqlStream.java` (an empty-shard guard) and the manual-shard branch of `TupleStream.getShards`. The `metadata.COLUMNS` query reads Calcite metadata, not shard data. That is inferred from the Calcite MetadataSchema class and not traced through `solr/modules/sql`. There is no shared file and no shared test class (9852: JdbcTest and DatabaseMetaDataImpl; 14200: StreamingTest, ParallelStream, SqlStream and TupleStream). Landing order: independent.

## SOLR-10882 findings

10. **The ticket's named premise is already handled on main.** `RecursiveEvaluator.normalizeInputType` (main lines 54 to 67) converts every Number (Long, Integer, non-NaN Double) to BigDecimal. `recursivelyEvaluate` (main lines 207 to 224) applies it to every input before `doWork`. `normalizeOutputType` (main lines 110 to 141) returns Doubles. So `array(sort=)` receives BigDecimal values and sorts mixed double and long correctly on main. The case `asc(array(11.5, 12.3, 4, 3, 1, 0))` is pinned at `MathExpressionTest.java` main lines 1278 to 1300. The ticket's last comment (2017-06-19, "doesn't take into account differing types (double and long)") is stale on main. The branch's `arrayMixedNumberTypesSortTest` (head `ArrayEvaluatorTest.java` lines 123 to 137) pins existing behavior and likely passes on main too.
11. **Real defect 1 on main: text or boolean mixed with numbers under sort.** Main `ArrayEvaluator.java` lines 68 to 77 check only Comparable. The comparator at lines 50 to 51 is a raw `left.compareTo(right)`, so a String against a BigDecimal throws ClassCastException from the bridge method. Head `ArrayEvaluator.java` lines 67 to 90 add a kind check: all Numbers count as one kind, other values group by exact class, and a mismatch throws IOException "values of different types (X and Y)". The test `arrayMixedTypesSortTest` (head lines 139 to 150, assertions at lines 148 to 149) expects that IOException. On main it fails with ClassCastException. That is a fail-before by reading, not run. The report can say a sort over text and numbers now gives a clear error.
12. **Real defect 2 on main: null under sort.** `FieldValueEvaluator` returns null for a missing field (main lines 91 to 99). `normalizeInputType` keeps null, and main `ArrayEvaluator.java` line 75 calls `value.toString()` in the error message, so a null throws NullPointerException. Head line 76 formats the value with `%s` and throws IOException "non-Comparable value ('null')". No test covers it: the branch test file has no null case, and TESTING.md says so. The changelog claim is right by reading but unpinned. The gate should add a null-value case, or the NPE claim should come out of the changelog and PR text.
13. **Exact-class grouping narrows one case.** Non-numbers are grouped by `getClass()`, so two Comparable values of different classes that compare on main (for example `java.util.Date` and `java.sql.Date`, since `Date.compareTo` takes any Date) now throw IOException. Solr tuples carry `java.util.Date`, so the impact is unlikely, and no test covers it. Low. The changelog's "incomparable types" wording is slightly loose for this case.
14. **TESTING.md claims check out by reading:** the BigDecimal normalization, the mixed-number test probably passing on main, the ClassCastException fail-before on main, and the untested null path. Its "guesses to verify" are answered by reading only.
15. **Handoff note.** `SOLR-10882-TESTING.md` is in the branch (added by `83fc3dfeb24`). Remove it, as in finding 7.
16. **Interaction with SOLR-13524 (the evaluator cluster).** Measured against main, 13524 changes only `OrEvaluator.java`, `RecursiveBooleanEvaluator.java` and `OrEvaluatorTest.java`. `validateValues` is extracted, and `OrEvaluator.doWork` is overridden as a disjunction (13524 head `OrEvaluator.java` lines 41 to 51; `RecursiveBooleanEvaluator.java` `doWork` at lines 45 to 56 and `validateValues` at line 62). `ArrayEvaluator` extends `RecursiveObjectEvaluator`, which extends `RecursiveEvaluator`. It does not extend `RecursiveBooleanEvaluator`, and it uses neither `validateValues` nor `Checker`. The normalization path that gives 10882 its BigDecimal inputs is untouched by 13524. The pinned tests at `f08e7c12a8ed` assert boolean results (AndEvaluatorTest, ExclusiveOrEvaluatorTest) and numeric compound results (`RecursiveEvaluatorTest.compoundTest`), and none touches array sort. AndEvaluator inherits the refactored `doWork` with the same checks in the same order. ExclusiveOrEvaluator overrides `doWork` and does not use `validateValues`. Answer: 13524 landing first does not change 10882's premise, and 10882 does not change 13524's pinned behavior. No file or test class overlaps.
17. **Shared suites.** 10882 touches only `ArrayEvaluatorTest`, which is not one of the round's shared suites, so no landing-order constraint applies.
