## 1. The call

The branch as it stands follows the adopted framing: the `DistributedUpdatesAsyncException` message names the replica a failed request was sent to (its URL, collection and shard), so the client's error carries that detail. The narrow alternative keeps the message as on upstream/main and puts the same detail in the server log only. The adopted framing accepts the message change but does not choose the channel, so this is an owner call. The facts below are for that call; the report does not make it.

## 2. Mechanism

**The branch change.** `DistributedUpdateProcessor.java` adds `describe(SolrError)` (branch lines 1243-1259). It appends ` (while sending to <node URL>, collection=..., shard=...)` to each error's text, and `buildMsg` (lines 1285-1300) calls it for one error or for several **[diff: origin/solr-12245-submit, +20/-2]**.

**When an error reaches the client.** The exception is thrown in one place, `DistributedZkUpdateProcessor.java:1366-1368`, when `errorsForClient` is not empty **[code: upstream/main]**. Entries go into `errorsForClient` in three cases:

- Forward-to-leader errors: "if it's a forward, any fail is a problem" (lines 1219-1225). These always reach the client.
- Leader-to-replica errors with cause `LeaderChanged` (lines 1254-1262).
- Leader-to-replica errors for a replica in a different shard, such as during split-shard (lines 1345-1349).

Any other leader-to-replica failure is not sent to the client. It is logged at WARN with the base URL (`DistributedZkUpdateProcessor.java:1231`, "Error sending update to {}"), and leader-initiated recovery follows (lines 1268-1334). So the detail reaches a client only on forward-to-leader failures and on the cross-shard and `LeaderChanged` cases. The ticket's own log line shows the exception thrown out of the update request's `finish()` and logged at ERROR, so it was returned to the caller. The 2018 log does not say whether that was the forward or the cross-shard case **[record: JIRA, description log line]**.

**Where the node comes from.** `SolrError.req` (`SolrCmdDistributor.java:481-491`) names the request whose send failed. Streaming sends are recorded by `ErrorReportingConcurrentUpdateSolrClient` (`StreamingSolrClients.java:126-151`). Clients are keyed by the full node URL (lines 68-70) and built from the `Req` that first needed them (lines 77-79), so the node is the target core of that client. `SolrCmdDistributor.java:485-490` notes that `req` may not be the request that caused the error when requests are merged. With one client per URL, the URL is right; the request that caused the error can differ **[code]**.

**Interaction with SOLR-5939 (not on this branch).** 5939 changes the same path so each merged request in a failed stream gets its own `SolrError` (`StreamingSolrClients.java` recordError per request; `ConcurrentUpdateBaseSolrClient.java` +61/-3; `StreamingSolrClients.java` +43/-6) **[diff: origin/solr-5939-submit; read, not run]**. If 5939 lands, one stream failure can yield several errors, and `describe()` would repeat per request inside one message **[hypothesis from the diff]**.

**The URL is already in the streaming message.** The streaming path builds `new RemoteSolrException(basePath, statusCode, remoteError)` (`ConcurrentUpdateBaseSolrClient.java:334`), and for other exceptions `new SolrServerException("Error from server at " + basePath + ": " + e.getMessage(), e)` (lines 348-352). `RemoteSolrException.java:42` formats "Error from server at <host>: msg". The base private `handleError(Throwable, List<String>, String)` passes the exception to `handleError(ex)` when no error handler is set (lines 625-629), and `StreamingSolrClients.java:77-87` sets none. So the exception stored in `SolrError.e` already names `basePath`, and `describe()` appends the core URL to it. The client-facing text would name the host twice. Composed text not run **[code; composition hypothesis]**.

## 5. Risk

- **Duplicate host on the streaming path.** Described above: the streaming message already names `basePath`, and `describe()` adds the core URL. If the detail is kept, `describe()` should skip the node URL when the message already contains it, or the draft should say the host appears twice.
- **Consumers.**
  - *Client applications:* SolrJ wraps the server's answer in `RemoteSolrException`, whose text begins "Error from server at <the node the client contacted>" (`RemoteSolrException.java:42`). A client already sees the node it talked to, not the failing replica. The branch adds the failing replica.
  - *Code in the repo:* none parses the text. `git grep` at the branch head finds "during distributed update" only in the constructor and in tests (audit finding 5). `CloudSolrClient.java:561-564` builds its own "Async failures during distributed update" text from tolerated errors, a separate message that `describe()` does not reach.
  - *TolerantUpdateProcessor:* catches the exception and reads `duae.errors` and metadata, not the message (`TolerantUpdateProcessor.java:232-250`, branch). Its own per-document list was not traced, so whether it reads `getMessage()` is a hypothesis; the only message-building path I read there is `CloudSolrClient`'s, which uses `ToleratedUpdateError` (`CloudSolrClient.java:566-571`) and is unchanged by the branch.
  - *Operators:* server logs. The 2018 log line in the ticket shows the final exception logged at ERROR with its message and an empty MDC (`? (:)`) **[record: JIRA]**. So the message text reaches the log as well.
- **Precedent for node URLs in client-visible errors.** `HttpSolrCall.java:656-662` returns "Error trying to proxy request for url: " + coreUrl as a SERVER_ERROR. `RemoteSolrException` puts the remote host in every SolrJ remote error. `HttpShardHandler.java:537-539` names the shard but not a URL. So node URLs in client errors have precedent here, and so does shard-only detail.
- **MDC on the log line.** The default pattern (`solr/server/resources/log4j2.xml:26`) prints `[c: s: r: x:]` from MDC. `SolrCore.open()` (`SolrCore.java:1694-1697`) calls `MDCLoggingContext.setCore(this)`, which takes collection, shard and replica from the core's descriptor (`MDCLoggingContext.java:133-152`). `CoreContainer.getCore` calls `open()` (`CoreContainer.java:2246`), so a request thread that acquires its core through `getCore` carries that core's MDC **[code; the request thread's acquisition path from HttpSolrCall was not traced, hypothesis]**. For a forward-to-leader or same-shard failure, the coordinator's shard equals the target's, so the final log line probably already carries collection and shard. For a cross-shard error it would not **[hypothesis; a main-side run would settle it]**.
- **Interactions (git merge-tree, read-only).** `DistributedUpdateProcessor.java` overlaps SOLR-14262 (+5/0); no conflict. The logs-only option's log line would sit in `DistributedZkUpdateProcessor.java`, which SOLR-5941 touches (+7/0); no conflict with 12245 today. SOLR-5939, SOLR-5754 and SOLR-14718 change the error-attribution code (`StreamingSolrClients.java`, `SolrCmdDistributor.java`); no textual conflict with 12245, but the semantic interaction with 5939 is described above.

## 6. Sized recommendation

**Still a judgment call, with the one fact that would settle it: whether the coordinator's server log line for this exception already names the collection and shard (a main-side run that forces a forward-to-leader failure and reads the line with the default log4j2 pattern).**

The TESTING.md lean (keep the detail in the client response) is supported but not settled, and the scoping evidence adds two caveats to it:

1. The client is the only consumer the response change reaches, and node URLs already appear in client-visible errors in this codebase. That favors keeping it.
2. The ticket asks about shard and collection in the logs (MDC), and the logs-only option is smaller. The response detail reaches clients only on forward-to-leader and cross-shard failures, and on the streaming path it repeats the host.

If the run shows the log line already has collection and shard, the response detail adds only client visibility, and the owner decides on that alone. If it does not, a logs-only change would not meet the ticket's own complaint, which favors keeping the response detail. Either way, if the detail is kept, fix the duplicated host in `describe()` before the PR.
