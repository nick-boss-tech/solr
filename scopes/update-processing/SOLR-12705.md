## 1. The call

Narrow option (a): exclude counting processors (CountFieldValuesUpdateProcessorFactory) from the new atomic-operand path, so a counted field behaves as it does on main for atomic input. Broader option (b): keep counting processors on the shared path as the branch does now, state the resulting behavior in the changelog and Limits, and pin it with a test. The branch has the code for (b) but neither the statement nor a test. TESTING.md recommends (b). The evidence below changes that recommendation to (a), because the (b) output for counted add and remove is not a count and it bypasses the SOLR-7504 rejection in a combined tree.

## 2. Mechanism

The branch adds `mutateAtomicOperations` to the `processAdd` loop of `FieldMutatingUpdateProcessor`. [verified: diff] Branch file lines 81 (processAdd), 95 (`dest = mutateAtomicOperations(fname, src)`), 96-97 (`mutate(src)` runs only when the result is NOT_ATOMIC). For a field whose only value is a map of atomic operations, and which has at least one of set, add, add-distinct or remove, the operand of each such operation is wrapped in a new `SolrInputField(fname)` and passed to `mutate` (branch lines 137-168; the operand loop is at 149-160). Operations outside that set (inc, removeregex) are kept as they are. A null operand is kept as it is (branch line 149), so `{set: null}` never reaches `mutate`.

Counter on main: `CountFieldValuesUpdateProcessorFactory.getInstance` wraps `mutator(...)` around `result.setValue(src.getValueCount())` (main lines 65-75, the setValue at line 72). [verified: code] On the branch, the operand "x" counts as 1, so:
- `{add: "x"}` becomes `{add: 1}`. [verified: code, derived from the two lines above]
- `{remove: "x"}` becomes `{remove: 1}`.
- `{set: ["a","b"]}` becomes `{set: 2}`.
- `{set: null}` is kept as `{set: null}` (null operand skip, branch line 149), so the counter never writes 0 here.
- `{inc: 1}` alone is NOT_ATOMIC, so it gets the base path: plain 1. [verified: code]
- On main, the same `{add: "x"}` gets the base path: plain 1. [verified: code, main lines 70-74]

Merge semantics: `AtomicUpdateDocumentMerger.merge` applies an `add` with `doAdd`, which calls `toDoc.addField(name, value)` (merger main lines 470-481, addField at 479). [verified: code] That appends to the stored values. It does not write a count of the resulting values. A `remove` of `1` goes to `doRemove` (merger lines 614-627), which removes a stored value equal to 1; it does not decrement a count, so a stored count of 3 is left alone. [verified: code] Whether an append to a single-valued count field errors or silently stores two values depends on the schema: [hypothesis, needs a run].

## 5. Risk

- Behavior surface: every processor listed in section 2, plus the two verified side effects (Ignore keeps atomic null set, RemoveBlank drops atomic set ""). Neither side effect is affected by the counting choice. Both need their own decision on this branch, because SOLR-12705 is marked "Ready for final review" in the reconcile report. [verified: record, reconcile report SOLR-12705 section]
- Review contention: the counted add and remove output is a judgment a maintainer is likely to reverse, because it is not a count (section 2). Option (a) avoids that. Option (b) makes it a stated behavior.
- SOLR-7504 interaction (verified by reading): under (b) a combined tree lets single-map add, remove, set and add-distinct on a counted field skip the 7504 rejection, and the operand is counted instead. Under (a) the counter takes the NOT_ATOMIC path, so `mutate` runs and the 7504 rejection is kept. [verified: code]
- SOLR-16655 overlap (verified by merge-tree and diff): merge-tree shows both branches changed FieldMutatingUpdateProcessor.java and ParsingFieldUpdateProcessorsTest.java, with conflict markers in the first. 16655 moves the loop body of processAdd into a recursive `mutateDocument` (16655 diff, FieldMutatingUpdateProcessor.java: processAdd now calls mutateDocument, and the per-field loop moves into it). Whichever branch lands second must rebase onto the other. A counting exclusion hook would also need to be threaded through mutateDocument. 16655 also adds 461 lines to FieldMutatingUpdateProcessorTest.java and 50 to ParsingFieldUpdateProcessorsTest.java. [verified: merge-tree, diff numstat]
- SOLR-7504 and SOLR-5065: the 12705 audit reports the same 7504 bypass and an untested combined case with 5065 (audit finding 7, hypothesis). Not checked here.

## 6. Sized recommendation

Ship narrow, the broader work is a separate change. Option (a): exclude counting processors from the atomic operand path, with one test. This changes TESTING.md's recommendation (state the behavior and ship). Why the evidence changes it: the (b) output for counted add and remove is `{add: n}` and `{remove: n}`, which the merger applies as append and remove operations rather than as a count; stating that in the draft would publish a semantic the owner is likely to reject. Option (b) also reopens the SOLR-7504 rejection in a combined tree. The cost of (a) is one production change on a branch in final review (a full re-run) and a textual conflict risk with 7504. The Ignore and RemoveBlank side effects are not fixed by either option and need a separate decision.

If the owner prefers (b), the fact that would settle it is a run showing what a single-valued count field does with an appended `{add: 1}`, because an error there makes (b) clearly worse.
