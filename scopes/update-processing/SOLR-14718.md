## 1. The call

Narrow option: ship the command-clone fix in SolrCmdDistributor.distribAdd as it stands (three files, +43/-1), record the attribution flaw in the draft's Limits, and keep the changelog limited to command reuse. Broader option: also change the per-node streaming-client association (StreamingSolrClients and ErrorReportingConcurrentUpdateSolrClient) so that a failure is reported against the document that failed. TESTING.md recommends the narrow option with a Limits note. The evidence supports that, and raises the stakes of the Limits note (section 2, retry path).

## 2. Mechanism

Association (the second flaw), verified by reading:
- One SolrCmdDistributor is created per update processor (DistributedZkUpdateProcessor.java line 118). Its constructor creates one StreamingSolrClients (SolrCmdDistributor.java line 73). [verified: code]
- doRequest (SolrCmdDistributor.java lines 361-375) calls clients.getSolrClient(req) and then solrClient.request(req.uReq) (line 364). [verified: code]
- StreamingSolrClients.getSolrClient (StreamingSolrClients.java lines 68-93) caches one ErrorReportingConcurrentUpdateSolrClient per full node URL (map solrClients, lines 50 and 69-70, 89). It builds the client with the Req that arrives first for that URL (lines 78-79: `new ErrorReportingConcurrentUpdateSolrClient.Builder(req.node.getBaseUrl(), httpClient, req, errors)`). [verified: code]
- The client stores that Req in its field req (ErrorReporting class lines 128 and 133). Every later Req for the same URL is queued on the same client, but handleError builds SolrError with error.req = req (lines 138-146), which is always the first Req. [verified: code]
- Errors come back asynchronously. ConcurrentUpdateBaseSolrClient.Runner sends one queued update per HTTP call (solrj ConcurrentUpdateBaseSolrClient.java, sendUpdateStream lines 298-340) and reports a non-200 through handleError (lines 337, 345-352). The reported Req is therefore the captured first Req. [verified: code]
- So a failure of any document after the first on the same URL, in the same request, is reported against the first document. The ticket's "cmd=add{,id=(null)}" text comes from the reused command; the branch's clone makes the first document's content visible instead. [verified: code, verified: packet]

Retry path (beyond the ticket's wording), verified by reading, end to end not run:
- doRetriesIfNeeded (SolrCmdDistributor.java lines 129-192) takes err.req, increments err.req.retries (line 141), and resubmits err.req (line 191: submit(err.req, false)). The resubmitted request is the first document's UpdateRequest, because each Req carries its own uReq built in distribAdd (lines 249-259). The failing document is not resubmitted. [verified: code]
- The error list is cleared before the resubmission (lines 167-168). If the resubmitted first document succeeds, nothing reports the failing document. [verified: code; the outcome is [hypothesis, needs a run]]
- Retries apply only where checkRetry is true. StdNode built with three arguments has maxRetries 0 (SolrCmdDistributor.java lines 536-538, retry false), so it never retries. The retry path is therefore the ForwardNode path, built in DistributedZkUpdateProcessor.java lines 514-519 with maxRetriesOnForward (DistributedUpdateProcessor.java line 87 and 150). [verified: code]
- Consequence to confirm by a run: a retriable error (503, 404, 403, or a connect exception) on the second or later document of a streamed batch to a ForwardNode resends the first document and drops the failing one without an error. [hypothesis]

Interaction with the clone fix: the branch's clone (reqCmd, branch SolrCmdDistributor.java line 251, one clone per distribAdd call, shared by every node Req of that call) keeps the first document's content in the error. Before the clone, the error text was empty. After it, the error names a concrete document, which is the first one and not necessarily the failing one. The branch therefore turns an empty error into a confidently wrong one for every asynchronous failure other than the first. Synchronous failures (the doRequest catch) already name the right Req. [verified: code]

Mock harness: MockStreamingSolrClients.getSolrClient (lines 43-47) wraps the real client, but MockSolrClient.request (lines 76-95) throws synchronously before anything reaches the ConcurrentUpdate queue. Those errors go through doRequest's catch (SolrCmdDistributor.java lines 365-374) with the correct Req. The mock never reaches ErrorReporting.handleError. [verified: code]

Existing solrj hook on main: SOLR-3284 (commit 14e85035717, 2026-07-14) added ConcurrentUpdateBaseSolrClient.UpdateErrorHandler and Builder.withErrorHandler (solrj lines 86-104 and 876-879). The handler receives the failed document ids and the collection, and when it is set the override handleError(Throwable) is not called for batch failures (solrj lines 625-639). solr/core does not use it (git grep: only solrj and its tests). So a core-only fix could register a handler, map failed ids to Reqs, and reimplement the error bookkeeping. [verified: code; the fix itself is not built]

## 5. Risk

- Behavior surface: StreamingSolrClients serves every distributed update (leader fan-out and forward-to-leader). The association fix changes which Req is retried, which is a behavior change beyond the error text. [verified: code]
- The branch's own change makes the error text confidently wrong for every asynchronous failure other than the first (section 2). That is the main risk of shipping narrow, and the Limits paragraph must say it, not only say that the flaw is "not changed".
- Review contention: a maintainer may keep the per-URL cache for throughput, which would rule out the per-request option. The solrj handler option adds id-to-Req mapping, where duplicate ids in one batch are ambiguous. [hypothesis]
- Category interaction: the SOLR-12705, SOLR-7504 and SOLR-16356 branches touch none of SolrCmdDistributor.java, StreamingSolrClients.java or the test file (verified by numstat). Other branches in the category were not checked.

Shared files and call paths, answering the lead's question directly:
- Test: the same class (SolrCmdDistributorTest), but a different method, and it cannot reuse the clone test's mock harness. A new method next to the clone test in test() is a likely textual conflict. [hypothesis]
- Files: the clone fix edits SolrCmdDistributor.distribAdd (branch lines 249-262). The association fix would edit StreamingSolrClients.java only, or SolrCmdDistributor.doRequest if the Req map is kept there. The two share SolrCmdDistributor.java only if the second fix goes into doRequest, and then they touch different methods.
- Call path: both end at the SolrError list and doRetriesIfNeeded (verified). The clone fix changes what err.req.cmd holds. The association fix changes which Req err.req is. They do not share a changed line.

## 6. Sized recommendation

Ship narrow, the broader work is a separate change. This supports TESTING.md's recommendation (record the second flaw as a follow-up and state it in Limits), with a stronger note. The second flaw is not only a wrong identity in the error. The retry path resubmits the first document (section 2, verified by reading, to be confirmed by a run), so the fix changes retry behavior, which the clone fix does not. That makes it a separate change, not a contained addition. The Limits paragraph should say that the reported document is the first one sent to a node in the request, and that retries are not per document.
