## 2. Mechanism

Two stack traces in the JIRA transcript, both from one run of the periodic task in DocExpirationUpdateProcessorFactory. [verified: packet]

Trace 1 (update log). DeleteExpiredDocsRunnable.run (main DocExpirationUpdateProcessorFactory.java 361-431) calls proc.processDelete (line 400). The delete reaches UpdateLog.deleteByQuery, which calls UpdateLog.openRealtimeSearcher (main UpdateLog.java 944-961; the callers are at lines 846 and 928, and line 928 is inside deleteByQuery, which starts at line 910). openRealtimeSearcher calls uhandler.core.openNewSearcher, which throws SolrCoreState.CoreIsClosedException (SolrCoreState.java line 239, extends AlreadyClosedException). The generic catch at main UpdateLog.java 952-955 logs it at ERROR. The branch adds an earlier catch for that type (branch UpdateLog.java, about lines 949-952), so this site is fixed. [verified: code, verified: diff]

Trace 2 (commit). The same run returns from processDelete with status 0 (the packet's INFO line for deleteByQuery), then calls proc.processCommit (factory line 407). The commit reaches DirectUpdateHandler2.commit, which calls solrCoreState.getIndexWriter, which calls DefaultSolrCoreState.lock. When the closed flag is set (DefaultSolrCoreState.java line 406), lock throws `SolrException(SERVICE_UNAVAILABLE, "SolrCoreState already closed.")` (line 181). That is a SolrException, not a CoreIsClosedException and not an AlreadyClosedException, so no existing type-based catch covers it. The runnable's `catch (RuntimeException re)` (factory lines 423-425) logs it at ERROR. The branch does not touch this factory. [verified: code, verified: diff]

Shared trigger. initDeleteExpiredDocsScheduler registers a close hook (factory lines 248-265). Its preClose calls executor.shutdown() and does not wait (lines 261-264). postClose waits (lines 251-258). SolrCore.close runs the preClose hooks (SolrCore.java lines 1765-1776) before updateHandler.close() (lines 1785-1794) and before solrCoreState.decrefSolrCoreState (lines 1796-1804). A run that started before preClose keeps going, and both throw sites are reached while the core is closing. The packet's trace order matches: "Triggering Graceful close" INFO, then the two ERRORs on the autoExpireDocs thread. [verified: code, verified: packet]

So the two traces share a root cause (a periodic run in flight during close) but have independent throw sites and log sites. The branch removes one of the two ERRORs.

Scope of the ticket text. The title is "DBQ is noisy during core close", and the description says "If we have a DBQ running and the core closes then we get lots of scary stack traces". Assertion: LogListener.error(DocExpirationUpdateProcessorFactory.class) sees no message. Estimated 50 to 80 lines including the test processor and its registration. [read-only, not run]

Constraint found while reading: deleteCore() waits for the full close, including postClose's shutdownAndAwaitTermination (factory lines 251-258). A release placed after deleteCore() returns would deadlock, so the release must come from inside the close sequence or from a timed release. [verified: code, reasoning from the hook order]

A timing-only variant (sleep in the blocking processor) is simpler, but it is flaky. [hypothesis]

## 5. Risk

- Behavior surface: the close-order option changes how long SolrCore.close takes for any core with a periodic deletion, because close waits for an in-flight DBQ and commit. Whether the wait can deadlock with the close path was not checked. [hypothesis]
- The guard option changes only logging, but it needs a new accessor on SolrCoreState, which is shared by every core. [verified: code]
- Review contention: a maintainer may prefer a debug log over an error, or may refuse the close wait. Both are judgments.
- Category interaction: none of the other update-processing branches in my share touches UpdateLog.java or DocExpirationUpdateProcessorFactory.java (verified by numstat for SOLR-12705, SOLR-7504 and SOLR-14718).
- Scope risk for the branch as it stands: the ticket text covers "a DBQ running and the core closes" (section 2), so a maintainer reading the ticket may expect trace 2 to be handled too. The changelog narrows the claim to the update-log path. [verified: packet, diff]

## 6. Sized recommendation

Still a judgment call, with the one fact that would settle it: whether the owner reads SOLR-16356's own scope ("DBQ is noisy during core close", and "if we have a DBQ running and the core closes") as covering the expiration task's commit trace. If yes, the close-order change is the smaller fix (one production file, a few lines) and needs a decision on close latency and a timed or latch-based test. If no, ship narrow and name the second trace in Limits, with the changelog kept on the update-log path. TESTING.md's split is supported on cost grounds (no clean deterministic pin, a close-order decision), but the ticket text argues for including trace 2, so the evidence does not settle it.
