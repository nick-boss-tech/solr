## 1. The call

The narrow option is the branch as it stands: `LogUpdateProcessorFactory.finish()` builds the INFO line and the slow WARN from one string and clears `rsp.toLog` once, so the slow WARN carries the same request details as the INFO line. `SolrCore.Request` is not touched. The broader option is the ticket's second item: the coupling in which `LogUpdateProcessorFactory` clears `rsp.toLog`, which decides whether `SolrCore.Request` logs update requests at all.

The ticket does not say what behavior it wants for that second item. Its description lists symptoms, and the reporter says in a comment that he has no firm grasp of the right behavior. No maintainer comment or decision is in the packet. So the desired behavior cannot be determined from the ticket, and that is the scoping result. The plausible versions are listed below and sized, so the owner can see what a decision would cost.

**The coupling on upstream/main.**

- `SolrCore.java:2881-2884`: a debug log of `rsp.toLog` before the handler runs. The handler runs at line 2893. Then `requestLog.info` of `rsp.toLog` at lines 2896-2904, but only if `rsp.toLog` is non-empty (line 2896). The slow query WARN is at lines 2907-2911 **[code: upstream/main]**.
- `LogUpdateProcessorFactory.getInstance` (lines 63-68) returns a Log processor only when INFO is enabled or the slow threshold is set; otherwise it returns `next`, so nothing is cleared **[code]**.
- The processor clears `rsp.toLog` in `finish()` when it logs. For an update that it logs, `SolrCore.Request` then finds an empty `toLog` and skips the request. For an update where the processor is absent, or INFO is off with no slow threshold, nothing is cleared and `SolrCore.Request` logs the update **[code; derived from the lines above]**. **Plausible broader versions.**

- **P1 (docs only).** Keep the coupling and document it: the INFO level of `LogUpdateProcessorFactory` decides whether `SolrCore.Request` logs updates. Code: none. Doc pages that mention the processor (see P3 count) would get a note **[estimate]**.
- **P2 (the ticket's first idea).** `LogUpdateProcessorFactory` stops clearing `rsp.toLog` and sets an MDC marker when it logs. `SolrCore.Request` then logs every request by default, so `/update` logs twice at INFO under the default config. Unless `SolrCore` checks the marker, which adds lines at `SolrCore.java:2896-2904`. Production: `LogUpdateProcessorFactory.java` (the clear logic in `finish()`, about 30 to 50 lines touched **[estimate]**) and possibly `SolrCore.java` (about 5 to 10 lines **[estimate]**). Tests: the branch's `LogUpdateProcessorFactoryTest.java` (133 added lines) asserts the clearing behavior and would need rewriting; a new update-path test modeled on `RequestLoggingTest` (about 60 lines **[estimate]**).
- **P3 (the ticket's third idea).** Deprecate the processor. A new `LogSummaryUpdateProcessorFactory` fills `rsp.toLog` and logs nothing. The default chain (`SolrCore.java:1639-1644`), the placement rule (`UpdateRequestProcessorChain.java:285`) and the clone whitelist (`DistributedZkUpdateProcessor.java:138-140`) all change. The ticket's version gates the default on `luceneMatchVersion`; the code at `SolrCore.java:1639-1644` is unconditional today **[code]**. Scope of the config and docs sweep: `LogUpdateProcessorFactory` appears in **38 files** at upstream/main (`git grep -l`, verified): 10 Java files, 19 XML configs (test-files, server configsets, cross-dc, solrj test-files), and 9 reference-guide `.adoc` pages **[code: upstream/main]**. ## 5. Risk

- **Behavior surface.** P2 changes default log volume for all update traffic, since `/update` would log twice. P3 changes the default chain and the set of classes that log. Both change log content, which matters to log parsers. The ticket's last scenario is exactly that: a tool parsing `slow:` WARN lines breaks when the level changes **[record: JIRA]**. The branch's own WARN change also alters that line: the slow WARN now carries the request details. That is intended, and the ticket describes the missing details as a problem.
- **Review contention.** High. The reporter says the right behavior is undecided, and the three ideas were not picked. A maintainer can reverse either P2 or P3. The current default (updates logged once, by the processor) is described in the ticket as the long-standing behavior **[record: JIRA]**.
- **Precedent outside Solr.** Smiley's site already does P3-like logging with a custom processor **[record: JIRA]**. That is evidence that the route works, not that it is wanted upstream.
- **Interaction in the category** **[diff; read-only overlap check across all origin/solr-*-submit branches]**. No other submit branch changes `LogUpdateProcessorFactory.java` or its test. `SolrCore.java` is changed by five other submit branches (SOLR-12007, SOLR-15003, SOLR-17047, SOLR-5011, SOLR-8628); their hunks were not inspected, so a P2 or P3 change there would need a merge check.
