## 1. The call

The narrow option is the branch as it stands: `normalizeExponent` rewrites a plus sign or a lowercase exponent marker before `NumberFormat` runs, for every locale, so an explicit `locale` never changes what is accepted. The same helper makes `DefaultSchemaSuggester` infer Double for those samples. The broader option (a) is a locale-aware parse, where an explicit locale decides which exponent syntax is accepted, instead of one regex for all locales. The broader option (b) is a unit test that pins the suggester inference, plus a judgment on whether the inference is intended. (a) changes production behavior for explicit locales, and the ticket is split on it. (b) is test-only.

## 2. Mechanism

**Helper and call sites.** `ParseNumericFieldUpdateProcessorFactory.java` holds two patterns (`EXPONENT_PLUS` at line 49, `LOWERCASE_EXPONENT` at line 51) and `static String normalizeExponent` (lines 62-65) **[code: origin/solr-5065-submit]**. Its callers:

- `ParseDoubleFieldUpdateProcessorFactory.java:104`, inside `public static Object parsePossibleDouble(Object srcVal, NumberFormat numberFormat)` (line 102). This method receives a `NumberFormat`, not a `Locale`, so the Double path has no locale in scope. Its callers are `ParseDoubleFieldUpdateProcessor.mutateValue` (line 92, where the locale is a field, line 71) and `DefaultSchemaSuggester.isFloatOrDouble` (`DefaultSchemaSuggester.java:300`, identical on main and on the branch) **[code]**.
- `ParseFloatFieldUpdateProcessorFactory.java:93`, inside `mutateValue`, where the instance `locale` field exists (lines 70 and 87) **[code]**.

**What the JDK parser does.** Read from the JDK 21 source, not run **[JDK source: java.base/java/text/DecimalFormat.java]**:

- The exponent separator comes from `symbols.getExponentSeparator()` (line 2434) and is matched with a case-sensitive `regionMatches` (line 2508).
- The exponent sign is parsed with positive prefix `""` and negative prefix the minus sign (line 2515). The class has no plus-sign handling anywhere.
- When no digit follows, the number parse returns -1 (lines 2546-2548), and the boolean `subparse` returns false (line 2351), so the exponent is not consumed.

So NumberFormat cannot consume a `+` or a lowercase `e` in an exponent, for any locale whose separator is `E`. That is the reason for the rewrite, and the rewrite is the only thing that changes what is accepted.

**Behavior by locale (branch against upstream/main).** upstream/main has no rewrite, so a plus sign or lowercase exponent is rejected for every locale. The branch accepts both for every locale. For ROOT this is the intended fix. For an explicit locale, the branch makes `4,5E+10` parse under fr_FR, which main does not. The French chain already exists in the test config: `parse-double-french-no-run-processor` (`solrconfig-parsing-update-processor-chains.xml:178-182`) **[code: upstream/main]**. Whether any locale's exponent separator is not `E` was not checked **[hypothesis: most CLDR locales use E; a main-side run listing `DecimalFormatSymbols.getExponentSeparator()` over `Locale.getAvailableLocales()` would settle it; read-only, not run]**.

**Locale-aware variants.**

- (a-i) Gate the rewrite on the default locale only. Explicit locales return to upstream/main behavior, so fr_FR `4,5E+10` is rejected. The Double call site needs the locale, so `parsePossibleDouble` gains a parameter or an overload.
- (a-ii) Take the marker from the locale's own symbols and strip a `+` only after it. For locales whose separator is `E`, this matches the branch for the plus sign. Lowercase acceptance still needs its own rule, because the symbols do not define a lowercase marker.

**Ticket evidence on the locale point** **[record: JIRA, comment ids as listed]**:

- Hostetter, 13718511 (2013-07-24): "+1 ... with the obvious caveat if the user explicitly configures a locale, we should use the parser of their choosen locale and the acceptable syntax obviously changes". This supports (a).
- Rowe, 13718025: the plus-stripping regex "would fix the immediate problem without making the implementations more complicated". This supports the branch.
- Krupansky, 13718535: NumberFormat first, then a Java-style fallback. This accepts the plus sign under explicit locales too, which supports the branch.
- Muir, 13718459: NumberFormat is for localized formats and "the purpose of this class is entirely different". This supports (a).

The ticket is split, and the audit's "no consensus" stands **[record]**.

**The suggester (b).** `guessFieldType` (`DefaultSchemaSuggester.java:222`) calls `isIntOrLong` (line 235), then `isFloatOrDouble` (line 239). `isFloatOrDouble` (lines 294-323) builds a NumberFormat from the locale (lines 295-297) and calls `parsePossibleDouble` (line 300). It returns `pdouble` when every value parses. `suggestField` passes `Locale.ROOT` (line 163) **[code: upstream/main]**. Before the branch, a sample like `4.5E+10` falls through to `string`. After the branch it becomes `pdouble`.

The second consumer: `validateNumericTypeChange` (lines 98-113) calls `isFloatOrDouble(fieldValues, Locale.ROOT)` for DOUBLE and FLOAT targets (line 113). It is reached from `validateTypeChange` (lines 90-94), which `SchemaDesignerConfigSetHelper.validateTypeChange` calls (`SchemaDesignerConfigSetHelper.java:458-467`) from the designer's field-update path (line 348) **[code: upstream/main]**. So the designer's type-change check also accepts E+ and lowercase samples now.

**Intended or accidental.** For intent: the suggester's own comment (`DefaultSchemaSuggester.java:306-308`) says it prefers `pdouble` because the parse processor is what gives locale-sensitive parsing in the chain, so the suggester is written to agree with ParseDouble. The destination type also accepts the syntax: `DoublePointField.java:54` calls `Double.parseDouble`, and the JDK 21 `Double` javadoc says an exponent is `e` or `E` followed by an optionally signed integer (regex `[eE][+-]?` in the javadoc, around `Double.java:700-706`) **[code, JDK source]**. Against intent: the ticket, the changelog (`changelog/unreleased/SOLR-5065-parse-double-exponent-plus.yml`) and the tests say nothing about the suggester, and the audit records it as open (finding 3). My reading: the inference is a consequence of sharing the helper, and it agrees with the processor and the field type. It was never a recorded decision. **[judgment from the code above]**

## 5. Risk

- **Explicit locales.** The branch accepts E+ under every locale. Either locale-aware variant changes that, so the Limits note is needed in any case (TESTING.md already plans it).
- **API.** `parsePossibleDouble` is `public static` with a `NumberFormat` parameter (`ParseDoubleFieldUpdateProcessorFactory.java:102`). (a) changes it or adds an overload. External callers are unknown.
- **Review contention.** High for (a), as the ticket split above shows. Moderate for (b): a maintainer may ask whether the designer should infer `pdouble` from E+ at all.

## 6. Sized recommendation

**Ship narrow, the broader work is a separate change.**

- (a) stays out of this branch. The one fact that would settle it is a decision on the ticket: whether an explicit locale should change which exponent syntax is accepted. The Hostetter caveat (13718511) says yes; the Rowe and Krupansky proposals say the syntax should not depend on the locale. A run cannot settle it.
- (b) is a change to TESTING.md. TESTING.md says to add a suggester test "only if maintainers ask". The scoping evidence changes that: the same helper also decides the designer's type-change check (`SchemaDesignerConfigSetHelper.java:348`, `458-467`), so the behavior reaches a second user-visible path, and the pin is test-only. I would add the unit test to this branch now, with its fail-before run.
- Draft wording: present the suggester change as a consequence of the shared parse helper, with the comment at `DefaultSchemaSuggester.java:306-308` as the stated rationale. That is a judgment, not a recorded decision, so the draft should not call it intended without the owner's sign-off.
