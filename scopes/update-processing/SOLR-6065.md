## 5. Risk

- **Global state (the main flake risk).** `IndexWriter.MAX_DOCS` is a JVM-wide static. `MiniSolrCloudCluster` starts `JettySolrRunner` instances inside the test JVM (`MiniSolrCloudCluster.java:281`, `:415`), so every core in that JVM sees the limit during the test **[code]**. The audit lists this as open (finding 4). Mitigation: set before collection creation, restore in `finally`, and keep the test to one collection.
- **Background activity.** Replica recovery or commits on other cores in the same JVM could hit a limit of 3 during the window. Unlikely with three documents, not impossible **[hypothesis]**.
- **Reflection never gated.** The reflective `privateLookupIn` path has no gate receipt at this head (`audit`: no receipt at `6aef011ee8d5`). The single-core test shares this risk, so a failure there would show the cause first **[audit]**.
- **Startup timing.** Use `waitForActiveCollection` before the adds, as `LeaderTragicEventTest` does.
- **Behavior surface.** The mapped message is user-visible text with advice ("Delete documents and optimize ... or split the shard", `DirectUpdateHandler2.java` around lines 430-436). The audit calls the wording cosmetic (finding 6). The message says deleted documents still count until merged, which makes "optimize" a partial remedy.
- **Review contention.** Low for the test. The mapping keys on message text (audit finding 3). The code comment states the dependence on Lucene 10.4.0's wording, and the test pins the text, so a reword fails the test.
- **Coverage gap.** `mergeIndexes` is unmapped (see Mechanism). A maintainer could ask for it. The cloud test does not cover it. Trace it or state it in Limits; the audit already asks for that.
