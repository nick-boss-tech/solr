## 1. The call

Narrow option: keep the chain as it is. Document the chain-placement limit in the draft's Limits, and narrow the changelog title (it says "fixed") so that it claims only the covered shape, where the source field is in the update. Broader option: change how the chain or the default-value processor treats an update that leaves the source field out, so that such an update does not write a count. ## 2. Mechanism

The documented chain is Clone (source to dest), then CountFieldValues on dest, then DefaultValue (dest = 0). Test config solrconfig-update-processor-chains.xml lines 492-504 (chain "clone-then-count"). The javadoc example (CountFieldValuesUpdateProcessorFactory.java lines 39-50) places DefaultValue after the counter, and its NOTE (lines 52-57) says the default is there so that every document gets a value. [verified: code]

Uncovered shape (source field absent from the update):
- CloneFieldUpdateProcessorFactory.processAdd (main, around lines 489-501) iterates only the fields present in the document and skips empty ones. With no source field nothing is copied, so no dest field exists. [verified: code]
- The counter runs over the document's own fields, so it does nothing for dest. [verified: code, same loop as FieldMutatingUpdateProcessor.processAdd, main lines 83-85]
- DefaultValueUpdateProcessor.processAdd (AbstractDefaultValueUpdateProcessorFactory.java lines 75-83) adds a plain 0 when the document has no dest field (lines 78-79). [verified: code]
- The atomic merger treats a plain field as a set (AtomicUpdateDocumentMerger.java lines 194-196: "normal fields are treated as a set"). The update is atomic when at least one field is a map (isAtomicUpdate, lines 88-97). So if the update has any atomic field, the stored count is set to 0. [verified: code]
- Consequence: under the documented chain, every atomic update that leaves the source field out writes 0 into the count field. That is stronger than the audit's wording ("the symptom persists for that shape"), and it is not in the reporter's example. [verified: code for each step; the end-to-end result is [hypothesis, needs a run]]

Why the counter cannot be moved to cover this shape:
- The counter sees only the update document. It cannot read the stored source values, so there is nothing for it to count when the source is absent. [verified: code]
- Placing DefaultValue before the counter would make the counter count the default 0 as one value (the counter sets getValueCount(), main line 72, and a plain 0 has count 1). Placing the counter before Clone has nothing to count. So the chain order is fixed by the design. [verified: code for line 72; the count-of-1 result is read, not run]

The reporter's example: the JIRA packet's example sets the source field (researchpagekeycontentcategorynames with set null), so the reported symptom is the covered shape. The uncovered shape is outside the example, though the packet's general title ("Atomic Update causes ... to be wrong") covers it. [verified: packet]

Branch mechanism (for reference): the 7504 counter checks `src.getFirstValue()` for a Map (branch lines 78-80) and then rejects non-set operations (countAtomicUpdate, lines 96-131). The plain-first case is a separate code fix (audit finding 3), not part of this question. [verified: diff]

## 6. Sized recommendation

Ship narrow, the broader work is a separate change. The narrow option is document the chain-placement limit in Limits and narrow the "fixed" title to the covered shape. This supports TESTING.md's recommendation, with two corrections from the scoping evidence: (1) the uncovered shape is not in the reporter's example, which sets the source field, so the claim that it is "arguably the ticket's own case" is weaker than TESTING.md states; (2) it cannot be fixed by changing where the counter sits. The only real fix is in default-value handling for partial documents, which changes every DefaultValue user, so it belongs in a separate change.
